## 計畫(動工前成文,憲法第二條 2)

### 目標

現在的 81 個綠燈**只存在於我這台機器上**——沒有 CI,任何人 push 都不會被重驗。
憲法第一條 3 明訂「M2 之後的 DoD 含 CI 綠燈」,接入指南 §9.1 也把 CI 列為必做。

本任務要建立 CI,並**順便實際建置 image**——Dockerfile 至今從未被建過(欠項 A5),
image 大小、non-root、`/health` 是否真的 60 秒內綠,全都只是紙上規格。

### CI 必做四項(接入指南 §9.1)

1. 跑單元測試與 lint
2. Build Docker image
3. **Trivy 掃描**——有 high / critical CVE 即失敗
4. Push 至 GHCR

我另外加一項:**文件同步檢查**(`render_docs.py --check`)。憲法第四條要求 md 與 HTML
兩版同步,靠人記得跑產生器遲早會漂移,交給 CI 擋。

### 影響範圍

| 類型 | 檔案 |
|---|---|
| 新增 | `.github/workflows/ci.yml` |
| 可能修改 | `Dockerfile`(若實際建置暴露問題) |
| 修改 | `docs/任務表.md`(T12、T10 狀態與欠項) |
| 不動 | `app/`、`tests/` 的行為(除非建置暴露缺陷) |

**對現有資料的影響:🟢 不動資料。** CI 與容器建置不觸及任何資料庫或物件儲存。

### 驗收標準

1. workflow 涵蓋:lint、測試、文件同步、build、Trivy、push GHCR
2. **Trivy 有 high/critical 即失敗**,不是只印出來當參考
3. push GHCR 只在 **版本 tag** 時發生——`latest` 是紅線,且「一個 git tag 對一個 image tag」
4. **image 實際建置成功**,並記錄實測大小(目標 ≤300 MB)
5. **實際啟動容器驗證**:以 UID 1000 執行、`/health` 回 200 且不查 DB
6. 任務表更新;A3、A5 依實測結果結案或保留

### 回滾方式

純新增 workflow 與文件,`git revert` 即可。CI 若造成困擾可直接停用 workflow,
不影響任何既有程式碼或部署。

### ⚠️ 本任務的已知限制

我在這個環境**無法驗證 workflow 在 GitHub Actions 上真的會綠**——只能驗證
語法正確、以及本機能重現 CI 的每一個步驟。首次 push 後仍需看 Actions 頁面確認。
這點會誠實寫進結果段,不宣稱「CI 已綠」。

## 結果(完工後補記)

### 做了什麼

新增 `.github/workflows/ci.yml`,三個 job:

| Job | 步驟 | 對應規約 |
|---|---|---|
| **test** | ruff → pytest → **文件 md/HTML 同步** → **git 紅線檢查**(`.env`/`*.sql`/`*.xlsx`/`.venv`/`*.pyc`)→ **SSO 紅線**(零 Authentik、`app/` 無 HS256) | 接入指南 §9.1-1、憲法第四條、平台鐵則 8、SSO 契約 §7 |
| **build** | build image → **image 大小**(>300MB 警告)→ **non-root 檢查**(`Config.User` 與執行期 UID 皆須為 1000)→ **`/health` 冒煙**(不接任何相依、60 秒內)+ `/ready` 須 503 + SIGTERM → **Trivy(high/critical 即失敗)** | 接入指南 §9.1-2/3、§3、平台鐵則 1 |
| **publish** | 僅 `v*` tag → 登入 GHCR → **確認該版本尚未發布過** → build & push **明確版號** | 接入指南 §9.1-4、「不可重發同版」「禁 latest」 |

三項我主動加進去、規約沒明寫但值得擋的:

1. **文件 md/HTML 同步**——憲法第四條要求兩版同步,靠人記得跑產生器遲早漂移
2. **不可重發同版**——`docker manifest inspect` 到就直接失敗,不覆蓋
3. **SSO 紅線 grep**——冒煙清單最後一項本來是人工做,可以自動化就自動化
   (`app/` 擋 HS256,但**測試檔允許**——測試刻意產生 HS256 token 來驗「必須被拒絕」)

### ✅ CI 實跑結果(2026-07-26,run #3 全綠)

前兩次都紅,而且**兩次都是本機看不到的問題**——這正好證明了建 CI 的價值:

| Run | 失敗點 | 根因 | 修正 |
|---|---|---|---|
| #1 | test job / pytest | `python -m pytest` 會把 cwd 加進 `sys.path`,**`pytest` 執行檔不會**。我本機一直用前者 | `pyproject.toml` 宣告 `pythonpath = ["."]` |
| #2 | build job / action 解析 | `aquasecurity/trivy-action@0.28.0` **不存在**——我憑印象填版本號,整個 job 在跑任何步驟前就死 | 查證 releases 後改 `@v0.36.0`(tag 是 v 前綴格式) |
| **#3** | — | — | **全綠** |

**run #3 的實測數字(這些就是 A5 要的證據):**

```

✅ image 大小:254 MB              (目標 ≤300 MB —— 未觸發超標警告)
✅ Config.User = 'app'
   執行期 UID = 1000               (平台鐵則 1:non-root)
✅ /health 在第 2 秒回 200(未接 DB/MinIO)   (規約上限 60 秒)
✅ /ready = 503(無相依時應為 503)
```

> 容器內 `/health` 只花 **2 秒**,比我本機的 20 秒快得多。原因是本機把相依指向 `.invalid` 網域,

> 兩者都在規約的 60 秒內,但這也說明「啟動時間」很依賴相依失敗的方式,不是固定值。

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| 只在 `v*` tag 推 GHCR | 規約:一個 git tag 對一個 image tag、禁 latest。每次 push 都推等於變相 latest | 每次 push 推 `:sha` 或 `:branch` |
| 推之前先查版本是否存在 | 「不可重新發布同一版本」若只寫在文件裡,遲早有人覆蓋掉正式版 | 只在文件寫規則,靠人遵守 |
| image 超 300MB 只警告不擋 | 規約原文是「超過要在 PR 說明」,不是硬性失敗;擋掉會逼人為了過 CI 而亂砍相依 | 硬性失敗 |
| Trivy `exit-code: 1` + `ignore-unfixed` | 規約明訂 high/critical 即失敗;但上游還沒修的 CVE 擋著也沒用,只會讓人養成 skip 的習慣 | 不設 exit-code(等於只是印出來好看) |
| `/ready` 必須回 503 也納入冒煙 | 只驗 `/health` 200 的話,把兩者寫成同一個實作也會過——那正是規約要避免的 | 只驗 `/health` |
| SSO 紅線 grep 只擋 `app/` | 測試必須能產生 HS256 token 來驗「拒絕」;連測試一起擋會逼人刪掉那條安全測試 | 全 repo 擋 HS256 |
