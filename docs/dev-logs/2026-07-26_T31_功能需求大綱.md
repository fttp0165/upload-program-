## 計畫(動工前成文,憲法第二條 2)

### 目標

寫出 upload-program 的**功能需求大綱**:把「簡易型 GitHub」這句話拆成可驗收、可排程、可追蹤的
功能項,作為後續所有任務的需求來源。每個功能項要有編號、優先級、對應里程碑,以及**目前實作狀態**
——讓「已經寫了什麼、還缺什麼」一眼看得出來,不再靠記憶。

### 影響範圍

| 類型 | 檔案 |
|---|---|
| 新增 | `docs/功能需求大綱.md`、`docs/功能需求大綱.html` |
| 修改 | `docs/任務表.md`(新增 T31 並更新版本歷史) |
| 修改 | `tools/render_docs.py`(把新文件納入產生清單) |
| 不動 | 所有 `app/` 程式碼、`tests/`、容器與部署設定 |

**對現有資料的影響:🟢 不動資料。** 純文件任務,不觸及資料庫、migration 或物件儲存。

### 驗收標準

1. 涵蓋六大功能模組(帳號權限、專案、版本、檔案、瀏覽搜尋、平台管理)+ 系統維運
2. 每個功能項具備:編號 `Fnn`、名稱、說明、優先級(P0/P1/P2)、對應里程碑、實作狀態
3. 明列**範圍外**項目,與開發計畫書 §1.2 的 MVP 界線一致,不得互相矛盾
4. 明列**開放問題**,每項標出待誰決定
5. 依第七條具備建立日期 / 最後更新 / 版本 / 版本歷史
6. 依第四條產出 HTML 版(light 主題),且 `render_docs.py --check` 通過
7. 任務表新增 T31 並標示狀態

### 回滾方式

純新增文件,`git revert` 該 commit 即可完全回復;不需資料庫或部署層動作。

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| 功能編號用 `Fnn` 與任務 `Tnn` 分離 | 需求是「要什麼」,任務是「怎麼做」,一個需求可能拆成多個任務,綁死會很難改 | 需求直接用任務編號 |
| 每項標「實作狀態」 | 程式碼先於規則寫成(見 T00),不標的話無從得知哪些是已寫、哪些只是想做 | 只寫需求不談現況 |
| 優先級用 P0/P1/P2 而非 MoSCoW | 與里程碑欄位並用已足夠表達取捨,三級最省溝通成本 | Must/Should/Could/Won't |
| 把「轉移擁有權」「latest 標記」等列為 P2 且標未實作 | 這些在程式碼裡有被提及(例如成員 API 的錯誤訊息叫使用者「先轉移擁有權」)但功能不存在,不列出來會變成隱藏的缺口 | 略過不提 |
| 範圍外清單直接引用開發計畫書 §1.2 | 避免兩份文件對 MVP 界線各說各話 | 在本文另立一套界線 |
