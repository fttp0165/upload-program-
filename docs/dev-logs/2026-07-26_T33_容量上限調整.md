## 計畫(動工前成文,憲法第二條 2)

### 目標

把容量預設值改成 Q7/Q10 的定案值:

| 設定 | 現值 | 改為 | 依據 |
|---|---|---|---|
| 單檔上限 | 512 MB | **100 MB** | Q7 裁示「50~100M」,取上限 |
| 專案總容量 | 5 GB | **2 GB** | Q10 裁示「一般員工的小工具 2G 就可以」 |

這些值是我在需求定案**之前**憑估計填的,現在有裁示了就該對齊。
上限**調高比調低容易**,所以先收到 2 GB;真的不夠用的個案走 T49 的擴充級距。

### 這個任務有多小,以及為什麼還是要走完整流程

只改兩個數字。但憲法第一條說「每個任務是獨立可交付、可回滾的增量」——
小任務照樣要有計畫、測試、日誌。而且這裡有一個**真正值得防的東西**:

`app/config.py` 的預設值與 `.env.example` 的示意值是**兩份各自為政的數字**,
改了一邊忘了另一邊,部署時就會用到錯的值而且沒人發現。
所以本任務要順便加一條**防漂移測試**:斷言 `.env.example` 裡的數字與 `Settings` 預設一致。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |
|---|---|---|
| 1 | 未設環境變數時的單檔上限 | 100 MB(104,857,600) |
| 2 | 未設環境變數時的專案容量 | 2 GB(2,147,483,648) |
| 3 | `.env.example` 的兩個數字 | **與 `Settings` 預設完全一致**(防漂移) |
| 4 | 既有的超限測試 | 仍綠(它們用 fixture 覆寫的小值,不受預設值影響) |

### 影響範圍

| 類型 | 檔案 |
|---|---|
| 修改 | `app/config.py`(兩個預設值) |
| 修改 | `.env.example`(兩個示意值) |
| 修改 | `tests/test_config_and_logging.py`(新增 3 條) |
| 修改 | `docs/功能需求大綱.md`(F34 狀態)、`docs/任務表.md` |
| 不動 | 上傳/下載邏輯、資料模型、migration |

**對現有資料的影響:🟢 不動資料。** 純設定變更,無 schema 異動。

> ⚠️ 上線後若要再調降此值,**已超標的既有專案會立刻無法上傳新檔**(既有檔案不受影響)。
> 目前尚未上線、無資料,所以現在調是零成本的;這也正是「先收緊」的理由。

### 回滾方式

改回兩個數字即可,`git revert` 一個 commit。不需資料層動作。

## 結果(完工後補記)

### 紅 → 綠(順便驗證了防漂移測試真的有用)

我刻意**分兩步**改,好證明那條防漂移測試不是裝飾:

```
步驟 0  先寫 3 條測試
        FAILED test_預設單檔上限為100MB   assert 536870912 == 104857600
        FAILED test_預設專案容量為2GB     assert 5368709120 == 2147483648
        PASSED test_env_example的容量值與程式預設一致   ← 此時兩邊都還是舊值,所以一致

步驟 1  只改 app/config.py(故意不動 .env.example)
        FAILED test_env_example的容量值與程式預設一致
               assert 536870912 == 104857600          ← 🎯 防漂移測試確實抓到了

步驟 2  補上 .env.example
        全部轉綠
```

```
$ pytest -q
125 passed in 11.62s

$ ruff check .
All checks passed!
```

測試總數 122 → **125**。

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `app/config.py` | `max_artifact_bytes` 512 MB → **100 MB**;`max_project_bytes` 5 GB → **2 GB** |
| `.env.example` | 兩個示意值同步,並註明「有測試在擋」 |
| `tests/test_config_and_logging.py` | 新增 3 條(兩條驗預設值、一條防漂移) |

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| 加一條「`.env.example` 必須與程式預設一致」的測試 | 這是**兩份各自為政的數字**,改了一邊忘了另一邊,部署時會套用到錯的值而且**不會有任何錯誤訊息**。這種靜默失效最值得用測試擋 | 靠註解提醒、靠 review 抓 |
| 分兩步改以驗證該測試 | 一次改完兩邊的話,那條測試從頭到尾都是綠的——**我不會知道它有沒有在做事** | 一次改完(測試變成沒被驗證過的裝飾) |
| 在 `config.py` 註明「調降會讓超標專案無法上傳」 | 現在調是零成本(未上線、無資料),上線後就不是了。這個限制寫在程式碼旁邊,比寫在文件裡更難被忽略 | 只寫在日誌裡 |
| 不改 413 的錯誤訊息 | 「訊息要含級距、已用量與申請指引」是 **T49** 的驗收標準;本任務只調值,不擴散範圍 | 順手一起改(會讓 T49 的驗收失去意義) |

### 對現有資料的實際影響

**無。** 與計畫一致,🟢 純設定變更、無 schema 異動。
專案尚未上線、無任何專案資料,所以這次調降是零成本的。

### 遺留問題與後續建議

| # | 問題 | 建議 |
|---|---|---|
| 1 | 413 的錯誤訊息仍是 `單檔上限 104857600 bytes` 這種原始位元組 | T49 會改成含級距、已用量與申請指引的人話訊息 |
| 2 | 上線後調降此值會讓超標專案無法上傳新檔 | 已在 `config.py` 就地註明;真要調降前需先盤點既有專案用量 |
| 3 | gateway 的 `client_max_body_size` 尚未設定 | 併入 T28 路由 PR(建議 128 MB,留 28 MB 餘裕給標頭與 multipart 開銷) |
