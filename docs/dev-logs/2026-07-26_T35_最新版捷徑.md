## 計畫(動工前成文,憲法第二條 2)

### 目標

實作 F26:以**固定網址**取得最新已發布版本與其檔案。

Q3 定案的理由是「影響下載連結是否穩定可寫進文件」。現在的下載網址含 `release_id` 與
`artifact_id`,每發一次新版就換一組 UUID——寫進 wiki、腳本、批次檔的連結全部作廢。
有了捷徑,同事可以在文件裡寫死一條連結,永遠指向最新版。

### 介面(需求大綱 §3.C 已定樁)

| 端點 | 用途 |
|---|---|
| `GET /v1/projects/{slug}/releases/latest` | 最新**已發布**版本(draft 不算) |
| `GET /v1/projects/{slug}/releases/latest/artifacts/{filename}/download` | 直接抓最新版的某個檔案 |

檔案用**檔名**定位而非 UUID——這正是「連結能寫進文件」的關鍵:
`.../latest/artifacts/tool.exe/download` 可讀、可預測、跨版本不變。

### 🔴 本任務最容易錯的一點

**「最新」必須以 `published_at` 判定,不得用版本號字串排序。**
版本號是自由字串(非強制 SemVer),字串排序會讓 `v9` 排在 `v10` 前面——
發到第十版時就會靜默地一直給出舊版,而且沒人會發現。

測試要**刻意設計成能區辨**:讓 `created_at` 順序、版本號字串順序、`published_at` 順序
三者給出不同答案,只有正確實作才會通過。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |
|---|---|---|
| 1 | 有已發布版本 | 200,回 `published_at` 最大者 |
| 2 | v10 比 v9 晚發布 | latest 是 **v10**(字串排序會答 v9) |
| 3 | 只有 draft | 404 —— latest 只看已發布 |
| 4 | 專案沒有任何版本 | 404 |
| 5 | internal 專案的非成員 | 200 可讀 |
| 6 | private 專案的非成員 | 404(不洩漏存在) |
| 7 | 下載最新版檔案 | 200 + `Content-Disposition: attachment` + `nosniff` + SHA-256 標頭 |
| 8 | 下載不存在的檔名 | 404 |
| 9 | 發新版後,同一條下載網址 | 自動指向新版的檔案 |

### 影響範圍

| 類型 | 檔案 |

### 回滾方式

純新增端點,`git revert` 即可。既有的 by-UUID 下載路徑不受影響,回滾不會讓任何現有連結失效。

> 這是 T34 之後第二次遇到,已成為固定的自我檢查:**凡是預期 4xx 的測試,都要斷言錯誤內容。**

### 那條關鍵測試怎麼設計的

`test_最新版以發布時間判定而非版本號字串` 刻意讓三種排序給出**不同**答案:

| 排序依據 | 答案 | 對錯 |
|---|---|---|
| `created_at` 倒序 | v9(後建立) | ❌ |
| 版本號字串倒序 | v9(`"v9" > "v10"`) | ❌ |
| **`published_at` 倒序** | **v10**(後發布) | ✅ |

做法:v10 先建立但最後才發布;v9 後建立卻先發布。這樣只有正確實作會通過
——如果只用「建立 v9、建立 v10、依序發布」,三種排序會給出同樣答案,測了等於沒測。

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `tests/test_latest_release.py` | 新增 13 條(先紅後綠) |
| `app/routers/releases.py` | `latest_published_release()` 查詢 helper + `GET /projects/{slug}/releases/latest` |
| `app/routers/artifacts.py` | 抽出 `_download_response()` 共用;新增 `latest_router` 與檔名下載端點 |
| `app/main.py` | 掛上 `artifacts.latest_router` |

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| 以 `published_at` 判定最新 | 版本號是自由字串,字串排序會讓 `v9` 排在 `v10` 前面,發到第十版就靜默給舊版 | 版本號字串排序;`created_at`(先建的可能後發布) |
| 下載捷徑以**檔名**定位 | 這條網址的意義就是「能寫進文件而不失效」;UUID 每發新版就換一組 | 用 artifact UUID(那就失去捷徑的意義) |
| **抽出 `_download_response()` 共用** | 安全標頭絕不能因為換一條路徑就鬆掉;共用同一段程式碼就不可能有一邊漏掉 attachment/nosniff | 兩個端點各寫一份(遲早不一致) |
| 另立 `latest_router` | 前綴是 `/v1/projects` 而非 `/v1/releases`,而 APIRouter 的 prefix 是整個 router 共用、無法逐條覆寫 | 把端點塞進 releases.py(會造成 artifacts↔releases 循環 import) |
| draft 不列入 latest | latest 是給使用者抓的,draft 是作者的工作區 | 包含 draft(等於把未完成的東西外流) |

### 對現有資料的實際影響

**無。** 與計畫一致,🟢 純新增查詢路徑,無 schema 變更。
既有的 by-UUID 下載路徑完全不受影響——回滾不會讓任何現有連結失效。

### 遺留問題與後續建議

| # | 問題 | 建議 |
|---|---|---|
| 1 | latest 查詢沒有索引輔助 | 目前 `releases` 只有 `project_id` 索引;版本數量大時可加 `(project_id, status, published_at)` 複合索引。資料量小,先不動 |
| 2 | 同一毫秒發布兩個版本時順序未定 | 現實上不會發生(發布是人為動作);若要絕對確定可用 `published_at DESC, id DESC` |
| 3 | 沒有 `latest` 之外的別名(如 `stable`) | 需求未要求;若日後要做,同一套查詢改個過濾條件即可 |
