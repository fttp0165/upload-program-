## 計畫(動工前成文,憲法第二條 2)

### 目標

把 Q9(前端技術選型)的裁示寫成正式決策文件,並把評估過程中發現的兩個既有設計缺口
轉成可執行的任務。**T40–T45 動工前必須完成本任務**——選型錯了整個 M7 要重做,
而子路徑靜態檔正是 Cats 平台踩過的坑(PLM v1.1.0 上線時 CSS 全部 404)。

| Q9 | 前端技術選型 | **Jinja2 + 原生 JS**(伺服器端模板,放在現有容器) |
| 坑一 | 上傳 API 發不出純 HTML 表單 | **維持 PUT,前端用 XHR** |

### 驗收標準

1. 決策文件涵蓋:背景與限制、選項比較、決定與理由、**後果與代價**、實作綱要、失效條件
2. 兩個缺口有明確處理方案並轉成任務:
   - 坑一(上傳需 JS)→ 寫進 T44 驗收標準
   - 坑二(錯誤回應只吐 JSON)→ 開新任務,列為 T40 前置
3. 靜態檔的「剝前綴 vs 保留前綴」有明確結論,可直接寫進 cats-portal 的路由 PR
4. 功能需求大綱的 Q9 由「未定案」移入「已定案」
5. 三份文件皆更新最後更新時間與版本歷史(第七條 4)
6. `render_docs.py --check` 通過

### 回滾方式

純文件變更,`git revert` 該 commit 即可完全回復。選型本身若日後要推翻,
因為系統是 API-first,改用 SPA 不需重寫後端——這也是本決策的主要止損設計。

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| Jinja2 而非 SPA | M7 指定的五個畫面全是讀取與呈現,不需用戶端狀態管理;SPA 會多一個容器、多一條 gateway 路由、多一次 portal PR | React / Vue SPA;HTMX(可行但 M7 範圍還用不到局部更新) |
| 放在現有 `svc` 容器 | 全 VM 只有 gateway 持 443,多一個對外容器就要多一條路由 | 獨立 nginx 容器供應前端 |
| **不使用 WhiteNoise** | PLM 的 CSS 全 404 正是「框架自動剝前綴、gateway 卻保留前綴」的錯配;我們自己組 URL 就沒有這個意外 | 沿用 PLM 的 WhiteNoise 做法 |
| 靜態檔採**剝前綴** | 與主 location 一致,一種規則好過兩種 | 保留前綴(要在應用端多做 mount) |
| 上傳維持 PUT + XHR | 新增 multipart 端點會讓大檔落到暫存檔,退回平台鐵則「容器內不寫檔當狀態」 | 加一個 multipart 端點讓純 HTML 表單可用 |
| 錯誤回應做內容協商而非改格式 | RFC 7807 的義務及於 API 回應,不禁止對瀏覽器回 HTML;改格式會違反平台規約 | 一律 JSON(F75 就做不到);一律 HTML(違反規約) |
| 開 T47 而非併入 T40 | 它動的是 `app/problems.py`(後端行為),不是版面;混在一起會讓回滾粒度變粗 | 併入 T40 |
