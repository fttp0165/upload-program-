## 計畫(動工前成文,憲法第二條 2)

### 目標

實作 F42:為專案加標籤(如 `python`、`工具`、`報表`),可依標籤瀏覽與篩選。
Q4 定案的理由是「專案數量少時搜尋就夠;多了會需要」——這是為了平台長大以後的可瀏覽性。

**本任務是本專案第一個 🟡 加表任務**,會第一次真正用到 migration 的 `downgrade()`
與 up → down → up 雙向演練(規約 §7.5)。

### 資料模型:為什麼用一張表而不是兩張

直覺會做 `tags` + `project_tags` 兩張表(標籤正規化)。我選**單一張 `project_tags`**,
標籤直接存正規化後的字串:

| | 單表(採用) | 雙表(tags + project_tags) |
|---|---|---|
| 列出所有標籤 | `SELECT DISTINCT tag` | join |
| 孤兒標籤 | 不存在的問題 | 最後一個專案移除標籤後,`tags` 留下無人使用的列,要另外清 |
| 改標籤名稱 | 要 UPDATE 多列 | 改一列 |
| 複雜度 | 低 | 高 |

MVP 沒有「重新命名標籤」的需求,而孤兒清理是實打實的維運負擔。**選簡單的那個**,
日後真需要正規化再遷移(屆時是一次可回滾的 migration)。

### 標籤正規化規則(要在測試裡釘住)

- 前後空白去除、轉小寫(`Python` 與 `python` 是同一個標籤)
- **不允許內含空白**——標籤要能直接放進網址查詢字串,`?tag=資料 分析` 只會製造麻煩
- 長度 1–32
- 同一次請求內自動去重
- 每個專案最多 10 個標籤(防濫用)
- **允許中文**(`工具`、`報表` 是實際會用的標籤)

### 介面

| 端點 | 用途 | 權限 |
|---|---|---|
| `PUT /v1/projects/{slug}/tags` | **整組取代**專案標籤(冪等) | maintainer 以上 |
| `GET /v1/projects?tag=python` | 依標籤篩選專案列表 | 依可見性 |
| `GET /v1/tags` | 列出所有標籤與使用計數 | 只計**當事人看得到**的專案 |

用 `PUT` 整組取代而非 `POST`/`DELETE` 逐個增刪:前端就是一個標籤輸入框,
送出時本來就是整組;整組取代天然冪等,也不必處理「加一個已存在的標籤」這種邊角。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |
|---|---|---|
| 1 | maintainer 設定標籤 | 200,`ProjectOut.tags` 回正規化後的排序清單 |
| 2 | 重複送同一組 | 200 冪等 |
| 3 | `  Python  ` | 存成 `python` |
| 4 | 送重複標籤 | 自動去重 |
| 5 | 空字串 / 純空白 / 含空白 / 超長 | 422 |
| 6 | 超過 10 個 | 422 |
| 7 | 中文標籤 | 可用 |
| 8 | 傳空陣列 | 200,標籤清空 |
| 9 | viewer / 非成員設定標籤 | 403 |
| 10 | `?tag=` 篩選 | 只回帶該標籤**且當事人看得到**的專案 |
| 11 | `GET /v1/tags` | private 專案的標籤**不出現在非成員的清單裡** |
| 12 | 刪除專案 | 其標籤列一併消失(CASCADE) |

### 影響範圍

| 類型 | 檔案 |
|---|---|
| 新增 | `alembic/versions/0002_project_tags.py`、`tests/test_tags.py` |
| 修改 | `app/models.py`、`app/schemas.py`、`app/routers/projects.py`、`app/routers/search.py` |
| 修改 | `docs/功能需求大綱.md`、`docs/任務表.md`、`docs/設計_MVP.md` |

**對現有資料的影響:🟡 加表。**
新增 `project_tags`,**不動任何既有表的欄位**。migration 必須提供 `downgrade()`
(drop table),並實際跑 **up → down → up** 雙向演練(規約 §7.5)。

> 目前尚未上線、無正式資料,所以這次演練是零風險的;但流程要照走,
> 因為**第一次做的方式會變成之後的慣例**。

### 回滾方式

1. 程式:`git revert`
2. 資料:`alembic downgrade -1` → drop `project_tags`。既有表不受影響,無資料損失風險
   (標籤本身會消失,但那是這個功能的全部內容)

### 🟡 migration 雙向演練(規約 §7.5,本專案第一次)

```
-- upgrade head
   Running upgrade  -> 0001_initial
   Running upgrade 0001_initial -> 0002_project_tags
   ['alembic_version','artifacts','project_members','project_tags','projects','releases','users']

-- downgrade -1(回到 0001)
   Running downgrade 0002_project_tags -> 0001_initial
   ['alembic_version','artifacts','project_members','projects','releases','users']   ← project_tags 消失,其餘不動

-- upgrade head 再來一次
   Running upgrade 0001_initial -> 0002_project_tags
   ['alembic_version','artifacts','project_members','project_tags','projects','releases','users']

-- downgrade base
   ['alembic_version']
UP_DOWN_UP_OK
```

重點不只是「跑得過」,而是**確認回滾只拿掉新表、既有表原封不動**——
這才是 §7.5 要求雙向演練的理由。

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `alembic/versions/0002_project_tags.py` | 新增表 + 兩個索引;`downgrade()` 完整反向 |
| `app/models.py` | `ProjectTag`;`Project.tags` 關聯(`lazy="selectin"`) |
| `app/schemas.py` | `normalise_tag()`、`TagsIn`、`TagCount`/`TagPage`;`ProjectOut.tags` |
| `app/routers/projects.py` | `PUT /{slug}/tags`;列表支援 `?tag=` |
| `app/routers/search.py` | `GET /v1/tags`;抽出 `_visible_condition()` 共用 |
| `tests/test_tags.py` | 18 條 |

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| **單張 `project_tags`,不做標籤正規化表** | 兩張表會帶來孤兒標籤(最後一個專案移除後留下無人使用的列)這個實打實的維運負擔;MVP 沒有「重新命名標籤」的需求。列出所有標籤 `SELECT DISTINCT` 就夠 | `tags` + `project_tags` 兩張表 |
| 標籤**不允許內含空白** | 標籤要能直接放進查詢字串;`?tag=資料 分析` 只會製造編碼與比對的麻煩 | 允許空白 |
| 一律轉小寫 | `Python` 與 `python` 若是兩個標籤,篩選會漏掉一半——這種錯不會報錯,只會靜默少資料 | 保留原樣大小寫 |
| **篩選時也要正規化查詢字串** | 只在寫入端正規化的話,`?tag=PYTHON` 會查不到存成 `python` 的標籤 | 只在寫入端正規化 |
| `PUT` 整組取代而非逐個增刪 | 前端就是一個標籤輸入框,送出時本來就是整組;整組取代天然冪等,不必處理「加一個已存在的標籤」 | `POST /tags` + `DELETE /tags/{tag}` |
| `Project.tags` 用 `lazy="selectin"` | 專案幾乎總是連同標籤一起呈現;也避開 T50 那類「序列化時才 lazy load」在 async session 下爆掉的問題 | 預設 lazy(會重演 MissingGreenlet) |
| **`GET /v1/tags` 只計看得到的專案** | private 專案的標籤出現在非成員清單裡等於洩漏該專案存在——**標籤名稱本身就可能是機密**(測試用 `機密專用` 當例子) | 列出全部標籤 |

### 對現有資料的實際影響

`downgrade()` 只 drop 新表與其索引,既有資料零風險。已完成 up → down → up 雙向演練。
