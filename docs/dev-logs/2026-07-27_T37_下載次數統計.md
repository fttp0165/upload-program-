## 計畫(動工前成文,憲法第二條 2)

### 目標

實作 F43:記錄並顯示**各檔案 / 各版本**的下載次數。
Q5 定案「需要」——這是給使用者看的熱門度訊號(哪個工具真的有人在用),
也是日後決定「舊版本要不要清掉」(Q13)的依據。

任務表對本任務的驗收標準寫得很明確:**下載即累計;統計不記個資;migration 有 backward。**

### 資料模型:計數欄位,不是事件表

| | 計數欄位(採用) | 事件表 `download_events` |
|---|---|---|
| 存什麼 | `artifacts.download_count` 一個整數 | 每次下載一列(誰、何時、哪個檔) |
| 個資風險 | **結構上不可能記到人** | 一定會存 user_id,要小心不要存到 email/IP |
| 成長 | 不成長 | 無上限成長,要排清理 |
| 能回答「誰下載了」 | 不能 | 能 |
| 查詢成本 | 讀一個欄位 | 每次顯示都要 `COUNT(*)` |

選**計數欄位**。理由是 F43 只要求「次數」,而「誰下載了什麼」是**稽核**的職責——
那是 T38(F54)的事,而且稽核有自己的保存期限與存取權限。
兩件事混在一張表裡,結果通常是稽核資料被當統計資料到處顯示。

> 🔴 任務表寫「統計不記個資」。用計數欄位的話,這件事**不是靠自律,是結構上做不到**——
> 表裡根本沒有可以放人的欄位。這比「我們有記得不要存」可靠得多。

**各版本的下載次數不另存欄位**,而是即時加總該版本底下所有檔案的計數。
兩個計數器分開存,遲早會對不起來(刪檔、補傳、回滾任何一個環節漏掉就分岔),
而版本的檔案本來就已經 `lazy="selectin"` 一起載入,加總不用額外查詢。

### 在哪裡累計:`_download_response()` 一個點

兩條下載路徑(`/releases/{id}/artifacts/{aid}/download` 與
最新版捷徑 `/projects/{slug}/releases/latest/artifacts/{filename}/download`)
**已經**共用 `_download_response()`——T35 就是為了「安全標頭不能因為換路徑就鬆掉」才抽的。
計數放同一個點,同樣不可能有一條路徑漏算。

代價:`_download_response()` 要改成 async 並吃 `session`。這是值得的——
另一個做法是在兩個呼叫端各寫一次累計,那正是 T35 想避免的東西。

### 何時算一次:回應建構時(「發起下載」)

兩種語意:

| 時機 | 意義 | 代價 |
|---|---|---|
| **回應建構時(採用)** | 發起下載的次數 | 客戶端下載到一半中斷也算一次 |
| 串流跑完後 | 完成下載的次數 | 要包裝迭代器或用 BackgroundTask;中斷/逾時的處理變複雜 |

選前者,並在文件與欄位註釋裡**誠實說明它算的是「發起」**。
理由:這個數字的用途是熱門度,不是計費;為了幾個中斷的請求把串流路徑複雜化不划算。
`_download_response()` 內的 `upload_status is ready` 檢查在計數之前,
所以**下載失敗(404)不會被算進去**。

### 🔴 併發:一定要用原子 UPDATE

```python
artifact.download_count += 1     # ❌ 讀-改-寫,兩個併發請求會掉一次
```

必須下 `UPDATE artifacts SET download_count = download_count + 1 WHERE id = ...`,
把加法交給資料庫。這種錯不會有任何錯誤訊息,只會讓數字**默默偏低**,
而且下載正是最容易併發的端點。

### 介面

| 端點 | 變更 |
|---|---|
| `ArtifactOut` | 新增 `download_count` |
| `ReleaseOut` | 新增 `download_count`(= 底下所有檔案的加總) |

不另開統計端點:數字跟著既有的檔案/版本回應一起出去,前端(M7)拿到就能顯示。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |
|---|---|---|
| 1 | 剛上傳的檔案 | `download_count == 0` |
| 2 | 下載三次 | `download_count == 3` |
| 3 | 走**最新版捷徑**下載 | 同一個計數器 +1(兩條路徑不得分岔) |
| 4 | 版本的計數 | 等於其所有檔案計數的加總 |
| 5 | 下載未上傳完成的檔案 | 404,且**不計數** |
| 6 | private 專案非成員下載 | 404,且**不計數** |
| 7 | 並發下載 5 次 | 計數為 5(原子 UPDATE) |
| 8 | 刪除檔案 | 版本加總跟著減少 |
| 9 | **不記個資** | 下載後除了 `artifacts.download_count`,資料庫沒有新增任何列;且模型中沒有任何「誰下載」的欄位 |

> 自我提醒:預期 4xx 的測試一律加上 detail/type 斷言(第 5、6 條),避免路由或前置檢查
> 出問題時靠 404 假通過。

### 影響範圍

| 類型 | 檔案 |
|---|---|
| 新增 | `alembic/versions/0004_artifact_download_count.py`、`tests/test_download_count.py` |
| 修改 | `app/models.py`、`app/schemas.py`、`app/routers/artifacts.py` |
| 修改 | `docs/功能需求大綱.md`、`docs/任務表.md`、`docs/設計_MVP.md` |

**對現有資料的影響:🟡 加欄位。**
`artifacts` 新增 `download_count`,`server_default='0'` ——既有列自動補 0,不需要資料回填。
**不動任何既有欄位。**

⚠️ 與 T49 相同:`downgrade()` 會**刪掉欄位連同累計值**。回滾後所有下載次數歸零、
無法還原(沒有事件表可以重算——這正是選計數欄位的代價)。
回滾前若要保留,先撈一份:

```sql
SELECT id, filename, download_count FROM artifacts WHERE download_count > 0;
```

### 回滾方式

1. 程式:`git revert`
2. 資料:`alembic downgrade -1` → drop `artifacts.download_count`。
   檔案本身、版本、專案完全不受影響;**唯一損失是累計值,且不可重建**。
3. 演練:up → down → up,並確認 `artifacts` 的其他欄位與資料列數不變(沿用 T49 的演練腳本)。

## 結果(完工後補記)

### 紅 → 綠

```
先寫 9 條測試 → 9 failed(全紅)
實作後       → 9 passed;全套 157 → 166 passed;lint 全過
```

過程中修掉一個**測試自己的 bug**:直接拿 JSON 回來的 `id` 字串去比對 `Uuid` 欄位,
SQLAlchemy 丟 `'str' object has no attribute 'hex'`。這是測試寫錯不是程式錯,
改成 `uuid.UUID(artifact_id)` 即可——記在這裡是因為下次寫「繞過 API 直接查 DB」
的測試還會再踩一次。

### 併發測試不是空測(實測)

「原子 UPDATE」這種要求最容易寫出一條**永遠會過**的測試,所以我把實作暫時換回
naive 寫法跑一次:

```
artifact.download_count += 1   →  FAILED test_併發下載不掉數 - assert 1 == 5
正確的原子 UPDATE               →  9 passed
```

5 次併發下載在 naive 寫法下只記到 **1** 次——掉了 4 次,而且**沒有任何錯誤訊息**。
這正是這條測試存在的理由。

### 🟡 migration 雙向演練

```
-- upgrade head
   artifacts 欄位: [... 14 個 ..., download_count]
   假資料:tool.bin 累計 42 次、manual.pdf 0 次

-- downgrade -1
   artifacts 欄位: [... 14 個 ...]                    ← download_count 消失
   ✔ 回滾只拿掉 download_count,其餘 11 個欄位與 2 筆資料原封不動

-- upgrade head 再來一次
   累計值: [(manual.pdf, 0), (tool.bin, 0)]
   ✔ 如計畫所述:tool.bin 的 42 次回不來——沒有事件表可重算

-- downgrade base → ['alembic_version']
UP_DOWN_UP_OK
```

第三段再次把計畫裡寫的風險變成實測結果:**回滾丟掉的累計值是不可重建的**。
這是「選計數欄位而非事件表」的代價,已寫進 migration 檔頭與本日誌。

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `alembic/versions/0004_artifact_download_count.py` | `artifacts` 加 `download_count`(`server_default='0'`);`batch_alter_table` 雙向 |
| `app/models.py` | `Artifact.download_count`(含「為什麼不做事件表」的註釋) |
| `app/schemas.py` | `ArtifactOut.download_count`;`ReleaseOut.download_count`(`model_validator` 加總) |
| `app/routers/artifacts.py` | `_download_response()` 改 async 並吃 session,在 ready 檢查後下原子 UPDATE |
| `tests/test_download_count.py` | 9 條 |

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| **計數欄位,不做下載事件表** | F43 只要求次數;「誰下載了什麼」是稽核(T38/F54)的職責,有自己的保存期限與存取權限。混在一起的結果通常是稽核資料被當統計資料到處顯示。且計數欄位讓「統計不記個資」成為**結構保證**而非自律 | `download_events` 表 |
| **版本計數用加總,不另存欄位** | 兩個計數器分開存,刪檔/補傳/回滾任何一個環節漏掉就永遠分岔;`artifacts` 本來就 `selectin` 一起載入,加總零成本 | `releases.download_count` |
| **計數點放在 `_download_response()`** | 兩條下載路徑(直接、最新版捷徑)已為了安全標頭共用這個函式;換一條路徑就不算數的統計等於沒有統計。代價是它得改成 async 並吃 session,值得 | 兩個呼叫端各寫一次 |
| 🔴 **原子 UPDATE** | `+= 1` 是讀-改-寫,併發會默默掉數且無錯誤訊息;下載正是最容易併發的端點。已實測 naive 寫法 5 次併發只記到 1 次 | Python 端累加 |
| **算「發起」而非「完成」下載** | 用途是熱門度不是計費;要算完成就得包裝迭代器或用 BackgroundTask,把串流路徑複雜化不划算。誠實命名比精確更重要 | 串流跑完才計數 |
| **計數放在 `ready` 檢查之後** | 失敗的下載(404)不該灌水 | 進函式就先計數 |

### 對現有資料的實際影響

**🟡 加欄位:`artifacts` 新增 `download_count`,未改動任何既有欄位。**
`server_default='0'` 讓既有列自動補 0,不需要資料回填。

⚠️ **回滾會刪掉欄位連同累計值,而且不可重建**(已由演練實證)——沒有事件表可以重算。
回滾前若要保留:

```sql
SELECT id, filename, download_count FROM artifacts WHERE download_count > 0;
```

目前尚未上線、無正式資料,零風險;但這條要與 T49 的級距設定一起進 T27 換版 runbook。

### 遺留問題與後續建議

| # | 問題 | 建議 |
|---|---|---|
| 1 | 算的是「發起下載」,中途中斷仍計一次 | 已在欄位註釋、設計文件與 API 語意上誠實標明;真要精確再改成串流完成後計數 |
| 2 | 沒有「熱門專案排行」 | 專案層的加總要跨 releases → artifacts,查詢成本高於版本層;真需要時再評估要不要在 `projects` 放一個快取欄位(那會是另一個 🟡 任務) |
| 3 | 同一人重複下載會重複計數 | 去重需要記錄「誰下載過」——那就回到事件表與個資問題。維持現況 |
| 4 | 沒有時間維度(這個月下載幾次) | 需要事件表或按期歸檔的快照;超出 F43 範圍 |
| 5 | 計數的 commit 與串流是兩件事 | 計數在回應建構時就已 commit,串流失敗不會回沖——與「算發起」的語意一致,非缺陷 |

## 後記(2026-07-28,T38 完成後補上的追蹤)

本篇當初把「誰下載了什麼」推給 T38 時,寫下的條件是稽核**「有自己的保存期限與存取權限」**。
那兩句話在 [T38 的日誌](2026-07-28_T38_稽核紀錄.md)已兌現:查詢只開給平台管理員
(專案 owner 也不行,正是為了不繞過本篇「統計只到次數」的個資決定),保留期
`AUDIT_RETENTION_DAYS` 365 天 + `tools/purge_audit.py`。

同時,本篇的 `test_統計在結構上不可能記到個資` **在 T38 實作完成後立刻變紅**——
它的「一次下載不在**任何**表新增列」在 F54 之後不再成立。處理方式是改成**具名例外**
(只允許 `audit_events` 增加恰好一列),不是放寬斷言;`設計_MVP.md` §3.5 亦已回寫範圍。
本篇正文維持原樣不改——它記的是當時的事實。
