## 計畫(動工前成文,憲法第二條 2)

### 目標

專案頁:專案資訊 + **最新已發布版本置頂**。

驗收標準:**最新已發布版本的說明與下載按鈕在頁面最上方直接可見。**
這是 Q8 裁示「最新版本至頂」的直接落實——來這一頁的人十之八九是要抓最新版,
不該讓他先捲過一堆 metadata。

順帶接上 T41 的遺留 #1:首頁專案卡片連到這一頁。

### 🔴 匿名訪客:訊息不得洩漏專案是否存在

`/projects/{slug}` 對匿名訪客要顯示登入提示。但這裡有個陷阱:
**如果先查專案、查不到就回 404、查得到才顯示登入提示,等於用兩種回應洩漏了專案存在。**

做法:**匿名(與待開通)一律不查詢**,直接顯示提示。
訊息與狀態碼在「專案存在」與「專案不存在」兩種情況下**完全相同**,
所以結構上不可能洩漏。測試會同時打一個存在的 private 專案與一個不存在的 slug,
斷言兩邊的回應一致。

已開通者才走 `require_project_read` —— 它對 private 非成員回 **404 而非 403**,
同樣是為了不洩漏存在;這條規則在 API 已經有,網頁沿用**同一個函式**,不另寫一份。

### 最新版本:沿用 `latest_published_release()`

不自己再查一次。那個函式已經釘住兩件事(T35 的教訓):

- 以 **`published_at`** 判定,不用版本號字串排序(`v9` 會排在 `v10` 前面,
  發到第十版就靜默地一直給出舊版)
- 也不用 `created_at`(先建的版本可能後發布)
- **draft 不算**——latest 是給使用者抓的,draft 是作者的工作區

它在「尚未發布任何版本」時會拋 404;網頁不能因此變成錯誤頁,所以要接起來改成
「尚無已發布的版本」的提示。

### 下載連結:兩種都給

| 用途 | 網址 |
|---|---|
| 頁面上的下載按鈕 | `/v1/releases/{id}/artifacts/{aid}/download`(精確指向這一版的這個檔) |
| 可貼進文件的固定連結 | `/v1/projects/{slug}/releases/latest/artifacts/{filename}/download`(F26) |

按鈕用精確網址(使用者按的當下看到的是哪一版就抓哪一版);
固定連結以可複製的文字呈現——那是 T35 做出來的東西,不放在使用者看得到的地方就沒人會用。

### 🔴 掃毒狀態要誠實顯示

紅線:「掃毒未接上前,`scan_status` 必須誠實標示 `not_scanned`」。
這一頁是使用者按下載之前最後看到的畫面,**必須把 `not_scanned` 顯示出來**,
不能只放在 API 回應裡。有測試釘住。

同時顯示 SHA-256(供自行校驗)、檔案大小、下載次數(F43)。

### 版面順序

```
專案標題列(名稱、slug、可見性、標籤、摘要)
    ↓
【最新版本】版本號、發布時間、說明、檔案清單 + 下載按鈕      ← 置頂的重點
    ↓
專案資訊(容量用量、建立/更新時間)
```

摘要留在標題列(它是一行,屬於「這是什麼專案」的一部分);
**其餘 metadata 一律排在最新版本之後**。測試會斷言下載按鈕出現在專案資訊區塊之前。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |

## 結果(完工後補記)

### 紅 → 綠

```
先寫 16 條測試 → 14 failed / 2 passed
實作後        → 16 passed;全套 208 → 224 passed;lint 全過
```

2 條一開始就綠的是「private 專案對非成員回 404」與「所有連結帶前綴」——
路由不存在時本來就 404,連結測試也沒有連結可檢查,兩條都是**當下空過**的。
不過同組的「成員看得到 private 專案」保證了實作後前者會有意義,
「首頁卡片連到專案頁」則保證了後者。

### 🔴 不洩漏存在:以「把實作改壞」實測

這是本任務最容易寫成空測的地方,所以把實作改成最自然的寫法跑一次:

```python
project = await get_project(session, slug)      # 先查
if identity is None or not identity.user.is_active:   # 再判身分
    return 登入提示
```

```
先查再判身分  →  FAILED test_匿名訪客的回應不洩漏專案是否存在
匿名不查詢    →  16 passed
```

改壞之後,存在的 private 專案回 200(登入提示)、不存在的 slug 回 404
——**回應本身就是答案**。這正是「匿名一律不查詢」要防的東西,
而且它是**結構保證**:程式碼裡根本沒有可以洩漏的分支。

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `app/routers/web.py` | `GET /projects/{slug}`;匿名/待開通不查詢;接住 `latest_published_release()` 的 404 |
| `app/templates/project.html` | **新檔**:標題列 → 最新版本 → 專案資訊 |
| `app/templates/home.html` | 專案卡片接上連結(T41 遺留 #1) |
| `app/static/app.css` | 專案頁、檔案清單、下載按鈕樣式 |
| `tests/test_web_project.py` | 16 條 |

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| **匿名/待開通一律不查詢** | 先查再判身分的話,存在與不存在會回不同狀態碼,**回應本身就洩漏了答案**。不查詢是結構保證,不是靠記得 | 先查專案再決定顯示什麼 |
| **沿用 `latest_published_release()`** | T35 已經在那裡釘住三件事:以 `published_at` 判定(版本號字串排序會讓 `v9` 排在 `v10` 前,發到第十版就靜默給舊版)、不用 `created_at`、draft 不算 | 網頁自己查一次最新版 |
| **把它的 404 接起來改成提示** | 「尚未發布任何版本」對 API 是 404,對網頁不是錯誤——那是一個正常的專案狀態 | 讓它變成錯誤頁 |
| **下載按鈕用精確網址、另外顯示 F26 固定連結** | 按鈕要精確(使用者看到哪一版就抓哪一版);固定連結是要貼進文件的,兩者用途不同。T35 做出來的東西不放在看得到的地方就沒人會用 | 只給其中一種 |
| **摘要留在標題列,其餘 metadata 排在最新版本之後** | 摘要是「這是什麼專案」的一部分,一行;容量、時間這些才是會擋路的東西 | 全部 metadata 都排在版本之前 |
| **`not_scanned` 顯示在下載按鈕旁邊** | 這一頁是使用者按下載之前**最後看到的畫面**;只放在 API 回應裡等於沒說 | 只在 API 誠實標示 |
