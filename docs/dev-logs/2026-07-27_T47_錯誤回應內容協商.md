## 計畫(動工前成文,憲法第二條 2)

### 目標

`app/problems.py` 目前一律回 `application/problem+json`。但 F75 要求
「未開通者看到**指引頁**,而非裸 403 JSON」——瀏覽器導覽拿到一坨 JSON 是不可接受的體驗。

決策文件 §5.2 已定案:**依 `Accept` 標頭做內容協商**;瀏覽器導覽回 HTML,
API 呼叫維持 `problem+json`。RFC 7807 的義務只及於 API 回應,不禁止對瀏覽器回 HTML。

本任務是 **M7 的第一項**,也是 T40 的前置——沒有它,前端的每一個錯誤畫面都是裸 JSON。

### 判斷規則:路徑 **且** Accept,兩個條件都要成立

只看 `Accept` 是不夠的。平台鐵則寫著「錯誤回應一律 RFC 7807」,而
`curl -H 'Accept: text/html' /v1/projects` 若因此拿到 HTML,等於**整個 API 表面的
錯誤格式可以被呼叫端的一個標頭改掉**。所以採兩個條件:

| 條件 | 規則 |
|---|---|
| 路徑 | **不是** `/v1/*`、`/health`、`/ready` 這類機器端點 |
| Accept | **明示**含 `text/html` |

兩者皆成立才回 HTML,否則一律 `problem+json`。

> 註:gateway 以尾斜線 `proxy_pass` **剝掉前綴**後轉發,所以到達本服務的路徑就是
> `/v1/...`,不含對外前綴。這裡直接比對 `/v1/` 是正確的,不需要拼 `api_prefix`。

**「明示」很重要**:`Accept: */*`(fetch、XHR、curl 的預設)**不算**。
只有 `text/html` 這個字面值出現才算。瀏覽器導覽送的是
`text/html,application/xhtml+xml,...,*/*;q=0.8`,會命中;
JS 呼叫送 `*/*`,不會命中——這正是我們要的分界。

### 為什麼用 Jinja2 而不是字串拼接

錯誤頁要顯示 `detail` 與 `instance`(= `request.url.path`),**兩者都含使用者可控內容**。
字串拼 HTML 就是 XSS 的標準做法。Jinja2 的 `.html` 模板預設 autoescape,
而且 T40 本來就要導入 Jinja2(決策文件 §6.1),現在裝正好。

🔴 這件事對本專案特別敏感:本服務散布可執行檔,紅線寫著
「絕不讓上傳內容在本服務網域被瀏覽器執行」。錯誤頁把 `/{惡意路徑}` 原樣吐回去,
等於自己開了一個 XSS——**必須有測試釘住**。

### 錯誤頁的樣式

- 憲法第四條:**一律 light 主題**,白底深字,**不使用 `prefers-color-scheme: dark`**
- **無外部資源**(不連 CDN、不載外部字型):內部平台,而且錯誤頁在服務半殘時也要能顯示
- CSS 直接內嵌在模板裡。**不建 base layout** ——那是 T40 的範圍;
  本任務只做「錯誤頁能出現」,T40 再讓它 extend 共用版型

### 回應標頭

| 標頭 | 為什麼 |
|---|---|
| `Vary: Accept` | 同一個 URL 有兩種表述,不標的話快取會把 HTML 餵給 API 呼叫端 |
| `X-Content-Type-Options: nosniff` | 與下載路徑一致的立場;錯誤頁也不給瀏覽器猜型別的機會 |
| 原有的 `WWW-Authenticate` 等 | 401 的挑戰標頭不因為換成 HTML 就消失 |

### 實作位置:`problem_response()` 一個點

四個 exception handler(ProblemError / HTTPException / RequestValidationError / 未處理例外)
全都經過 `problem_response()`。協商放在那裡,就不可能有某一類錯誤漏掉。
這與 T35(下載回應)、T37(下載計數)是同一個模式:**同一件事只能有一條路**。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |
|---|---|---|
| 1 | `/v1/*` + `Accept: text/html` | **仍是 `problem+json`**(平台規約不因瀏覽器而鬆動) |
| 2 | `/health`、`/ready` + `Accept: text/html` | 仍是 JSON(機器端點) |
| 3 | 非 API 路徑 + 瀏覽器 Accept | **HTML**,status code 不變 |
| 4 | 非 API 路徑 + `Accept: */*` | `problem+json`(fetch / XHR / curl 預設) |
| 5 | 非 API 路徑 + 無 Accept 標頭 | `problem+json` |
| 6 | 非 API 路徑 + `Accept: application/json` | `problem+json` |
| 7 | HTML 頁內容 | 含 status、title、detail、trace_id |
| 8 | 🔴 使用者可控內容 | `<script>` 一律逸出,不得原樣出現在 HTML 中 |
| 9 | HTML 回應標頭 | 含 `Vary: Accept` 與 `nosniff` |
| 10 | 401 走 HTML | `WWW-Authenticate` 標頭仍在 |
| 11 | 憲法第四條 | 頁面無 `prefers-color-scheme: dark`、無外部資源網址 |
| 12 | 未知路徑瀏覽器導覽 | 404 HTML 頁(這是最常見的情境) |

> 預期 4xx 的測試一律加上內容斷言,不能只看 status code——這批測試裡每一條的
> status code 本來就會是對的(協商不改 status),真正要驗的是**表述**。

> ⚠️ **計畫與實作的差異(憲法第二條 5)**:計畫預期要改 `app/main.py` 掛 `Jinja2Templates`,
> 實際上**沒有動到 main.py**——協商既然住在 `problems.py`,模板 Environment 就一起放在那裡,
> 不必經由 app.state 傳遞。少一個全域狀態、少一條相依。
> T40 引入網頁路由時會需要 app 層的模板設定,屆時再處理。

```

實作後        → 13 passed;全套 166 → 179 passed;lint 全過
```

**這次不是全紅,而且是預期中的**:7 條綠的全部是「這個情境應該回 JSON」——
協商還不存在時,一律回 JSON 本來就會通過。它們不是假通過,而是
**釘住「不該改變的行為」的迴歸測試**:實作協商時最容易犯的錯就是讓太多情境變成 HTML,
這 7 條的用途正是在那時候變紅。

### 兩條測試在動工前被自己駁回

寫完第一版測試後重看,發現兩條不夠實,在跑紅之前就改掉:

| 原本 | 問題 | 改成 |
|---|---|---|
| `test_401的挑戰標頭…` 去斷言 `problems.unauthorized()` 回傳的物件 | 那只驗證了工廠函式,**完全沒走到協商程式碼** | 直接呼叫 `problem_response()` 並斷言 HTML 回應仍帶 `WWW-Authenticate` |
| `test_健康檢查端點不做協商` 打 `/health/nope` | 語意含糊——那條路徑該算機器端點還是一般頁面?取決於實作用前綴比對還是精確比對,等於**讓測試遷就實作** | 改成一張 12 列的**真值表**,直接測 `wants_html()` 這個純函式,把 `/health`、`/ready`、`/v1/*` 與各種 Accept 一次攤開 |

### 逸出測試不是空測(實測)

把 `autoescape` 關掉跑一次:

```
autoescape=False                        →  FAILED test_HTML錯誤頁對使用者可控內容做逸出
autoescape=select_autoescape(["html"])  →  13 passed
```

`/%3Cscript%3Ealert(1)%3C/script%3E` 這條路徑會原封不動出現在頁面上。
🔴 本服務散布可執行檔,紅線寫著「絕不讓上傳內容在本服務網域被瀏覽器執行」——
錯誤頁自己開一個 XSS 是同一件事的反面,所以這條測試必須是真的。

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `app/problems.py` | `wants_html()` 協商判斷;`problem_response()` 依判斷產 HTML 或 JSON;四個 handler 的回傳型別改 `Response` |
| `app/templates/error.html` | **新檔**:light 主題、零外部資源、內嵌 CSS |

| `tests/test_error_negotiation.py` | 13 條 |

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| **路徑 AND Accept 兩個條件** | 只看 Accept 的話,`curl -H 'Accept: text/html' /v1/projects` 就能把整個 API 表面的錯誤格式改掉;平台鐵則「錯誤回應一律 RFC 7807」不該被呼叫端的一個標頭鬆動 | 只看 Accept(決策文件原本的寫法,已回寫修正) |
| **`*/*` 不視為瀏覽器** | 那是 fetch / XHR / curl 的預設值——程式在呼叫,不是人在看。這正是「人 vs 程式」最乾淨的分界 | 用 q-value 完整排序比較(過度工程,且 `*/*` 的判定仍要特例處理) |
| **`/health`、`/ready` 用精確比對而非前綴** | 前綴比對會誤傷未來的 `/health-dashboard` 這類頁面 | `startswith("/health")` |
| **Jinja2 而非字串拼接** | `detail` 與 `instance` 都是使用者可控內容,字串拼 HTML 就是 XSS 的標準做法;而且 T40 本來就要導入 Jinja2 | f-string 組 HTML |
| **`Vary: Accept` 連 JSON 回應也帶** | 同一個 URL 有兩種表述,方向是雙向的——不標的話快取也可能把 JSON 餵給瀏覽器 | 只在 HTML 回應帶 |
| **錯誤頁不 extend 共用版型** | base.html 是 T40 的範圍,現在還不存在;本任務只負責「錯誤頁能出現」 | 順手把版型骨架也做了(會變成兩個任務混在一起) |
| **錯誤頁零外部資源** | 它正是在服務半殘、外網不通時要顯示的東西 | 用 CDN 的 CSS |

### 對現有資料的實際影響

**🟢 不動資料。** 純回應層,無 migration、無欄位變更。

行為變更僅一項:**非 API 路徑 + 瀏覽器 Accept** 的錯誤回應從 JSON 變成 HTML。
目前非 API 路徑只有「不存在的路徑」(網頁路由是 T40 之後才有),
所以實務上的影響就是「網址打錯時看到一頁人話而不是 JSON」。
