## 計畫(動工前成文,憲法第二條 2)

### 目標

實作 F17:專案容量分兩個級距——**標準 2 GB**(預設)與 **擴充 10 GB**(需申請,
平台管理員核可)。目前 T33 只有一個全站共用的 `MAX_PROJECT_BYTES`,
所有專案吃同一個數字,沒有個案放寬的餘地。

**本任務是本專案第一個 🟡 加欄位任務**(T36 是加表)。差別在於:
加表的 `downgrade()` 是 drop table,乾淨俐落;**加欄位的 downgrade 會刪掉欄位裡的資料**
——回滾後所有專案的級距設定一律消失、退回標準級距。這件事必須在計畫裡先講明白。

### 資料模型:存「級距代號」而不是「位元組數字」

兩種做法:

| | 存級距代號 `quota_tier`(採用) | 存 `quota_bytes` 數字 |
|---|---|---|
| 政策數字在哪 | 設定檔一處 | **複製到每一列** |
| 把標準級距從 2 GB 調成 3 GB | 改設定值,重啟 | `UPDATE projects SET quota_bytes=...`,要小心別蓋掉個案值 |
| 個案任意數值 | 做不到(只有兩級) | 做得到 |
| 與 F17 的吻合度 | F17 明文就是兩級距 | 超出需求 |

選**級距代號**。理由是政策數字散進資料列是一種真實的技術債:
日後調整級距就變成一次資料遷移,而遷移最怕的正是「分不清哪些列是政策預設、
哪些列是個案調整」。若日後真需要任意值,再加一個可為 NULL 的 `quota_bytes_override`
欄位覆寫級距——那是另一次可回滾的 migration,而且語意清楚。

### 設定值命名

沿用既有的 `MAX_PROJECT_BYTES`(標準級距)並新增 ~~`MAX_PROJECT_BYTES_EXTENDED`~~。
不改名為 `PROJECT_QUOTA_STANDARD_BYTES` 這種對稱寫法,因為:

1. `.env.example` 的註解**已經**寫著「專案標準級距;擴充級距 10 GB 見 T49」——
   語意早就對齊了,改名只是換皮。
2. ~~`test_env_example的容量值與程式預設一致` 這條防漂移測試用的是
   `^(MAX_\w+_BYTES)=(\d+)` ——新變數**自動被納入防護**,不用改測試。~~

> ⚠️ **第 2 點是錯的,實作時被測試抓到**:`MAX_PROJECT_BYTES_EXTENDED` 結尾是
> `_EXTENDED` 而非 `_BYTES`,不符合 `MAX_\w+_BYTES` 樣式,根本不會被納入防護。
> 變數已改名為 **`MAX_PROJECT_EXTENDED_BYTES`**。詳見〈計畫的修正〉。

### 誰能調級距

**只有平台管理員**(`AdminUser`)。owner 不行——否則等於沒有上限,
專案負責人自己就能把自己調到 10 GB,F17 的「由平台管理員核可」就成了空話。

MVP 的「申請」走線下(口頭/郵件),管理員直接調。站內申請單是 F18(P2,不在本任務)。

### 降級的處理:允許,但不刪檔

管理員把一個已用 5 GB 的擴充級距專案降回標準(2 GB)時:

- **允許降級**,回 200 —— 管理員可能正是要用降級逼專案清理。
- **既有檔案不動、仍可下載** —— 刪別人的檔案不是「調級距」該做的事。
- 之後的**新上傳一律 413**,直到用量降回上限以下。
- log 記一筆 warning(降級後已超標),讓這件事在營運上看得見。

這與 T33 在 `config.py` 寫下的註解一致:「調降此值會讓已超標的既有專案立刻無法上傳
新檔(既有檔案不受影響)」。

### 413 訊息:F17 要求「不能只丟一句 Payload Too Large」

超限的錯誤回應要能讓使用者自己搞懂怎麼辦,所以 detail 要含
**目前級距、上限、已用量、本次大小**,以及**下一步指引**;
指引還要**依級距而異**:

| 目前級距 | 指引 |
|---|---|
| `standard` | 可向平台管理員申請擴充級距(10 GB) |
| `extended` | 已是最大級距,請刪除不再需要的舊版本以釋出空間 |

對 extended 專案還講「可申請擴充」是明確的錯誤指引——會讓人去申請一個不存在的東西。

同時以 RFC 7807 的擴充成員(extension members)帶出
`quota_tier` / `quota_bytes` / `used_bytes` / `incoming_bytes`,前端才能畫用量條
而不必去 parse 中文句子。

### 介面

| 端點 | 用途 | 權限 |
|---|---|---|
| `PUT /v1/projects/{slug}/quota` | 設定級距(冪等) | **平台管理員** |
| `ProjectOut` 新增 `quota_tier`、`quota_bytes` | 前端顯示「已用 x / 上限 y」 | 依可見性 |

### 順帶收掉的重複:`ProjectOut` 的組裝散在 8 處

`ProjectOut.model_validate(project)` + `out.my_role = ...` 目前散在
`projects.py`(7 處)與 `search.py`(1 處)。加上 `quota_bytes` 之後,
**漏掉任何一處就是一個欄位為 null 的靜默 bug**。
抽成一個 `project_out()` 放進 `security.py`(那裡已經住著 `get_project`、
`project_role` 等 router 共用的專案輔助函式),讓「組裝當事人視角的專案輸出」只有一條路。

這是純重構的部分,依憲法第三條 4:不寫新測試,但既有測試必須維持全綠當安全網。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |
|---|---|---|
| 1 | 新建專案 | `quota_tier == "standard"`,`quota_bytes == 標準值` |
| 2 | admin 調成 extended | 200,`quota_tier`/`quota_bytes` 同步更新 |
| 3 | 重複調成 extended | 200 冪等 |
| 4 | owner(非 admin)調級距 | 403 |
| 5 | 非成員 / viewer 調級距 | 403 |
| 6 | 不存在的 slug | 404 |
| 7 | 不合法的級距值 | 422 |
| 8 | standard 專案超限上傳 | 413,detail 含級距/上限/已用量,且提到**申請擴充** |
| 9 | 同一份上傳,改 extended 後 | **201 成功**(級距真的有作用——本任務的核心) |
| 10 | extended 專案超限 | 413,指引改為**清理舊版本**,不再說「可申請」 |
| 11 | 降級後已超標 | 降級本身 200;之後上傳 413 |
| 12 | Content-Length 預檢的 413 | 與收完才發現的 413 **同一套訊息與擴充成員** |
| 13 | 列表 / 詳情 / 搜尋 | 都回 `quota_tier` 與 `quota_bytes` |

> 自我提醒(前兩次的教訓):**所有預期 4xx 的測試都要一併斷言 detail 或 type**,
> 否則路由還沒寫時 404/403 也會「通過」,那是假通過。

**對現有資料的影響:🟡 加欄位。**
`projects` 新增 `quota_tier`,`server_default='standard'` ——既有列自動補上預設值,
不需要另外的資料回填(data migration)。**不動任何既有欄位**。

⚠️ **與 T36 的關鍵差別:`downgrade()` 會刪掉這個欄位,連同裡面的資料。**
回滾後所有專案的級距設定消失、一律退回標準級距;曾被調成 extended 的專案
會立刻無法上傳新檔(既有檔案仍在)。這不是資料損毀,但**是可感知的功能倒退**,
必須在換版 runbook(T27)裡標明。

### 回滾方式

1. 程式:`git revert`
2. 資料:`alembic downgrade -1` → drop `projects.quota_tier`。
   既有專案的檔案、成員、標籤完全不受影響;**唯一損失是級距設定本身**
   (回滾後全部視為標準級距)。要保留的話,回滾前先
   `SELECT slug, quota_tier FROM projects WHERE quota_tier <> 'standard'` 存一份。
3. 演練:up → down → up 雙向,並確認 downgrade 後 `projects` 的**其他欄位與資料列數不變**
   ——加欄位的演練重點就在這裡,和加表不同。

## 結果(完工後補記)

### 紅 → 綠

```
先寫 13 條測試 → 13 failed(全紅)
實作後        → 13 passed;全套 143 → 157 passed;lint 全過
```

其中 `不存在的專案回404` 是**在 detail 斷言上失敗**而非靠 404 假通過——
路由還沒寫時它拿到的 404 detail 是 FastAPI 的 `Not Found`,斷言 `"專案" in detail` 直接紅。
「預期 4xx 的測試一律加上 detail/type 斷言」這條自我規範第三次生效。

### 🟡 migration 雙向演練(加欄位版,與 T36 加表不同)

加欄位的演練重點不是「新表有沒有消失」,而是**回滾後其他欄位與資料列有沒有被弄丟**
(`batch_alter_table` 在 SQLite 上是「建新表→搬資料→換名」,搬錯就是真的掉資料)。
演練腳本先造兩筆假專案(一筆 standard、一筆 extended),再比對回滾前後的快照:

```
-- upgrade head
   projects 欄位: [id, slug, name, summary, visibility, owner_id, total_bytes,
                   created_at, updated_at, quota_tier]

-- downgrade -1
   projects 欄位: [id, ..., updated_at]                    ← quota_tier 消失
   回滾前後同樣欄位的資料列:完全相同(alpha 123 bytes / beta 999 bytes,含中文 summary)
   ✔ 回滾只拿掉 quota_tier,其他欄位與 2 筆資料原封不動

-- upgrade head 再來一次
   級距: [(alpha, standard), (beta, standard)]
   ✔ 如計畫所述:回滾會丟掉級距設定,beta 從 extended 退回 standard(server_default)

-- downgrade base → ['alembic_version']
UP_DOWN_UP_OK
```

**第三段是這次演練最有價值的一段**:它把計畫裡寫的風險(「回滾 = 級距設定全部消失」)
從一句預測變成實測結果。beta 原本是 extended,down → up 之後變成 standard——
這正是換版 runbook(T27)要標明的東西。

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| **存級距代號 `quota_tier`,不存 `quota_bytes` 數字** | 政策數字散進資料列是真實的技術債:調整級距就變成一次資料遷移,而且分不清哪些列是政策預設、哪些是個案調整 | 每列存位元組數字 |
| **只有平台管理員能調級距** | owner 能自調等於根本沒有上限;F17 明文「由平台管理員核可」 | owner 可自行升級 |
| **降級允許,而且不刪檔** | 管理員可能正是要用降級逼專案清理;刪別人的檔案不是「調級距」該做的事。已超標時記 warning,讓它在營運上看得見 | 拒絕降級(409)/ 降級時自動刪舊版本 |
| **413 指引依級距而異** | 對已是最大級距的專案講「可申請擴充」是**錯誤指引**,會讓人去申請一個不存在的東西 | 兩種級距共用同一句話 |
| 數值走 **RFC 7807 擴充成員** | 前端要畫用量條,不該去 parse 中文句子 | 只給 detail 文字 |
| **兩道配額檢查共用 `quota.too_large()`** | 預檢(有 Content-Length)與收完後檢查是兩條程式路徑,訊息各寫一份必然漂移——這與 T35 把下載回應抽成共用函式是同一個教訓 | 各自組訊息 |
| **抽出 `security.project_out()`** | `ProjectOut` 有兩個非 ORM 欄位(`my_role`、`quota_bytes`),組裝原本散在 8 處;漏掉任何一處就是一個欄位靜默變 null,不會有錯誤訊息 | 在 8 個地方各加一行 |

### 計畫的修正(憲法第二條 5)

計畫段原本寫「新變數 `MAX_PROJECT_BYTES_EXTENDED` **自動被納入**防漂移測試的
`MAX_\w+_BYTES` 樣式」——**這是錯的**:該名稱結尾是 `_EXTENDED` 而非 `_BYTES`,
根本不符合樣式。防漂移測試在補完 `.env.example` 之後直接紅燈抓到。

修正方式是**改名為 `MAX_PROJECT_EXTENDED_BYTES`**,而不是放寬正規表達式:
讓「結尾必須是 `_BYTES`」成為一條由測試強制執行的命名慣例,比多一條寬鬆的 regex 有用。
`config.py` 已就地補上這條註記,下一個加容量設定的人才不會重蹈。

> 這也是防漂移測試本身的一次意外驗收:它抓到的不是數字寫錯,而是**我對它的理解寫錯**。

### 對現有資料的實際影響

**🟡 加欄位:`projects` 新增 `quota_tier`,未改動任何既有欄位。**
`server_default='standard'` 讓既有列自動補值,不需要資料回填。

⚠️ **回滾會刪掉這個欄位連同資料**(已由演練實證):所有專案的級距設定消失、
一律退回標準級距;曾調成 extended 的專案會立刻無法上傳新檔(既有檔案仍在、仍可下載)。
回滾前若要保留,先撈:

```sql
SELECT slug, quota_tier FROM projects WHERE quota_tier <> 'standard';
```

目前尚未上線、無正式資料,所以這次是零風險的;但這條註記必須進 T27 換版 runbook。
