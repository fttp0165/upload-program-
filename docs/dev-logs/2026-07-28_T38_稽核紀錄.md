## 計畫(動工前成文,憲法第二條 2)

### 目標

F54 原文:**「可查詢的操作紀錄:誰在何時開通了誰、建了/刪了什麼、上傳與下載了什麼」**

任務表的驗收標準:可查詢誰在何時做了什麼;**只存 `user_id`,不存 email/姓名**;
migration 有 backward。

### 🔴 這個任務其實是在兌現 T37 開出的支票

T37(下載次數統計)當時刻意**不做下載事件表**,理由寫在日誌裡:

> 「誰下載了什麼」是稽核(T38/F54)的職責,**有自己的保存期限與存取權限**。
> 混在一起的結果通常是稽核資料被當統計資料到處顯示。

這句話有兩個承諾,T38 必須兌現,否則 T37 的取捨就只是把問題丟給未來:

| T37 承諾 | T38 的義務 |
|---|---|
| 稽核有**自己的存取權限** | 稽核查詢**只開給平台管理員** —— 見下方 §存取權限 |
| 稽核有**自己的保存期限** | 要有保留期設定與清除手段,不能只是一張無限長大的表 |

**特別要講清楚存取權限的理由。** T37 讓下載統計停在「次數」這個粒度,是一個**刻意的
個資決定**。如果 T38 讓專案 owner 從稽核頁看得到個別下載者,那個決定就被繞過了 ——
表面上沒有 `download_events` 表,實際上同樣的資訊從另一扇門走出來。
所以「只有平台管理員可查」不是新增的限制,是 T37 那個決定的延續。

### 🔴 稽核表要存快照,不能只存外鍵

這是本任務最容易做錯的地方。

直覺寫法是 `target_id` 存 UUID、顯示時 join 回去。但稽核紀錄最重要的用途之一是
**「誰刪掉了什麼」** —— 而東西一旦刪掉,那個 UUID 就 join 不回任何東西。
結果是稽核頁顯示「Benny 在 03:14 刪除了 `9f2c…`」:**正是最需要它的時候最沒用。**

所以寫入時就把人可讀的定位**快照**下來(`target_label`:slug、version、filename)。
稽核記的是「當時的事實」,不是「現在的狀態」——這兩者的差別就是快照與外鍵的差別。

⚠️ `target_label` 只放 slug / version / filename 這類**識別用**字串,
**不放使用者輸入的自由文字**(專案摘要、版本說明)。稽核不是繞過個資紅線的後門。

### 寫入時機:與業務操作**同一個 transaction**

| | 同交易(採用) | 獨立 session |
|---|---|---|
| 業務成功 | 有紀錄 | 有紀錄 |
| 業務失敗 rollback | **沒有紀錄** | **有紀錄,但事情沒發生** |

採用同交易,保證 **「有紀錄 ⇔ 事情真的發生了」**。
獨立 session 會產生「記了但沒發生」的假紀錄,而假紀錄會讓整張表失去可信度 ——
一旦稽核紀錄需要被質疑,它就沒有存在的意義了。

**代價(必須誠實記下):失敗的嘗試不會進稽核表。** 它們仍然在 stdout log 裡。
F54 要的是「誰做了什麼」,不是入侵偵測;真要做失敗嘗試的偵測,那是另一個需求。

### `action` 用 Python enum,但**不下 DB CHECK**

本專案其他 enum 欄位都用 `_enum()`(VARCHAR + CHECK)。稽核的 `action` 刻意不同:

- 稽核動作的字彙**會隨著功能持續成長**。把它釘進 schema 的話,
  「每加一個被稽核的動作就要一次 migration」。
- 🔴 **而阻力會讓人選擇不記** —— 那是稽核最糟的失效方式:表存在、看起來運作正常,
  但漏掉的動作沒有任何跡象。寧可容忍字彙漂移的風險,也不要製造「不記」的誘因。

改用:`String(64)` 欄位 + `AuditAction(StrEnum)` 作為**唯一的字彙來源**,
再加一條測試把命名格式(`^[a-z]+\.[a-z_]+$`)與「程式裡出現的 action 都在 enum 裡」釘住。

### 存取權限

| 誰 | 可查 |
|---|---|
| 平台管理員 | 全部 |
| 專案 owner / maintainer | ❌ **不可** —— 理由見上方 §兌現 T37 |
| 一般成員 | ❌ |

### 保留期限

- 新增設定 `AUDIT_RETENTION_DAYS`(預設 **365**)
- **不做自動清理排程**:本服務沒有排程器,MVP 也不打算引入
- 提供 `tools/purge_audit.py`(預設 `--dry-run`),由 VM 的 cron 或人工執行

一支腳本 + 一個設定值,讓 T37 的承諾有落點,而不是一句寫在日誌裡的空話。

### 單一入口:`app/audit.py`

🔴 稽核不能變成「每個 router 各記一份、格式各異」。所有寫入走
`audit.record(session, actor=…, action=…, target=…)` 一個函式。

而且 `record()` **內部同時寫 stdout log** —— 收掉「log 記了但 audit 沒記」這條分岔。
這是本專案反覆出現的「同一件事只能有一條路」(`_download_response`、
`query_projects`、`project_out`、`problem_response`)的第五次應用。

### 🐛 T37 的紅測試立刻抓到了 T38(而且它是對的)

實作完成後跑全域回歸,`test_download_count.py::test_統計在結構上不可能記到個資` **變紅**。
它的第 2 點斷言是「一次下載**不在任何表**新增資料列」——T38 讓下載多了一筆 `audit_events`。

這不是回歸,但也不能直接把斷言放寬。判斷過程:

1. **T37 保護的主張是什麼?** 「下載**統計**不記個資」。`artifacts` 沒有下載者欄位,
   統計數字永遠只是個總數 —— 這一點 T38 完全沒有動到。
2. **那筆稽核列是需求要的嗎?** 是。F54 的字面就寫著「上傳與**下載**了什麼」。
   而且 T37 自己的日誌白紙黑字把它推給了 T38。
3. **所以斷言錯在哪?** 它寫得比它保護的主張**更寬**。當時那樣寫是對的(沒有別的
   消費者),T38 之後它就過度延伸了。

處理方式與 `/account` 撞上「所有連結帶前綴」時相同:**改成具名例外,不放寬斷言**。
現在斷言是「下載只讓 `audit_events` 增加**恰好一列**,其餘各表一列都不增」——
比原本的版本更嚴,因為它連「增加幾列」都釘住了。

同時依第二條 5 回寫 `設計_MVP.md` §3.5,把「統計不記個資」的**範圍**講清楚。

### 為什麼這樣做

1. **這個任務的本質是兌現 T37 開的支票。** T37 不做下載事件表時說稽核「有自己的
   保存期限與存取權限」。那句話當時沒有落點,T38 讓它有:
   - 存取權限 → `AdminUser`,專案 owner 也不行
   - 保存期限 → `AUDIT_RETENTION_DAYS` + `tools/purge_audit.py`

   **「只有平台管理員可查」不是新增的限制。** 若 owner 能從稽核頁看到個別下載者,
   T37「統計只到次數」那個個資決定就被從另一扇門繞過了——表面上沒有 `download_events`,
   實際上同樣的資訊照樣流出去。

2. **`target_label` 存快照而非只存外鍵。** 這是本任務最容易做錯的地方:
   直覺寫法是存 UUID、顯示時 join 回去,但東西刪掉之後 join 不回任何東西,
   而「誰刪掉了什麼」正是稽核最重要的用途之一——**最需要它的時候最沒用**。
   捨棄的替代方案:軟刪除(範圍太大,且會污染所有既有查詢)。

3. **同交易,不用獨立 session。** 保證「有紀錄 ⇔ 事情真的發生了」。
   捨棄的替代方案是「稽核一定寫進去,即使業務失敗」——它換來的是「失敗的嘗試也留痕」,
   付出的是「表裡可能有沒發生過的事」。**一張混進假紀錄的稽核表就不能用了**,
   而失敗的嘗試本來就還在 stdout log。這個取捨的代價已寫進遺留問題。

   連帶的實作細節:`create_project` / `create_release` 改為 **flush → record → commit**。
   flush 失敗(短名/版本號重複)時根本走不到 record,不留假紀錄;而且 `id` 要 flush
   之後才存在。

4. **`action` 不下 DB CHECK。** 本專案其他 enum 欄位都用 `_enum()`(VARCHAR + CHECK),
   這裡刻意不同:稽核字彙會持續成長,釘進 schema 等於每加一個動作就要一次 migration,
   而**阻力會讓人選擇不記**——那是稽核最糟的失效方式,因為漏記不留任何跡象。
   守門改由 `AuditAction` 單一字彙來源 + 兩條測試(命名格式、禁止裸字串)負責。

5. **`record()` 同時寫 stdout log。** 各處原本已有 `log.info("建立專案", ...)`;
   稽核若另外寫一份,就會出現「log 記了但 audit 沒記」的分岔。這是本專案第五次
   套用「同一件事只能有一條路」(前四次:`_download_response`、`query_projects`、
   `project_out`、`problem_response`)。

6. **`actor_id` 用 `ondelete="RESTRICT"`。** 有稽核紀錄的使用者就刪不掉——這是刻意的。
   稽核不得因為當事人被刪除而消失。

### 遺留問題與後續建議

1. **🔴 保留期不會自己生效。** 本服務沒有排程器,`AUDIT_RETENTION_DAYS` 只是給
   `tools/purge_audit.py` 讀的。**部署時必須把它掛進 VM 的 cron**,否則這張表會無限成長,
   而且會是一張越長越久的個資表。已寫進 `.env.example` 與稽核頁本身,但那不等於做了。
2. **失敗的嘗試不進稽核表**(同交易的必然代價)。若日後需要「誰一直在試著存取沒權限的
   東西」,那是另一個需求(入侵偵測),需要獨立 session 或另一張表,不要改這裡的語意。
3. **⚠️ 開通/停用仍有 API 與網頁兩條實作路徑**(T45 遺留)。T38 讓兩邊寫入相同的 action
   並有測試釘住,但**兩條路本身沒有收掉**。要收的話是把網頁那條改為呼叫共用函式。
4. **稽核頁沒有時間區間篩選**(API 有 `since`/`until`,網頁只有 action)。
   查特定事件時要退回 API。等真的不夠用再補。
5. **`target_label` 的格式是自訂的**(`slug:version`、`slug:user_id:role`)。
   目前靠 `audit.py` 的呼叫端自律,沒有結構化欄位。若日後要對 label 做精確查詢,
   應改為 JSON detail 欄位而不是繼續往字串裡塞。
6. **MVP 的最後一項自主任務至此完成。** 剩下 T26–T29 全部等平台方。
