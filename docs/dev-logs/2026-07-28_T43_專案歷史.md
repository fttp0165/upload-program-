## 計畫(動工前成文,憲法第二條 2)

### 目標

專案歷史頁:列出該專案的所有版本,**依發布時間倒序**,可展開看各版檔案並下載。
順帶接上 T42 的遺留 #1:專案頁加一個「版本歷史」入口。

驗收標準:**依發布時間倒序;可展開看各版檔案並下載。**

### 🐛 動工前就發現的既有缺陷:`list_releases` 用錯了排序欄位

寫計畫時去看 `GET /v1/projects/{slug}/releases`,發現它是:

```python
.order_by(Release.created_at.desc())
```

**這與 T35 自己確立的原則矛盾。** `latest_published_release()` 的註釋寫得很清楚:

> 也不用 `created_at`:先建的版本可能後發布,建立順序不等於發布順序。

後果是**列表第一筆與 `/latest` 可能指向不同版本**——使用者在歷史頁看到最上面是
v9,點 latest 下載卻拿到 v10,而且兩邊都「沒有錯誤」。
T35 的測試已經造出這個情境(v10 先建、v9 後建;v9 先發、v10 後發),
只是當時沒有人去驗列表的順序。

**這不是 T43 引入的問題,但 F73 的驗收標準正是「依發布時間倒序」,
所以修它就是 T43 的份內事。** 而且如果只改網頁不改 API,就會製造出
我一路在避免的那種分岔。

**做法:**

1. 把版本查詢抽成 `queries.query_releases()`,API 與網頁共用(同 T41 的 `query_projects()`)
2. 排序改為 **`published_at DESC NULLS FIRST`,再 `created_at DESC`**
   - draft 的 `published_at` 是 NULL,浮在最上面——那是作者正在做的東西,
     對看得到 draft 的人(成員)來說最相關
   - 已發布的部分嚴格依**實際發布時間**倒序,滿足 F73
3. 先寫一條會失敗的紅測試釘住這個順序,再改

> 這是**修改既有 API 的行為**。目前沒有任何測試釘住舊的排序(已確認),
> 也尚未上線、無正式資料,所以風險是零;但仍要在日誌與任務表寫明,
> 因為它確實改變了 `GET /v1/projects/{slug}/releases` 的回應順序。

### draft 的可見性:沿用既有規則,不另寫

`list_releases` 已經有:非成員只看得到已發布的版本,draft 是作者的工作區。
抽出來的共用函式**原封不動帶走這條規則**,網頁不另外判斷。

### 展開看檔案:用 `<details>`,不用 JS

CSP 是 `default-src 'self'`,inline script 一律被擋(T40 的設計)。
而「展開/收合」根本不需要 JS——`<details>`/`<summary>` 是原生 HTML,
無障礙支援也更好。**最新版預設展開,其餘收合。**

### 分頁

沿用首頁的做法:每頁 20 筆,上一頁/下一頁連結用 `urlencode` 在路由端組好。

## 結果(完工後補記)

### 紅 → 綠

```
先寫 16 條測試 → 14 failed / 2 passed
實作後        → 16 passed;全套 224 → 240 passed;lint 全過
```

其中 `test_API的版本列表依發布時間倒序` 的紅燈不是「功能還沒做」,
而是**既有程式碼真的答錯了**——它拿到的是 `v9`,而 `/latest` 給的是 `v10`。

### 🐛 缺陷修正:三條測試同時證明它是真的

修正前後各跑一次(把排序退回 `created_at`):

```
.order_by(Release.created_at.desc())                              →  3 failed
.order_by(Release.published_at.desc().nullsfirst(), created_at)   →  16 passed
```

三條一起紅:API 排序、**列表第一筆與 `/latest` 一致**、歷史頁排序。
第二條是最有價值的——它把「兩個端點對『最新是哪一版』不能各說各話」寫成了可執行的斷言,
而這正是原本沒人發現的原因:**兩邊各自看都很合理,只有放在一起比才看得出矛盾。**

資料用的是 T35 那組情境(v10 先建、v9 後建;v9 先發、v10 後發),
當時就造好了,只是沒有人拿它去驗列表的順序。

### 測試寫得太脆的一處

`test_最新版預設展開其餘收合` 原本寫 `body.count("<details open") == 1`,
但模板產出的是 `<details class="release" open>` ——**斷言綁死了屬性順序,
測的是 markup 的寫法而不是行為**。改成 regex `<details[^>]*\bopen\b[^>]*>`。

改測試而不是改模板:模板的寫法沒有錯,是斷言表達錯了意圖。

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| **一併修 API 的排序,不只修網頁** | 只改網頁就會製造出我一路在避免的分岔:同一個問題兩個答案。而且 F73 的驗收標準本來就是「依發布時間倒序」 | 網頁自己排序、API 維持原樣 |
| **`published_at DESC NULLS FIRST` + `created_at DESC`** | draft 沒有 `published_at`,浮在最上面正好符合「作者正在做的東西最相關」;已發布的部分嚴格依實際發布時間 | 用 `COALESCE(published_at, created_at)`(語意含糊,兩種時間混在一個排序鍵裡) |
| **`<details>` 而非 JS** | CSP 是 `default-src 'self'`,inline script 被擋;而且展開/收合本來就不需要 JS,原生元素的無障礙支援更好 | 寫一個 toggle 的外部 JS |
| **最新版預設展開** | 來這頁的人多半在找最近發生什麼;其餘收合才看得到全貌 | 全部展開 / 全部收合 |
| **draft 可見性規則原封不動帶走** | 那條規則(非成員只看得到已發布)已經對了,重寫只會製造第二個答案 | 網頁另外判斷 |
