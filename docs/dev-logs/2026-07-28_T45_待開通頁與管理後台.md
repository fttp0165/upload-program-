## 計畫(動工前成文,憲法第二條 2)

### 目標

M7 的最後一項:

- **F75 待開通頁** —— 未開通者看到的指引頁,而非裸 403 JSON
- **F76 管理後台頁** —— 待開通清單與一鍵開通(否則管理員得手打 API)

### 🔴 待開通頁最重要的內容:顯示使用者自己的 `sub`

這一點不明顯,但它解決一個實務上必然會發生的死結。

契約 §4.2:業務庫**只存 `sub`**,沒有 email、沒有姓名。
所以管理後台的清單裡,管理員看到的是一串 UUID。

那麼:**使用者要怎麼告訴管理員「我是誰」?** 管理員又要怎麼在一排 UUID 裡認出他?

答案只有一個:**待開通頁必須把使用者自己的 `sub` 顯示出來**,讓他可以複製給管理員。
不然這兩邊永遠對不上——使用者說「我是王小明」,管理員的畫面上沒有這四個字。

> 這也正好呼應 [SSO接入計畫.md](../plans/SSO接入計畫.md) §4.3 的 D2/D3:
> 「第一個管理員要先登入一次、取得他的 `sub`」——**取得的地方就是這一頁**。
> 原本那是一個手工步驟,現在有了落點。

待開通頁還要有:目前狀態、找誰開通、帳號設定連結(契約 §2.1)。

### 管理後台:誠實說明「這裡只有 sub」

同樣的理由,管理後台會讓第一次用的管理員困惑:「怎麼沒有名字?」

**頁面上要直接寫明原因**——業務庫依契約只存 `sub`,顯示用資料一律來自 IdP 且不落地。
這不是缺陷,是紅線。與其讓人以為壞掉,不如講清楚。

### 權限與既有規則

| 頁面 | 需要 | 規則來源 |
|---|---|---|
| `/pending` | 已登入(任何狀態) | —— |
| `/admin/users` | **平台管理員** | ~~既有的 `AdminUser` 依賴~~ → 見下方修正 |
| 一鍵開通 | 同上 | 既有的 `PATCH /v1/admin/users/{id}` 邏輯 |

🔴 **不得停用自己**——API 已有這條規則(否則平台可能一個管理員都不剩),
網頁沿用同一條,不另寫。

> **🐛 計畫修正(憲法第二條 5,執行中回寫)**
>
> 計畫寫「直接用既有的 `AdminUser` 依賴」是錯的。`AdminUser` 對**未登入**者會拋
> 401,但網頁的未登入語意是 T53 裁示的「深層頁 302 送去 IdP」——管理後台是深層頁,
> 不該例外。而規格第 5、6 項要的正是「未登入 302、已登入非管理員 403」這兩種不同回應,
> `AdminUser` 一條路徑給不出來。
>
> 改法:用 `OptionalUser` 取身分,再由 `_require_web_admin()` 分流——
> 未登入走 `_login_redirect()`,其餘**直接呼叫 API 用的同一個 `require_admin()` 函式**。
> 權限規則仍然只有一條路(這是重點),分岔的只有「未登入時給什麼回應」這一層。

### 已開通者開 `/pending` 怎麼辦

導回首頁。停在一頁「你已經開通了」沒有意義,而且會讓人以為出錯。

### 各頁的待開通區塊要連到這一頁

首頁/專案頁/歷史頁現在都直接顯示 `pending_activation().detail`。
改為在那段文字旁加一個連到 `/pending` 的連結——完整指引在專屬頁面,
其他頁面只要指路就好。

### 為什麼這樣做

1. **待開通頁的主體是 `sub`,不是文案。** 這一頁看起來像客套的「請稍候」頁,
   但它真正的功能是**把識別碼交到使用者手上**。業務庫只存 `sub` 是紅線,
   代價就是使用者與管理員之間少了一條天然的對照鍵——這一頁補的就是那條鍵。
   所以 `sub` 用 `<code>` 呈現(方便整串選取複製),而且獨立一個標題段,
   不是塞在說明文字裡。

2. **管理後台把「為什麼沒有名字」寫在頁面上。** 捨棄的替代方案是「加一個備註欄位
   讓管理員自己記」——那等於在業務庫落地個資,直接違反契約 §4.2。
   誠實說明成本最低,而且順帶告訴管理員正確的對人方式(請對方複製 sub 過來)。

3. **`_require_web_admin()` 只分流「未登入」,權限判斷轉呼叫 `require_admin()`。**
   捨棄的替代方案是在網頁端重寫一次 `is_admin` 判斷——那是本專案反覆出現的
   「同一件事兩條路」反模式(`_download_response`、`query_projects`、`project_out`
   都是為了收掉它)。權限規則分岔的後果是越權,不是畫面不一致。

4. **導航列的「管理」入口。** 沒有入口的頁面等於不存在,管理員只能手打網址;
   而手打網址這件事本身會讓人以為這是未完成的功能。

5. **開通/停用一律 POST 表單。** GET 會被瀏覽器預抓、被貼在聊天室裡誤觸。
   CSRF 沿用 T44 的評估結論(SameSite=Lax),不加 token。

### 測試結果(紅 → 綠)

- 紅:`tests/test_web_admin.py` 18 條 → **16 failed / 2 passed**(模板不存在、路由未接上)
- 綠:`.venv/bin/python -m pytest tests/test_web_admin.py -q` → **18 passed**
- 全域回歸:`.venv/bin/python -m pytest -q` → **303 passed**(T44 結束時為 285)
- `ruff check app tests` → All checks passed

**證明測試非空轉**(刻意弄壞實作,確認對應測試會紅):

| 弄壞的地方 | 變紅的測試 |
|---|---|
| 待開通頁不印 `identity.sub` | `test_待開通頁顯示使用者自己的sub` |
| 拿掉 `_require_web_admin()` 呼叫 | `test_非管理員開管理後台回403`、`test_未登入開管理後台會302` |
| 拿掉「不得停用自己」的判斷 | `test_不得停用自己` |

最後一項值得記一筆:拿掉判斷之後,管理員把自己停用了,接著的轉址就再也載不進
任何頁面(停用帳號在 `get_identity` 被擋)。**這正是這條規則存在的理由的實地演示**
——不是理論上的風險。

### 對現有資料的影響

🟢 **不動資料結構。** 開通寫的是既有的 `users.status` / `users.activated_at`,
與 `PATCH /v1/admin/users/{id}` 同一段欄位語意。無 migration。

### 遺留問題與後續建議

1. **管理後台沒有分頁**,目前寫死 `limit(200)`。內部平台的使用者數量遠低於此,
   但這是一個會安靜出錯的上限——超過 200 人之後新註冊的人會**看不見**(依
   `created_at` 倒序,新的反而在前,所以實際掉的是最舊的那批,影響較小)。
   人數接近時要補分頁。
2. **停用沒有二次確認。** 誤點停用會讓對方立刻進不來(雖然可以重新啟用)。
   若實務上真的誤觸過再補。
3. `/pending` 的 `sub` 目前要使用者自己反白複製。加一鍵複製需要 JS,
   而 CSP 禁 inline script——要做就得再開一個 `app/static/*.js`,
   為了一個複製按鈕不值得,先不做。
4. **M7 至此收尾。** MVP 剩下 T38 稽核紀錄,以及等平台的 T26–T29。
