# T52 網頁 session 自動續期(access token 300s)

**建立日期:** 2026-07-28 02:06
**最後更新:** 2026-07-28 02:20
**版本:** v1.1
**對應任務:** T52(M3 補強)、SSO 契約 v1.7 §3.3

---

## 計畫(動工前成文,憲法第二條 2)

### 🐛 缺陷:登入 5 分鐘後,網頁會靜默退回「未登入」

SSO 契約 §3.3(v1.3 定案)把 **access token 壓到 300 秒**:

> Access token **300 秒(5 分)** — 取設計區間下限:管理員收權 / IdP 停用帳號後,
> 既發 token 最長只再活 5 分鐘。內網 refresh 成本低,用延遲換收權即時性。

我們的續期是 `POST /auth/refresh`,**要呼叫端主動打**。但:

- 網頁全站**零 JS**(Q9 定案 Jinja2 + 原生 JS,目前連一行 JS 都沒有)
- 瀏覽器導覽不會自己去打 `POST /auth/refresh`
- session cookie 活 **36000 秒**(10 小時)

所以登入 5 分鐘後,`_session_token()` 交出的是**過期 token** → 驗證失敗 →
`optional_identity` 回 `None` → **所有頁面顯示「請先登入」**。
使用者只會覺得「怎麼一直要我登入」,而伺服器沒有任何錯誤。

> **為什麼 240 條測試一條都沒抓到:** `FakeOidc` 的 token 永不過期。
> 這是「測試全綠、上線就爆」的典型——測試替身把被測行為給抹平了。

### 做法:在伺服器端續期,不依賴呼叫端

`_session_token()` 目前只是把 cookie 裡的 access token 交出去。改成:

1. 先照舊拿 access token
2. 驗證失敗(過期/無效)且**手上有 refresh token** → 用它向 IdP 換一組新的
3. 換到了 → 用新 token 繼續這次請求,並把新 cookie 寫回回應
4. 換不到(refresh 也過期 / IdP 拒絕) → 才視為未登入

**為什麼放在伺服器端而不是等前端寫 JS:**

- 這是**伺服器端算繪的網頁**,身分本來就在伺服器這一側判定;讓瀏覽器負責維持
  伺服器的 session 是把責任放錯地方
- CSP `default-src 'self'` 之下,靠 inline script 定時 refresh 是行不通的;
  要做也得是外部 JS 檔 + 定時器,對「只是看一頁專案列表」的使用者是過度設計
- **API 呼叫端(帶 Bearer)不受影響**——他們本來就該自己管 token,
  `POST /auth/refresh` 留著給他們用

### 🔴 續期不得繞過收權

契約把 access token 壓到 300 秒的**目的**是「管理員收權 / IdP 停用帳號後,
既發 token 最長只再活 5 分鐘」。自動續期若寫錯,就把這個保護拆掉了。

關鍵:**續期一定要真的去問 IdP**(refresh_token grant),不是自己延長什麼。
IdP 那邊帳號被停用時,refresh 會失敗 → 使用者立刻被登出。這正是我們要的。

另外 `get_identity()` 裡「`user.status is disabled` → 403」那道本地檢查仍在,
兩層都保留。

### 寫回 cookie 的難處

`_session_token()` 是在**相依注入**階段跑的,那時還沒有 response 物件。
新 cookie 要怎麼寫回去?

**做法:把新 session 暫存在 `request.state`,由一個中介層在回應產生後寫入 cookie。**
中介層是唯一看得到「請求開始」與「回應完成」兩端的地方。

不用 `BackgroundTask`(它在回應送出**之後**才跑,設 cookie 已經來不及)。

### 測試:必須能模擬 token 過期

現有 `FakeOidc` 的 token 永不過期,所以**先要讓它會過期**:

- `FakeOidc.issue()` 加一個 `expired=False` 參數
- `verify_access_token()` 遇到過期的 token 就拋 401(與真實行為一致)
- `FakeOidc.refresh()` 換出一組**新的、未過期的** token

這等於補上一個測試替身原本缺的行為。**這件事本身就有價值**——
替身與真實行為的落差,正是這個缺陷藏了這麼久的原因。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |
|---|---|---|
| 1 | 🐛 access token 過期、refresh 可用 | **自動續期**,頁面照常顯示登入狀態 |
| 2 | 續期後的 cookie | 回應帶上**新的** session cookie(下次請求不用再換) |
| 3 | 🔴 refresh 也失效(IdP 停用帳號) | 視為未登入,**不得**自行延長 |
| 4 | 沒有 refresh token 的 session | 視為未登入(不崩潰) |
| 5 | access token 仍有效 | **不去打 IdP**(不要每次請求都 refresh) |
| 6 | Bearer 呼叫端(API) | **行為不變**——不自動續期,維持 401 |
| 7 | 續期後的 cookie 屬性 | 仍是 HttpOnly / Secure / SameSite=Lax / Path 綁前綴(§4.10) |
| 8 | 本地停用檢查 | `user.status is disabled` 仍回 403(續期不繞過它) |

## 結果(完工後補記)

### 紅 → 綠

```
先給 FakeOidc 補上過期與 refresh → 既有 240 條**全部維持綠**(替身的新行為沒有誤傷)
再寫 9 條測試 → 4 failed / 5 passed
實作後       → 9 passed;全套 240 → 249 passed;lint 全過
```

5 條一開始就綠的是「**不該**續期」那組(token 仍有效時不打 IdP、refresh 失效視為未登入、
沒有 refresh token 不崩潰、Bearer 呼叫端維持 401、本地停用檢查)。
它們不是假通過——它們釘住的是**續期不得越界**,而實作續期時最容易犯的錯正是越界。

4 條紅的就是缺陷本身。已把續期拿掉實測,那 4 條會**再次全紅**。

### 先修測試替身,才看得見缺陷

這次的順序值得記下來:**動手改程式之前,先把 `FakeOidc` 的過期與 refresh 補上**。

原本的替身 token 永不過期,所以「登入 5 分鐘後全站退回未登入」這件事,
240 條測試裡**沒有任何一條有機會失敗**。補完替身之後既有測試仍全綠,
證明新行為沒有誤傷;然後新測試才紅得出來。

> **替身與真實行為的落差本身就是風險。** 這個缺陷不是寫錯程式,
> 是測試環境把被測行為抹平了——而抹平的東西不會有人發現。

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `tests/conftest.py` | `FakeOidc` 加 `expired` / `issue_refresh()` / `refresh()` / `dead_refresh` / `refresh_calls` |
| `app/security.py` | `_session_token()` 改 async,驗不過就用 refresh token 向 IdP 換發 |
| `app/middleware.py` | `SessionRenewalMiddleware`:把續期後的 session 寫回 cookie |
| `app/main.py` | 掛上中介層(最外層) |
| `tests/test_session_refresh.py` | 9 條 |

### 為什麼這樣做(決策理由與捨棄的替代方案)

| 決策 | 理由 | 捨棄的方案 |
|---|---|---|
| **在伺服器端續期** | 這是伺服器端算繪的網頁,身分本來就在伺服器這側判定;讓瀏覽器負責維持伺服器的 session 是把責任放錯地方。而且 CSP `default-src 'self'` 之下 inline script 行不通,要做得寫外部 JS + 定時器,對「只是看一頁專案列表」的人是過度設計 | 前端寫 JS 定時打 `/auth/refresh` |
| 🔴 **真的去問 IdP,不自行延長** | 契約把 access token 壓到 300 秒的**目的**就是收權即時性。自行延長會把這個保護整個拆掉。IdP 停用帳號 → refresh 失敗 → 立刻登出,這正是我們要的 | 續期時只檢查本地狀態 |
| **token 仍有效就不打 IdP** | 每次請求都 refresh 會把 IdP 打爆,也讓 300 秒的設計失去意義 | 每次請求都換一次 |
| **用中介層寫回 cookie** | 續期發生在相依注入階段,那時還沒有 response 物件;中介層是唯一同時看得到請求與回應兩端的地方 | `BackgroundTask`(在回應**送出之後**才跑,設 cookie 來不及) |
| **Bearer 呼叫端不自動續期** | API 呼叫端本來就該自己管 token,而且他們也拿不到 cookie。`POST /auth/refresh` 留著給他們 | 一律自動續期 |
| **先修替身再修程式** | 替身抹平了被測行為,不先補上就永遠看不到紅燈 | 直接改程式,測試照樣全綠 |

### 對現有資料的實際影響

**🟢 不動資料。** 無 migration、無欄位變更。

行為變更:**帶 session cookie 的請求在 access token 過期時會自動續期**,
並在回應寫回新 cookie。Bearer 呼叫端行為完全不變。

### 遺留問題與後續建議

| # | 問題 | 建議 |
|---|---|---|
| 1 | 續期是「用到才換」,不是背景預先換 | 使用者感受不到差別;預先換要排程,對這個規模不划算 |
| 2 | 併發請求可能同時觸發兩次 refresh | Keycloak 預設允許 refresh token 重用一小段時間;真出現問題再加單次飛行鎖 |
| 3 | 續期失敗時只是「視為未登入」,沒有告訴使用者為什麼 | 深層頁 302 到 IdP(T53)之後,這個情況會自然變成「重新登入一次」 |
| 4 | `_session_token()` 現在會發網路請求 | 已限制在「驗不過且有 refresh token」時;正常路徑不打 IdP |
| 5 | 沒有測到「refresh 後 IdP 又給了一個過期 token」 | 那是 IdP 的錯誤行為,超出本服務可處理的範圍 |
