## 計畫(動工前成文,憲法第二條 2)

### 背景:首次上線抓到四個真缺陷

2026-07-29 首次在 Cats VM 部署 `v0.1.0`,一路走到管理員開通,過程抓到:

| # | 缺陷 | 現場症狀 | 現場處置 |
|---|---|---|---|
| 1 | 🐛 **bootstrap 只在建號時生效** | 第一個管理員永遠卡在待開通,只能手打 SQL 解鎖 | `UPDATE users SET ...` |
| 2 | 🐛 `backup.sh` 假設 minio 容器內有 `tar` | 首次執行即 `tar: command not found` | 現場改用 `docker cp` 版 |
| 3 | 🐛 `ensure_bucket()` 把「bucket 已存在」當錯誤 | 每次啟動 log 一筆 `BucketAlreadyOwnedByYou` error | 無(無害但誤導) |
| 4 | compose 缺內部 CA 與 DNS hairpin 設定 | 容器連不上 IdP(先 refused 後憑證失敗) | 現場加 `extra_hosts` + CA 掛載 |

### 🐛 缺陷 1 是設計矛盾,不是邊角案例

`upsert_user()` 的 bootstrap 判斷只在**帳號首次建立**時生效;帳號已存在就直接
return。但 T45 的「先部署、後拿 sub」自助流程**在結構上保證了帳號會先於
bootstrap 設定存在**——要看到自己的 sub 就得先登入,一登入帳號就以 pending
建立了。SSO 接入計畫 §4.3 寫「填入後再登入一次即成為管理員」,程式做不到。
**兩份自己的文件互相打架,而且兩邊都測過綠——因為沒有任何測試涵蓋
「先登入、後設 bootstrap」這個順序。**

修法:既有帳號若在 bootstrap 清單內**且狀態為 pending**,登入當下升級為
active + admin,並寫一筆稽核(`user.activate`,actor 為系統)。
**disabled 不升級**——那是被刻意停權的帳號,bootstrap 不是繞過停權的後門。

### 缺陷 2:backup.sh 的兩個未實測假設

- minio 映像檔(UBI micro base)**沒有 `tar`** → 改 `docker cp`(由 daemon 執行,
  不依賴容器內工具),主機側再打包
- 完整性驗證用主機的 `pg_restore` → 主機未必裝 postgresql-client → 改用
  **db 容器內的** `pg_restore --list < dump`

已在 VM 現場改好並實測通過(`OK: /home/deploy/upload-backups/...`),
本任務把同一版回寫 repo 的 `tools/backup.sh`,兩處不再漂移。

### 缺陷 3:ensure_bucket 冪等化

`create_bucket` 拋 `BucketAlreadyOwnedYou`/`BucketAlreadyExists` 時,目標狀態
(bucket 存在)已達成——吞掉,不再在每次啟動留一筆嚇人的 error log。

### 缺陷 4:compose 補部署形態設定(含理由註釋)

VM 實測發現兩件 repo compose 沒涵蓋的事:
- `cats-edge` 內 `catsapp.sporton.com.tw` 別名掛在 **keycloak**(只聽 8080)上,
  容器對它打 443 必然 refused → `extra_hosts: host-gateway` hairpin 回宿主機
- gateway TLS 是內部 CA(catsRootCA)簽的 → 掛 CA + `SSL_CERT_FILE`

一併回寫 compose(附「為什麼」註釋)與 runbook §A0。

### 行為規格(即驗收標準)

| # | 情境 | 預期 |
|---|---|---|
| 1 | 🐛 既有 **pending** 帳號,sub 補進 bootstrap 清單後登入 | 升級 active + admin |
| 2 | 既有 **disabled** 帳號在清單內登入 | **不升級**,維持 403 停用 |
| 3 | 既有 **active 一般成員**在清單內登入 | 不動(不搶既有角色語意;要升管理員走管理後台) |
| 4 | bootstrap 升級 | 留下 `user.activate` 稽核(actor 為系統/空) |
| 5 | 首登建號走 bootstrap | 行為不變(active + admin)——補測試釘住,原本沒有 |
| 6 | `ensure_bucket` 遇 bucket 已存在 | 不拋錯、不留 error log |
| 7 | `tools/backup.sh` | 與 VM 實測版一致(docker cp、容器內 pg_restore 驗證) |

本修正是讓「下一次部署」不再需要那條 SQL。

### 測試結果(紅 → 綠)

- `tests/test_bootstrap.py` 8 條:升級主體 3 條先紅(帳號已存在直接 return)、
  `ensure_bucket` 冪等 1 條先紅 → 修正後 **8 passed**
- 三條守門(首登 bootstrap、disabled 不升、active 成員不升權)從頭到尾綠——
  它們釘的是「修正不能帶來的副作用」
- 全域回歸 + ruff + `render_docs --check`:見 commit 記錄

### 為什麼這樣做(核心取捨)

1. **只升 pending。** disabled 是被刻意停權的,清單若能復活它,停權形同虛設;
   active 成員的升權是管理後台的職權——清單只解「第一個管理員」的死結,
   不該成為藏在環境變數裡、稽核看不到操作者的第二條派角色路。
2. **bootstrap 升級寫稽核、actor 為空。** 開通就是開通,不因操作者是系統就不留
   紀錄;actor 為空即「系統動作」的明確語意。
3. **教訓:兩份自己的文件互相打架,而且兩邊都「測過綠」。** T45 寫了自助拿 sub、
   SSO 計畫寫了「再登入即升級」,但沒有任何測試涵蓋「先登入、後設清單」這個順序
   ——順序性的行為要有順序性的測試。

### 對現有資料的影響

🟢 不動結構。正式環境第一個管理員已由現場 SQL 處理(等同本修正的行為);
本修正讓下一次部署不再需要那條 SQL。
