## 診斷

1. **不是程式紅燈**:同一份程式的 PR 檢查(337 測試 + ruff + 文件同步 + 紅線掃描)
   在合併前全綠;程式問題的失敗一定看得到死在哪個步驟,這次**什麼都沒有**。
2. 失敗形態=「job 建立後數秒 completed/failure、runner 從未分配、零輸出」,
   兩次 attempt 一致,且**同時間所有 push 事件的 run 都一樣**——指向帳號層:
   - 最可能:**私有 repo 的 Actions 免費額度(2000 分/月)用罄**
     ——今日 CI 跑了大量輪次,每輪含 docker build + Trivy
   - 次可能:GitHub Actions 事故(githubstatus.com)
3. 佐證:失敗與程式內容無關(main push / tag push / 分支 push 同型),
   而稍早同日的 PR run 正常取得 runner。

## 教訓

- **冒煙要有版本哨兵**:四條全 200 也可能是舊版在回應;「只有新版才有的檔案」
  才能證明版本切換發生。已回寫 runbook §A.4。
- **紅燈先分「程式紅」與「基建紅」**:有步驟輸出的紅燈修程式,
  零輸出零 runner 的紅燈查帳/查事故——方向錯了會白折騰。
- 發版流程對「CI 綠才換版」的堅持是對的:這次若不看 CI 直接 pull,
  `docker compose pull` 會拉不到 manifest,錯誤會更晚、更難懂。
