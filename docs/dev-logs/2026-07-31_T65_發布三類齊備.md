# T65 發布強制三類齊備(文件 + 執行檔 + 原始碼包)

**建立日期:** 2026-07-31 02:00
**最後更新:** 2026-07-31 15:00
**版本:** v1.1
**對應任務:** T65(新開)——Benny 裁示:每一版發布都要上傳三個:更新文件、執行檔、source code 包(99% Python 開發)

---

## 計畫(動工前成文,憲法第二條 2)

### 目標

發布規則從「至少一個檔案」改為「**doc、binary、source 三類各至少一個**
(upload_status=ready)才可發布」。API 與網頁走同一條檢查;錯誤訊息明列缺哪類。
Python 產物對應:執行檔=pyinstaller exe/zip/whl(binary 白名單已涵蓋)、
原始碼=zip/tar.gz、文件=pdf/md。格式白名單不動。

### 影響範圍

`app/routers/releases.py`(共用檢查 + API 發布)、`app/routers/web.py`
(網頁發布 + 上傳頁傳入缺項清單)、`app/templates/upload.html`(三類檢查表、
按鈕停用條件)、tests(新檔 + 既有 _publish helper 改為上傳三檔)、
功能需求大綱 F22、任務表。
**對現有資料的影響:🟢 純規則;既有已發布版本不回溯檢查。**

### 驗收標準

紅→綠:只有 binary → 422 且訊息列出缺 doc/source;三類齊 → 發布成功;
空版本維持原錯誤;冪等重發不變;網頁按鈕在缺類時停用且列缺項;
全套既有測試改造後全綠。

### 回滾方式

git revert(單一 commit;規則回到「至少一檔」)。

## 結果(完工後補記)

### 做了什麼(異動檔案)

- `app/routers/releases.py`:新增 `missing_required_kinds()`(規則唯一出處:
  doc/binary/source 三類各需至少一個 `upload_status=ready`)與 `_REQUIRED_KINDS`
  中文標籤表;`publish_release` 在「空版本」檢查之後加三類檢查,缺項回 422
  `release-missing-kinds`,detail 明列缺哪幾類。
- `app/routers/web.py`:網頁發布表單走同一個 `missing_required_kinds()`,缺項
  302 回上傳頁帶 `?error=missing-kinds`;上傳頁 render 傳入 `missing_kinds`。
- `app/templates/upload.html`:缺項提示(明列缺哪幾類)+ 發布鈕 `disabled`
  (提示性;真正的兜底在伺服器端,和「空版本」同一個哲學)。
- `tests/conftest.py`:新增 `complete_kinds()` helper(補上 source zip + doc pdf),
  給既有「上傳一檔就發布」的測試最小補齊。
- `tests/test_publish_requires_kinds.py`(新檔):4 條釘住規則本體。
- 既有 7 個測試檔(test_audit / test_download_count / test_latest_release /
  test_upload / test_web_project / test_web_releases / test_web_upload)的發布
  前置補 `complete_kinds()`;test_audit 的上傳稽核計數 1→3(三檔皆有紀錄)。
- 文件:功能需求大綱 F22 加嚴(v3.8)、任務表 T65(v1.44)。

### 為什麼這樣做

- **規則只寫一份**:API 與網頁表單都呼叫 `releases.missing_required_kinds()`,
  避免兩處規則漂移(T20 空版本檢查當年就是這樣做的,沿用同一結構)。
- **錯誤訊息明列缺項**:「發布內容不齊」若不說缺什麼,使用者只能猜——detail
  直接列「目前缺:更新文件(doc)、原始碼包(source)」。
- **不回溯既有已發布版本**:規則只在發布動作時檢查;歷史版本不動(🟢)。
- 捨棄的替代方案:前端 JS 擋(CSP 下可行但可繞過,且規則會出現第二份)、
  DB constraint(發布是狀態轉移不是寫入形狀,constraint 表達不了)。

### 測試結果(紅→綠)

- 紅:`git stash` 三個實作檔後跑新測試檔——**3 failed, 1 passed**
  (422 缺項、網頁退回、按鈕停用三條紅;「三類齊備可發布」在舊規則下本來就過)。
- 綠:恢復實作後全套 **365 passed**(新增 4 條),`ruff check` 全過。
- 過程紅燈:test_audit 上傳稽核計數 assert 3 == 1——`complete_kinds` 多傳兩檔,
  屬預期行為改變,斷言改為三檔皆有紀錄(順手加強:驗三個檔名集合)。

### 對現有資料的實際影響

🟢 無 schema 異動、無資料異動;純發布規則。既有 draft 若只有一兩類,下次發布
時會被要求補齊——這正是需求本意。
