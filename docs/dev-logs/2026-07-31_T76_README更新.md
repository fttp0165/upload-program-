## 計畫(動工前成文,憲法第二條 2)

### 目標

現行 README 只有兩行(標題 + 一句描述),看不出這是什麼、跑到哪、怎麼開發。
改寫成新人第一次打開 repo 就能自己動起來的文件:

1. **這是什麼、現在在哪** —— 定位、線上網址、目前版本、里程碑進度。
2. **功能一覽** —— 依已完成的 F 項寫,不寫沒做的(避免 README 變成願望清單)。
3. **技術棧與架構** —— gateway 剝前綴的拓撲用 ASCII 圖交代(這是最常誤解的一點)。
4. **本地開發與測試** —— 可貼可跑的指令。
5. **部署與換版** —— 只放指標,細節在 runbook(不製造第二份會漂移的說明)。
6. **平台整合** —— SSO 契約 v2.0 對齊狀態、路徑前綴由平台分配。
7. **紅線摘要** —— 只列與「改這個 repo 的人」最相關的幾條,其餘指向憲法。
8. **文件索引** —— docs/ 底下十幾份文件目前沒有入口。
9. 依憲法第七條補上日期、版本與版本歷史表(README 明列於該條適用範圍)。

### 影響範圍

`README.md`(改寫)、`docs/dev-logs/`(本篇)、任務表。
**對現有資料的影響:🟢 純文件。**

### 驗收標準

- 內容與現況一致:版本號、測試數、已完成功能、契約對齊版本,全部與 repo 現狀相符
  (不寫「即將支援」);
- 指令可直接複製執行;
- 有日期/版本/版本歷史(第七條);
- 不重複 runbook 與憲法的內容,只給指標。

### 回滾方式

git revert(單一 commit;純文件)。

## 結果(完工後補記)

- `README.md` 由 2 行改寫為完整門面(v2.0):定位與線上狀態表、功能一覽(只寫已實作)、
  技術棧、**路徑拓撲 ASCII 圖**(gateway 剝前綴這件事最常被誤解)、本地開發指令、
  專案結構、部署三條必記紅線(細節指向 runbook)、平台整合與契約 v2.0 對齊、
  開發規則八條摘要 + 五條紅線、文件索引表、版本歷史。
- 🐛 **過程抓到自己的錯**:初稿寫 `pip install -e ".[dev]"`,但 `pyproject.toml`
  開宗明義寫著「僅作為 lint / test 設定;相依仍以 requirements*.txt 為準」——
  照抄慣例會讓新人第一步就失敗。改為 `pip install -r requirements-dev.txt`
  (該檔第一行 `-r requirements.txt`,一次裝齊)。**寫指令就要確認它真的能跑。**
- 刻意**不重複** runbook 與憲法的內容,只給指標——兩份會漂移的說明比一份難用的更糟。
- 🟢 純文件;無程式、無資料異動。文件同步檢查通過(README 不在 render_docs 目標內,
  它是 GitHub 的著陸頁,md 即發布形式)。

### 遺留

1. README 寫死了「測試 409 條」與里程碑進度,會隨開發過期——
   下次大幅變動時記得一併更新(或改成不寫死數字,如功能需求大綱的作法)。
2. 線上版本號刻意**不寫死**在 README,指向 `app/version.py` 與首頁頁尾。
