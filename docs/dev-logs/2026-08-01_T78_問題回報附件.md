## 計畫(動工前成文,憲法第二條 2)

### 目標

讓回報能附截圖,並且**在頁面上直接看得到**(不是下載下來自己開)。

### 🔴 這一期會開本專案第一條「非 attachment」的下載路徑

現況紅線:所有下載一律 `Content-Disposition: attachment` + `nosniff`,
就是為了不讓上傳內容在我們的網域被瀏覽器呈現。截圖要 inline,這條紅線得開一個口。
依施工計畫書 §4.2 的**六條收窄**,每一條都要有測試:

1. 只有回報附件端點是 inline;`/v1/releases/.../download` **完全不動**(要有回歸測試);
2. 型別由 **magic bytes 判定**,只放行 `image/png`、`image/jpeg`、`image/gif`;
3. 🔴 SVG 一律拒收(可執行的 XML);
4. 回應仍帶 `nosniff`,`Content-Type` 用**判定值**而非使用者宣稱;
5. 僅回報者本人與平台管理員可讀,其他人 **404**;
6. 單張 ≤ 5 MB、單則回報 ≤ 5 張。

### ⚠ 與施工計畫書的差異(依第二條 5,完工後回寫)

計畫書原本設想「在建立表單裡貼上圖片」。實作上那需要**回報還不存在時就先有 id**,
得引入暫存區與孤兒清理——複雜度不成比例。

改為:**先送出回報 → 在詳情頁附加截圖**(貼上、拖曳或選檔)。
好處是附件永遠掛在一件已存在的回報上,沒有孤兒;代價是使用者多一步。
補充說明的討論串同樣可附圖,所以「邊講邊補圖」的流程仍然順。

### 影響範圍

`app/models.py`(IssueAttachment)、`alembic/versions/0008_issue_attachments.py`(新)、
`app/routers/issues.py`(三個端點:表單上傳、XHR 上傳、inline 讀取)、
`app/static/issue-upload.js`(新,漸進增強)、`app/templates/issue_detail.html`、
`app/audit.py`(`issue.attachment_upload`)、`tests/test_issue_attachments.py`(新)。

**對現有資料的影響:🟡 新增一張表 + MinIO 前綴 `issues/`**;既有資料不動。
backward = DROP TABLE(🔴 會刪掉附件紀錄;物件本身需另行清理,見遺留)。

### 驗收標準

紅→綠:
1. PNG / JPEG / GIF 各能上傳並在詳情頁以 `<img>` 顯示;
2. 🔴 HTML、SVG、PDF **偽裝成 .png** 一律拒收,且**不留物件**;
3. 🔴 inline 端點:`Content-Disposition` **不是** attachment、帶 `nosniff`、
   `Content-Type` 為判定值;
4. 非本人非管理員讀附件 → **404**;
5. 單張超過 5 MB → 413;第 6 張 → 422;
6. 🔴 **回歸**:`/v1/releases/.../download` 仍然是 attachment;
7. **無 JS 也能附圖**(純表單 multipart 送出);
8. 上傳寫稽核;migration up→down→up 演練通過。

### 回滾方式

`alembic downgrade -1`(🔴 刪附件表)+ git revert。MinIO 內的物件不隨 migration 消失,
需要時以 `issues/` 前綴手動清理。

## 結果(完工後補記)

### 做了什麼

- `app/models.py`:`IssueAttachment`(`content_type` 存**判定值**,不是使用者宣稱的)。
- `alembic/versions/0008_issue_attachments.py`:**up→down→up 演練通過**。
- `app/routers/issues.py`:三個端點——XHR 上傳(raw PUT)、**純表單上傳**(multipart)、
  **inline 讀取**;共用 `_store_attachment()`,型別與張數的判斷只有一份。
- `app/static/issue-upload.js`(新):貼上 / 拖曳 → XHR → 把 markdown 插進輸入框。
- `app/templates/issue_detail.html`:附件區 + 上傳表單。
- `app/audit.py`:`issue.attachment_upload`。
- `tests/test_issue_attachments.py`(新):13 條。

### 六條收窄如何兌現

1. 只有 `/v1/issues/{id}/attachments/{aid}` 是 inline;**回歸測試**確認
   `/v1/releases/.../download` 仍是 attachment。
2. 型別由 `filetypes.sniff()` 在 `on_head` 判定,只放行三種圖片。
3. SVG 判為 `image/svg+xml`,不在白名單 → 422。
4. 回應帶 `nosniff`,`Content-Type` 用**資料庫裡的判定值**;
   讀取時**再檢查一次**型別在白名單內(就算資料被動手腳也不 inline)。
5. 非本人非管理員 404。
6. 5 MB / 5 張,超過分別 413 / 422。

### 為什麼附件區要獨立一段

透過貼上上傳的圖,若使用者沒把 markdown 送出,圖就「存在但看不到」。
附件區保證**每張上傳過的圖都看得到**,不會憑空消失。

### ⚠ 與施工計畫書的差異(第二條 5)

計畫書原設想「在建立表單裡貼圖」,那需要回報還不存在時就先有 id(得引入暫存區與
孤兒清理)。改為**先送出回報 → 在詳情頁附圖**:附件永遠掛在已存在的回報上,沒有孤兒。
補充說明的討論串同樣可附圖,所以「邊講邊補圖」的流程仍然順。
