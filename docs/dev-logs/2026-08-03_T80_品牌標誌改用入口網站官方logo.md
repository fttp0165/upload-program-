# T80 品牌標誌改用入口網站官方 logo

**建立日期:** 2026-08-03 16:20
**最後更新:** 2026-08-03 16:20
**版本:** v1.0
**對應任務:** T80(使用者交辦 2026-08-03「把網頁服務 logo 都換成入口網站的 logo」)

---

## 一、目標(計畫段,動工前寫)

導航列的品牌標誌改用 **入口網站(cats-portal)的官方 SPORTON LAB. 標誌**
——即 `cats-portal/landing/assets/sporton-logo.png`,與 portal landing 首頁、
Keycloak 登入頁使用同一支檔案。

### 現況

本服務**沒有任何 logo 圖檔**。導航列的品牌標記是 `app.css` 的
`.nav-brand::before` 偽元素——用一個藏青圓 + `box-shadow` 疊出綠圓,
「純偽元素、零標記」(T56 設計稿的近似作法)。

它形狀對、比例對,但它是**近似**:官方標誌的兩個橢圓有交錯的白色鋸齒,
且帶 SPORTON LAB. 字樣,偽元素畫不出來。使用者從 portal 首頁點進本服務時,
看到的是一個「很像但不一樣」的標記——這正是這次要消除的落差。

另外本服務**沒有 favicon**,分頁上是瀏覽器的預設空白圖示。

## 二、影響範圍

| 影響對象 | 分級 | 說明 |
|---|---|---|
| 資料庫 | 🟢 不動 | 無 schema、無 migration |
| SSO / 認證 | 🟢 無 | 不碰 `auth`、cookie、CSP 以外的任何契約面 |
| 平台共用資源 | 🟢 無 | 不改 gateway、compose network、port |
| 前端外觀 | 🟡 有感 | 導航列品牌標記換成真圖;新增 favicon |

異動檔案(預定):

- 新增 `app/static/logo.png`(自 cats-portal 官方檔複製)
- `app/templates/base.html`:品牌 `<img>` + `<link rel="icon">`
- `app/static/app.css`:移除 `.nav-brand::before`,改 `.nav-brand-logo`
- `tests/test_branding.py`:新增 logo 斷言(先紅)

### 兩條必須守住的紅線(接入契約 §4.10 / T40 的舊坑)

1. **所有 `href` / `src` 一律經過 `url()`**。gateway 以尾斜線 `proxy_pass`
   剝掉前綴後轉發,服務收到的是 `/static/logo.png`,但瀏覽器要的是
   `/upload/static/logo.png`。漏掉一個就是 404(PLM 出過這個事故,
   決策文件 §6.2)。`tests/test_web_layout.py` 會解析 HTML 逐一檢查所有連結,
   新增的 `<img src>` 與 favicon `<link href>` **都會被它掃到**——
   這是既有的安全網,不必另寫。

2. **CSP `default-src 'self'` 不放寬**。自託管的 `/static/logo.png` 屬 `self`,
   不需要任何 CSP 調整;**不得**改用 data: URI(漢堡鈕圖示就是因為 data: URI
   被 CSP 擋掉才改用文字字元「☰」,而放寬 CSP 是 §4.10 紅線、有測試釘著)。

## 三、驗收標準

1. `app/static/logo.png` 存在且**與 cats-portal 的官方檔位元組相同**
   (以 SHA-256 比對;「看起來很像」不算,那正是偽元素現在的問題)。
2. `base.html` 的品牌區有指向該檔的 `<img>`,且路徑經過 `url()`(帶前綴)。
3. 有 favicon `<link rel="icon">`,同樣經過 `url()`。
4. `.nav-brand::before` 已移除——留著會在真圖旁邊再畫一個近似標記
   (Keycloak theme 那次就是同時有兩層 header 各畫一個 logo,實測才發現)。
5. `GET /static/logo.png` 回 200 且 `Content-Type: image/png`。
6. `tests/test_web_layout.py` 既有的「所有連結帶前綴」維持全綠。
7. 全測試套件維持全綠。

以上 1–5 寫進 `tests/test_branding.py`,**先跑成紅**再動工。

## 四、回滾方式

單一 commit,`git revert <hash>`。無資料、無 migration、無 `.env` 新增變數,
換版只需改 image tag 後 pull(檔案由 Dockerfile 的 `COPY` 進 image)。

`tests/test_branding.py` 新增 5 條,動工前 **5 條全紅**:

```
FAILED test_logo檔案與入口網站官方檔一致    - app/static/logo.png 不存在

FAILED test_有favicon                        - base.html 沒有 favicon <link>
FAILED test_偽元素標記已移除                 - app.css 仍有 .nav-brand::before
FAILED test_logo可被下載                     - assert 404 == 200
```

完工後 5 條全綠,**全套件 468 passed**(原 463)。

**反向驗證**:

| 反例 | 結果 |
|---|---|
| 在 `app.css` 末尾補回 `.nav-brand::before { content: "" }` | ❌ 紅 |
| 把 `logo.png` 截掉最後一個 byte(模擬「另存/轉檔」而非複製) | ❌ 紅,訊息報出實得的 digest |
| 還原 | ✅ 綠 |

第二條反例是這次刻意設計的:本任務要修的問題就是「很像但不是同一支」,
所以驗收標準必須是**位元組相同**。若斷言只寫「有一張圖」或靠目視,
一支重新輸出過、看起來一模一樣的 PNG 會通過——那正是現在偽元素的狀態。

### 決策與捨棄的方案

1. **捨棄「保留偽元素、只加圖」**。兩個標記會並排。這不是假設——
   Keycloak login theme 那次就是卡片內外兩層 header 各畫了一個 logo,
   而**本機預覽看不出來**(預覽的 DOM 只有一層),上線才發現。
   所以偽元素整段移除,並留下根因註解防止有人改回去。

2. **捨棄 data: URI 內嵌**(可省一次請求)。CSP `default-src 'self'` 會擋掉,
   而放寬 CSP 是接入契約 §4.10 紅線、有測試釘著。漢堡鈕當初就是為此
   從 Bootstrap 的 data: URI 圖示改成文字字元「☰」。

3. **`alt=""` + `aria-hidden`**:標誌與 `site_name` 在同一個 `<a>` 裡,
   站名已經是這個連結的無障礙名稱,再讀一次標誌名只是重複。

4. **回歸斷言先剝 CSS 註解再檢查**。第一版直接 `".nav-brand::before" not in css`,
   結果被我自己寫的那段「這裡以前是什麼、為什麼換掉」的註解判成紅。
   註解不會畫出任何東西;把它算進去,這條斷言會逼人刪掉那段歷史——
   而那段歷史正是防止有人改回去的東西。改為剝註解後再比對(反向驗證仍會紅)。

### 對現有資料的實際影響

🟢 **不動**。無 schema、無 migration、`.env` 無新增變數。

### 遺留問題

1. **未在真實瀏覽器目視確認** `height:22px` 在導航列的視覺重量是否恰當——
   本次環境無法渲染。測試能保證「圖是對的、路徑是對的、舊標記沒了」,
   保證不了「好不好看」。上線後值得看一眼。
2. 側欄 `.side-head`(專案中心 / 站名)目前仍是純文字,未放標誌。
   本次刻意不動:側欄是 App 內部導航,頂列品牌已足以承擔識別;
   兩處都放會在同一畫面出現兩個標誌。
3. 本次未動 `APP_VERSION`(憲法第八條是**發版**時的義務,本任務不發版)。
   下次發版時一併 bump。
