# T81 靜態檔快取破壞(CSS/JS 帶版本查詢字串)

**建立日期:** 2026-08-04 11:40
**最後更新:** 2026-08-04 11:40
**版本:** v1.0
**對應任務:** T81(T80 上線後實測發現的缺陷)

---

## 一、目標(計畫段,動工前寫)

讓 `app.css` / `app/static/*.js` 的變更能被瀏覽器**確實取得**,方法是在
`base.html` 的引用網址後面加上以 `APP_VERSION` 為值的查詢字串。

### 缺陷經過(2026-08-04 v0.2.0 上線後實測)

v0.2.0 上線後,首頁實際長這樣:

- 官方 logo 以**原始尺寸** (320×328) 顯示,佔掉整個畫面上半
- T80 應該已經移除的 `.nav-brand::before` **小圓點仍然畫著**

兩個症狀指向同一件事:瀏覽器用的是**舊版 `app.css`**。舊檔裡有
`.nav-brand::before`(所以小圓點還在),也沒有 `.nav-brand-logo`
(所以 `<img>` 沒有被縮到 22px)。伺服器端的 HTML 是對的,CSS 是舊的。

根因不在 T80 的 CSS 本身,而在 **`base.html` 引用 `app.css` 時沒有任何
快取破壞機制**:

```html
<link rel="stylesheet" href="{{ url('/static/app.css') }}">
```

Starlette 的 `StaticFiles` 只送 `ETag` / `Last-Modified`,**不送
`Cache-Control`**。沒有 `Cache-Control` 時瀏覽器會套用**啟發式快取**
(heuristic freshness,常見為距 `Last-Modified` 時間的 10%),在那段期間
連 revalidate 都不做,直接用本機副本。

**為什麼這個缺陷特別容易漏掉:** 開發與測試環境每次都是全新 client
(pytest 的 `AsyncClient`、剛開的無痕視窗),永遠拿得到最新檔案。
只有**已經用過這個網站的人**會中招——也就是所有現有使用者。
T80 的測試全綠、CI 全綠、伺服器吐的內容也正確,卻仍然壞在使用者眼前。

### 為什麼是現在才炸

T80 是本專案**第一次修改既有 CSS 選擇器的語意**(移除 `.nav-brand::before`、
新增 `.nav-brand-logo`)。在此之前 CSS 都是新增規則,舊快取頂多少一點樣式,
不會出現「舊規則畫出一個不該存在的東西」。這次舊規則與新標記同時存在,
缺陷才顯形。

> 對照:sporton_core 早就有這個慣例(`quote.js?v=N`、`auth.js?v=N`,
> 見其 CLAUDE.md「bump `?v=N`」)。本專案沒有,而我在 T80 動 CSS 時也沒補上。

## 二、影響範圍

| 影響對象 | 分級 | 說明 |
|---|---|---|
| 資料庫 | 🟢 不動 | 無 schema、無 migration |
| SSO / 認證 | 🟢 無 | 不碰任何契約面 |
| 平台共用資源 | 🟢 無 | 不改 gateway、network、port |
| 前端 | 🟡 有感 | 換版後所有人會重新下載一次 CSS/JS(一次性) |

異動檔案(預定):

- `app/templates/base.html`:三個靜態資源引用加 `?v={{ app_version }}`
- `tests/test_web_layout.py` 或新測:斷言引用帶版本
- `app/routers/web.py`:靜態檔回應補 `Cache-Control`(見下)

### 設計選擇

**採「查詢字串帶 APP_VERSION」**,不採其他方案:

- ❌ **檔名雜湊**(`app.abc123.css`):要引入建置流程(目前零建置,
  CSS 直接是 `app/static/app.css`),為一個小問題換來一整條 pipeline。
- ❌ **關掉快取**(`Cache-Control: no-store`):每次載入都重抓,
  平白拖慢每一頁。快取本身是對的,壞的是「沒有辦法讓它失效」。
- ✅ **`?v=<APP_VERSION>`**:零建置、與既有的「版本單一來源」對齊
  (`app/version.py`,發版時本來就會改),而且**發版即自動失效**——
  不必記得手動 bump 某個數字(sporton_core 的 `?v=N` 要人記得,
  那正是它會漂掉的原因)。

另外補上 `Cache-Control: public, max-age=31536000, immutable`:
既然網址已經帶版本,同一個網址的內容就**永遠不會變**,可以放心讓瀏覽器
長期快取。這比現在「沒有 Cache-Control、靠啟發式猜」兩邊都好:
命中率更高,而且失效是確定的而不是猜的。

🔴 但 `immutable` 只對**帶版本的網址**成立。直接請求 `/static/app.css`
(無查詢字串,例如 T80 冒煙用的哨兵檔 `/static/logo.png`)不能套用,
否則哪天真的要用固定網址發東西就再也換不掉了。所以只在**有 `v` 查詢字串**
時送長快取,沒有時維持現狀。

## 三、驗收標準

1. `base.html` 對 `app.css`、`vendor/bootstrap.min.css`、以及所有
   `static/*.js` 的引用都帶 `?v=<APP_VERSION>`。
2. 渲染後的 HTML 中,該查詢字串的值等於 `app.version.APP_VERSION`
   ——寫死一個數字等於又製造一個要記得改的地方。
3. `GET /static/app.css?v=0.2.0` 回 200,且帶
   `Cache-Control: public, max-age=31536000, immutable`。
4. `GET /static/app.css`(無查詢字串)回 200,且**不**帶 `immutable`。
5. `tests/test_web_layout.py` 既有的「所有連結帶前綴」維持全綠
   ——加了查詢字串不得讓那條斷言誤判。
6. 全測試套件維持全綠。

以上寫成測試,**先跑成紅**再動工。

## 四、回滾方式

單一 commit,`git revert <hash>`。無資料、無 migration、無 `.env` 變更。
回滾後回到「CSS 變更靠瀏覽器自己發現」的現況。

### 修了一條既有斷言 —— 為什麼這不是放水

`test_導航列品牌使用官方logo圖檔` 原本比對模板原始碼裡的
`url('/static/logo.png')` **字面值**,靜態檔改走 `static()` 之後它變紅。

憲法第三條(CI 紅線)規定「紅燈一律照設計改回,嚴禁改測試放水,
唯測試斷言本身有誤才修測試,並於 dev-log 說明」。這裡屬於後者:
該斷言想保護的是「路徑要帶 `/upload` 前綴」,而 `static()` 內部就是包著
同一個 `web_url()` —— 前綴照補,受保護的性質**原封不動**,壞掉的只是
它辨識這件事的方式。

順手把它改成驗**渲染後的輸出**(`"/upload/static/logo.png" in resp.text`)
而不是原始碼字串。理由:前綴有沒有真的補上去,是渲染的結果決定的;
比對原始碼只是在賭 helper 的行為,helper 一換就白驗 —— 這次就是白驗了一次。

### 對現有資料的實際影響

### 遺留問題

1. **這個修正要換版才會生效。** v0.2.0 已經在線上,而問題正是「舊 HTML 沒帶版本」
   —— 修正本身也得靠一次換版送出去。在那之前,現有使用者仍需 Ctrl+F5。
2. **`app/static/` 以外的靜態引用未納入**(目前沒有)。若日後新增,
   `test_模板不得直接用url引用靜態檔` 會擋下繞過 `static()` 的寫法。
3. runbook §C.2 / §D 與 `tools/backup.sh` 的備份路徑說明與 VM 現況不符
   (文件寫 `/home/deploy/upload-backups` + `/var/log/…`,實際可用的是
   `/srv/backups/upload-program` + `/opt/backup/upload-backup.log`),
   且 §D 的稽核清理排程未安裝 —— **不屬本任務範圍,另立任務處理**。
