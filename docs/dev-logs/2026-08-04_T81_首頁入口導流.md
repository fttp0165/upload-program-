**最後更新:** 2026-08-04 10:30
**版本:** v1.1
**對應任務:** T81

## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny 從 portal 卡片點進 `/upload/`,看到的是落地頁(「請先登入」+ 系統介紹三張卡),
裁示:

> 點擊卡片還是會進入登入頁面,不要進到這一頁。
> **沒權限就回入口,沒登入就進登入頁,有權限就進總覽。**

落地頁是 T53(2026-07-28)的裁示產物——當時定「深層頁 302、**首頁留落地頁**」,
理由是首頁要承擔「這是什麼系統、找誰開通」的說明功能。今天這條被推翻:
**從卡片進來的人已經知道這是什麼系統**,他要的是進去,不是再讀一次介紹。

### 目標

匿名/未開通的瀏覽器不再停在落地頁,依身分分三條路:

| 身分 | 現況 | 改為 |
|---|---|---|
| 未登入(瀏覽器) | 靜默探測 → 失敗 → **落地頁** | **302 `/auth/login`(互動式)** |
| 已登入、未開通或已停用 | 首頁顯示「待開通」文案 | **302 回平台入口** |
| 已登入、已開通 | 專案總覽 | 不變 |
| 非瀏覽器(`Accept: */*`) | 200 落地頁 | **不變**(見下) |

### 為什麼改用「互動式」而不是繼續靜默探測

T64 的靜默探測(`prompt=none`)目的是「portal 登入過的人免再按登入」。
改成互動式**同樣達成這個目的**——Keycloak 若已有 SSO session,互動式授權一樣
直接發 code 導回,不顯示任何畫面;差別只在**沒有 session 時**:靜默會無聲送回
落地頁(就是 Benny 不想看到的那一頁),互動式則直接顯示登入畫面。

所以首頁不再發起靜默探測。`/auth/login?silent=1` 端點與 callback 的
`login_required` 處理**保留**:那段是把 IdP 的正常回應擋在 401 之外的保險,
拆掉會讓任何未來的探測情境變成錯誤頁。

### 🔴 非瀏覽器維持 200 落地頁,不動

冒煙(runbook §A.4)與監控用 `Accept: */*` 打首頁,**以 200 當作服務活著的判準**。
沿用 T47 / T64 已經確立的「路徑 AND Accept 兩個條件」寫法:只有 `text/html` 才轉址。
改這一條會讓監控在換版當下集體變紅,而那與登入完全無關。

### 🔴 迴圈風險與防線

1. **未登入 → 登入頁**:互動式登入不會再回首頁繞圈(要嘛拿到 session,要嘛停在 IdP)。
2. **未開通 → 平台入口**:若 `PORTAL_HOME_URL` 被設成指回本服務(`/upload/...`),
   未開通者會在 portal 與本服務之間無限彈跳。**加防線**:轉址目標若落在本服務的
   對外前綴之內,退回 `/pending`(至少停得下來,且那一頁有他自己的 `sub`)。

### 影響範圍

`app/routers/web.py`(`home()` 分流)、`tests/test_silent_sso.py`(兩條行為改變)、
`tests/test_web_home.py` 與新測試。文件:任務表、T53 決策回寫(第二條 5)。

**對現有資料的影響:🟢 不動資料**(純轉址邏輯,無 schema、無 UPDATE)。

### 已知代價(先寫下來,不裝作沒有)

未開通者從首頁被送回 portal,就**看不到 `/pending` 那一頁,也就看不到自己的 `sub`**。
`/pending` 本身仍可直接開啟(不從首頁自動導向),管理員或客服可以把連結給他。
影響已被 T59 的顯示名稱快取沖淡——管理後台現在看得到名字,不再只有一排 UUID,
「使用者要把 sub 念給管理員」不再是唯一的對應手段。

若日後認為「被靜靜彈回入口」太難懂,替代方案是先停在 `/pending` 三秒再回入口;
本次依裁示原文做直接轉址,不自作主張。

### 驗收標準(紅→綠)

1. 匿名 + `Accept: text/html` 打 `/` → **302 到 `/auth/login`**,且 **不帶 `silent=1`**;
2. 匿名 + `Accept: */*` 打 `/` → **200**(落地頁,行為不變);
3. 已登入但 `pending` 打 `/` → **302 到平台入口**;
4. 已登入但 `disabled` 打 `/` → **302 到平台入口**;
5. 已開通打 `/` → **200 且看得到專案總覽**(不轉址);
6. `PORTAL_HOME_URL` 指回本服務時 → 未開通者 **302 到 `/pending`**(迴圈防線);
7. 全站測試全綠。

### 回滾方式

純程式碼、無 migration:回上一版 image 即可(runbook §B.1)。

### 為什麼這樣做(取捨)

1. **擋在 callback 而不是首頁。** 停用者的迴圈表面上是首頁造成的,但「被停用的帳號
   不該有 session」這件事跟首頁怎麼導流無關,即使日後改回落地頁也應該成立。
   擋在 callback 是把修正放在根因上,不是放在症狀上。
2. **不改 `optional_identity`。** 讓它對 disabled 回傳 Identity 看似更直觀
   (它的 docstring 本來就這樣寫),但那會讓**所有**用 `OptionalUser` 的頁面改變行為
   ——包括 T77 的問題回報(停用者會因此變得可以發文)。血本大於收益,不動。
   代價是 docstring 與實際行為的落差仍在,已記為遺留問題。
3. **F79 版本號搬家不是順手改。** T68 選首頁的理由白紙黑字是「三種狀態都看得到」;
   T81 讓其中兩種到不了首頁,不搬家等於把 F79 悄悄廢掉。這是第二條 5 說的
   「發現計畫與現實不符必須回寫」的實例。

### 對現有資料的實際影響

🟢 **無**。純轉址邏輯,沒有 schema 異動、沒有 UPDATE、沒有刪除。

### 遺留問題與後續建議

1. **待開通者被靜靜彈回入口,不知道為什麼**。`/pending` 仍可直接開啟(有他的 `sub`),
   但沒有任何地方會把他帶過去。若實際使用後覺得難懂,替代方案是先停 `/pending`
   三秒再回入口——本次依裁示原文做直接轉址,不自作主張。
2. **`optional_identity` 的 docstring 說「被停用的人也該看得到導覽列」,但實際回 None**
   ——落差先前就存在,本次沒有擴大也沒有修掉,記在這裡免得下一個人以為是新 bug。
3. **T29 冒煙第 1 項的說明要更新**:當初報給 portal 的是「深層頁 302、首頁落地頁」,
   現在首頁也 302,比原本更貼近契約 §7,但仍應主動更新說明而不是讓對方自己發現。
4. 🐛 **登入曾出現 401「授權碼交換失敗」**(trace `5983122e`):`app/oidc.py:149` 只記
   status 不記 IdP 的 `error`,無法一眼定位。錯誤回應的 body 只有 `error` /
   `error_description`(不含 token),建議另立任務補上;**裁示前不動工**。
