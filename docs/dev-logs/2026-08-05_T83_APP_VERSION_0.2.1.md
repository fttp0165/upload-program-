## 計畫(動工前成文,憲法第二條 2)

### 起因

PR #24 合併後,main 的狀態是:

```
main (d73c1b3) 的 APP_VERSION = "0.2.0"
v0.2.0 tag                   → c504b1c   ← 不是 main
```

T81(入口導流)與 T82(cryptography CVE)已在 main,但版本常數還停在 0.2.0
——**main 上的程式碼自稱是 v0.2.0,而 v0.2.0 這個 tag 指的是另一個 commit**。

憲法第八條 4 白紙黑字:`APP_VERSION` 必須在打 tag **之前**隨 PR 改好,
「tag 與這裡不一致的話,首頁會對使用者說謊,換版驗證也會判錯」。
現在就是那個不一致的狀態,只是還沒發版所以還沒痛。

### 目標

把 `APP_VERSION` 推到 **0.2.1**,讓下一次打 tag 時常數與 tag 一致。

### 為什麼是 0.2.1 而不是 0.3.0

這一版的內容是 T81(既有入口行為的調整)與 T82(相依安全修補),
**沒有新增功能面**。0.2.1 是 patch 語意上正確的位置。

### 為什麼不重發 v0.2.0

第八條 5:同一個版本 tag 不重發(v0.1.3 事故的結論)。v0.2.0 已經發布且**已部署到 VM**,
把 tag 移到新 commit 會讓「使用者手上那一版」與「tag 說的那一版」變成兩件事。
發下一個 patch 版是唯一乾淨的做法——這與 T69 更名沒搭上 v0.1.6 時的處置一致。

### 影響範圍

`app/version.py` 一行。文件:任務表。**對現有資料的影響:🟢 不動資料。**

### 為什麼不寫新測試(憲法第三條 4)

版本號的既有測試(`test_version_display.py`、`test_issues.py`、`test_admin_dashboard.py`)
全部**讀同一個常數**再比對畫面,所以改常數之後它們自動跟著驗新值——這正是 T68
把單一真相收在 `app/version.py` 的用意。

再寫一條 `assert APP_VERSION == "0.2.1"` 只是把同一個字面值抄第二遍,
它不會抓到任何錯誤(改常數的人也會順手改測試),只會製造「改版本要改兩個地方」的摩擦。
比照第三條 4 的純重構條款:**不寫新測試,既有測試維持全綠**當安全網。

### 驗收標準

1. `APP_VERSION == "0.2.1"`;
2. 全站測試全綠(既有版本號測試會跟著驗新值,OpenAPI 防漂移測試同源);
3. `ruff check` 乾淨。

### 回滾方式

純常數、無 migration:改回字串即可。
