## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny 貼出稽核頁的一筆紀錄:

```
user.activate  2026-07-29T13:26:37+00:00
操作者  0f499ea4-e10a-4fc0-95b8-772cf32f94ea
目標    user d99c5e93-018c-4ba8-9e81-5930f239cd98
```

裁示:「稽核紀錄顯示使用者名稱」。

現況是兩排 UUID。實務上「誰把誰開通了」根本認不出來——而稽核紀錄的用途就是事後追人,
認不出人的稽核紀錄等於沒有稽核紀錄。

`admin_audit.html` 的檔頭註解目前寫著「業務庫只存 sub,稽核表更只存本地 user id
——頁面上直接寫明,免得有人以為是壞掉或想去補個姓名欄位」。**那段話寫於 T59 之前**,
當時確實沒有任何名字可用;T59(契約 §4.2a L1)之後有了 `display_name_cache`,
前提變了,這段註解要一併回寫(第二條 5)。

### 目標

稽核頁的「操作者」與「目標(當 `target_type == "user"`)」顯示名稱,查不到就退回 UUID。

### 🔴 契約邊界:名字只上後台頁,不上 API

契約 §4.2a L1 給的例外是**僅管理後台顯示**。`AuditEventOut` 的 docstring 白紙黑字:
「只有 `actor_id`,沒有 email / 姓名……稽核不是繞過個資紅線的後門」。

所以:

- ✅ `GET /admin/audit`(HTML,平台管理員限定)顯示名字
- ❌ `GET /v1/admin/audit`(JSON)**維持不含名字**,一個欄位都不加

這不是保守,是那條例外本來的範圍。API 一旦帶名字,任何拿得到 admin token 的程式
都能整批匯出姓名對照表,那正是 §4.2 要防的事。

### 🔴 查詢數不得隨列數成長

設計文件《管理員後台與數據面板》§2 的紅線是「查詢數固定」。稽核頁一次 20 列,
若每列各查一次名字就是 N+1,而且會隨分頁大小惡化。

作法:**兩次批次查詢**——一次撈本頁所有 `actor_id` 對應的使用者,
一次撈 `target_type == "user"` 的 `target_id`,各用一個 `IN` 查完,在 Python 端組字典。
不論 20 列還是 1 列,查詢數都一樣。

### 影響範圍

`app/routers/web.py`(`admin_audit_page()` 補兩次批次查詢)、
`app/templates/admin_audit.html`(顯示 + 回寫過時註解)、
`tests/test_audit.py` 或新測試檔。

**對現有資料的影響:🟢 不動資料**(唯讀查詢,無 schema、無 UPDATE)。

### 已知限制(寫下來,不裝作沒有)

1. **名字是快取,可能是空的。** `name` claim 由 firstName + lastName 推導,兩者皆空時
   本欄為 NULL(`models.py` 已註明「這是會真的走到的路徑」)。此時顯示 UUID,
   與現況相同——不得因為要顯示名字就讓欄位空白。
2. **名字是登入當下的快照,不是即時值。** 使用者改名後、下次登入前,稽核頁顯示舊名。
   這是 L1 快取的本質;要即時得走 Admin API,而那條路 §4.2a L1 明文禁止(見 T73)。
3. **目標使用者可能已被刪除。** `target_id` 刻意不是外鍵(「查不回去也無妨」),
   查無此人時顯示原本的 UUID。

### 驗收標準(紅→綠)

1. 操作者有 `display_name_cache` → 頁面顯示名字;
2. 操作者無快取 → 顯示 UUID(不得空白);
3. `target_type == "user"` 且該使用者有名字 → 目標顯示名字;
4. 目標使用者查無此人 → 顯示原本的 UUID,頁面不炸;
5. 🔴 `GET /v1/admin/audit`(JSON)**不含任何名字欄位**;
6. 🔴 查詢數不隨列數成長(1 列與 20 列的查詢數相同);
7. 🔴 名字含 HTML 時被逸出(名字來自 IdP,不是我方可控字串);
8. 全站測試全綠。

### 回滾方式

純唯讀查詢與模板、無 migration:回上一版 image 即可(runbook §B.1)。

## 結果

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `app/routers/web.py` | `admin_audit_page()` 補一次批次查詢;新增 `_display_names()` |
| `app/templates/admin_audit.html` | 操作者/目標顯示名稱;**回寫過時註解**(第二條 5) |
| `tests/test_audit_names.py` | 新檔,8 條 |

實作只用**一次** `IN` 查詢:actor 與 user 目標的 id 併成同一個集合再查,
不是原計畫寫的兩次——同樣是 users 表,沒有理由拆成兩趟。

### 紅 → 綠

先寫 8 條:`3 failed, 5 passed`。5 條綠的是護欄(API 不含名字、查詢數不成長、
查不到退回 UUID、非 user 目標不受影響),它們的作用是**釘住不該改的東西**。

### 🐛 過程中抓到自己寫的假綠測試

`test_JSON_API不含名稱` 一開始就綠,但那是**假綠**:我原本用
`session.merge()` 手動把名字塞進資料庫,而 §4.2a 規定**每次登入以本人 token 的
`name` claim 覆寫快取(claim 不存在就覆寫成 NULL)**——測試用的 token 不帶 `name`,
名字在讀頁面之前就被清成 NULL 了。

於是那條測試是在「根本沒有名字」的情況下斷言「回應不含名字」,等於沒有測。
一個反向的安全測試假綠,比沒有這條測試更危險——它會讓人以為那條紅線有人守。

修法:名字一律由 `oidc.issue(sub, name=...)` 經登入寫入(這才是真實路徑),
並在該測試裡加一條**前提斷言**「後台頁確實看得到名字」,
讓它下次若再假綠會直接紅。

### 驗證

- 全站 **485 passed**(477 → +8)、`ruff check` 乾淨。
- 查詢數:1 列與 10 列的 SQL 條數相同(由 `before_cursor_execute` 實際計數)。

### 對現有資料的實際影響

🟢 **無**。唯讀查詢,無 schema、無 UPDATE。

### 遺留問題與後續建議

1. **名字是登入當下的快照。** 使用者改名後、下次登入前,稽核頁顯示舊名。
   這是 L1 快取的本質;要即時得走 Admin API,而 §4.2a L1 明文禁止(T73 仍待裁示)。
2. **舊事件的操作者可能永遠沒有名字**——那些人從未在 T59 之後登入過。
   這不是缺陷,是快取的起始點;UUID 仍在,追得回去。
3. `admin_users.html` 顯示名字時會截斷 sub,本頁**保留完整 UUID**。
   兩頁的取捨不同是刻意的:使用者管理頁重在辨識人,稽核頁重在事後追查。
