## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny 在 `/admin/users` 實測後回報:「還是沒有申請者名字與身分」。

畫面現況:

```
待開通(1)
  3f0d33bc-5c15-461d-adc3-8215d6e88b21   待開通   [開通]
其他帳號(2)
  be9a536c-db97-470a-802e-14de7a7dd279   active   [停用]
  benny lin  745497ee…   active  管理員   (你自己)
```

### 根因:T59 只做了一半

`admin_users.html` 有兩個迴圈,**T59 只改了下面那個**:

- `{% for user in other_users %}` → 有 `display_name_cache` 的判斷 ✅
- `{% for user in pending_users %}` → **只印 `user.sub`,完全沒有名字** ❌

而且頁首的說明文字仍是 T59 之前的版本:

> 本平台依帳號系統接入契約,業務資料庫只存 sub,個資一律不落地。
> **所以下面只有識別碼、沒有名字。**

T59 之後這句話已經不成立(其他帳號那半有名字),文案卻沒跟著改
——畫面因此自相矛盾:說明說沒有名字,`benny lin` 卻有名字。
依第二條 5 一併回寫。

🔴 **漏掉的正好是最需要名字的那一半。** 「開通」是這一頁唯一有後果的操作,
而**認不出是誰就不該按下開通**;其他帳號那半反而只是查閱。

### `be9a536c` 為什麼也沒有名字(這不是 bug)

`display_name_cache` 只在**該使用者自己登入時**寫入(§4.2a:每次登入以本人 token 的
`name` claim 覆寫,claim 不存在就覆寫成 NULL)。所以空白有兩種成因,都不是缺陷:

1. 那個人的 Keycloak 帳號**沒有 firstName / lastName** → `name` claim 不存在 → NULL。
   `models.py` 早就註明「這是會真的走到的路徑,不是防禦性假設」。
2. 那個人**最後一次登入早於 T59 上線**,之後沒再登入過 → 快取從未被填。

兩種都只能等他下次登入,或走 T73 的即時查詢(仍待 portal 裁示)。
所以本任務**不能只靠名字**解決「認出申請者」。

### 目標

1. 待開通清單顯示名稱(與其他帳號同格式:名字 + 截斷 sub,完整 sub 放 `title`);
2. **補上申請時間**(`created_at`)——名字空白時,管理員唯一還能對上的線索是
   「剛剛誰跟我說他申請了」。時間不是個資,不動任何紅線,卻是空白名字時的救命稻草;
3. 頁首說明文字回寫成現況。

### 🔴 不做的事

- **不加 email、部門、任何新的個資欄位。** 業務庫只存 `sub` 是平台鐵則,
  §4.2a L1 的例外只涵蓋 `name` claim。
- **不用 `preferred_username` 補位。** `security.py` 已註明「§4.2a:快取來源**僅限**
  `name` claim(裁決原文;`preferred_username` **不在准許範圍**)」。
- **不改成用截斷 sub 當操作鍵。** 契約 L1 第 8 條:截斷值僅供人眼辨識,
  任何操作一律以完整鍵為準——本頁的開通/停用表單送的是資料庫 `id`,維持不動。

### 影響範圍

`app/templates/admin_users.html`(待開通區塊 + 頁首文案)、`tests/`。

**對現有資料的影響:🟢 不動資料**(純顯示,無查詢變更——`pending_users` 已是完整
User 物件,名字與時間都在手上,不需要多一次查詢)。

### 驗收標準(紅→綠)

1. 待開通者有 `display_name_cache` → 清單顯示名字;
2. 待開通者無快取 → 顯示完整 sub(不得空白);
3. 待開通清單顯示申請時間;
4. 🔴 開通表單的 action 仍以資料庫 `id` 為鍵,**不因顯示改動而改用截斷值**;
5. 🔴 名字含 HTML 時被逸出;
6. 頁首不再宣稱「只有識別碼、沒有名字」;
7. 全站測試全綠。

### 回滾方式

純模板、無 migration:回上一版 image 即可(runbook §B.1)。

## 結果

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `app/templates/admin_users.html` | 待開通區塊補名稱 + 申請時間;頁首文案回寫 |
| `tests/test_pending_list_names.py` | 新檔,6 條 |
| `tests/test_web_admin.py` | 修正一條**早已失效**的斷言方式(見下) |

### 紅 → 綠

6 條先寫:`4 failed, 2 passed`。2 條綠的是護欄(沒有名字時顯示完整 sub、
表單以資料庫 id 為鍵),它們釘的是**不該因為要顯示更多而鬆動**的東西。實作後全綠。

### 🐛 順帶修掉一條「守的東西早已不是字面所寫」的測試

`test_管理後台不顯示個資欄位` 原本整頁搜尋「姓名」二字。這在 T59 之前等價於
「頁面沒有名字」;**T59 之後名字本來就會顯示**,那條測試還能綠,只是因為當時的文案
剛好沒用到那兩個字。它守的東西早已與字面脫節,而任何一句提到「姓名」的說明文字
都會誤觸它——本次就誤觸了。

處理方式**不是把文案改掉繞過它**(那等於讓一條失效的測試繼續指揮程式碼),
而是改成斷言真正的 invariant:**頁面不得出現 email**,並用 `@` 掃全頁——
比原本只找「電子郵件」這個標籤更嚴(標籤可以改名,email 本身不會沒有 `@`)。
名字的邊界交回給 §4.2a L1 的專屬測試把關,不由這條的字串比對代管。

### 驗證

- 全站 **491 passed**(485 → +6)、`ruff check` 乾淨。
- 無新增查詢:`pending_users` 本來就是完整的 User 物件,名字與時間都在手上。

### 對現有資料的實際影響

🟢 **無**。純模板顯示。

### 遺留問題與後續建議

1. **名字空白仍會發生,而且不是我們能修的**:IdP 沒有 firstName/lastName,
   或那個人最後一次登入早於 T59。申請時間是這種情況下的替代線索,不是解法。
   真正的解法是 T73 即時查詢,仍待 portal 裁示。
2. **T59 這種「只改了一半」值得警惕**:同一份模板兩個迴圈,改了下面忘了上面,
   而且**漏掉的那半才是有後果的操作**。日後動這類多區塊清單頁,
   建議測試直接切出區塊斷言(本檔的 `_pending_block()` 就是為此),
   不要用整頁字串比對——否則另一半的內容會替你假綠。
