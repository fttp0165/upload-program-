**建立日期:** 2026-08-05 13:00
**最後更新:** 2026-08-05 13:40
**版本:** v1.1
**對應任務:** T86

## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny 實測上傳頁後提兩點:

> 1. 上傳錯誤 無法取消
> 2. 直接三成三格卡片 說明 程式碼 執行檔

截圖裡的狀態正好說明了問題:選了 `files.zip`,類型下拉卻停在 **`doc —— 程式文件`**。
那是預設值造成的錯配——`files.zip` 是原始碼包,選成 doc 會被伺服器的 magic bytes 驗證退回。

### 問題 1:上傳中沒有任何退出路徑

`static/upload.js` 現況:

```js
button.disabled = true;      // 唯一的按鈕被停用
xhr.send(file);              // 沒有 timeout、沒有 abort、沒有取消按鈕
```

- 送出後**唯一的按鈕被停用**,畫面上沒有第二個可按的東西;
- `XMLHttpRequest` **沒有設 timeout** → 連線卡住(不是斷線,是不回應)時
  `onerror` 不會觸發,進度條停在某個百分比,按鈕永遠停用;
- 使用者選錯檔案或選錯類型,**送出後才發現也沒辦法中止**,只能重新整理頁面。

`onload` / `onerror` 都會把按鈕解鎖,所以「伺服器有回應的失敗」是可以重試的;
真正無解的是**還在飛的那段**。這與 Benny 說的「無法取消」一致。

### 問題 2:類型下拉是錯配的來源

T65 已經規定每一版必須 doc + binary + source **三類齊備**,但介面把它表達成
「一個檔案輸入 + 一個類型下拉」,再在頁面最底下用一行紅字說「目前還缺⋯」。
於是:

- 使用者要自己把「我手上這個檔」對應到「哪一個下拉選項」;
- 下拉有預設值(`binary` 在最前,但截圖停在 `doc`),**不選就是錯的那一類**;
- 「還缺什麼」離「要在哪裡補」很遠(頁面最底 vs 頁面最上)。

改成**三格卡片**之後,需求本身就是介面:一格 = 一類,格子裡直接說「這格要放什麼」,
已經有檔的格子顯示檔名與 ✓。錯配的機會從「選錯下拉」降到「放錯格子」,
而放錯格子在視覺上是看得見的。

### 目標

1. 上傳區改為三張卡片,順序依 Benny 所述:**說明(doc) → 程式碼(source) → 執行檔(binary)**;
   每格自帶檔案輸入與上傳按鈕,`kind` 由格子決定,**移除類型下拉**;
2. 每格顯示該類目前的狀態:已上傳(檔名 + ✓)/ 尚缺;
3. 補「取消上傳」:上傳中出現取消鈕,按下 `xhr.abort()` 並復原介面;
4. 補 **timeout**,讓卡住的連線不會永久佔住介面。

### 🔴 不變的東西

- **伺服器端驗證一步不減。** magic bytes、kind 比對、大小上限、SHA-256 全部不動。
  卡片只是讓人少選錯,**前端的檢查永遠只是體驗,不是防線**(`upload.js` 檔頭原有的話)。
- **仍然是 XHR raw body PUT。** 不改成 multipart 表單——那會把大檔落到暫存檔,
  違反「容器內不寫檔當狀態」。
- **JS 不碰 token、不自己拼路徑**(端點與上限仍由 `data-*` 帶進去)。
- **CSP 不放寬**:JS 仍是外部檔案,不引入任何 inline script / style。
- `_REQUIRED_KINDS` 仍是三類與其中文標籤的**單一真相**;卡片從它產生,
  不在模板裡另寫一份清單(否則哪天加類別會兩邊不同步)。

### 一個順帶的調整

`_REQUIRED_KINDS` 的順序由 doc→binary→source 改為 **doc→source→binary**,
與卡片順序一致。它同時決定「目前還缺⋯」那句話的列舉順序,兩處用同一份順序
才不會出現「卡片這樣排、缺項那樣念」。沒有測試綁定原順序(已確認)。

### 影響範圍

`app/templates/upload.html`、`app/static/upload.js`、`app/routers/releases.py`
(僅 `_REQUIRED_KINDS` 順序)、`tests/`。

**對現有資料的影響:🟢 不動資料**(純介面,無 schema、無 UPDATE、無新端點)。

### 驗收標準(紅→綠)

1. 上傳區有**三張卡片**,分別對應 doc / source / binary,順序為說明→程式碼→執行檔;
2. 頁面**不再有類型下拉**(`kind` 由卡片決定);
3. 已上傳某類 → 該卡片顯示檔名;未上傳 → 顯示尚缺;
4. 🔴 每張卡片的 `data-kind` 必須是合法的 `ArtifactKind` 值(擋打錯字);
5. 🔴 已發布的版本**不顯示任何上傳卡片**(既有規則不得因改版鬆動);
6. 取消按鈕存在於 DOM,且 `upload.js` 確實會 `abort()` 與設定 timeout;
7. 🔴 `upload.js` 仍不出現任何瀏覽器儲存 API(既有 `test_sso_contract` 的掃描續保);
8. 全站測試全綠。

### 回滾方式

純介面、無 migration:回上一版 image 即可(runbook §B.1)。

### 紅 → 綠

9 條先寫:`6 failed, 3 passed`。實作後全綠;全站 **500 passed**、`ruff check` 乾淨。

### 三個實作上的決定

1. **`abort()` 要接 `onabort`,不是靠 `onerror`。** `xhr.abort()` 觸發的是 `onabort`;
   少了那個 handler,取消之後畫面會停在「上傳中 47%」不動,**看起來更像當掉**
   ——比不能取消還糟。
2. **一格一個獨立的上傳器,不共用狀態。** 三格各自持有自己的 `inFlight`,
   所以同時傳兩格不會互相蓋掉進度或互相解鎖按鈕。
3. **`REQUIRED_KINDS` 合成一個結構而不是兩張表。** 卡片與「還缺⋯」那句話用同一份
   資料與同一個順序;分成兩份的話,哪天加一類就會出現「卡片有、缺項沒有」
   這種只在特定情境才看得出來的不一致。

### 對現有資料的實際影響

🟢 **無**。純介面,無 schema、無 UPDATE、無新端點;伺服器端驗證一步未減。

### 遺留問題與後續建議

1. **卡片只降低選錯的機會,不能杜絕。** 把 PDF 丟進「程式碼」那一格仍會送出,
   由伺服器的 magic bytes 退回——這是刻意的分工,前端不做防線。
2. **上傳成功仍是整頁 reload**(沿用 T44 的作法)。三格之後 reload 會讓另外兩格
   已選但未送的檔案消失。目前可接受(一次傳一個是常態),
   若實際使用覺得煩,再改成局部更新。
3. **timeout 訂 10 分鐘**是「卡住的連線最晚多久放人走」,不是效能調校;
   單檔上限 100 MB 在慢速內網下要傳得完。真的有人傳到逾時再調。
