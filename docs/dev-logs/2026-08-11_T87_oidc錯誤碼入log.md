# T87 OIDC 失敗時記下 IdP 的 `error` 碼

**建立日期:** 2026-08-11 11:00
**最後更新:** 2026-08-11 11:40
**版本:** v1.1
**對應任務:** T87

---

## 計畫(動工前成文,憲法第二條 2)

### 起因

2026-08-05 與 08-11 兩次登入故障(trace `5983122e-…`),排查時發現我方 log 只有:

```json
{"message": "授權碼交換失敗", "status": 400, "trace_id": "5983122e-…"}
```

**只有 status,沒有 IdP 說的原因。** 於是 `invalid_grant`(code 用過/過期/PKCE 不符/
redirect_uri 不一致)與 `invalid_client`(secret 錯)在 log 裡長得一模一樣,
只能靠猜——實際上這兩次都是猜的。

`app/oidc.py:149` 當時的註解寫著:

> 不把 IdP 回應原文吐給呼叫端,也不記進 log(可能含 token)。

前半對,後半**過度保守**:token 端點的**錯誤**回應依 RFC 6749 §5.2 只有
`error`、`error_description`、`error_uri` 三個欄位,**不會有 token**
(有 token 的是 200 的成功回應,而那條路徑本來就不記)。
我們為了一個不存在的風險,放棄了唯一能一眼定位的欄位。

### 目標

非 200 時,把 IdP 的 `error` 記進 log。三個地方都要:
`exchange_code`(授權碼交換)、`refresh`(續期,目前**完全沒有 log**)、
以及未來任何打 token 端點的路徑。

### 🔴 只記 `error`,不記 `error_description`

`error` 是**列舉值**(`invalid_grant` / `invalid_client` / …),內容可預期;
`error_description` 是**自由字串**,由 IdP 決定內容,我方無法保證裡面不會出現
使用者名稱、email、或某些實作塞進去的請求片段。

診斷需要的是前者——知道是 `invalid_grant` 就知道往哪查了。
後者的邊際價值遠低於「log 不記個資」這條紅線的風險,**不記**。

### 🔴 三條不得鬆動的界線

1. **回應給呼叫端的訊息一字不改。** 使用者看到的仍是「授權碼交換失敗,請重新登入。」
   ——IdP 的錯誤碼是我方維運資訊,不是給瀏覽器看的(洩漏 client 設定細節無益)。
2. **200 的成功回應仍然一個欄位都不記。** 那裡面才有 token。
3. **body 不是 JSON 或沒有 `error` 欄位時不得炸。** IdP 可能回 HTML 錯誤頁
   (gateway 擋下來時就會),解析失敗要安靜降級成「沒有 error 碼」,
   不能讓 log 這件事本身變成新的例外。

### 影響範圍

`app/oidc.py`(`exchange_code`、`refresh`)、`tests/`。

**對現有資料的影響:🟢 不動資料。**

### 驗收標準(紅→綠)

1. 交換失敗且 body 含 `{"error": "invalid_grant"}` → log 出現 `invalid_grant`;
2. 🔴 log **不含** `error_description` 的內容;
3. 🔴 log **不含**任何 token 字樣(即使 body 裡有——防禦性,不該發生但要釘住);
4. body 不是 JSON(例如 HTML 錯誤頁)→ 不炸,仍記下 status;
5. `refresh` 失敗同樣記下 `error`(它目前完全沒有 log);
6. 🔴 回應給呼叫端的 detail 文字未變;
7. 全站測試全綠。

### 回滾方式

純 log、無 migration:回上一版 image 即可(runbook §B.1)。

## 結果

### 做了什麼

`app/oidc.py`:新增 `_error_code()`,`exchange_code` 與 `refresh` 的失敗路徑
各記一行帶 `oidc_error` 的 warning(`refresh` 原本**完全沒有 log**)。

### 紅 → 綠

6 條先寫:`2 failed, 4 passed`。4 條綠的是護欄(不記 description、不記 token、
body 非 JSON 不炸、回應文字不變)——它們在紅階段是**空的**(當時什麼都不記),
實作後才真正生效。這種「先綠後真」的護欄要留意:它們是防止實作**做過頭**的,
不是驗證功能存在的。

全站 **506 passed**、`ruff check` 乾淨。

### 為什麼只記 `error` 不記 `error_description`

`error` 是 RFC 6749 §5.2 的列舉值,內容可預期;`error_description` 是自由字串,
由 IdP 決定內容,我方無法保證裡面不會出現使用者名稱、email 或請求片段。

診斷需要的是前者——知道是 `invalid_grant` 就知道往哪查(code 用過/過期/PKCE/
redirect_uri),知道是 `invalid_client` 就是 secret。後者的邊際價值遠低於
「log 不記個資」的風險。

### 對現有資料的實際影響

🟢 **無**。

### 遺留問題與後續建議

1. **這一版還沒上線,所以下一次故障仍然查不到。** 要等 v0.2.1 換版之後才生效。
2. **只涵蓋 token 端點。** discovery 與 JWKS 的失敗仍只記例外類別
   (`app/routers/auth.py` 的 `無法取得 OIDC discovery`)。目前夠用——
   那兩條失敗時 `/ready` 會直接反映,不像 token 端點是**只在使用者登入當下才發生**。
