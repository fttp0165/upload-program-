# T100 🐛 草稿版本回不去:版本歷史頁沒有編輯入口

**專案:** upload-program
**建立日期:** 2026-08-12 21:50
**最後更新:** 2026-08-12 22:05
**版本:** v1.1
**對應任務:** T100

---

## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny 實測(`benny's test` 專案的版本歷史頁):**「草稿版本就不能再發布與編輯了」**。
截圖裡 5 個版本,其中 **4 個是草稿、0 個檔案**,每一個都只有一枚「草稿」徽章,
旁邊什麼都沒有。

### 根本原因(已查證)

草稿的編輯與發布都在**上傳頁** `/releases/{id}/upload`——那頁有三格上傳卡片
與「發布這個版本」按鈕。問題是**只有一條路會到那裡**:

```
建立版本(表單送出)→ _redirect(request, f"/releases/{release.id}/upload")
```

`app/routers/web.py:575`。也就是說,**上傳頁只在剛建立版本的那一刻自動出現一次**。
使用者一旦離開(關分頁、按上一頁、跑去看別的專案),那個草稿就再也沒有入口——
版本歷史頁只印徽章不給連結(`releases.html:51-52`),專案頁只顯示**最新已發布**版本
(`latest_published_release()` 明文「draft 不算」)。

草稿因此變成孤兒:**存在、看得見、但點不進去**。Benny 那 4 個 0 檔案的草稿
就是這樣累積出來的——每次建立版本後沒有一次做完,就多一個回不去的殼。

### 這不是「功能沒做」,是「入口漏掉」

要澄清一件事:發布與上傳的**功能都在,而且是好的**——
API `POST /v1/releases/{id}/publish`、網頁 `POST /releases/{id}/publish`、
三類齊備檢查、已發布不可變更的 409,全部都有測試。
**缺的只是版本歷史頁上的一個連結。** 修正範圍因此很小。

### 目標

版本歷史頁的**草稿**列,給一個「繼續編輯」連結指向該草稿的上傳頁。

### 🔴 誰看得到這個入口

草稿本來就只有成員看得見(`include_drafts=role is not None or is_admin`),
但**看得見不等於改得動**:發布要 `maintainer` 以上(`require_project_role`)。
所以入口的判準要與發布同一條,否則 viewer 會看到一個按下去就 403 的連結。

新增 `security.may_manage_releases(role, user)`,與
`require_project_role(..., maintainer)` **共用 `_ROLE_RANK`**,只是不拋例外——
網頁層要的是「按鈕該不該出現」,不是「擋下請求」。
🔴 **真正的把關仍在 API**;這裡少判一次只會少一個入口,不會放行任何操作。

### 順手修一個顯示 bug

`app/templates/upload.html:37`:

```html
<p class="notice">此版本**已發布**,不可再變更檔案。</p>
```

`**` 是 Markdown 語法,寫在 HTML 模板裡**不會變粗體,會原樣顯示成星號**。
改成 `<strong>`。

### 明確不做

- **不做網頁版刪除草稿**。API 有 `DELETE /v1/releases/{id}`(會連 MinIO 物件一起刪),
  但那是破壞性操作,網頁入口需要確認流程與更多防呆,該有自己的任務。
  本次先讓草稿「進得去」,清理另議。
- 不動專案頁(它顯示最新已發布版本,是刻意的:給下載者看,不是給作者看)。

### 影響範圍

`app/security.py`(新增一個判斷函式)、`app/routers/web.py`(傳旗標)、
`app/templates/releases.html`(草稿列加連結)、`app/templates/upload.html`(粗體)、
`tests/test_web_releases.py`、任務表、本日誌。

**對現有資料的影響:🟢 不動資料**(純顯示,唯讀)。

### 驗收標準(紅→綠)

1. maintainer/owner/admin 在版本歷史頁看到草稿的「繼續編輯」,連到 `/releases/{id}/upload`;
2. 🔴 **viewer 角色看得到草稿,但看不到編輯入口**(避免給出必然 403 的連結);
3. 🔴 **已發布的版本不得出現該入口**(已發布不可變更,給連結等於誤導);
4. 全站測試全綠。

### 回滾方式

純顯示與唯讀判斷,無 migration:`git revert` 即可。

## 結果

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `app/security.py` | 新增 `may_manage_releases(role, user)`——與 `require_project_role(..., maintainer)` 共用 `_ROLE_RANK`,只是不拋例外 |
| `app/routers/web.py` | 版本歷史頁傳 `can_edit_releases` 與 `edit_url` |
| `app/templates/releases.html` | 草稿列加「繼續編輯」連結 |
| `app/templates/upload.html` | 🐛 `**已發布**` → `<strong>已發布</strong>` |
| `app/static/app.css` | `.release-edit` 樣式 |
| `tests/test_web_releases.py` | 新增 **3 條** |

### 紅 → 綠

3 條先寫:`1 failed / 2 passed`——**功能紅、兩條護欄綠**,正是想要的比例
(護欄在實作前後都必須綠,才證明它們守的是權限與狀態,不是「功能還沒做」)。
實作後全綠;全站 **534 passed**、ruff 乾淨。

### 修的是入口,不是功能

值得記一筆,免得日後誤讀這個任務的規模:**上傳與發布的功能一直都在,而且是好的**
——三類齊備檢查、已發布回 409、maintainer 把關,全都有測試。
唯一缺的是版本歷史頁上的一個連結。

「功能做完了」與「使用者找得到」是兩件事。這次是後者出問題,而它的症狀
(「不能再發布與編輯了」)聽起來完全像前者——如果照字面去找發布功能的 bug,
會在一堆好的程式碼裡繞很久。

### 順手修掉的顯示 bug

`upload.html` 寫了 `此版本**已發布**,不可再變更檔案。`
`**` 是 Markdown,在 HTML 模板裡**不會變粗體,會原樣印出星號**。
已發布的版本頁面上一直掛著兩對星號,沒人回報過。

### 對現有資料的實際影響

🟢 **無**。純顯示與唯讀判斷,不加欄位、不改既有值、無 migration。

### 遺留問題與後續建議

1. **Benny 那 4 個 0 檔案的草稿仍在**。現在點得進去了,可以補檔案發布,
   但**網頁沒有刪除草稿的入口**(API 有 `DELETE /v1/releases/{id}`)。
   刪除會連 MinIO 物件一起刪,是破壞性操作,需要確認流程與防呆——另立任務,不順手做。
2. 專案頁仍只顯示最新**已發布**版本(刻意:那頁是給下載者看的)。
   若日後要讓作者在專案頁就看到自己的未完成草稿,是另一個設計問題。
