## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny 實測截圖:在「說明」卡片上傳 `客戶規格書.md`,回

> 上傳失敗(422):檔案實際型別為 application/octet-stream,不在 kind=doc 的
> 允許清單(application/pdf, application/x-ole-storage, application/zip,
> image/gif, image/jpeg, image/png, text/plain)。

而同一張卡片自己寫著「使用說明、更新內容(**PDF / Markdown / 文字檔**)」。
**平台承諾收 Markdown,卻把 Markdown 擋掉**——不是使用者用錯,是我方的 bug。

### 根本原因(已重現)

`filetypes._looks_like_text()` 判斷檔頭是不是文字。判型只看前
`magic_sniff_bytes = 4096` bytes,**尾端幾乎必然切在字元中間**,所以原本寫了補救:

```python
try:
    head.decode("utf-8")
except UnicodeDecodeError:
    try:
        head[:-3].decode("utf-8")   # 🐛 這裡
```

「砍掉尾端 3 bytes 再試」對 ASCII 沒問題,**對中文是錯的**:
中文一個字佔 3 bytes,若被切斷的殘尾是 **1 或 2 bytes**,砍掉 3 bytes 會把
**前一個完整的字**也砍掉一部分,製造出**新的**不完整字元 → 仍然 decode 失敗
→ 判定不是文字 → 回 `application/octet-stream` → 白名單擋下。

實測(純中文內容,只差一個 ASCII 前綴):

| 前綴 | 4096 切點落在哪 | 判定 |
|---|---|---|
| 0 bytes | 剛好切在字元邊界 | ✅ `text/plain` |
| 1 byte | 殘尾 2 bytes | ❌ `application/octet-stream` |
| 2 bytes | 殘尾 1 byte | ❌ `application/octet-stream` |

**三種對齊有兩種會失敗**——所以症狀是「有時可以有時不行」,難怪沒早點抓到。

### 影響範圍比截圖更大

1. **只影響大於 4096 bytes 的檔案**。小檔整份都在檔頭裡,不會被截斷,所以
   短的中文 `.md` 上傳得了——這正是這個 bug 能活到現在的原因。
2. **不只 doc 卡片**:`kind=source` 也允許 `text/plain`,所以**帶中文註釋的
   `.py` / `.txt` 原始碼**只要超過 4KB 同樣會被擋。
   本專案的使用者是公司內部開發者,中文註釋是常態,受影響面很廣。
3. 英文文件不受影響(ASCII 單 byte,砍 3 bytes 不會破壞前一個字元)——
   所以這個 bug **專打中文**。

### 目標

修 `_looks_like_text`,改用 **UTF-8 增量解碼器**:
`codecs.getincrementaldecoder("utf-8")()` 的 `final=False` 語意正是
「後面還有,尾端不完整不算錯」,而**真正的非法位元組照樣會拋錯**。
這不是放寬判型,是把「截斷」和「不是文字」這兩件事分開——舊寫法把它們混在一起。

### 🔴 不做的事

- **不**把 `application/octet-stream` 加進 doc/source 的白名單。那會讓任意二進位
  檔案冒充文件,等於拆掉白名單本身。
- **不**改看副檔名。憲法紅線:不信副檔名、不信前端送的 Content-Type。
- **不**放寬 HTML/SVG 的一律拒收。

### 影響範圍(檔案)

`app/filetypes.py`(`_looks_like_text` 一個函式)、
`tests/test_filetypes.py`(新增案例)、任務表、本日誌。

**對現有資料的影響:🟢 不動資料。**
已經上傳成功的檔案不受影響;先前被擋下的檔案本來就沒進系統,使用者重傳即可。

### 驗收標準(紅→綠)

1. 先寫紅測試:**大於 4096 bytes 的純中文內容,三種切齊方式都要判成 `text/plain`**
   (目前會有兩種失敗);
2. 真正的二進位內容(含 NUL、非法 UTF-8 序列)仍判成 `octet-stream`——
   修正**不得**放寬到收二進位;
3. HTML / SVG 仍一律拒收;
4. 既有 `test_filetypes.py` 全數維持綠;全站測試全綠。

### 回滾方式

單一函式的純邏輯修正,無 migration、無資料異動:`git revert` 即可。

## 結果

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `app/filetypes.py` | `_looks_like_text` 改用 UTF-8 增量解碼器;補上完整 docstring 記錄根本原因(第五條 4:修 bug 要註明,避免後人改回去) |
| `tests/test_filetypes.py` | 新增 **5 條**:三種切齊、中文 doc、中文註釋 source、二進位護欄、中文 HTML 仍拒收 |

修正本體只有一行:

```python
codecs.getincrementaldecoder("utf-8")().decode(head)   # final=False
```

### 紅 → 綠

先寫 5 條,`2 failed / 17 passed`——失敗訊息與 Benny 截圖**一字不差**:
`檔案實際型別為 application/octet-stream,不在 kind=doc 的允許清單(…)`。
修正後 `19 passed`;全站 **520 passed**、ruff 乾淨。

實測還原截圖情境(同一份中文內容,只差 ASCII 前綴):

| 前綴 | 修正前 | 修正後 |
|---|---|---|
| 0 bytes | ✅ text/plain | ✅ text/plain |
| 1 byte | ❌ octet-stream | ✅ text/plain |
| 2 bytes | ❌ octet-stream | ✅ text/plain |

### 為什麼這個 bug 活得這麼久

三個條件要同時成立才會踩到:**檔案 > 4KB**、**內容含中文**、**4096 切點剛好落在
字元中間(2/3 機率)**。短檔整份都在檔頭裡不會截斷,英文檔砍 3 bytes 傷不到前一字——
於是它看起來像「偶爾出包」而不是「一定壞」,測試也剛好都用小檔與英文內容。

**這是測試資料選得太乾淨的代價。** 新增的測試刻意用 >4096 bytes 的中文,
並把三種對齊全測,而不是只測一種剛好會過的。

### 護欄(修正沒有放寬什麼)

| 仍然擋 | 驗證方式 |
|---|---|
| 含 NUL 的二進位 | 測試 |
| 非法 UTF-8 序列(不是截斷,是不合法) | 測試 |
| 合法中文中間夾雜非法位元組 | 測試 |
| HTML / SVG(任何 kind、中文內容也一樣) | 測試 |
| `octet-stream` 冒充 doc / source | 白名單未動 |

**沒有**把 `octet-stream` 加進白名單、**沒有**改看副檔名、**沒有**碰
`Content-Disposition: attachment` + `nosniff` 那道兜底。

### 對現有資料的實際影響

🟢 **無**。不動資料庫、不動已上傳的檔案。先前被擋下的檔案本來就沒進系統,
使用者重傳即可——**但要等這一版上線才有用**(見遺留 1)。

### 遺留問題與後續建議

1. 🔴 **修正要換版才生效**。正式站現在跑 v0.2.1,仍有此 bug;
   Benny 那份規格書在換版前傳不上去。建議併入下一個 patch 版(v0.2.2)。
2. 影響面比截圖大:`kind=source` 也吃 `text/plain`,所以**帶中文註釋、超過 4KB 的
   `.py` / `.txt`** 先前同樣被擋。換版後這兩類一起解。
3. 判型窗口 4096 bytes 的截斷問題已解,但 `sniff` 對 HTML/SVG 的偵測只看前 512
   bytes 的開頭——與本 bug 無關,未動;若日後要收窄,另立任務。
