## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny 看正式站的專案頁(`fcc-power-analyzer`):**「沒有顯示作者的名字」**。

查證屬實:`專案資訊` 只有容量、建立時間、最後更新——**完全沒有擁有者欄位**。
對一個程式分享平台來說,這是核心缺口:使用者要下載一支 `.py` / `.exe`,
「這是誰放的」是判斷要不要信任它的第一個依據,尤其在**掃毒還沒接上**的現在。

### 🔴 為什麼不能直接把名字放上去

名字的唯一來源是 `display_name_cache`(T59),而它受契約 §4.2a L1 管。
**限制是我方自己寫的**——`申請_姓名快取特例_給portal.md` 第 45 行:

> 用途:**僅管理後台顯示**(使用者管理、稽核紀錄的操作者辨識);
> **不出現在一般使用者可見頁面**、不進 API 回應、不作任何授權判定依據

專案頁正是「一般使用者可見頁面」。當初為了讓申請容易通過把範圍縮到最小,
現在反過來咬到自己。**要解就得送新申請,不能自行放寬**——
偏離平台契約的權限不在本專案(見〈位階〉)。

### 目標(Benny 裁示「兩個都做」)

1. **過渡(本任務程式面)**:專案資訊加「擁有者」一列,顯示 **sub 前 8 碼**。
   UUID 認不出是誰,但它做到兩件事:欄位存在了(獲准後換成名字是一行的事)、
   而且**同一個人發布的專案可以互相對照**。
2. **正解(本任務文件面)**:寫申請書送 portal,請求把 §4.2a L1 的用途
   從「僅管理後台」擴大到「專案頁顯示擁有者」。依第九條新格式命名並登記進索引。

### 為什麼過渡選 sub 前 8 碼而不是留白

- **sub 不是個資**:它是 IdP 的不透明識別碼,本來就是我方業務庫唯一的身分欄位
  (紅線要求的正是「只存 sub」)。顯示它不觸及任何一條紅線。
- 截斷 8 碼比照管理後台既有慣例(T59:「截斷值僅供人眼辨識」),
  不給完整值——完整 UUID 對人眼沒有更多幫助,少給就少一分外洩面。
- 欄位旁**誠實標註**為什麼是識別碼而不是名字。這與 `not_scanned` 同一個態度:
  做不到的事就明說,不假裝沒這回事。

### 🔴 護欄(本任務必須守住)

| 完整 sub 外流 | 測試:頁面不得含完整 sub |
| 名字進 API | 未動 schema;T84 既有測試仍守著 |

### 🐛 測試自己先寫錯了一次(值得記)

第一版三條測試都讓**擁有者自己**去看自己的專案,結果:

- 「不得洩漏完整 sub」當場紅——但**不是因為功能有問題**,而是導覽列的使用者
  下拉本來就會顯示**檢視者自己的** sub(沒有名字時的既有行為);
- 同理「不得出現顯示名稱」那條,若檢視者有名字,導覽列就會有他的名字,
  這條斷言**永遠不可能過**。

改成**由另一個人來看**才是真正要問的問題:「別人看得到擁有者是誰嗎?」
同一人看自己的頁面,測不出擁有者欄位到底有沒有做出來。

**教訓**:寫反向斷言(「某某不得出現」)時,要先確認頁面上沒有**另一個合法來源**
會產生同一個字串,否則測到的是別的東西。
