## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny 四項需求之一:「建立管理員權限」。
依 [施工計畫書 T122–T125](../plans/施工計畫書_審核與回饋_T122-T125.md) §1,
本任務先做——**T123 審核制度需要有可指派的管理員,否則全卡在 `.env` 那一個帳號**。

### 現況:後端早就做完了

| 已有 | 位置 |
|---|---|
| `User.platform_role`(`member` / `admin`) | `models.py` |
| 改角色的 API 與稽核 | `PATCH /v1/admin/users/{id}` |
| 後台顯示「管理員」徽章 | `admin_users.html` |
| 第一個管理員的來源(雞生蛋) | `.env` 的 `BOOTSTRAP_ADMIN_SUBS` |

**唯一缺的是網頁按鈕**——與 T121 同一個形狀:功能在,入口沒有。
現在要指派管理員只能自己打 API,而**會打 API 的人不需要這個系統的後台**。

### 目標

`/admin/users` 每一列加「設為管理員 / 取消管理員」(POST 表單,
比照既有的「開通」按鈕),語意與 `PATCH /v1/admin/users/{id}` 完全相同。

### 🔴 三條防呆(這是給權限,不是給顏色)

1. **不能取消自己的管理員身分。**
   平台沒有 root 後門——最後一個管理員把自己降級,就沒有人能再指派任何人,
   只能改 `.env` 重啟容器才救得回來。一個手滑不該有這種代價。
2. **不能把「未開通」的人設為管理員。**
   待開通是 deny-by-default 的狀態(契約 §3);跳過開通直接給管理權,
   等於用後門繞過自己的門禁。要給就先開通,兩個動作都留稽核。
3. **稽核照記**,而且與 API 產生**相同的 action**(`user.role_change`)——
   稽核紀錄不該因為管理員用的是網頁還是 API 而長得不一樣
   (這條是 `admin_activate` 已經立下的規矩,照抄)。

### 為什麼不做「最後一個管理員不能被降級」

想過,但**不做**:它需要「數一數還有幾個管理員」,而那個計數在並行下不可靠
(兩個管理員同時降對方,兩邊都讀到「還有 2 個」)。
防呆 1(不能降自己)已經涵蓋最常見的手滑,而且**不需要計數**——
它只看「你是不是你」,永遠正確。真的把彼此都降光,那是兩個人刻意為之,
不是防呆該解的問題。

### 影響範圍

`app/routers/web.py`(新增一條 POST 路由)、`app/templates/admin_users.html`、
`tests/test_web_admin.py`、任務表、本日誌。

**對現有資料的影響:🟢 不動資料**(改的是既有欄位的值,不加欄位、無 migration)。

### 驗收標準(紅→綠)

1. 管理員可在 `/admin/users` 把一位**已開通**的成員設為管理員,並可取消;
2. 🔴 **不能取消自己**——按了要被擋下且說明理由;
3. 🔴 **不能把未開通者設為管理員**;
4. 稽核產生 `user.role_change`,與 API 同一個 action;
5. 全站測試全綠。

### 回滾方式

純新增路由與按鈕,無 migration:`git revert` 即可。
已經改過的角色不會被還原(那是資料,不是程式)——但角色本來就可以再改回去。

## 結果

### 做了什麼

| 檔案 | 異動 |
|---|---|
| `app/routers/web.py` | 新增 `POST /admin/users/{id}/role`(含兩條伺服器端防呆) |
| `app/templates/admin_users.html` | 每一列加「設為管理員 / 取消管理員」;自己那一列不給按鈕 |
| `tests/test_web_admin.py` | 新增 **5 條** |

### 紅 → 綠

5 條先寫,全紅(路由不存在)。實作後全綠;全站 **539 passed**、ruff 乾淨。

### 防呆做了兩層,不是一層

| 防呆 | 伺服器端 | 畫面 |
|---|---|---|
| 不能取消自己 | 409 | 自己那一列**不給按鈕** |
| 未開通者不能設為管理員 | 409 | 未開通者**不顯示**「設為管理員」 |

畫面那層只是不給機會按;**真正的把關在伺服器端**——表單可以偽造,
而這兩條防的正是「有人刻意繞過畫面」與「手滑」兩種情況。

### 為什麼不做「最後一個管理員不能被降級」

想過,**刻意不做**。它需要「數一數還剩幾個管理員」,而那個計數在並行下不可靠:
兩個管理員同時降對方,兩邊都讀到「還有 2 個」,結果一個都不剩。
要做對得上資料庫層的鎖,成本遠高於它擋掉的情境。

防呆 1(不能降自己)**不需要計數**——它只看「你是不是你」,永遠正確,
而且已經涵蓋最常見的手滑。兩個人刻意互降,那不是防呆該解的問題。

### 🐛 測試踩到的小坑

`test_web_admin.py` 的慣例是**每個測試各自 local import** `select` / `User`,
我照抄了別處的寫法卻漏掉 import,四條測試以 `NameError` 紅——
**紅的原因不是功能有問題**。這種紅要先看清楚錯誤型別再動程式,
否則會去改一個根本沒壞的東西。

### 對現有資料的實際影響

🟢 **無**。改的是既有欄位的值,不加欄位、無 migration。

### 遺留問題與後續建議

1. 本任務讓 **T123 有路可走**:審核制度需要可指派的管理員,
   否則會全卡在 `.env` 裡那一個 bootstrap 帳號。
2. `BOOTSTRAP_ADMIN_SUBS` 仍是唯一的「第一個管理員」來源,這是刻意的
   (雞生蛋問題無法在系統內解決)。上線後若把所有管理員都降級,
   仍只能改 `.env` 重啟——防呆 1 讓這件事**不可能因為單一個人的手滑而發生**。
