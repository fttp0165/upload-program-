## 計畫(動工前成文,憲法第二條 2)

### 起因與裁示

Benny:「使用者發布後,要管理員審核才會讓其他使用者下載」。
依 [施工計畫書](../plans/施工計畫書_審核與回饋_T122-T125.md) §6 的裁示:

- ✅ **所有版本都要審**(不做專案層開關——開關本身會變成繞過審核的路);
- ✅ 既有已發布版本 **一律視為已核准**;
- ✅ 退回**必須寫理由**;
- ✅ 待審版本對**非成員隱藏**;
- ✅ 管理總覽待辦區加「待審版本」。

### 狀態機

```
draft ──(作者送審)──> pending_review ──(管理員核准)──> published
  ^                         │
  └──(管理員退回 + 理由)────┘
```

`published` 的語意**不變**:可下載。這一點是整個設計的樞紐,見下。

### 🎯 關鍵設計:讓 migration 變成「只加欄位、不改任何一列」

最初以為要把既有 `published` 的資料重新標記,那是 🔴 UPDATE。
但只要**不動 `published` 的語意**(它一直都是「可下載」),既有資料就
**一列都不用改**——新的送審走 `pending_review`,舊的 `published` 原地不動,
自然滿足「既有已發布視為已核准」的裁示。

**資料影響因此從 🔴 降為 🟡(純加欄位)。**

### 🔴 一個 SQLite 測不出來、PostgreSQL 才會炸的坑

`_enum(..., native_enum=False)` 存成 **VARCHAR**,長度取**最長值**:
`release_status` 目前只有 `draft`(5)與 `published`(9)→ **VARCHAR(9)**。

新值 `pending_review` 是 **14 個字元**——PostgreSQL 會直接拒絕寫入,
而 **SQLite 不檢查 VARCHAR 長度,測試會全綠**。

所以 migration **必須 `alter_column` 放寬長度**,而且這一項
**不能靠 pytest 驗**(測試跑 SQLite)。驗證方式見〈驗證〉。

### 新增欄位(`releases`)

| 欄位 | 型別 | 用途 |
|---|---|---|
| `review_note` | `Text`,預設 `""` | 🔴 **退回理由**(裁示:必填) |
| `reviewed_by_id` | `Uuid`,可空,FK users | 誰審的 |
| `reviewed_at` | `DateTime(tz)`,可空 | 何時審的 |

`published_at` 仍在**核准當下**寫入——`latest_published_release()` 依它排序,
語意維持「最新**可下載**的版本」,那條查詢**一行都不用改**。

### 可見性:沿用既有規則,不另立一套

下載端現在已經有:
```python
if release.status is ReleaseStatus.draft and role is None and not admin:
    raise not_found  # 🔴 404 不洩漏存在
```
只要把 `is draft` 改成 `is not published`,`pending_review` 就自動獲得
**與草稿相同的可見性**(非成員 404、成員看得到)——正是裁示要的,
而且**不必發明新規則**。`query_releases(include_drafts=...)` 同理。

### 🔴 不做的事

- **不做通知**。平台沒有 email / 推播(T79 已載明),這是已知限制;
  緩解是管理總覽待辦區加一項,但仍要求管理員主動看。
  **不在本任務裡自建通知機制**——那是另一個系統。
- **不做「自己審自己」的禁令**。管理員發布自己的版本後仍可自行核准:
  本系統的管理員是平台維運者,不是外部稽核;加這條會讓單一管理員的
  情境完全動不了(而那正是目前的實況)。⚠️ 記為已知取捨,不是疏漏。
- **不做批次核准**。一次核一個,逼人看過內容——這個功能的意義就在那一眼。

### 驗收標準(紅→綠)

1. 作者按發布 → 版本進 `pending_review`,**其他使用者下載不到**(404);
2. 專案成員**看得到**自己送審的版本與狀態;
3. 管理員核准後 → `published`,任何人都下載得到;
4. 🔴 **退回沒寫理由要被擋下**;退回後回到 `draft` 且理由看得到;
5. 🔴 **非管理員不能核准**(403);
6. 既有 `published` 版本**行為完全不變**(回歸測試釘住);
7. 管理總覽待辦區出現待審數;
8. 全站測試全綠。

### 驗證(超出 pytest 的部分)

- 🔴 **migration up→down→up 本機演練**(紅線要求),用 **PostgreSQL** 而不是 SQLite
  ——VARCHAR 長度那個坑只有 PostgreSQL 抓得到;
  用 `docker compose -f docker-compose.dev.yml`(T119)起真的 PG。
  **✅ 已完成**,結果見〈遺留問題〉第 1 項。

### 回滾方式

`alembic downgrade -1`:刪三個欄位、縮回 VARCHAR 長度。
⚠️ **退版會遺失「待審」這個狀態**——`pending_review` 的版本必須先決定
(核准或退回),否則 downgrade 會把它們一律當回 `draft`(即未送審)。
這一項要寫進 runbook §B 的不可逆清單。

### 🎯 設計換來的:migration 不改任何一列

實測產出的 PostgreSQL DDL(`alembic upgrade --sql`):

```sql
ALTER TABLE releases ALTER COLUMN status TYPE VARCHAR(20);
ALTER TABLE releases ADD COLUMN review_note TEXT DEFAULT '' NOT NULL;
ALTER TABLE releases ADD COLUMN reviewed_by_id UUID;
ALTER TABLE releases ADD CONSTRAINT fk_releases_reviewed_by_id ...;
ALTER TABLE releases ADD COLUMN reviewed_at TIMESTAMP WITH TIME ZONE;
```

**沒有任何一行 UPDATE**(除了 alembic 自己的版本號)。
因為 `published` 的語意刻意不變,既有已發布的版本原地不動就等於「已核准」——
裁示的第 2 條因此不是靠資料遷移達成,是靠設計。

### 🐛 演練當場抓到的兩個 migration bug(測試全綠也看不到)

`pytest` 用 `create_all` 建表,**根本不跑 migration**——所以下面兩個錯
在 548 條全綠的情況下依然存在,只有真的演練一次才看得到:

1. **SQLite 不支援 `ALTER COLUMN ... TYPE`**。直接 `op.alter_column` 在 SQLite 上
   以語法錯誤炸掉(PostgreSQL 沒事)。改用 `op.batch_alter_table`:
   SQLite 走「建新表→搬資料→換名」,PostgreSQL 原樣轉成一般 ALTER。
2. **batch 模式下外鍵必須具名**:重建表時匿名約束搬不過去,
   alembic 直接拒絕(`Constraint must have a name`)。

**這正是紅線要求 up→down→up 演練的理由。** 兩個都不是想出來的,是跑出來的。

### 🔴 VARCHAR 長度:SQLite 永遠測不到的那一個

`_enum(..., native_enum=False)` 存成 VARCHAR,長度取最長值 →
原本 `VARCHAR(9)`(`published`)。新值 `pending_review` 有 **14 個字元**,
PostgreSQL 會直接拒絕寫入,而 **SQLite 不檢查長度**。

這個坑不是靠測試發現的,是**讀 `_enum` 的實作推出來的**——而且它在 SQLite 上
永遠不會紅。因此驗證分三層走完,一層比一層硬:

| 層 | 做了什麼 | 證明了什麼 |
|---|---|---|
| 推 | 讀 `_enum` 的實作,算出原本是 `VARCHAR(9)`、新值 14 字元 | 有這個風險 |
| 讀 | `alembic upgrade --sql` 產出 PostgreSQL DDL | 放寬語句**寫在**裡面 |
| 量 | 真的 PG 上 `information_schema.columns` → **20** | 放寬**真的生效** |

前兩層都可能是我自己看錯;第三層是資料庫自己說的。

### 順手補上的一道洞:待審中不得再改檔案

原本只擋 `published`。但**待審中若還能換檔,管理員核准的就不是他看過的那一份**
——審核會變成一個能被繞過的形式。改成「只有草稿能改檔案」,上傳與刪除都擋。

### 對現有資料的實際影響
