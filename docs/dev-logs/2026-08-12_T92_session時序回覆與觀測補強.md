## 計畫(動工前成文,憲法第二條 2)

### 起因

portal 回函 v2.0:三個提問全排除(redirect_uri / secret / gateway 變更都不是),
現場重現顯示登入流程走通,並把主線**指向我方**的 session/refresh 處理,
給了三個問題(§6.5)。

### 我方程式碼查核結論(動工前已完成閱讀)

1. **「callback 同一秒發 refresh」是時序誤讀。** 對照其 gateway log 逐行:
   第一行 `GET /upload/ → 302` 是**帶著舊 session cookie 的進站請求**——
   `_session_token` 對過期 access 嘗試 refresh(舊 refresh token 已死)→
   `Token is not active` → 視為未登入 → T81 送登入。**refresh 事件屬於
   authorize「之前」的第一行**,不是 callback 之後;同一秒內走完整條鏈
   (IdP 有 SSO session)。我方**不存在**「callback 後主動 refresh」的程式路徑。
2. **§6.5-2(新 token 是否取代舊的):有。** `SessionRenewalMiddleware` 把續期
   結果(含輪替後的 refresh token)寫回 cookie;登入時 `set_session` 以同名同
   path 覆蓋舊 cookie。
3. **§6.5-3(補記 error):已於 v0.2.1 上線**(T87)——對方回的是我方 v1.0,
   未及見 v1.1;v1.1 §3.1 貼的那筆 `invalid_grant` log 就是新欄位的產物。

### 真正未解釋的:登入成功後 23 秒被踢回(08:18:44)

以現有程式碼**推不出**:新 cookie 的 access token 有效 300 秒,:44 時應仍有效。
三種可能,各需不同資料:

| 可能 | 需要的資料 |
|---|---|
| :44 有續期嘗試且失敗 | 我方 v0.2.1 log(已含 `oidc_error` + trace_id) |
| :44 cookie 送達但**無法解析** | 🔴 **目前這條路是靜默的**(`read_session` 壞簽章回 None 不留痕)——本任務補上 |
| :44 根本沒帶 cookie(分頁/登出/另一 client 交錯) | 對方 gateway log 的毫秒序與 UA/來源比對 |

### 目標

1. **觀測補強(程式)**:session cookie「存在但無法解析」時記 warning
   (只記長度,🔴 不記內容——cookie 內含 token);讓第二種可能從此可見。
2. **回覆文件**:時序更正(逐行對照表)、§6.5 三點正面回覆、
   :44 的三種可能與雙方各自要提供的資料、我方撈 log 的指令。

### 影響範圍

`app/security.py`(`_session_token` 加一行 warning)、`tests/`、
`docs/plans/回覆_portal_session時序.md`(新)、任務表。

### 判讀重點(回覆文件的核心)

- portal 的證據是實的,但**時序讀反了**:那筆 refresh 失敗屬於 authorize
  之前、帶舊 cookie 的進站請求——同一秒走完整條登入鏈,事件相鄰不代表因果。
- 9 筆/120h 有無害解釋:各舊 session 過期後的首訪。這正是 T52「真的去問 IdP」
  的設計代價,換來的是收權 5 分鐘內生效。
- **:44 踢回仍未解**,不迴避:三種可能各配上「誰、拿什麼資料」;
  其中(b)型從此不再靜默。
