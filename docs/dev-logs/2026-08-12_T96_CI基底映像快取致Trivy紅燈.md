## 計畫(動工前成文,憲法第二條 2)

### 起因

PR #33(v0.2.2 前置)CI 三 job:
`測試 / lint / 文件同步` ✅、**`Build image + Trivy 掃描` ❌**、`Push GHCR` ⏭。

Trivy 列出的是 **`util-linux` 家族的 OS 套件**——`mount` / `login` /
`libmount1` / `libblkid1` / `libsmartcols1` / `libuuid1` / `util-linux`,
CVE-2026-53612 ~ 53615(TOCTOU、SUID mount 繞過 nosuid/noexec、整數溢位),
installed `2.41-5`。

**這些全部來自 base image,與本 PR 的 diff 無關**:runtime stage 從頭到尾
沒有 `apt-get`,OS 套件原封不動來自 `python:3.12-slim`。

### 根本原因

CI 的建置指令是:

```
docker build -t upload-program:ci .
```

**沒有 `--pull`。** runner 是 self-hosted(同一台 VM),`python:3.12-slim`
這個 tag 一旦拉過就躺在本機層快取裡,之後每次建置都沿用**第一次拉到的那一份**。
上游把同一個 tag 重建、把 Debian 的安全更新併進去,我們永遠取不到。

於是:**時間到了自己會紅**,而且 main 一起紅——看起來像「這個 PR 弄壞的」,
其實是快取放著爛。T82 那次是 Python 相依(`cryptography`),這次是 OS 層,
病灶不同但症狀一樣。

### 目標

`docker build` 加 `--pull`,確保同一個 tag 取到上游最新重建的那份。

### 🔴 這不是放寬紅線

- **tag 仍然鎖版本**:`python:3.12-slim` 是版本 tag,不是 `latest`。
  `--pull` 只影響「同一個 tag 取哪一份」,禁 `latest` 那條紅線不受影響。
- **不用 `.trivyignore`、不放寬 `--severity`**(T82 already 立過的界線):
  本服務散布可執行檔,掃描是自我加嚴的一環,調鬆掃描是拿紅線換方便。
- `--ignore-unfixed` 維持原狀——它本來就在,代表這批 CVE **上游有修好的版本**,
  我們只是拿不到。

### 如果 `--pull` 之後還是紅

代表上游 `python:3.12-slim` 尚未重建。那時的處置是在 runtime stage 明確
`apt-get update && apt-get upgrade -y` 受影響套件——**但先不做**:
多裝一層 apt 會讓 image 變大、且在上游修好後變成長期贅生物。先讓 CI 告訴我們。

### 影響範圍

`.github/workflows/ci.yml` 一行(加 `--pull`)、任務表、本日誌。

**對現有資料的影響:🟢 不動資料**(CI 設定,不碰程式與資料庫)。

### 驗收標準

CI 的 `Build image + Trivy 掃描` job 轉綠。

### 回滾方式

移除 `--pull` 即可。
