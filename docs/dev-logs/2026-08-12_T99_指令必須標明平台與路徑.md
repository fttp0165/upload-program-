## 計畫(動工前成文,憲法第二條 2)

### 起因

Benny:「給指令要說明在哪一個平台執行 以及執行的檔案路徑」。

這不是龜毛,是**已經出過事**的地方。2026-08-11 換版第一次失敗的根因就是這一類:

> `docker-compose.yml` 的 image tag 沒改到——**那一步是「編輯檔案」,
> 卻被當成 shell 指令貼進終端機**。結果 pull 拉的仍是 v0.2.0。
> ——任務表 v1.65

那次是「指令 vs 編輯」分不清。現在文件裡同時有**三種機器**的指令:

| 機器 | 典型工作目錄 |
|---|---|
| WSL(Benny 的開發機) | `~/upload-program-` |
| Windows(Docker Desktop 設定) | 無(GUI) |
| Cats VM(ssh 進去) | `/opt/upload-program` |

三種混在同一份文件裡,**每個區塊都長得一模一樣**(黑底、`$` 開頭)。
在 WSL 上跑到 VM 的指令頂多是報錯;**在 VM 上跑到本機的指令會出事**——
`docker compose -f docker-compose.dev.yml up -d` 貼到 VM 就把資料庫的 port
開到主機上了。

### 現況盤點

| 文件 | 待標的區塊 |
|---|---|
| `docs/runbook_本地開發與CI.md` | 16 個 `bash` |
| `docs/runbook_換版與備份還原.md` | 6 個 `bash` + 1 個 `cron` |

一個都沒有標。

### 目標

1. **憲法新增第十條**,把規則定死;
2. **兩份 runbook 全數補標**;
3. **測試守門**——與第九條同一個道理:規約沒有測試,三個月後就是一句沒人記得的話。

### 格式

每個可貼的區塊**正上方**加一行標記,三選一:

```markdown
> 🖥️ **在哪執行:** WSL · 工作目錄 `~/upload-program-`
> 🖥️ **在哪執行:** Cats VM(ssh)· 工作目錄 `/opt/upload-program`
> 📄 **編輯哪個檔:** `~/upload-program-/.env`
```

- 🖥️ = 貼進終端機執行;📄 = **編輯檔案內容**,不是指令
  (🔴 這正是 08-11 那次踩到的分界)
- 工作目錄一律寫**絕對路徑或 `~` 起頭**,不寫「專案根目錄」這種要讀者自己換算的話

### 🔴 為什麼要測試,而不是「以後記得寫」

第九條的教訓才剛發生:文件規約寫進憲法的同一天就配了守門測試。
理由一樣——**新增區塊時忘記標,不會有任何錯誤訊息**,
文件會慢慢退回原狀,而退化的過程沒有人看得見。

守門規則:兩份 runbook 裡,每個 ` ```bash ` 或 ` ```cron ` 區塊,
**往上 8 行內**必須出現 `在哪執行:` 或 `編輯哪個檔:`。
非指令的區塊(` ```json ` 的 log 範例、純文字畫面)不要求——它們不是拿來貼的。

### 標記時才看見的三個坑

1. 🔴 **換版 runbook §A.1「打 tag」是在本機 repo,不是 VM。**
   那份文件從頭到尾都在講 VM,只有這一段例外——**而它夾在
   §A.0(VM)與 §A.2(VM)中間**。原文只有一句不起眼的「在開發機(不是 VM):」,
   標記讓它變成與其他段落**視覺上就不同**的一塊。
2. 🔴 **§C.2 的 cron 是「編輯 crontab」不是「貼進終端機」。**
   這正是 08-11 那次踩到的同一個分界,只是換了個地方等著。
   標成 📄 之後不可能再誤讀。
3. **`.env` 那兩段也是編輯不是指令。** 本地 runbook §3.2 原本寫「`.env` 改四行」
   然後接一個 ```bash 區塊——**看起來就像四條指令**。
   照著貼進終端機會得到四個「command not found」,而且沒有人會知道錯在哪。

**這三個都不是我加標記時「順便發現」的——是標記這個動作逼出來的。**
要寫「在哪執行」就得先回答「這到底是執行還是編輯」,一問就露餡。
