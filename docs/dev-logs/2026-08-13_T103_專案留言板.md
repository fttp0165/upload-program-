## 計畫(動工前成文,憲法第二條 2)

### 起因與裁示

Benny 四項需求之三:「專案可以增加 user feedback」。
[施工計畫書](../plans/施工計畫書_審核與回饋_T101-T104.md) §6-4 裁示:**做專案留言板**。

### 🔴 不能沿用問題回報系統

平台已經有問題回報(T76–T79),但那是**回報這個網站的問題**:
只有本人與平台管理員看得到、🔴 **404 不洩漏存在**。
專案回饋的可見性設計**完全相反**——它就是要給同專案的人看的。
兩者長得像但方向相反,混用會把其中一邊的保證弄壞。

### 資料模型

新表 `project_comments`:

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | Uuid PK | |
| `project_id` | FK projects **CASCADE** | 專案刪掉,留言跟著走,不留孤兒 |
| `author_id` | FK users **RESTRICT** | 與既有慣例一致:留言還在就不讓使用者被硬刪 |
| `body_markdown` | Text | 存原文,顯示時才轉譯(沿用 `markdown_lite`) |
| `created_at` | DateTime(tz) | |

索引 `(project_id, created_at)`——留言一律依專案取、依時間排。

### 誰看得到、誰能寫

- **看**:能讀這個專案的人就看得到(走 `require_project_read`)。
  🔴 private 專案的留言**絕不外洩**——不另寫可見性邏輯,沿用同一個函式,
  private 非成員拿到的仍是 404 而不是 403(403 等於承認專案存在)。
- **寫**:能讀就能寫。viewer 也能留言——**那正是回饋的意義**,
  只有 maintainer 能講話的留言板不叫 user feedback。

### 🔴 誰能刪:作者本人與平台管理員,**專案擁有者不行**

這是本任務最需要想清楚的一條。

專案擁有者若能刪掉別人對自己專案的評語,這個留言板就只會剩下好話——
**一個只能留下讚美的回饋區,比沒有回饋區更糟**,因為它讓讀的人誤以為
「沒有負評」等於「沒有問題」。

所以刪除權限只給:
1. **留言者本人**(寫錯、後悔);
2. **平台管理員**(不當內容的管理責任)。

專案擁有者想回應批評,方式是**再留一則言**,不是讓批評消失。

### 🔴 不做自動清理(與問題回報不同)

`purge_issues.py` 會清掉關閉滿 365 天的回報——那合理,因為回報是**事務**,
處理完就沒有價值了。

留言是**內容**:「v1.2 在 Win11 會閃退」這句話一年後仍然有用。
自動刪掉等於把使用者累積的東西定期丟掉。**不做**,並記進本日誌以免日後有人
「比照 issues」順手加上。

### 身分顯示:又是契約 §4.2a L1

留言者顯示 `sub` 前 8 碼,格式與 T97(專案頁擁有者)、T104(版本建立者)一致。
名字待 portal 對申請書裁示。⚠️ 一串 UUID 的留言板體驗確實不好——
這是誠實的過渡狀態,不是設計目標。

### 影響範圍

`app/models.py`、`alembic/versions/0010_project_comments.py`(新)、
`app/schemas.py`、`app/routers/projects.py`(API)、`app/routers/web.py`(表單)、
`app/templates/project.html`、`tests/test_project_comments.py`(新)、
runbook §B、任務表、本日誌。

**對現有資料的影響:🟡 加一張表,不動既有任何一列。**

### 驗收標準(紅→綠)

1. 能讀專案的人可以留言,留言依時間顯示在專案頁;
2. 🔴 **private 專案的留言對非成員不可見**(且是 404 不是 403);
3. 🔴 **專案擁有者不能刪別人的留言**;作者本人與平台管理員可以;
4. 🔴 留言內容的 HTML 被逸出(使用者可控字串);
5. 查詢數與留言數無關(批次取作者識別碼,比照 T104);
6. migration up→down→up 演練通過;
7. 全站測試全綠。

### 回滾方式

`alembic downgrade -1` → `DROP TABLE project_comments`。
🔴 **會失去全部留言**,且無法重建——與 `0007_issues` 同一類,要寫進 runbook §B。

### 🐛 第一版有一條假綠,而且是最陰險的一種

「private 專案的留言對非成員回 404」那條**一開始就是綠的**——
因為**端點根本還不存在**,FastAPI 本來就回 404。

它為了**錯的理由**而通過,而且**永遠不會紅**:就算日後有人把可見性寫錯,
只要路徑還在,這條測試也不會告訴你。

補上前提斷言(先確認擁有者拿得到 200 且有 1 則留言)之後它才轉紅,
實作完成後才為對的理由而綠。

**反向斷言必須先證明「正向那條路是通的」**——這是 T84 假綠的同一課,
換了一個面貌又出現一次。

### 🔴 最重要的一條界線:專案擁有者不能刪別人的留言

刪除權限只給**留言者本人**與**平台管理員**。擁有者不在內。

理由不是技術的:擁有者若能刪掉別人對自己專案的評語,留言板就只會剩下好話,
而**一個只留得住讚美的回饋區比沒有回饋區更糟**——它讓讀的人誤以為
「沒有負評」等於「沒有問題」,而那正是這個功能想解決的事情的反面。

擁有者想回應批評,方式是**再留一則言**,不是讓批評消失。
不當內容的管理責任在平台方,不在被批評的人身上。

### 不做自動清理(與問題回報刻意不同)

`purge_issues.py` 會清掉關閉滿 365 天的回報——那合理,回報是**事務**,
處理完就沒有價值。但留言是**內容**:「v1.2 在 Win11 會閃退」一年後仍然有用。

**刻意不做**,並寫在這裡,以免日後有人「比照 issues」順手加上。

### 對現有資料的實際影響

🟡 **加一張表,不動既有任何一列。**

### 遺留問題與後續建議

1. **PostgreSQL 演練建議與 T102 一起做**(0010 是單純的 `CREATE TABLE`,
   沒有 0009 那種 `ALTER COLUMN TYPE` 的風險,但紅線要求就是要求)。
2. 留言者顯示的是識別碼,**一串 UUID 的留言板體驗確實不好**——
   這是誠實的過渡狀態,不是設計目標。等 portal 對申請書裁示。
3. 沒有分頁:留言少的時候沒問題,多起來要加。**不預先做**,
   但記在這裡,免得日後有人以為是漏掉的。
4. 沒有通知:被留言的專案擁有者不會收到任何提醒(平台沒有通知管道,
   與 T102 同一個限制)。
