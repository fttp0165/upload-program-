## 計畫(動工前成文,憲法第二條 2)

### 起因

`APP_VERSION` 現在是 **0.2.2**——那是 T116 決定的,而當時這一版的內容只有
「中文檔案上傳的 bug 修正 + 一個觀測補強」,patch 語意完全正確。

**但這一版後來長大了。** 目前累積的內容包含:

| 內容 | 性質 |
|---|---|
| T122 管理員指派入口 | **新功能** |
| T123 發布審核制度 | **新功能**,且**改變既有行為** |
| T124 專案留言板 | **新功能** |
| T125 版本作者屬名 | **新功能** |
| T115/T117/T118/T119/T120/T121 | bug 修正、工具、文件 |
| migration 0009 / 0010 | 🟡 兩個 |

### 為什麼是 0.3.0 而不是 0.2.2

SemVer 在 0.x 的慣例:**新功能與行為變更都升 minor**。

而且這一版有一件比「新功能」更重的事:
🔴 **`POST /v1/releases/{id}/publish` 的語意改了**——原本是「發布,馬上可下載」,
現在是「送審,等管理員核准」。同一條端點、同樣回 200,**結果完全不同**。

用 0.2.2 發這一版,等於對看 Release 頁的人說「這只是小修正」,
而他下一步就會發現自己發布的東西沒人下載得到。**版本號會說謊。**

### 為什麼不重發 v0.2.1

第八條 5:同一個版本 tag 不重發。v0.2.1 已發布且已部署到 VM。

### 順帶:0.2.2 這個號碼就此跳過

它從未被打成 tag、從未發布,只在分支上當過幾個小時的常數值。
**跳號不留洞**——SemVer 沒有「號碼必須連續」的要求,
而硬要發一個 v0.2.2 只為了不跳號,是為了整齊而發版。

### 影響範圍

`app/version.py` 一行。文件:任務表、本日誌。**對現有資料的影響:🟢 不動資料。**

### 為什麼不寫新測試(憲法第三條 4)

版本號的既有測試全部**讀同一個常數**再比對畫面,改常數後自動驗新值
(T68 把單一真相收在 `app/version.py` 的用意)。
再寫一條 `assert APP_VERSION == "0.3.0"` 只是把同一個字面值抄第二遍。

### 驗收標準

1. `APP_VERSION == "0.3.0"`;
2. 全站測試全綠;`ruff check` 乾淨;
3. CI 三 job 綠燈。

### 回滾方式

純常數、無 migration:改回字串即可。
