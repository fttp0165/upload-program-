## 計畫(動工前寫,第二條 2)

### 目標

`app/version.py` 的 `APP_VERSION` 由 `0.2.1` 改為 **`0.2.2`**,並更正任務表裡
**已經過期的版本號記載**。

### 為什麼(這是一次被過期文件誤導的發版)

發版規劃原本寫「tag `v0.2.1`、`APP_VERSION` 已是 0.2.1 不需改」,依據是
`docs/任務表.md` 的「三個版本號現在各在哪裡」表:

```
| GitHub 最新 tag | v0.2.0 | 指向 c504b1c,不含 T81 / T82 |
```

🔴 **實際上 `v0.2.1` 早就發布過了**,指向 `568014b`(T87/T88 合併後的 main)。
所以:

1. 這批(T89–T93)**不能**用 `v0.2.1` —— 第八條 5:同一個版本 tag 不重發。
2. 走 **`v0.2.2`**,而第八條 4 要求常數在打 tag **之前**隨 PR 改好。

⚠ **代價已經發生**:VM 上照原計畫執行了換版,拉到的 `v0.2.1` 是 T87/T88 那一版
——**不含這批改動**。沒有造成故障(它是合法的較舊版本,且容器本來就在跑它),
但「照著文件做,部署了一個不是預期內容的版本」正是第七條存在的理由。

### 影響範圍

- `app/version.py`(`0.2.1` → `0.2.2`)
- `docs/任務表.md`:更正「三個版本號」表(第二條 5 回寫),並記錄本任務

**對現有資料的影響:🟢 不動。** 無 migration、無欄位。

### 為什麼不寫新測試(第三條 4)

既有的版本號測試全部讀同一個常數(T68 的單一真相),再寫一條
`assert APP_VERSION == "0.2.2"` 只是把字面值抄第二遍、抓不到任何錯 ——
與 T83 同樣的理由。首頁顯示與 `main.py` 的一致性已有防漂移測試釘住。

### 驗收標準

1. `APP_VERSION == "0.2.2"`,全套測試綠。
2. 任務表的版本號表與 GitHub 實況一致(v0.2.1 已發、指向 568014b)。
3. tag `v0.2.2` 推上後,CI 的 publish job 推出 `ghcr.io/fttp0165/upload-program:v0.2.2`。

### 回滾方式

改回常數即可;tag 一旦推出則依第八條 5 不重發,改發下一個 patch 版。
