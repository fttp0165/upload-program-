## 計畫(動工前寫,第二條 2)

### 目標

`APP_VERSION` 由 `0.2.2` 改為 **`0.2.3`**,把 **T89–T96** 一次發成同一版。

### 為什麼(v0.2.2 從未推出 tag,而 main 已經多了 T96)

- `v0.2.2` 的常數在 T94 就備好了,但 **tag 一直沒推**(本 session 的憑證推 tag 回 403,
  由 Benny 手動執行,而在那之前 T96 先合併進了 main)。
- 於是 main 的內容 = T89–T95(原定 v0.2.2)**+ T96**。
  🔴 這時候推 `v0.2.2`,tag 會指到**含 T96** 的 commit,而常數與 Release 都說 0.2.2
  ——正是第八條 4 要防的「tag 與內容對不起來、對使用者說謊」。
- Benny 裁示:**發 0.2.3,一版含 T89–T96**(少發一次版、VM 只換一次)。

⚠ `v0.2.2` 這個版號**就此跳過,永遠不會存在**。這是誠實的結果:
它的內容沒有單獨出貨過,硬要補發一個指向舊 commit 的 tag 只會多一份沒人跑過的版本。

### 影響範圍

- `app/version.py`(`0.2.2` → `0.2.3`)
- `docs/任務表.md`(「三個版本號」表 + 本任務列)

**對現有資料的影響:🟢 不動。** 無 migration。

### 為什麼不寫新測試(第三條 4)

同 T83 / T94:既有版本號測試全部讀同一個常數(T68 的單一真相),
再寫 `assert APP_VERSION == "0.2.3"` 只是把字面值抄第二遍、抓不到任何錯。

### 驗收標準

1. `APP_VERSION == "0.2.3"`,全套測試綠。
2. tag `v0.2.3` 推出後,CI publish 推 `ghcr.io/fttp0165/upload-program:v0.2.3`。
3. VM 換版後首頁側欄顯示 `upload-program v0.2.3`。

### 回滾方式

改回常數即可;tag 一旦推出依第八條 5 不重發。
