## 結果

### 盤點的兩個發現決定了這個任務的形狀

1. **權限模型與 API 早就齊備**(`Project.visibility` / `ProjectMember` / `ProjectRole` /
   `require_project_read` / `PUT+DELETE /v1/projects/{slug}/members` / 稽核字彙
   `member.set`、`member.remove`)—— **缺的只是介面**。
   從零設計一套權限會做出第二套規則,而兩套規則遲早分岔 —— 那是 private 專案外洩的起點。
2. 🔴 **「ADMIN 都看得到」施工前就已經成立,但沒有任何測試**
   (只靠 `security.py:302` 的 `or identity.user.is_admin` 與 `queries.py:32` 兩行)。
   使用者明確要求的行為卻沒有守門 —— 下一次有人「優化」那兩行時,不會有東西攔住他。
   本次補了 3 條。

### 為什麼搜尋是「純 HTML 的 GET 表單」

本專案的表單一律零 JS(T44 的決定,CSP `default-src 'self'` 擋 inline script)。
搜尋做成 GET 表單回本頁(`?member_q=`)+ 候選清單各自一個 POST 按鈕,
不需要 JS、不需要新端點、也不會因為 CSP 而壞掉。

### 🔴 搜尋是本任務唯一的新外洩面,五條約束逐一釘住

| 約束 | 測試 |
|---|---|
| 空白 `q` 不列全部 | `test_空白搜尋不列出全部` |
| 最多 5 筆 | `test_搜尋最多五筆` |
| 只回 active | `test_搜尋只回已開通者且不含email`(pending 那半) |
| 絕不回 email(L1b 第 14 條) | 同上(email 那半) |
| 只有 owner 能用 | `test_非擁有者看不到權限區塊` |

### 🐛 施工中的一個真實風險(自己造成、自己抓到)

重構 API 去共用 `members.py` 時,第一版用「字串位置」定位要替換的區塊,
結果 `if payload.user_id == project.owner_id:` **在 `transfer_owner` 裡也有一行**,
於是那支處理器被吃掉 —— `test_ownership.py` 立刻紅(`'OwnerTransfer' object has no
attribute 'role'`)。已 `git checkout` 還原後改用函式範圍內的精確區塊替換。

⚠ 值得記下來的不是「我改錯了」,而是:**既有測試在 30 秒內抓到一個我看不見的破壞**。
那 41 條專案/擁有權/稽核的測試就是為此存在的。

### 遺留問題與後續建議

1. **owner 轉移沒有介面**(API 早就有 `project.transfer_owner`)。
   現在「把專案交給別人」還是只能打 API —— 值得另立任務。
2. 搜尋只比對**顯示名稱與識別碼**。顯示名稱來自 L1 快取,對方**沒登入過就沒有名字**
   ——畫面上已寫明「對方需先登入過一次」,但這仍是使用者會撞到的第一個困惑。
3. 沒有「批次加人」。單一內部平台、一個專案幾個人,先不做。
