# T98:CI 建置遇到失效的層快取時自動重試

**建立日期:** 2026-08-25 06:15
**最後更新:** 2026-08-25 06:15
**版本:** v1.0
**任務編號:** T98

---

## 計畫(動工前寫,第二條 2)

### 現象

`v0.2.3` 的 tag 推上後,CI 的 **`Build image` 第一步就死**(32 秒),
於是 Trivy 與 `Push GHCR` 全部 skipped —— **發版被擋在最後一哩**。

```
ERROR: failed to build: failed to solve: failed to compute cache key:
failed to copy: httpReadSeeker: failed open: could not fetch content descriptor
sha256:48579d87…(application/vnd.oci.image.layer.v1.tar+gzip) from remote: not found
```

### 根因(不是我們的程式)

本機(VM)的層快取指向一個**已經不存在於 registry 的 base image layer**。
T93 加了 `--pull` 之後,base image 的 manifest 會被更新,而舊 manifest 引用的 blob
可能已被上游/鏡像回收 —— 此時 buildkit 想重用快取層,卻抓不到它的內容。

⚠ **與 T93 那次的關係:** `--pull` 是對的(它讓我們拿到修補過的 base image),
但它也讓「本機快取」與「registry 現況」更容易對不上。這是那個決定的**已知副作用**,
不是它的錯誤。

### 做法

`Build image` 那一步加一層 fallback:第一次失敗就**以 `--no-cache` 重試一次**。

```
docker build --pull -t upload-program:ci . || {
  echo "::warning::建置失敗,可能是層快取指向已消失的 base image layer;以 --no-cache 重試"
  docker build --pull --no-cache -t upload-program:ci .
}
```

🔴 **這不會遮蓋真正的建置錯誤**:程式壞掉的話,第二次一樣會失敗,job 照樣紅。
它只在「第一次失敗」時多花約 1–2 分鐘,換掉「發版被環境問題擋死」這個結果。

⚠ **本次的 `v0.2.3` 不會因為這個修正而變綠** —— 重跑會用 tag 那個 commit 的
workflow 檔案(不含本修正)。當下的解法是在 VM 上 `docker builder prune -f`
再重跑;本任務要的是**下一次不必靠人記得去清快取**。

### 影響範圍

- `.github/workflows/ci.yml`(build 與 publish 兩處的 `docker build`)

**對現有資料的影響:🟢 不動。** 只有 CI 設定。

### 驗收標準

1. CI 綠(正常路徑不變)。
2. fallback 的訊息會出現在 job summary 的 warning(真的觸發時看得到)。
3. 🔴 掃描門檻、image tag 規則一字未改。

### 為什麼不寫新測試(第三條 4)

CI 的建置環境無法在本機重現(這個容器沒有 docker daemon)。
唯一誠實的驗證是 CI 本身跑過一次;宣稱「測過」會是假的。

### 回滾方式

`git revert`;移除 fallback 即回到現行行為。

---

## 結果

### 異動檔案

| 檔案 | 改了什麼 |
|---|---|
| `.github/workflows/ci.yml` | `Build image`(build job)與 publish job 的 `docker build` 各加一層 `--no-cache` fallback |

### 測試

```
540 passed        # 未受影響(只改 CI 設定)
ruff check .      # All checks passed!
```

🔴 **fallback 本身只能由 CI 驗證** —— 這個環境沒有 docker daemon。
真正的證據是下一次 build 的 job log(觸發時會有 `::warning::`)。

### 對現有資料的實際影響

🟢 **不動。**

### 遺留問題與後續建議

1. 本次 `v0.2.3` 仍需人工處置:VM 上 `docker builder prune -f` + 重跑那一輪。
2. 更根本的做法是**把 base image 鎖成 digest**(`python:3.12-slim@sha256:…`):
   那樣「manifest 換了而舊 blob 被回收」就不會發生。代價是每次 base image 更新
   都要人工改 digest —— 而 T93 才剛證明「不更新 base image」會累積 CVE。
   兩者的取捨值得另開任務討論,不在本次修。
