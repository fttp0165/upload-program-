### 為什麼是「通則」而不是申請例外

契約 §4.2a **L1b 通知用信箱**(2026-08-12 Benny 裁決 A 案通則化)明文
「不必另外申請」。本任務逐條落地它的條件:

| 條件 | 落地方式 |
|---|---|
| 只從本人 ID token 取得 | `verified_email(claims)`;**不查 Admin API**(T73 仍未裁示) |
| 🔴 只信 `email_verified=true` | `is not True` 一律回 None ——**缺席不等於通過** |
| 每次登入覆寫(含成 NULL) | 與 T59 `display_name_cache` 同一條路徑、同一個判斷 |
| 🔴 不得顯示在任何頁面 | `/admin`、`/admin/users`、`/issues` 三頁掃描斷言 |
| 🔴 不進 log | 本服務 logger 的掃描斷言(排除第三方) |
| 🔴 不得作 join key / 授權 | 查詢一律以 `sub` / `platform_role`;寄信只是 `SELECT notify_email` |
| nullable + 清除工具 | `tools/purge_notify_email.py`(整批清空,理由同 `purge_name_cache.py`) |
| 寄信失敗不得阻斷 | `Mailer.send()` **絕不拋**,只回 True/False;且在回應之後才跑 |

### ⚠ 施工中改正的三件事(依 CI 紅線說明)

1. **「`/v1/me` 不得含 email」這個斷言是我寫錯的。** `MeOut.email` 來自 **IdP claims**
   (schema 註解明寫「由 IdP 即時提供,不存在業務庫」),而且是呼叫者**自己**的信箱;
   L1b 管的是**快取副本**。照錯的斷言改程式,會為了讓測試綠而拆掉一個合法且既有的功能。
   改為釘住「`notify_email` 這個欄位名不得出現在 API 回應與 OpenAPI」。
2. **log 測試原本用 `DEBUG`,那會打開 aiosqlite 驅動層的 SQL 參數輸出** ——
   地址當然在那裡,而那不是我們的程式在記 log。改用 `INFO`(正式環境的層級)並排除第三方。
   🔴 **由此得到一條新結論:正式環境不得把 `LOG_LEVEL` 開成 DEBUG** ——
   開了,信箱就會隨 SQL 參數進 log,而契約明文禁止。已寫進 `.env.example`。
3. 🐛 **側欄同時反白兩個項目**(devserver 截圖當場抓到):「回報問題」(`/issues/new`)
   與新增的「回報管理」(`/issues`)active 條件都是 `startswith('/issues')`。
   已收窄,並加一條「任何頁面反白項目 ≤ 1」的測試 —— 那條測試涵蓋的是整個側欄,
   不只這兩項。
