## 為什麼這樣做(決策與捨棄的替代方案)

1. **三態而不是四態**:「退回」直接回 draft 並把理由存 `review_note`,不設獨立的
   rejected 狀態——rejected 與 draft 對作者的可做動作完全相同(改、重送),
   多一個狀態只多一組轉移規則。代價:重送時清掉理由(舊理由是上一輪的事)。
2. **`/publish` 保留為 submit 別名且冪等**:既有腳本重跑不該爆炸;
   對 published 回 200 原樣,沿襲舊行為。
3. **email 走 §4.2b 而不是 Admin API**:「跟 Keycloak 要」唯一合規的路是本人登入
   token 的 `email` claim(§4.2a 第 1 條禁止 Admin API)。訂閱 **opt-in 預設關**
   ——§4.2b 第 4 條要求「已明示訂閱」,替管理員預設打開不是明示。
4. **通知同步送、失敗吞掉只記 log**:通知是加分不是流程;fire-and-forget 的
   背景工作在測試裡無法決定性斷言,同步 + 短逾時(5 秒)換取可測與簡單。
5. **管理員可自審**:平台現實是管理員只有一兩位,禁止自審會把管理員自己的專案
   鎖死;稽核留有「誰送審、誰核准」。
6. **退回理由不進稽核**:AuditEvent 紅線——`target_label` 不收使用者自由文字。

## 遺留問題與後續建議

1. **流程風險不是程式問題**(已寫進計畫 §10):通知要生效,管理員得登入一次
   (email 進快取)並在佇列頁打開訂閱;上線後版本若常態卡審,檢討流程與人力。
2. SMTP 主機資訊要向 portal/MIS 要(`.env` 三個變數);未設定前唯一提醒是
   管理總覽待辦區。
3. §4.2b 的孤兒清除輸入(sub 名單)依契約由平台管理員匯出——本工具的 `--all`
   不需要名單,個案 `--sub` 需要。
4. 發版時(第八條)Release content 記得標 🟡 有 migration + 新增 `.env` 變數。
