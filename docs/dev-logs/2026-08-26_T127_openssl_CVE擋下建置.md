## 計畫(動工前成文,憲法第二條 2)

### 起因

PR #33(v0.3.0)CI 三 job:

- ✅ `測試 / lint / 文件同步` — 綠
- ❌ **`Build image + Trivy 掃描` — 紅**
- ⏭ `Push GHCR(僅版本 tag)` — 跳過

Trivy 報告(`upload-program:ci (debian 13.6)`,Total: 3,HIGH: 3):

```
libssl3t64              CVE-2026-14456  HIGH  fixed  3.5.6-1~deb13u2 → 3.5.7-1~deb13u2
openssl                 CVE-2026-14456  HIGH  fixed  3.5.6-1~deb13u2 → 3.5.7-1~deb13u2
openssl-provider-legacy CVE-2026-14456  HIGH  fixed  3.5.6-1~deb13u2 → 3.5.7-1~deb13u2
```

三筆是**同一個 CVE 的同一個來源套件**(openssl),Trivy 依二進位套件分列。

**與本 PR 的 diff 無關**——runtime stage 從頭到尾沒有 `apt-get`,
OS 套件原封不動來自 `python:3.12-slim`。main 現在建置也會紅。

### 根本原因:這次**不是** T117 的快取問題

T117 才剛加上 `--pull`,而且它確實生效了:掃到的是 `3.5.6-1~deb13u2`
(Debian 13.6 的當期版本),不是某個被釘住的老版本。

真正的原因是**上游 `python:3.12-slim` 尚未重建**:
Debian 已經發出修好的 `3.5.7-1~deb13u2`,但官方 image 還沒把它併進去。
`--pull` 只能保證「同一個 tag 取到上游最新的那份」,**上游沒動,我們就沒得取**。

### 處置:T117 已經預先寫好這一步

T117 日誌〈如果 `--pull` 之後還是紅〉那一節:

> 代表上游 `python:3.12-slim` 尚未重建。那時的處置是在 runtime stage 明確
> `apt-get update && apt-get upgrade -y` 受影響套件——**但先不做**:
> 多裝一層 apt 會讓 image 變大、且在上游修好後變成長期贅生物。先讓 CI 告訴我們。

CI 現在告訴我們了。本任務執行的就是那個已經想過一輪的方案。

### 🔴 仍然不用 `.trivyignore`,理由與 T82 / T117 同一條

本服務**散布可執行檔**,掃描是自我加嚴的一環;把掃描調鬆來換綠燈是拿紅線換方便。

值得寫下來的是:這一次「調鬆」的誘惑比前兩次都大,因為**這個 CVE 對我們幾乎確定不適用**
——CVE-2026-14456 是 OpenSSL **QUIC 伺服器**的記憶體無限成長,而本服務沒有任何
QUIC 伺服器路徑(TLS 在 gateway 終結,容器內只有 gunicorn 的明文 HTTP;
OpenSSL 只被 Python 用在**對外的 client** 連線:JWKS、MinIO)。

**但「我判斷用不到」不是關掉掃描的理由**:
判斷可能錯(誰能保證某個相依日後不會走上那條路?),而 `.trivyignore` 一旦寫下去
就會留在那裡,下一個人只會看到一行 CVE 編號,看不到今天這段推理。
既然上游**已經有修好的版本**,拿到它才是正解——`--ignore-unfixed` 一直開著,
它出現在報告裡就代表「有得修」。

### 做法:只升 openssl 家族,不做 `apt-get upgrade -y` 全套

```
apt-get install -y --no-install-recommends --only-upgrade \
    libssl3t64 openssl openssl-provider-legacy
```

**為什麼不整包 upgrade:** 全套 upgrade 會把 base image 裡每個套件都可能換版,
等於讓「這個 image 裝了什麼」隨建置時間漂移——那正是 T82 遺留問題(相依不可重現)
的 OS 版本。只升被點名的那個來源套件,影響面看得見、之後要拿掉也一眼看得出拿掉什麼。

**放在 runtime stage**:Trivy 掃的是最終 image(runtime),builder stage 只有
`/opt/venv` 被複製過去,它的 OS 套件不會進最終 image。
必須在 `USER app` 之前(apt 要 root)。

結尾 `rm -rf /var/lib/apt/lists/*`,不讓套件索引留在 image 裡。

### ⚠️ 一個誠實的風險:apt 在 CI 的網路可能不通

Dockerfile 第 12–16 行有一段自己的歷史:2026-07-30(run #85)builder stage
的 `apt-get` 在 self-hosted runner 上**直接炸**,原因是「apt 套件庫從該網路不可達」,
當時的修法是**把 apt 整個拿掉**。

本次要把 apt 加回來,**有可能撞上同一堵牆**。

- 若撞牆:build 會**大聲失敗**並印出 apt 的錯誤,不會靜悄悄產出仍有洞的 image。
  ⚠️ **刻意不加 `|| true`**——吞掉失敗等於發布一個自己以為修好的 image,
  比紅燈危險得多。
- 撞牆之後的下一步(**本任務不預先做**):要嘛在 VM 的 dockerd 設定 apt proxy /
  內部鏡像,要嘛就只能等上游重建。那是網路與平台的事,要 Benny 裁示,
  不是在 Dockerfile 裡繞。

### ✅ 若上游先一步重建了

那 `--only-upgrade` 會發現沒有更新的版本可裝、**安靜地成功**(不是失敗)。
所以這幾行在上游修好之後不會弄壞任何東西,只會變成贅生物——
到時候拿掉它,並在此日誌補一筆。

### 影響範圍

`Dockerfile`(runtime stage 加一個 `RUN`)、任務表、本日誌。

**對現有資料的影響:🟢 不動資料**(容器建置,不碰程式邏輯與資料庫)。

### 驗收標準

1. CI 的 `Build image + Trivy 掃描` job 轉綠(HIGH/CRITICAL 為 0);
2. 既有的三道 image 護欄仍過:non-root UID 1000、`/health` 60 秒內 200、
   `/ready` 無相依時 503;
3. image 大小仍在 300 MB 目標內(apt 只升版不新增套件,理應幾乎不變);
4. 全站測試不受影響(本次不動 `app/`)。

### 回滾方式

移除該 `RUN` 即可(🟢 無 migration、無資料)。
但那等於把洞放回來,且 CI 會立刻再紅——**回滾的正當理由只有一個**:
上游已重建、這幾行變成贅生物。

## 結果

### ❌ 方案失敗,已回退。而且失敗的方式比預期的糟

計畫段的〈⚠️ 一個誠實的風險〉猜對了一半:apt 確實不通。
**但猜錯了失敗的形狀**——我預期「撞牆會大聲失敗」,實際上它**安靜地成功了**。

CI run(job 98090706297)第 9 層的原始輸出:

```
#9 [runtime 2/8] RUN apt-get update && apt-get install -y --only-upgrade libssl3t64 ...
#9 30.66 Ign:1 http://deb.debian.org/debian trixie InRelease
#9 37.67 Err:1 http://deb.debian.org/debian trixie InRelease
#9 37.67   Could not connect to debian.map.fastlydns.net:80 (199.232.114.132), connection timed out
#9 37.70 W: Failed to fetch http://deb.debian.org/debian/dists/trixie/InRelease
#9 37.70 W: Some index files failed to download. They have been ignored, or old ones used instead.
#9 37.73 libssl3t64 is already the newest version (3.5.6-1~deb13u2).
#9 37.73 0 upgraded, 0 newly installed, 0 to remove and 0 not upgraded.
#9 DONE 37.7s                    ← ✅ 建置「成功」
```

### 🔴 這一層有兩個發現,第二個比第一個重要

**發現一:deb.debian.org 從 CI 容器網路仍然不可達。**
run #85 那堵牆還在,而且不是只擋 builder stage——`trixie` / `trixie-updates` /
`trixie-security` 三個 suite 全部 connection timed out。

**發現二(重要得多):`apt-get update` 抓不到索引時只印 `W:`,exit code 仍是 0。**

於是後面的 `--only-upgrade` 拿 base image 裡的**舊索引**去比對,理直氣壯地回報
「已經是最新版」,整條 `&&` 鏈**成功**,建置產出一個**看起來已修好、實際一個位元組都沒動**的 image。

計畫段那句「🔴 刻意不加 `|| true`:吞掉失敗等於發布一個自己以為修好的 image」
——那條護欄立意正確,**但守錯了地方**:我防的是「指令回傳非 0 而我把它吞掉」,
而 apt 根本不回傳非 0。**它自己把我的護欄繞過去了。**

**真正抓到這件事的是 Trivy**,不是我寫的任何一道保險。
如果那一版恰好上游已重建、Trivy 剛好轉綠,我會**永遠不知道**這幾行從未生效,
而它會以「openssl 有在升」的身分留在 Dockerfile 裡不知道多久。

📌 **可帶走的一課(不限本任務):`&&` 鏈只證明「每個指令都自稱成功」,
不證明「事情做到了」。** 對「取得外部資源」這類步驟,必須自己驗結果,
不能把 exit code 當成事實。這與 T84、T124 的假綠是同一個病:
**為錯的理由而綠**,只是這次的載體從測試換成了 shell。

### 已回退

Dockerfile 的那段 `RUN apt-get` 已移除——留著只會每次建置多花 37 秒、
什麼也沒做,還讓下一個讀 Dockerfile 的人以為 openssl 有在升。
原地留一段註釋說明為什麼不要再試,以及**日後網路若開通、要把 apt 加回來時
必須自己驗 `apt-get update` 的結果**。

### 🔴 結論:這條紅燈我方修不掉,需要裁示

三條路,**沒有一條在本 repo 裡**:

| 選項 | 內容 | 代價 |
|---|---|---|
| **A. 等上游** | 等 `python:3.12-slim` 重建併入 `3.5.7-1~deb13u2` | 🕐 ETA 未知(通常數天);期間 **v0.3.0 發不出去** |
| **B. 開通 apt(建議)** | 讓 CI VM 的**容器網路**連得到 `deb.debian.org`,或指向公司內部 Debian 鏡像 | 需網路/平台側處理;**一勞永逸**——下一個 OS 層 CVE 必然還會來 |
| **C. 放寬掃描** | `.trivyignore` 記下這個 CVE | 🔴 T82 / T117 已立過兩次界線,**不建議**;本專案散布可執行檔 |

**建議 B**,以 A 為「若上游先一步重建就自然解除」的備援。
理由:本次是**第三次**因 base image 的 OS 套件被擋(T117 util-linux、本次 openssl),
而 runtime stage 沒有 apt 就代表**我方對 OS 層 CVE 完全無能為力**,只能等上游。
把 apt 打通不是為了這一個 CVE,是為了讓「上游慢半拍」不再等於「我們發不出版」。

⚠️ **影響發版**:`publish` job `needs: build`,Trivy 紅 → GHCR 推不上去 →
**v0.3.0 的 tag 打了也不會有 image**。這條紅燈是 v0.3.0 的硬阻塞。

### 對現有資料的實際影響

🟢 **無**(全程只動 Dockerfile 與文件)。

### 遺留問題

1. 🔴 **CVE-2026-14456 尚未修掉**,等 A 或 B。
2. 📌 若日後採 B(apt 開通),把 apt 加回來時**必須驗 `apt-get update` 的結果**,
   不能重蹈本次覆轍——Dockerfile 原地註釋已寫明。
