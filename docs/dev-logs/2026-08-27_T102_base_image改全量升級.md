**建立日期:** 2026-08-27 07:00
**最後更新:** 2026-08-27 07:00
**版本:** v1.0
**任務編號:** T102

---

## 計畫(動工前寫,第二條 2)

### 現象

T101 那一輪 CI:測試 / lint / 文件同步 ✅(574)、image 建置 ✅、non-root ✅、
冒煙 ✅,**只有 Trivy 紅**:

```
Total: 3 (HIGH: 3, CRITICAL: 0)
libssl3t64 / openssl / openssl-provider-legacy
CVE-2026-14456  OpenSSL QUIC server 記憶體無上限成長 → DoS
Installed 3.5.6-1~deb13u2 → Fixed 3.5.7-1~deb13u2
```

### 🔴 根因不是這支 CVE,是 T93 的白名單設計

T93 修 util-linux 那 36 條時,選擇**明列八個套件**升級,理由寫在 Dockerfile 註解:
「明列讓『這次修了什麼』在 diff 上看得見;`upgrade` 會把不相關的套件一起動,
出問題時分不出是誰。」並在 dev-log 寫下
**「日後其他來源的 CVE 就再開一個任務、再加一行」**。

⚠ **三天後就來了第二次(openssl)。** 那不是巧合,是設計在收費:

| 白名單的代價 | 實際發生的事 |
|---|---|
| 每支新 CVE 都要改程式 | T93(util-linux)→ T102(openssl),三天內兩次 |
| 每次都要一輪 CI(約 4 分鐘)+ 一個任務編號 | 而 base image 的 CVE 是**持續發生的環境漂移**,不是偶發事件 |
| 🔴 **紅燈變成常態** | 常態紅燈的下一步是「先合併再說」—— 那才是真正的風險 |

**T93 的判斷在當時是對的**(那時要證明 apt 升級這條路走得通、要看得見改了什麼)。
現在證據夠了:走得通、而且會反覆發生。所以換設計。

### 做法

`apt-get upgrade -y` 全量升級 OS 套件,並**保留 T93 最有價值的那一半**:

```
RUN for attempt in 1 2 3; do
      apt-get update && apt-get upgrade -y --no-install-recommends && break
      ...換 CDN 節點重試(T93 第五輪的教訓:Debian CDN 節點索引不一致)
    done
    && rm -rf /var/lib/apt/lists/*
    # 🔴 驗證:升級後不得還有「可升級」的套件
    && apt-get update && apt-get -s upgrade | grep -q '^0 upgraded' || exit 1
```

🔴 **驗證的形式從「比對某個版本號」換成「升級後不得有殘留」** ——
後者不必知道有哪些 CVE、不必維護清單,而且同樣擋得住 T93 第五輪那個
「`apt-get` 回 0 卻什麼都沒做」的無聲失敗(那次正是靠驗證擋下的)。

### 放棄的東西(誠實記下)

- **「diff 上看得見改了什麼」不再成立。** 全量升級的 diff 只有一行,
  升了哪些套件要看 build log。**這是這次交換掉的東西**,不是被忽略的。
- 換到的是:base image 的 CVE 不再需要人逐支追、不再需要為每一支開任務。

### 影響範圍

- `Dockerfile`(runtime 階段那一段 RUN)

**對現有資料的影響:🟢 不動。** 無 migration;image 會大一些(升級後的套件)。

### 驗收標準

1. CI 的 `Build image + Trivy 掃描` 轉綠(**唯一有效的證據** ——
   這個環境沒有 docker daemon,本機驗不了)。
2. non-root / 冒煙 / image 大小三項維持綠(全量升級不得動到 UID 或啟動)。
3. 掃描門檻一字未改(`--severity HIGH,CRITICAL --exit-code 1 --ignore-unfixed`)。

### 為什麼不寫新測試(第三條 4)

同 T93 / T98:CI 的建置環境無法在本機重現。宣稱「測過」會是假的。

### 回滾方式

`git revert`。⚠ 回滾會退回白名單,而白名單**現在少了 openssl** —— 真要回退,
記得把 openssl 那三個套件補進清單,否則 Trivy 立刻紅回來。
