## 計畫(動工前寫,第二條 2)

### 目標

`APP_VERSION` 由 `0.2.3` 改為 **`0.2.4`**,把 **T98–T102** 發成同一版。

### 為什麼是 0.2.4(不是 0.2.3、也不是 0.3.0)

- `v0.2.3` **已經發布過**:tag 指向 `46d265f`,內容是 T89–T96。
  第八條 5 同版不重發,所以這一批必須走新的版號。
- 為什麼是 **patch** 而不是 minor:這一批沒有改變任何既有介面的契約。
  T99 是新增功能(通知信 + 側欄入口)、T100/T101 是把既有權限模型接上介面、
  T102 與 T98 是建置面。唯一的行為**收窄**(T101 的 `PATCH` 收到 `visibility`
  要求 owner)是修補一條外洩路徑,不是使用者會依賴的介面。
- 第八條 4:常數必須在**打 tag 之前**隨 PR 改好。本任務就是那一步。

### 影響範圍

- `app/version.py`(`0.2.3` → `0.2.4`)
- `docs/任務表.md`(「三個版本號」表 + 本任務列 + 進度計數)

**對現有資料的影響:🟢 本任務不動。**
⚠ 但**這一版整體是 🟡** —— 同批的 T99 含 migration `0009_notify_email`(加 nullable 欄位、
可 down)。🔴 換版時必須跑 `alembic upgrade head`,這件事寫進 Release 的「部署注意」。

### 為什麼不寫新測試(第三條 4)

同 T83 / T94 / T97:既有版本號測試全部讀同一個常數(T68 的單一真相),
再寫 `assert APP_VERSION == "0.2.4"` 只是把字面值抄第二遍、抓不到任何錯。

### 驗收標準

1. `APP_VERSION == "0.2.4"`,全套測試綠、`ruff` 乾淨。
2. PR #34 的 CI 綠(含 Trivy)。
3. tag `v0.2.4` 推出後,CI publish 推 `ghcr.io/fttp0165/upload-program:v0.2.4`。
4. VM 換版(**先 `alembic upgrade head`**)後首頁側欄顯示 `upload-program v0.2.4`。

### 回滾方式

改回常數即可;tag 一旦推出依第八條 5 不重發。
資料面的回滾是 `alembic downgrade -1`(migration `0009` 已 up→down→up 演練過)。
