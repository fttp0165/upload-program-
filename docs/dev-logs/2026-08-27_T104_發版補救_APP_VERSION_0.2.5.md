## 計畫(動工前寫,第二條 2)

### 發生了什麼(事實,已逐項核對)

| 項目 | 值 |
|---|---|
| `v0.2.4` tag 指向 | `6dabe7d` —— 即 PR #34 的合併,**PR #35 之前** |
| 該 commit 的 `APP_VERSION` | **`0.2.3`** |
| `main` 現況 | `5a5e866`,`APP_VERSION = 0.2.4` |
| tag 那輪 CI(run #256) | ✅ success → **`ghcr.io/fttp0165/upload-program:v0.2.4` 已推上 GHCR** |

🔴 於是存在一個叫 `v0.2.4` 的 image,而它的首頁會顯示 `v0.2.3` ——
**正是第八條 4 要防的「tag 與內容對不起來、對使用者說謊」**,而且換版驗證
(看側欄版號)會判成「換版失敗」,實際上是版號本身錯的。

### 為什麼不刪 tag 重推

1. **第八條 5:同一個版本 tag 不重發。** 原文的結論來自 v0.1.3 事故。
2. image 已經推上 GHCR。重推會讓**同一個 tag 在不同人手上是不同的東西** ——
   比錯一次更難查,因為兩邊都會說自己是 v0.2.4。
3. 刪除已發布的 tag 與 Release 是破壞性動作,而它換到的只是「版號數字比較漂亮」。

**所以走第八條 5 的既定解:發下一個 patch 版 v0.2.5。**
⚠ `v0.2.4` 這個 tag 保留不刪,但其 Release 說明須標明作廢並指向 v0.2.5
(不標的話,後來的人會照它部署,而它會裝上一個版號說謊的 image)。

### 目標

`APP_VERSION` 由 `0.2.4` 改為 **`0.2.5`**。內容與 v0.2.4 預定要發的完全相同
(T98–T103),差別只有版號 —— 這一版是**補救**,不是新功能。

### 根因(不是「誰不小心」)

三次卡在版本號上,形狀一次比一次糟:

| 次 | 任務 | 形狀 |
|---|---|---|
| 1 | T94 | 任務表寫錯最新 tag → VM 部署到不是預期內容的版本 |
| 2 | T97 | tag 沒推而 `main` 又前進了一個任務 → 版號與內容分家 |
| 3 | **本次** | PR 合併與 tag 的**時序**交錯 → **錯的 image 真的上了 GHCR** |

🔴 **前兩次的結論都寫成了「建議」,而建議不會執行自己。** 三次都是靠人臨場發現
(這次還是靠截圖裡那行 `6dabe7d` 才看見)。故本任務的遺留段把守門升為
**下一個要做的任務(T105)**,不再只是一句建議。

### 為什麼不寫新測試(第三條 4)

同 T83 / T94 / T97 / T103:既有版本號測試全部讀同一個常數(T68 的單一真相)。
⚠ **而這次要誠實講一句**:那個慣例對「常數與 tag 對不上」這類錯**本來就無效**——
它不是測試抓得到的東西,得由 CI 拿 GitHub 的 tag 來比。那正是 T105。

### 驗收標準

1. `APP_VERSION == "0.2.5"`,全套測試綠、`ruff` 乾淨。
2. PR 的 CI 綠(含 Trivy)。
3. **合併後**在 `main` 上確認 `grep APP_VERSION` 得到 `0.2.5`,**才**打 tag。
4. tag `v0.2.5` 的 CI 綠 → `ghcr.io/fttp0165/upload-program:v0.2.5`。
5. VM 換版(**先 `alembic upgrade head`**)後側欄顯示 `upload-program v0.2.5`。

### 回滾方式

改回常數即可。🔴 **v0.2.4 不會因此變成可用版本** —— 它的 image 版號永遠是錯的。
