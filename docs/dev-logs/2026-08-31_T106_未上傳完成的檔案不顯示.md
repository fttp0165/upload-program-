# T106:沒有上傳成功的檔案就不要顯示

**建立日期:** 2026-08-31 09:20
**最後更新:** 2026-08-31 09:45
**版本:** v1.1
**任務編號:** T106

---

## 計畫(動工前寫,第二條 2)

### 現象(Benny 截圖回報)

專案頁的檔案清單出現:

```
[下載 dashboard.html]   binary · 0 bytes · 0 次下載
SHA-256:(空白)
固定連結 /upload/v1/projects/srrc/releases/latest/artifacts/dashboard.html/download
```

Benny:「沒有上傳成功的 就不用顯示了」。

### 根因

`Artifact.upload_status` 有三態(`pending` / `ready` / `failed`)。

- **下載端點早就擋了**:`artifacts.py` 檢查 `upload_status is ready`,否則 404「尚未上傳完成」。
- **發布門檻也早就擋了**:`releases.py` 的三類齊備、配額計算都只算 `ready`。
- 🔴 **只有網頁的清單沒有過濾** —— `web.py` 三處直接把 `release.artifacts` 整包丟給模板。

於是使用者看到一個下載按鈕,按下去會 404。**畫面在承諾一件伺服器已經拒絕的事**,
而中間沒有任何東西告訴他那不是他的網路問題。

⚠ 順帶記一個獨立的疑點(不在本任務修):檔名是 `dashboard.html`,而本專案紅線是
**HTML 一律拒收**(magic bytes)。`0 bytes` + SHA-256 空白顯示這一列是
**PUT 剛建列、內容還沒寫進去就中斷**的殘留 —— 也就是拒收有生效,但**列先建了**。
本任務讓它不顯示;「殘留列要不要自動清掉」另立 T107 評估(見遺留)。

### 做什麼

| 頁面 | 現在 | 改成 | 為什麼 |
|---|---|---|---|
| 專案頁 `project.html` | 全列 | **只列 `ready`** | 檢視者面向。按了會 404 的按鈕不該存在 |
| 版本歷史 `releases.html` | 全列 + 「N 個檔案」含未完成 | **只列 `ready`**,計數同步 | 同上;計數不改的話會出現「3 個檔案」但只列 2 個 |
| 上傳頁 `upload.html` | 全列(有顯示狀態) | **維持全列** | 🔴 **刻意不過濾**:這是擁有者的作業面,他必須看得到「這個檔沒傳成功」才知道要重傳;藏起來會讓孤兒列變成沒有任何入口的幽靈 |

過濾邏輯集中成一個函式(`ready_artifacts()`),三處共用 —— 三份各寫一次的過濾條件
遲早分岔,而分岔的方向是「某一頁又開始顯示壞掉的檔案」。

### 影響範圍

- `app/routers/web.py`(專案頁、版本歷史頁傳入的清單)
- `app/templates/releases.html`(計數與迴圈)
- `app/queries.py`(新增 `ready_artifacts()`)
- `tests/test_artifact_visibility.py`(新增)

**對現有資料的影響:🟢 不動。** 無 migration —— 這是顯示層的過濾,
未完成的列仍然留在資料庫(刪除是另一件事,見遺留)。

### 驗收標準(先寫會失敗的測試)

1. 🔴 專案頁不出現 `upload_status != ready` 的檔名(紅起步)
2. 🔴 版本歷史頁同上,且「N 個檔案」不把它算進去(紅起步)
3. 上傳頁**仍然**看得到它(反向驗證:確認我沒有過濾過頭)
4. `ready` 的檔案照常顯示且下載連結還在(防止過度過濾)

### 回滾方式

還原三個檔案即可。🟢 沒有資料變更,不需要 migration 回滾。

### 測試(紅 → 綠)

先寫的四條裡**兩條紅起步、兩條一開始就綠**——後者是刻意的守門:

```
FAILED test_專案頁不顯示未上傳完成的檔案               ← 紅起步
FAILED test_版本歷史頁不顯示也不計入未上傳完成的檔案   ← 紅起步
PASSED test_上傳頁仍然看得到未完成的檔案               ← 防我過濾過頭
PASSED test_全部ready時三頁顯示不變                    ← 防我把好的一起濾掉
```

修完:`4 passed`;全套 **578 passed**(574 → 578)、`ruff check` 乾淨。

### 遺留問題與後續建議

1. ⚠ **殘留列本身沒有被清掉。** `dashboard.html` 那一列(0 bytes、SHA-256 空白)
   仍在 DB 與清單查詢裡,只是不顯示。要不要自動清理是另一個決定:
   - 清:PUT 失敗時直接刪列。乾淨,但**失敗原因也一起消失**,使用者看不到「為什麼傳不上去」。
   - 不清:留給擁有者在上傳頁自己刪(現況)。
   建議另立 **T107** 評估,**不在本任務內順手改** —— 它會動到上傳的錯誤路徑,
   而那條路徑正是 magic bytes 拒收的所在。
2. 🔴 **`dashboard.html` 這個檔名值得追一次。** 本專案紅線是 HTML 一律拒收,
   而它留下了一列 —— 目前的推斷是「拒收有生效,但列先建了」。
   要證實需要看 `artifacts.py` 的 PUT 順序(建列 → 寫檔 → 驗型 → 標 ready)。
   若順序是先建列,那每一次被拒收的上傳都會留下一列殘骸,**而使用者看到的是
   一個永遠 0 bytes 的檔案**。這與第 1 點是同一件事的兩面。
