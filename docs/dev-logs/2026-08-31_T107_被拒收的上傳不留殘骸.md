## 計畫(動工前寫,第二條 2)

### 根因(已在原始碼證實,不是推測)

`app/routers/artifacts.py` 的 PUT 順序:

```
1. 建 Artifact 列(size_bytes=0, sha256="", storage_key="")  ← await session.commit()
2. key = f"projects/.../{artifact.id}/{name}"                ← storage key 需要 artifact.id
3. 收串流 + magic bytes 判型
4. 失敗 → _mark_failed(status=failed),列留著
```

第 1 步**必須**在第 2 步之前(storage key 用 `artifact.id`),所以「先建列」本身
不是錯的設計。錯的是**失敗之後把列留下來**:

- `dashboard.html` 被 HTML 紅線擋下 → 留下一列 `failed` / 0 bytes / SHA-256 空白;
- T106 已讓它不顯示在檢視面,但**列還在**,而且**每一次被擋下的上傳都會再留一列**;
- 更糟的是 storage 裡可能有寫到一半的物件,而唯一指向它的那一列如果被使用者刪掉,
  那個物件就變成**沒有任何東西指得到的垃圾**。

### 決定:失敗即刪列(含 best-effort 刪 storage 物件)

⚠ **這個決定有代價,先寫下來**:刪了列,使用者就無法「事後在畫面上看到上次為什麼失敗」。

之所以判斷代價可以接受:

1. **失敗原因當下就回給呼叫端了** —— RFC 7807 的 `rejected-file-type` / `payload-too-large`
   / `checksum-mismatch`,含 `detected_type` 等欄位。使用者不是沒被告知。
2. **log 已經有一行** `上傳遭拒:型別不符`(含 artifact_id、detected、kind)。
3. 而留著的那一列**不會告訴任何人原因** —— 它只顯示 0 bytes。
   **一個不帶資訊的殘骸不是紀錄,是垃圾。**

🔴 同時補一件現在沒有的事:新增稽核動作 `artifact.upload_rejected`。
稽核的 `action` 欄位是 `String(64)` 而非 DB enum(`models.py:308` 的註解寫明
「刻意讓新增動作不需要 migration,因為阻力會讓人選擇不記」),所以**這一條零成本**。
於是「誰在何時試著傳了一個被擋下的檔」變成查得到的事 —— 那正是散布可執行檔的
平台會想知道的訊號(有人反覆試著上傳 HTML,值得看一眼)。

### 涵蓋哪些失敗路徑

| 路徑 | 現況 | 改成 |
|---|---|---|
| magic bytes 拒收(`_Rejected`) | `failed` 留列 | **刪列** + 稽核 |
| 超過單檔上限(`TooLarge`) | `failed` 留列 | **刪列** + 稽核 |
| SHA-256 不符 | 刪 storage + `failed` 留列 | **刪列** + 稽核 |
| 收完才發現超配額 | 刪 storage + `failed` 留列 | **刪列** + 稽核 |
| 其他例外(網路中斷等) | `failed` 留列 | **刪列** + 稽核 |

⚠ **`UploadStatus.failed` 這個狀態值保留不刪** —— DB 裡既有的殘骸列仍是這個值,
而且刪掉列舉值要 migration。它只是不再被寫入。

### 既有殘骸怎麼辦

新增 `tools/purge_failed_artifacts.py`:
- **預設 `--dry-run`**(只印出會刪什麼),要真的刪必須加 `--apply`;
- 只刪 `upload_status != ready` 的列,**一律不碰 ready**;
- 同步 best-effort 刪 storage 物件;
- 印出每一列的 project / release / filename,讓執行的人看得到自己在刪什麼。

🔴 這支工具會動正式資料,所以**執行前必須備份**(紅線),用法寫進 runbook。

### 影響範圍

- `app/routers/artifacts.py`(五條失敗路徑改走同一個 `_discard()`)
- `app/audit.py`(新增一個動作)
- `tools/purge_failed_artifacts.py`(新增)
- `tests/test_artifact_residue.py`(新增)
- `docs/換版runbook.md`(工具用法)

**對現有資料的影響:🟢 程式面不動資料、無 migration。**
⚠ 清理工具會刪列,但它是**手動、預設 dry-run、要求先備份**的獨立動作。

### 驗收標準(先寫會失敗的測試)

1. 🔴 被拒收的上傳**不留下任何 artifact 列**(紅起步)
2. 🔴 被拒收時寫下 `artifact.upload_rejected` 稽核(紅起步)
3. 超過單檔上限同樣不留列(紅起步)
4. **成功的上傳完全不受影響**(守門:別把好的一起刪掉)
5. 重傳同名檔案在前一次被拒收後仍然可以成功(守門:刪列不能擋住下一次)

### 回滾方式

還原 `artifacts.py` 與 `audit.py` 即可(🟢 無 migration)。
已經被刪掉的殘骸列不會回來 —— 但它們本來就不含任何資訊。

### 測試(紅 → 綠)

```
FAILED test_被拒收的上傳不留下artifact列    ← 紅起步
FAILED test_被拒收時留下稽核                ← 紅起步
PASSED test_超過單檔上限也不留列            ← 本來就沒問題(見下)
PASSED test_成功的上傳完全不受影響          ← 守門
PASSED test_拒收之後重傳同名檔案仍然成功    ← 守門
```

⚠ **第三條一開始就是綠的,誠實記下來**:超過上限的請求在 `Content-Length` 階段
就被擋掉了,**列根本還沒建**。我原本以為它會紅 —— 寫測試前的推測錯了一半,
而那正是先寫測試的價值:它把「我以為的失敗路徑」與「實際的失敗路徑」分開了。
這條測試留著當守門(chunked 上傳沒有 Content-Length,走的是收完才發現那條路)。

修完:`5 passed`;全套 **583 passed**(578 → 583)、`ruff check` 乾淨。

### 遺留問題與後續建議

1. ⚠ `UploadStatus.failed` 這個列舉值**不再被寫入**,但保留不刪 ——
   DB 裡既有的殘骸列仍是這個值,而刪列舉值要 migration。清乾淨之後也不急著拿掉:
   留著不花任何成本,拿掉要一次 migration。
2. 🔴 **`artifact.upload_rejected` 現在有資料了,但沒有人在看。**
   稽核頁可以篩 action,但沒有「同一個人短時間內反覆被拒收」的訊號。
   對散布可執行檔的平台,那是值得看一眼的東西 —— 建議與「後台使用者登入紀錄」
   (Benny 2026-08-31 提的另一件事)一起設計,不要各做一個半套。
