## 計畫(動工前寫,第二條 2)

### 發現的經過(不是review出來的,是撞到的)

Benny 照 runbook §C.3 在 VM 上清 T107 的殘骸:

```
python: can't open file '/app/tools/purge_failed_artifacts.py': [Errno 2] No such file
```

第一層解釋是「那支工具是 T107 才寫的,VM 跑的 v0.2.5 沒有它」——**但那不是根因**。

`Dockerfile:69-72` 只 COPY `alembic.ini` / `alembic/` / `app/`,
而 `tests/test_devserver.py::test_image內不得含有這支腳本或其相依`
**明文禁止 COPY tools/**(T92 為了讓 `devserver.py` 進不了正式環境而蓋的第三層防線)。

🔴 於是:

> **runbook §C.2 的兩行 cron —— `docker compose exec -T svc python tools/purge_audit.py --apply`
> 與 `tools/purge_issues.py --yes` —— 從寫下的那天起就不可能執行成功。**

⚠ 實測 `crontab -l | grep purge` **沒有任何一行** —— cron 從來沒掛上去。
所以沒有發生「每晚靜默失敗」,但換來的事實一樣不好看:
**稽核保留期清理從上線起一次都沒跑過**,而那是一張只增不減的個資表;
後台稽核頁上寫的「保留期 N 天」是一個沒有被執行的承諾(頁面自帶警語,至少沒說謊)。

### 決定:A 案(Benny 2026-08-31 裁示)

`Dockerfile` 加 **`COPY --chown=app:app tools/purge_*.py ./tools/`**,
並把 T92 那條測試從「不得 COPY tools」**收窄**為
「不得 COPY `tests/`、不得讓 `devserver.py` 進入 image」。

🔴 **為什麼這不算拆掉 T92 的防線 —— 意圖與文字要分開看:**

T92 要防的是「**偽造 session 的 devserver 出現在正式環境**」,它的三層是
①要 `DEV_UNSAFE_LOCAL=1` ②只綁 127.0.0.1 ③**image 裡根本沒有這支腳本**。
第三層之所以成立,關鍵不是「tools/ 整個不在」,而是
**`devserver.py` 不在、而且它 import 的 `tests/` 也不在**。

`tools/purge_*.py` 是**維運腳本**,不偽造任何身分,而且它們的執行位置本來就該是
正式容器內(runbook 的 cron 就是這樣寫的)。把它們排除在外,換到的不是安全,
是**一份跑不起來的維運文件** —— 而跑不起來的維運文件,結果就是那件事沒有人做。

⚠ 收窄之後,`devserver.py` 仍然進不去,而且**多了一條正面守門**(見下)。

### 🔴 這個任務真正的產出:一條「文件與 image 對不上就紅燈」的測試

只把檔案 COPY 進去,下一次有人寫了新的維運腳本、runbook 也寫了指令,
但忘了改 Dockerfile,同一件事會**一模一樣地再發生一次**。

所以加一條測試:**掃 runbook 裡所有 `python tools/xxx.py` 的引用,
逐一檢查 Dockerfile 的 COPY 是否涵蓋它**。涵蓋不到就紅。

這一條擋的不是這次的 bug(這次已經知道了),是**下一次**。

### 影響範圍

- `Dockerfile`(一行 COPY)
- `tests/test_devserver.py`(收窄那條,並說明為何收窄)
- `tests/test_ops_scripts.py`(新增:文件↔image 一致性守門)
- `docs/runbook_換版與備份還原.md`(§C.2 標明 cron **尚未掛**,以及最低版本要求)

**對現有資料的影響:🟢 不動、無 migration。** image 多幾 KB。

### 驗收標準(先寫會失敗的測試)

1. 🔴 runbook 引用的每一支 `tools/*.py` 都被 Dockerfile 的 COPY 涵蓋(紅起步)
2. 🔴 `devserver.py` **不得**被任何 COPY 涵蓋(收窄後仍要成立,反向驗證)
3. 🔴 `tests/` 不得被 COPY(同上)
4. `app/` 不得引用 devserver(既有,維持綠)

### 回滾方式

還原 Dockerfile 與兩個測試檔。🟢 無資料變更。

## 結果

### 異動檔案

| 檔案 | 改了什麼 |
|---|---|
| `Dockerfile` | 加一行 `COPY --chown=app:app tools/purge_*.py ./tools/` + 為何只收 purge_* 的理由 |
| `tests/test_devserver.py` | 那條收窄為「不得 COPY `devserver.py` / `tests/` / 整個 `tools/`」,並寫明意圖未減 |
| `tests/test_ops_scripts.py` | 新增 3 條(正面守門) |
| `docs/runbook_換版與備份還原.md` | §C.2 標註 cron 從未掛 + 需要 v0.2.6;§C.3 同步。升 v1.9 |

### 測試(紅 → 綠)

```
FAILED test_runbook引用的維運腳本都在image內   ← 紅起步(purge_audit.py 沒被 COPY)
PASSED test_devserver不得進入image             ← 收窄後仍成立
PASSED test_tests目錄不得進入image
```

⚠ **修的過程中我自己踩了一次同型的錯**:第一版把守門寫成
`assert "devserver" not in DOCKERFILE`(整份檔案),結果我在 Dockerfile 註解裡
寫下「為什麼只收 purge_*.py」時**被自己的測試擋下來**。已改為只檢查 COPY 指令 ——
因為**逼人把理由從註解裡刪掉,下一個人就會「順手」把整個 `tools/` 收進來**。
守門要擋的是行為,不是把解釋一起擋掉。

全套 **593 passed**(590 → 593)、`ruff check` 乾淨。

### 對現有資料的實際影響

🟢 **不動、無 migration。** image 多幾 KB。

### 遺留問題與後續建議

1. 🔴 **換版到 v0.2.6 之後才掛 cron**,而且掛完要**當場手動跑一次**確認不是
   `No such file` —— 這次的教訓就是「寫進文件不等於跑得起來」。
2. ⚠ **稽核表已經無保留期地長了兩個月**。第一次跑 `purge_audit.py --apply` 會一次
   刪掉一批 —— 🔴 **跑之前先備份**,而且先用不帶 `--apply` 的 dry-run 看數量。
3. ⚠ `AUDIT_RETENTION_DAYS` 的值要在跑之前確認一次:它從來沒有生效過,
   所以**沒有人驗證過那個數字是不是大家以為的那個**。
