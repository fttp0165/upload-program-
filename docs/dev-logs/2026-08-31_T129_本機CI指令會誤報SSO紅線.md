# T129:runbook 的本機 CI 指令會誤報「踩到 SSO 紅線」

**建立日期:** 2026-08-31 14:40
**最後更新:** 2026-08-31 14:40
**版本:** v1.0
**任務編號:** T129

---

## 計畫(動工前寫,第二條 2)

### 現象(Benny 實跑,不是推測)

照 `docs/runbook_本地開發與CI.md` §4.1 貼上去:

```
grep -ri "authentik\|HS256" app/ tests/ && echo "❌ 踩到 SSO 紅線" || echo "✅"
→ ❌ 踩到 SSO 紅線
```

而同一個 commit 的 CI 那一步是**綠的**。

### 根因:runbook 上的是簡化版,與 CI 實際跑的不是同一條指令

`.github/workflows/ci.yml` 的檢查有三層排除,runbook 版一層都沒有:

| | runbook §4.1(錯) | CI(對) |
|---|---|---|
| Authentik | 掃 `app/ tests/` 全部 | `--exclude='test_sso_contract.py'` —— **那支測試自己就是掃描器,它必須寫出被禁的字** |
| HS256 | 掃 `app/ tests/` | **只掃 `app/`**,並排除 `不接受 / 一律拒 / 禁` 這類說明用法的行 |
| 檔案型別 | 不限 | `--include='*.py' --include='*.yml'` → 不會掃到 `__pycache__/*.pyc` |

於是命中的每一行都是「說明它被禁止」或「測試它被拒絕」,**沒有一行把 HS256
當成可接受的演算法**。

🔴 **這與 T109 是同一類的錯**:文件寫得出來、照做卻得到錯的結果。
而這一種比 T109 更陰險 —— T109 是 `No such file`(當場知道有問題),
這一支**會給出一個看起來很嚴重的假警報**。後果有兩種,都不好:
①有人開始找一個不存在的問題;②**有人學會忽略紅字**,而下次是真的。

### 做什麼

`docs/runbook_本地開發與CI.md` §4.1 的兩條指令換成**與 CI 逐字相同**的版本,
並加一句說明為什麼有那些排除(不寫理由,下一個人會覺得排除很可疑而「順手」拿掉)。

⚠ 順帶說明:同一節的「不該進 git 的檔案」那條沒有問題,實跑 ✅。

### 影響範圍

- `docs/runbook_本地開發與CI.md`(§4.1 兩條指令 + 說明),升版。

**對現有資料的影響:🟢 純文件,不動程式、不動資料。**

### 為什麼不寫新測試(第三條 4)

`tests/test_sso_contract.py::test_repo無Authentik與HS256` 已經在驗**這件事本身**
(而且它就是被誤報的那個檔案)。再寫一條「runbook 裡的指令要與 ci.yml 一致」的
字串比對測試,擋得住的只有「有人改了其中一邊」這種情況 —— 而那正是 T109 已經
建立的守門形狀。⚠ 但這次的教訓值得記進遺留:**同一句指令出現在兩個地方,
遲早會分岔。**

### 驗收標準

1. 照 runbook 新指令實跑,得到 ✅(不是 ❌)。
2. 該指令與 `ci.yml` 的排除條件逐項一致。

### 回滾方式

還原該檔。🟢 無程式、無資料變更。

### 遺留問題與後續建議

1. 🔴 **同一句指令出現在兩個地方(ci.yml 與 runbook),遲早會分岔** ——
   這次分岔的方向是「文件比 CI 嚴格」,結果是假警報;下一次可能是
   「文件比 CI 寬鬆」,那就變成本機綠、CI 紅。
   建議 T130:讓 runbook 的本機 CI 那節**從 `ci.yml` 產生**(比照 `render_docs.py`
   的做法),或退一步 —— 加一條測試比對兩邊的關鍵字。⚠ 前者較貴但根治,
   後者便宜但只擋得住「改了一邊」。
