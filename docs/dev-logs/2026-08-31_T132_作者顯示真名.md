### 起因

### 契約現在准了什麼(逐字對照,不擴大解釋)

| 項目 | v3.3 | v3.4 |
|---|---|---|
| 用途 | 僅管理後台顯示 | 管理後台 **+ 專案/版本/內容頁的擁有者、作者、上傳者辨識** |
| 進 API 回應 | ❌ | ❌ **不變** |
| 再散布(寄信/匯出/轉發) | (未明文) | ❌ **新增禁止** |
| 其餘七項(來源、覆寫、授權、log、nullable、清除、截斷值僅供人眼) | | **一字未動** |

⚠ **L1b(通知用信箱)一個字未動** —— 它仍然「不得顯示在任何頁面」。
姓名回答「這是誰做的」,信箱回答「怎麼聯絡他」,後者放上頁面沒有業務理由。

### 做什麼

1. 新增 `_labels_by_id()`:一次 `IN` 查完 `(sub, display_name_cache)`,
   回傳 `{user_id: 標籤}`,標籤 = **有名字就用名字,沒有就退回 `sub` 前 8 碼 + `…`**。
   取代現有的 `_subs_by_id()`(它刻意只取 sub,那個理由現在消失了)。
2. 三個顯示點換過去:專案頁擁有者、版本歷史的建立者、專案留言的作者。
3. 憲法紅線據實改寫(L1 的顯示範圍變了,紅線寫著舊範圍就是自相矛盾)。
4. 裁決書原樣存 `docs/plans/inbox/`(第九條 4),並回寫跨專案文件索引的「對方回了沒」。

### 🔴 為什麼保留 fallback 而不是「沒名字就空白」

`display_name_cache` 只有**登入過的人**才有(每次登入覆寫,契約第 1、2 項),
而且 `name` claim 由 firstName + lastName 推導,**兩者皆空就是 NULL**。
空白會讓人以為欄位壞了 —— 契約第 6 項本來就要求「為空時不得阻斷任何功能,
顯示退回 `sub`」。這一條不是我方的貼心設計,是條文要求。

### ⚠ 要改既有測試,依 CI 紅線逐條說明(這不是放水)

三條測試現在斷言「**頁面不得出現顯示名稱**」:
`test_專案頁不得出現顯示名稱`、`test_版本歷史不得出現顯示名稱`、留言那條同型。

它們釘的是 **v3.3 的契約**,而契約已經改了。**照舊斷言改程式,等於讓一條已被
裁決放寬的限制繼續生效** —— 那不是嚴謹,是拿過期文件當現況(第七條存在的理由)。

改寫方向:**反向斷言不刪除,改成釘住新的界線** ——
- 頁面**得**出現名字(新行為);
- 🔴 **API 回應仍不得出現名字**(v3.4 未放寬這一項)—— 這條由「不得出現」搬到
  API 測試那邊,強度不減。

| 原測試 | 改成 | 為什麼不是放水 |

### 遺留問題與後續建議

1. 🔴 **線上要看到這個,得先合併 PR #37 並發 v0.3.0。** 目前 VM 跑 v0.2.5,
   連 T118/T125 的識別碼版本都還沒上去。
2. ⚠ **沒登入過的人仍然只有 8 碼識別碼。** 這不是缺陷:名字只能從本人的 ID token

   我方**沒有任何合法管道**知道他的名字。
3. 🔴 **落地裁決書時踩到兩條守門,而照它們做會違反憲法** ——
   `test_跨專案文件抬頭四欄齊備` 與 `test_登記在案的對外文件都有HTML版`
   對 `inbox/` 那份**別人寫的**文件開火。但第九條 4 明文「收到什麼原樣保存,
   **不改內容**」,而那兩條要求的是**我方的**格式。只有兩條路:改對方的檔
   (違反第九條 4),或讓 CI 永遠紅。**一條逼人違反憲法才能變綠的守門,
   比沒有守門更糟。** 已把 `inbox/` 排除,並把理由寫進測試檔。
   ⚠ 那兩條測試寫於 `inbox/` 還是空的時候(索引當時寫著「尚未在本 repo 落地保存」),
   所以這個死角一直沒被執行到 —— **第一份真的落地的他方文件就是它的反例**。
   🔴 **反向驗證做過**:拿掉我方文件的「受文專案」欄 → 守門仍然紅;還原 → 綠。
   排除範圍只到 `inbox/`,沒有把守門本身弄鬆。
4. ⚠ **從申請到裁決躺了 19 天**,期間使用者看到的是 UUID。已記進跨專案文件索引 ——
   索引的用途正是回答「對方回了沒」,而它答不出來的時候就是這種結果。
