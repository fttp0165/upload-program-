## 🔴 施工中抓到自己寫的假綠 —— 第四種形狀:切片切錯位置

兩條防誤判的反向測試(`Tool` / `Tool 2` 不同組、兩個中文名不同組)
**一開始就是綠的**,我當時記為「本來就對」。

做完之後依計畫做反向驗證(故意把判準改成「去掉 slug 的 `-N` 後綴」),
**測試仍然綠** —— 守門是假的。追下去發現:

```python
dup = body.split("疑似重複")[1].split("全部專案")[0]   # ← 第一版
```

而「疑似重複」在頁面上出現**兩次**(說明文字 + 標題),
`split(...)[1]` 切到的是那兩次之間的 **201 個字**,斷言等於在檢查一段空白。

修法:改用結構定位 `<section class="dup-group">` 的 `re.findall`,不隨文案改動而失效。

**重驗兩次,各自故意改壞:**

| 故意改壞 | 結果 |
|---|---|
| 判準改成「去掉 slug 後綴」 | `test_Tool與Tool2不得被判成重複` **紅** ✅ |
| 拿掉中文的 fallback(`group_key` 直接回 `slugify()`) | `test_兩個不同的中文名稱不得被判成重複` **紅** ✅ |
| 還原 | 全綠 ✅ |

🔴 **本 repo 假綠的四種形狀**(值得放在一起看):

| 形狀 | 出處 |
|---|---|
| 整頁搜尋撞到 placeholder | T90 |
| 迴圈跑零次,斷言等於沒執行 | T132 |
| 測試資料本身撞到關鍵字 | T133 |
| **文字切片切錯位置** | **本次** |

共同點一句話:**綠燈不是因為程式對,是因為斷言問錯了問題。**
而四次裡有三次是**「一開始就綠」的那種**——那才是最該懷疑的。

## 遺留問題與後續建議

1. 🔴 **上線後第一次使用前先跑一次 `./backup.sh`**(runbook §C.1)。
   已刪掉的專案沒有還原路徑,而備份是唯一的後路。
2. ⚠ **本判定抓不到「名字打得不完全一樣」的重複**(多一個字、錯一個字母)。
   那要靠人眼,而本頁列出全部專案供瀏覽。若日後真的常見,再考慮相似度比對 ——
   但相似度會帶來誤判,而誤判的代價是刪錯專案。**現在不做是刻意的。**
3. ⚠ 刪除沒有「軟刪除 / 垃圾桶」。要不要做取決於實際誤刪頻率;
   在有備份 + 輸入短名確認 + 稽核留痕之下,先不加一層狀態。
