### 發版與換版的實際結果(2026-09-07 22:36–22:51)

| 步驟 | 結果 |
|---|---|
| PR #40 合併 | `2182bf0`,CI 三關全綠(666 passed、Trivy 零 HIGH) |
| tag `v0.3.1` | → `2182bf0`,而該 commit 的 `APP_VERSION` **確實是 `0.3.1`** —— 🔴 **v0.2.4 錯的正是這一格,這次先驗後打** |
| Push GHCR | ✅(tag 才觸發;`main` 那輪依設計 skipped) |
| VM 換版 | ✅ `docker exec upload-program python -c "…APP_VERSION"` → **`running 0.3.1`** |
| GHCR 憑證 | ✅ `pull` 正常,`unauthorized` 未再出現 |

🔴 **換版過程再次踩到「編輯檔案 vs 貼指令」**:第一次貼的指令沒有改 compose 的
`image:` tag(那一步是編輯檔案),於是 `pull` 拉到的仍是 `v0.3.0`,而容器顯示
`Running`、gateway reload 成功 —— **看起來一切正常**。
**這與 2026-08-11 換版失敗、與同日 runbook §C.2 ③ 完全同一個形狀,一天內第三次。**
修法同 §C.2:**不要求人編輯,改成一行含 `sed` 的可貼指令**(先備份 compose、
改完印出那一行給人看),之後就一次到位。

🐛 **但我給的等待迴圈本身有一個缺陷,誠實記下:**

```
for i in 1..10; do docker compose pull svc && break; echo …; sleep 60; done && docker compose up -d svc && …
```

**十次都失敗時,`for` 的離開碼仍是 0**(最後一個指令是 `echo`/`sleep`),
`&&` 會照樣往下執行 `up -d` —— 而那會**用舊 image 重建,不會有任何錯誤訊息**。
這次恰好成立,是因為 image 剛好在第 10 次之後推上去。
🔴 **那是運氣,不是設計。** 修法:迴圈之後加一道 `docker image inspect` 確認
tag 真的存在才往下走。已列進狀態總覽 §5.1 的欠項。
