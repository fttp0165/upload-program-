### 三條守門測試,以及它們各自擋的是什麼

| 測試 | 擋的東西 |
|---|---|
| `test_帳號值大於全站上限時取全站上限` | 🔴 `min()`。少了它,日後把全站上限**調小**這個動作會**靜默地對已被設定過的帳號無效** —— 而那正是最需要它生效的時候(磁碟吃緊) |
| `test_不得存下大於全站上限的值` | 🔴 **那個欄位會撒謊**:存得下、畫面說可以,而上傳撞 gateway 的 413。**2026-09-08 這件事真的發生過一次**(App 已 500 MB 而 gateway 還 128m,使用者只看到「上傳失敗(413)」)—— 所以這條不是防禦性寫作,是紀錄 |
| `test_上傳頁的預檢值是該使用者的有效上限` | 🔴 漏掉這一處,前端會用**全站**的值預檢 —— 對被調小的帳號**放行一個必定失敗的上傳** |
| `test_沒設定的帳號仍走全站上限` | 既有帳號**行為逐字不變**(反向:訊息裡不得出現「帳號」字眼) |

### ⚠ 施工中修正的一件事:測試環境的上限是 1 MB

第一版測試填 `limit_mb=50`,而 `conftest` 刻意把全站上限設成 **1 MB**
(讓「傳超大檔」的測試跑得快)—— 於是 50 MB 被「不得超過全站上限」那條
規則擋掉,回 422。**那不是 bug,是我的測試在跟自己寫的規則打架。**
改填 `1` 並在測試裡註明理由。
📌 一課:**測試環境的設定值本身也是待測系統的一部分**,不能當背景。

### 對現有資料的實際影響

🟡 **加欄位。** 既有帳號一律 `NULL`,而 `NULL` 的語意是「沿用全站上限」,
故**行為逐字不變**。不動任何既有檔案、專案、版本。

🔴 **downgrade 會失去管理員的決定**(哪些帳號有個別上限),而那不在任何
其他地方。migration 檔頭寫了退版前要先跑的 SELECT ——
**寫在那裡而不只寫在這裡,是因為執行 downgrade 的人讀的是那個檔案。**

### 遺留問題與後續建議

1. ⚠ **待開通(pending)那一段沒有這個欄位。** 刻意的:還沒開通的人也還不能上傳,
   先設上限沒有意義。若日後要「開通時順便設」,那是另一個介面決定。
2. ⚠ **沒有「批次設定」**。一次一個,理由同 F17 的級距:這是逐人的決定。
3. 🔴 **全站上限仍只能改 `.env` + 重啟**,而它必須 ≤ gateway。
   **刻意不把它搬進後台**:App 看不到 gateway 的設定,搬進去就是製造
   一個能被設定成無效值的欄位 —— 那正是本任務用 §2 那道夾擠在防的事。
