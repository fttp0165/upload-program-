### 測試(紅→綠的證據)

```
9 failed, 2 passed   ← 起步(門禁與端點都不存在)
7 failed, 4 passed   ← 門禁完成
2 failed, 9 passed   ← 端點完成
11 passed            ← 樣板與 context 完成
```

全套 **692 passed**、`ruff` 乾淨。
🔴 **真 PostgreSQL up→down→up 演練通過**(本機起 PG 實跑):建表 → 刪表 → **再建成功**。

⚠ **再 up 那一步是刻意要跑的**:PostgreSQL 的 enum 型別**不會隨表消失**,
`downgrade` 若沒有 `_STATUS.drop(...)`,第二次 upgrade 會撞
「type already exists」—— 而**只做 up 的人永遠看不到那個錯**。
本專案一律演練 up→down→up 就是為了這種只在回頭路上出現的錯。

### ⚠ 施工中被既有守門咬了一次(而我改的是自己)

`test_action字彙集中且格式一致` 要求 action 的 prefix 是**單一個詞**
(`[a-z]+\.[a-z_]+`),而我第一版取名 `source_access.request` —— prefix 帶底線,**紅**。

🔴 **修法是改名字,不是放寬正則:** 改為 `project.source_request` 等四個。
放寬那條規則等於讓下一個人隨便取名,而字彙一亂就再也看不出
「這是對什麼東西做的事」。
📌 這條守門是 T38 的產物(`action` 刻意不下 DB CHECK,以測試代替),
今天第一次真的擋到人 —— **擋的是我**。

### ⚠ 另外兩個自己寫錯的地方

1. 測試 helper `_request` 被同一個測試呼叫兩次(驗「重複申請只有一筆」),
   而它每次都 `make_user` → 撞 `users.sub` 的唯一約束。
   🔴 **症狀會誤導**:錯誤訊息指向 `users` 而不是本功能,
   而測試在「還沒測到重複申請」之前就死了。改成「不存在才建」。
2. 成員 API 是 `PUT /v1/projects/{slug}/members` 而我寫 `POST` → 405。

### 對現有資料的實際影響

🟡 **加表。** 既有專案、版本、檔案**一列都不用改**。

🔴 **但行為會變**:今天能下載 `source` 的**非成員**,升級後要先申請。
**那是需求本身,不是副作用 —— 但上線前要先跟使用者講**,
否則他們只會覺得平台壞了。既有的下載連結不會 404,而是 403 + 申請入口。

🔴 **downgrade 會失去所有核准紀錄**,而那不在任何其他地方 ——
migration 檔頭寫了退版前要跑的匯出 SQL(寫在那裡而不只寫在計畫書,
**因為執行 downgrade 的人讀的是那個檔案**)。

### 遺留問題與後續建議

1. 🔴 **這個功能的成敗取決於作者會不會回來看。** 平台沒有 email 也沒有推播,
   所以待辦數字放在**專案頁**(作者一定會經過的地方)而不是只在申請清單頁。
   ⚠ 與 T123 審核制度是**同一個營運風險**,不是技術問題。
2. ⚠ **管理總覽刻意不加這個待辦** —— 這是作者的待辦不是管理員的,
   混進去會讓管理員以為該他處理。
3. ⚠ **`viewer` 也能下載程式碼**(既有語意:能讀專案就能取得其內容)。
   本任務不改它;要更嚴屬另一個決定,不夾帶。
4. ⚠ **版本頁(`releases.html`)的下載鈕還沒換成「申請下載」** ——
   伺服器端已經擋住(403),所以**不是漏洞**,是體驗。
   下一輪補;現在按下去會看到我們自己的 403 訊息,裡面寫著怎麼申請。
