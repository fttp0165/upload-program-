## 事故

| 項目 | 值 |
|---|---|
| tag `v0.4.0` 指到 | `1c4b530` —— **2026-07-29** 的 PR #5 合併(**六週前**) |
| 應該指到 | `ef3ec03`(PR #42 的合併) |
| CI | **三關全綠**(測試 / Build+Trivy / **Push GHCR 成功**) |
| 後果 | `ghcr.io/fttp0165/upload-program:v0.4.0` 裝的是七月底的程式 —— 沒有 T137~T142,**連 `app/version.py` 都還不存在**(T68 之後才有) |

### 根因

`git tag` 是在 **VM 的 `~/upload-program-`** 下執行的,而那個 clone **停在六週前**。
`git tag` 標的是當下的 HEAD,而那個 HEAD 是七月底。

🔴 **這是 v0.2.4 事故的完全重演。** 那次的結論寫進了第八條 4
(「`APP_VERSION` 必須在打 tag 之前改成該版」),而**我這次確實寫了「先驗常數再打 tag」**——

**但我把它寫成兩個可以分開貼的區塊。而可以分開貼的東西就會被分開貼。**

⚠ **同一天內我已經修過這個形狀一次**:runbook §C.2 ③ 的結論是
「**修法不是把警語寫大一點,是把區塊變成真的可以貼**」。
而我在自己的發版步驟裡又犯了一次 —— 差別只在那次是「該編輯卻被貼進終端機」,
這次是「該先驗證卻被跳過」。**同一個根源:一個步驟能被單獨略過,它就會被略過。**

### CI 為什麼沒有攔住

`Push GHCR` 有一步「確認此版本尚未發布過」—— 它只確認**這個 tag 沒發布過**,
不確認**這個 tag 指到的東西對不對**。而 T105(「`APP_VERSION` 不得 ≤ 最新 tag」的 CI 守門)
**至今沒做**,這是它第二次收費。

🔴 **七月底那份程式的測試在今天照樣全綠** —— 那正是最可怕的一點:
綠燈證明的是「那一版自己是完整的」,不是「那一版是我們要發的」。

## 處置

| 動作 | 理由 |
|---|---|
| **不刪 tag、不刪 image** | 第八條 5「同版不重發」(v0.1.3 事故的結論)。刪掉會讓已經拉過它的人手上有一個「不存在的版本」,比留著一個被明確標示作廢的更難查 |
| **v0.4.0 的 Release 內容改成「作廢,請勿使用」** | Release 頁是唯一有人會看的地方 |
| **改發 v0.4.1** | 內容與 v0.4.0 應有的內容完全相同(T137/T138/T140/T141/T142) |
| **VM 千萬不要 pull v0.4.0** | 它跑得起來、看起來正常(七月的程式本來就能跑),但**資料庫已經是新 schema**,行為會很奇怪 |

## 這次改掉的東西:發版指令變成一行,驗不過就不會打 tag

```bash
cd ~/upload-program- && git checkout main && git pull \
  && test "$(grep -c 'APP_VERSION = \"0.4.1\"' app/version.py)" = 1 \
  && git tag v0.4.1 && git push origin v0.4.1 \
  || echo "❌ 停:常數不是 0.4.1 或不在 main,tag 沒有打出去"
```

🔴 **關鍵不是那個 `test`,是那個 `&&`**:驗證與打 tag 在**同一個指令**裡,
所以「先驗證」這件事**沒有辦法被單獨略過**。
⚠ 這條指令已回寫 runbook §A.1。
