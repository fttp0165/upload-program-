## 計畫(動工前寫)

### 目標

把 **T144 的七項前端可讀性修正**送到使用者面前。它們 2026-09-08 11:14 就併進 main 了
(PR #44),但 **`v0.4.1` 是 10:26 發的 —— 早於它**,所以線上到現在看到的仍然是
`195245216 bytes` 和 `source`。

📌 **合併不是交付。** 這七項在 repo 裡躺了一天,而它們全部都是「使用者看得到」的東西。

### 本版內容

| 任務 | 內容 | 資料影響 |
|---|---|---|
| **T144** | 前端可讀性七項:①容量顯示改 `186.2 MB / 2.0 GB`(原始值移到 hover)②檔案大小同上 ③`source/binary/doc` → **程式碼 / 執行檔 / 說明** ④`未掃描 not_scanned` → `未掃描` ⑤固定連結改為**可點的絕對網址**+點一下全選 ⑥SHA-256 完整保留 + 點一下全選 ⑦移除過時文案「顯示名稱待平台核准」 | 🟢 |
| **文件更正** | L1 放寬引用的契約版號 `v3.4` → **`v3.7`**(`CLAUDE.md` v2.9、`docs/狀態總覽.md` v2.5)—— cats-portal 併回時因撞號改編,不改這裡就會指到別的條款 | 🟢 |

### 為什麼是 patch 版而不是 0.5.0

**七項全部是呈現層,沒有任何一項改變語意:**
API 回應一個位元組都沒改(bytes 在 API 裡維持整數,那是給程式看的)、
資料庫沒動、權限判定沒動、三道紅線(magic bytes / attachment + nosniff / SHA-256)一字未動。

對照 **v0.3.0 之所以升次版號**,是因為 `publish` 從「發布」變成「送審」——
**那才是會讓看 Release 頁的人誤判的改動**。本版沒有那種東西。

### 做什麼

1. `app/version.py`:`APP_VERSION` → `0.4.2`(🔴 第八條 4:**打 tag 之前**)
2. `docs/任務表.md`:T145 一列 + 版本歷史
3. `docs/狀態總覽.md`:🔴 **§1 / §2 / §3 目前是過期的** —— 它們寫「線上 v0.3.1、
   v0.4.1 待發」,而 `v0.4.1` 的 tag 早就存在。這一頁的用途就是回答
   「線上是哪一版」,**留著過期內容比沒有這一頁更糟**(它會被當成事實引用)。
4. 三份文件的 HTML 由 `python tools/render_docs.py` 重產(第四條 6)

### 🔴 一件不能用猜的:VM 現在到底跑哪一版

狀態總覽寫「VM 實測 **0.3.1**(2026-09-07 22:51)」,而 `v0.3.2` / `v0.4.0` / `v0.4.1`
三個 tag 都已存在。**我方沒有 09-08 之後的 VM 實測紀錄。**

這件事直接決定部署指令對不對:

| 若 VM 現在是 | 升到 0.4.2 需要 |
|---|---|
| **v0.4.1** | 🟢 只要 pull + up + reload,**不必跑 alembic** |
| **v0.3.x 或更早** | 🔴 **必須 `alembic upgrade head`** —— 中間隔著 `0011_project_comments` / `0012_user_upload_limit` / `0013_source_access` 三個 migration(v0.4.0/v0.4.1 那批帶進來的) |

📌 **「本版沒有 migration」不等於「換版不用跑 migration」** ——
前者講的是這一版新增了什麼,後者取決於**要跨過多少版**。
把兩者混為一談,就會在 VM 落後好幾版時漏跑 alembic,
而症狀是**服務起得來、頁面看起來正常、直到有人碰到那張新表**。

⚠ 故本篇**不寫死**部署指令的 alembic 那一步,改為「先量再決定」,
量的指令寫進結果段。**憑印象寫版本號這件事,本 repo 09-08 才剛踩過一次**
(狀態總覽 v2.4 的自我更正:「我沒看到」不是「沒有發生」)。

### 驗收標準

1. `APP_VERSION == "0.4.2"`
2. `python -m pytest` **700 passed**、`ruff check .` 乾淨、`render_docs.py --check` 綠
3. 狀態總覽**沒有任何一句與現況衝突**(特別是「線上是哪一版」「下一版是哪一版」)

⚠ 若換版時跑了 `alembic upgrade head`(VM 落後好幾版的情況),
那三個 migration 屬於 v0.4.1,**回滾到 v0.4.1 不需要 downgrade**;
只有要退到 v0.3.x 才需要,而那是另一件事,不在本版範圍。

### 🔴 狀態總覽原本有三格是過期的

這不是順手整理,是它**已經在說謊**:

| 格 | 原本寫 | 實際 |
|---|---|---|
| §1 一句話 | 「線上 v0.3.1;v0.3.2 已測完待發」 | `v0.4.1` 早在 09-08 10:26 就發了 |
| §2 最後發布的 tag | `v0.3.2` | `v0.4.1` |
| §3 標題 | 「v0.4.1:這一版有什麼(**待發**)」 | 已發布 |

⚠ 而這正是 **v2.0 開版時自己寫下的理由**:
「一頁格式整齊、有版本號、每一格都在說謊的文件,比沒有這一頁更危險。」
**同一個病在同一頁上又犯了一次** —— 因為 v2.0 立的規矩是
「發版任務一律連同本頁回寫」,而 `v0.4.1` 那次沒有回寫。

📌 規矩沒有觸發器,就只在有人想起來時才發生。

### 🔴 「VM 實測」這一格改成誠實的「未知」

原本寫 **0.3.1**(2026-09-07 22:51 實測)。其後 `v0.3.2` / `v0.4.0` / `v0.4.1`
三個 tag 陸續發布,而**我方沒有 09-08 之後的 VM 實測紀錄**。

**沒有把它改成 0.4.1** —— 那會是憑印象填的,而 09-08 才剛因為同一件事更正過
(本頁 v2.4:「我沒看到」不是「沒有發生」)。改成 ⚠ 未知 + 一行量測指令。

### ⚠ 這一版的部署指令不能照抄「🟢 無 migration」

本版確實沒有新增 migration,但**換版要不要跑 alembic 取決於 VM 落後幾版**:

| VM 現在是 | 升到 0.4.2 需要 |
|---|---|
| **0.4.1** | 🟢 pull + up + reload,不必跑 alembic |
| **0.3.x 或更早** | 🔴 **必須 `alembic upgrade head`** —— 中間隔著 `0011_project_comments` / `0012_user_upload_limit` / `0013_source_access` |

📌 **「本版沒有 migration」與「換版不用跑 migration」是兩句不同的話。**
把它們當成同一句,就會在 VM 落後好幾版時漏跑 ——
而症狀是**服務起得來、頁面看起來正常,直到有人碰到那張新表**。

### 對現有資料的實際影響

🟢 **不動。** 無 migration、無 `.env` 新變數、資料庫未觸及。
