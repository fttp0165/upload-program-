## 計畫

### 目標

portal-admin 的管理員在後台按「+ upload」開通某人時,portal 會呼叫本服務
`POST /v1/provision`,請我方**先開一列**本地 user —— 讓本服務的管理員
**不必等那個人第一次登入**就能在後台開通他、設角色、設單檔上限。

### 端點形狀(依徵詢函 §2,我方決定路徑)

```
POST http://upload-program:8080/v1/provision      ← cats-edge 內網,不經 gateway
Authorization: Bearer <portal 管理員本人的 access token,aud 含本服務 client_id>
X-Trace-Id: <portal 追蹤碼>

{"subject": "<被開通者 sub>", "service": "upload", "action": "join" | "leave"}
```

### 驗證(徵詢函 §2.1,四層全部要過,deny-by-default)

| # | 檢查 | 不過 |
|---|---|---|
| 1 | 驗簽 / RS256 / `iss` / `exp`(沿用 `OidcClient.verify_access_token`) | 401 |
| 2 | 🔴 **`aud` 明確含本服務 client_id**。不接受既有的 `azp` 退路 —— 那條是給本服務自己的登入 token 用的 | 401 |
| 3 | `scope` 含 `account:provision:<client_id>` | 403 |
| 4 | 🔴 呼叫者是**平台管理員**(realm 角色 `portal-admin`)**或部門主管**(任一 `/mgr/` 群組) | 403 |

第 4 條是徵詢函特別強調的:少了它,任何拿得到該 scope 的登入者都能在我方庫裡建列。

### 行為

| action | 對方庫裡已有 | 對方庫裡沒有 |
|---|---|---|
| `join` | **什麼都不動**,回 200 `exists` | 建一列 **pending、member、無名字**,回 201 `created`,寫稽核 `user.provision` |
| `leave` | **忽略**,回 200 `ignored`(採徵詢函 §2.3 平台預設) | 同左 |

🔴 三個刻意的選擇:

1. **建的是 pending,不是 active。** 開通(本服務的「誰能用」)仍是本服務管理員的職權
   (契約 §4.4、T63「`/svc/upload` 只讀不判」)。Push 只解「人不在庫裡就設不了」這個死結,
   不偷偷改授權模型。
2. **既有列一個欄位都不碰** —— 不能重用 `security.upsert_user()`:它會把 `display_name_cache`
   / `notify_email` **覆寫成 NULL**(那是登入時的語意),推送沒有 token claims 可給,
   重用的話每推一次就抹掉一次那個人的名字。
3. **`leave` 忽略** —— 本地列不是授權來源之一的理由在本服務**部分不成立**:本服務的授權看的是
   本地 `status`,不看 groups。所以「忽略」的實際效果是:portal 取消開通**不會**讓那個人
   在本服務被停用(與今天手動流程相同,沒有變差,也沒有變好)。**這一點要寫進回函**,
   不能讓 portal 以為取消開通會連帶收權。

### Payload 拒收多餘欄位

`extra="forbid"`:portal 若哪天多送一個 `email`,我方回 **422** 而不是默默吃下去。
這是我方這一側對「業務庫只存 sub」的結構保證(portal 那側有 AST 檢查,兩邊各守一道)。

### 影響範圍

| 系統 | 影響 |
|---|---|
| upload-program 既有功能 | 🟢 無(新增一條路由,不改登入、不改既有表) |
| 資料庫 | 🟢 **不動 schema、無 migration**;執行期新增 `users` 列(pending)、`audit_events` 列(`action` 是 String,不需 migration) |
| portal / Keycloak | 🟢 無。portal 旗標 `SVC_PROVISION_PUSH` 仍 off;scope 尚未建立 → 即使被呼叫,第 3 層也會 403 |
| 對外 | 經 gateway 也打得到 `/upload/v1/provision`,但四層驗證一樣適用;內網呼叫是建議路徑而非安全邊界 |

### 驗收標準

1. 四層驗證各有一條**反向**測試(缺 aud / 缺 scope / 一般使用者 / 無 token);
2. join 新人 → 201 + pending + 無名字 + 一筆稽核;
3. join 既有人 → 200,**名字與信箱不被抹掉**、狀態不變、不寫稽核;
4. 重送同一筆 → 結果相同(冪等,以 `sub` 唯一鍵);
5. leave → 200 ignored,不建列、不改狀態;
6. payload 多一個 `email` → 422;`service` 不是 `upload` → 422;
7. 全套測試綠、`ruff check .` 乾淨。

### 回滾方式

`git revert` 該 commit 即可:無 migration、無設定必填變數。
已被推送建出的 pending 列與一般首登建出的 pending 列無異,不需清理。
