## 計畫(動工前寫,第二條 2)

### 起因

Benny 截圖回報:專案頁「最後更新 2026-10-08 05:54」,問「時間不對 確認是為台北時間嗎」。

**答案:不是 —— 那是 UTC,而且是直接印出來、不帶任何標示的 UTC。**

`models.py` 的 `_now()` 一律 `datetime.now(UTC)`,寫進 `created_at` /
`updated_at` / `published_at` / `requested_at` / `last_login_at` 等欄位——
**這個部分是對的**,與平台 gateway / Keycloak 的 log 同一個時區,跨系統
對時才有基準。

🔴 **錯的是顯示層。** 模板對這些 UTC 值直接呼叫 `.strftime('%Y-%m-%d %H:%M')`,
印出的是 UTC 的時刻數字,**不帶任何時區標示**。本平台使用者全部在台灣
(CLAUDE.md:「公司內部開發者程式分享平台」),看到一串時間數字只會讀成
台北時間——而實際差 8 小時。截圖裡的 `05:54` 其實是台北時間 `13:54`。

### 盤點範圍

全站共 **13 處**裸 `strftime` 呼叫,7 支模板:

| 模板 | 欄位 |
|---|---|
| `project.html` | 版本發布於、建立時間、最後更新、留言時間 |
| `releases.html` | 版本發布於 |
| `admin_users.html` | 申請於、最後登入 |
| `admin_projects.html` | 建立 |
| `issue_detail.html` | 回報於、留言時間 |
| `issue_list.html` | 回報於 |
| `project_access.html` | 下載申請時間 |

⚠ **`admin_audit.html` 刻意不在清單內**:它用
`event.occurred_at.isoformat(timespec='seconds')`,**本來就帶 `+00:00` 的
時區標示**,不會被誤讀。稽核頁的用途之一是對照平台其他系統的 log(也是
UTC),維持 UTC 顯式標示反而是對的——這與本任務要修的「不帶標示的裸數字」
是兩回事,不動它。

### 做什麼

1. **新增 `app/clock.py`**:集中換算邏輯(UTC → Asia/Taipei)。
   🔴 `dashboard.py` 裡已經有一份幾乎一樣的 `_aware()`(補時區,處理
   SQLite 測試環境不存時區的問題)——**搬到這裡讓兩邊共用同一份**,
   不是又建第二份「補時區」的邏輯。
2. **`templating.py` 新增 Jinja filter `taipei_time`**,換算 + 格式化。
3. **七支模板的 13 處**改用 `{{ 值 | taipei_time }}`,並把**原始 UTC 值**
   放進 `title` 屬性(`isoformat(timespec='seconds')`,帶 `+00:00`)——
   沿用 T144 已經立下的規矩(`human_bytes` 把原始位元組放 title):
   **人看的東西換算過,要對照原始值的人 hover 就有**。

### 🔴 容器裡可能沒有時區資料庫,這件事必須在這次一併解決

`zoneinfo.ZoneInfo("Asia/Taipei")` 需要系統或套件提供的時區資料庫。
`python:3.12-slim`(本專案 runtime base image)是瘦身過的 Debian,
**`tzdata` 系統套件不在裡面**——而這份 Dockerfile 的註解已經兩次記下
「`deb.debian.org` 從 CI runner 的容器網路不可達」(T93、T106),apt 這條路
在這個環境裡不可靠。

**修法:把 `tzdata` 加進 `requirements.txt`(PyPI 套件,純資料、無編譯、
走 wheel,不碰 apt)。** 這是 CPython 官方文件對這個情境的建議做法——
`zoneinfo` 模組本來就設計成「系統沒有就找得到 pip 裝的 `tzdata`」。
**不是破例新增相依**:比照 `mailer.py` 優先標準庫的原則,`zoneinfo`
本身是標準庫,這裡加的只是它所需的**資料**,不是另一個時區函式庫。

⚠ 本機測試環境(非 slim image)本身就有系統時區資料庫,**測試跑得過
不代表正式環境跑得過**——這條本身無法在本機測試完全證偽,只能靠
「加上 PyPI `tzdata` 之後任何環境都有資料來源」這件事本身成立。

### 影響範圍

**對現有資料的影響:🟢 不動。** 資料庫裡的值一個位元組沒改,只改顯示。

### ⚠ 已知會撞到一條既有測試

`tests/test_login_audit.py::test_後台使用者頁顯示最後登入時間` 斷言
`stamp.strftime("%Y-%m-%d")`(UTC 的日期)要出現在頁面裡。

🔴 **那條斷言的前提本身就是這次要修的 bug**(「畫面顯示 = UTC」)。
換算成台北時間之後,在 UTC 16:00–23:59:59 之間執行測試(= 台北已經是
隔天),頁面顯示的日期會跟 UTC 的日期不一樣——**這條測試會變成看執行
時刻決定過不過的 flaky 測試**,而且修正顯示之後它測的東西本身就錯了。

**修法:斷言改成比對台北時間換算後的日期**(`taipei(stamp).strftime(...)`),
而不是放寬或刪掉這條測試——它要守的「後台看得到最後登入時間」這件事
沒有變,變的只是「畫面上那個日期字串現在要怎麼算」。依 CI 紅線在此說明。

### 驗收標準(先寫會失敗的測試)

1. 🔴 `taipei_time` filter 把 UTC 轉成台北時間(+8 小時)
2. 🔴 **跨午夜**的情況:UTC 當天 20:00 要顯示成台北**隔天** 04:00——
   只測同一天的加減法不會抓到「連日期都沒跟著跳」這種錯
3. 🔴 專案頁畫面上看得到換算後的台北時間,**看不到**未換算的 UTC 原始字串
   (原始值留在 `title`,HTML 原始碼裡還在,只是不在「畫面上」)
4. 🔴 naive datetime(SQLite 測試環境常見)視為 UTC 再換算,不炸例外
5. `test_login_audit.py` 既有斷言改為比對換算後的日期

### 回滾方式

還原 `app/clock.py`(刪除)、`templating.py` 兩行、七支模板、
`requirements.txt` 一行、`tests/test_login_audit.py` 一行。🟢 無資料變更。

🔴 **兩條關鍵測試各自故意改壞重驗過:**

| 故意改壞 | 期望 | 實測 |
|---|---|---|
| filter 繞過換算,直接 `value.strftime(fmt)` | filter 測試 + 整合測試紅 | ✅ `2 failed, 3 passed` |
| `taipei()` 改成「只加 8 小時到 hour 欄位,不處理跨日」 | **只有跨午夜那條紅**(最貼近真實會犯的錯) | ✅ `3 failed, 2 passed`(`test_換算跨過午夜`在列) |

第二個尤其值得記:**這正是這類 bug 最常見的犯法**——有人「修」時區問題時隨手
`+ timedelta(hours=8)` 或改 `hour` 欄位,看起來測試會過(同一天的案例全綠),
只有真的跨過午夜的案例才會露餡。**只測同一天的加減法不會抓到這個**,
這也是為什麼 `test_換算跨過午夜` 跟 `test_taipei把UTC轉成台北時間` 分開寫
而不是合併成一條——分開寫,反向驗證時才看得出是哪一半壞了。

### ⚠ 一個無法在本機完全驗證的風險,已用結構性修法處理

`zoneinfo.ZoneInfo("Asia/Taipei")` 在本機測試環境跑得過(系統本身有
`/usr/share/zoneinfo`),**但正式環境的 `python:3.12-slim` 是瘦身過的
Debian,系統 `tzdata` 套件不在裡面**——這件事本身無法在本機測試證偽
(本機測試環境不是 slim image)。

🔴 **沒有繞過這個風險,而是把它變成一個不依賴 apt 的依賴**:加
`tzdata`(PyPI 套件,純資料、無編譯)進 `requirements.txt`。選它而不是
apt 裝系統套件的理由寫在 `requirements.txt` 的註解裡——這份 Dockerfile
已經兩次記下 `deb.debian.org` 從 CI runner 的容器網路不可達(T93、
T106),apt 這條路在這個環境不可靠,而 `tzdata` PyPI 套件正是 CPython
官方文件對「image 沒有系統時區資料庫」這個情境的建議解法。

⚠ **換版後的人工驗證應包含**:VM 上跑 `docker exec upload-program
python -c "from zoneinfo import ZoneInfo; print(ZoneInfo('Asia/Taipei'))"`
確認正式容器裡真的找得到時區資料,而不是只看畫面上的時間「看起來對」——
看起來對也可能是本機剛好有系統時區資料庫在撐。

### 遺留問題與後續建議

1. ⚠ **`admin_audit.html` 刻意不動**(計畫段已說明):稽核頁的
   `occurred_at.isoformat(timespec='seconds')` 本來就帶 `+00:00`,不會被
   誤讀,而且稽核頁常拿來對照平台其他系統的 UTC log,維持顯式 UTC 反而
   是對的。若日後要讓稽核頁也顯示台北時間,那是另一個決定,不在本任務
