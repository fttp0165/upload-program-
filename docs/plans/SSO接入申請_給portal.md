### 2.3 🔴 §4.10 同源環境的額外義務(v1.5 新增)

我方認知:MIS 只核可單一 hostname,**IdP 與各 App 共用 origin**——
瀏覽器的同源政策不再提供隔離,**我方一旦出現 XSS 即等同全平台帳號淪陷**。
此條在我方內部已列為最高等級風險。

| 契約要求 | 我方落實 | 備註 |
|---|---|---|
| session cookie `Path=/«PREFIX»/` + HttpOnly + SameSite=Lax | ✅ | Path 由設定的前綴導出,不寫死 |
| 嚴格 CSP(至少 `default-src 'self'`,禁 unsafe-inline) | ✅ | 實際值:`default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'` |
| 前端 base path 設為自己的子路徑 | ✅ | 頁面內連結一律 root-relative 並帶前綴;**不使用 WhiteNoise** |
| 使用者輸入的輸出一律消毒 | ✅ | Jinja2 autoescape;模板禁用 `\|safe`;有 XSS 迴歸測試 |
| **不得**把 token 存進 `localStorage` | ✅ | token **只在 HttpOnly cookie**;上傳頁已導入外部 JS(XHR PUT + 進度條),原始碼層級掃描守門(禁止 `localStorage`/`sessionStorage` 字樣出現在任何 JS/HTML/CSS) |

> 我方另有**自我加嚴**的相關措施(非契約要求,但與同源風險同向):
> 上傳檔案驗 **magic bytes** 且 **HTML/SVG 任何情況皆拒收**;
> 下載一律 `Content-Disposition: attachment` + `nosniff`
> ——本服務散布可執行檔,絕不讓上傳內容在本網域被瀏覽器執行。

## 4. ⚠️ 需要 portal 裁決的一項偏離

### §7 冒煙清單第 1 項:「未登入開你的 App → 302 到登入頁」

**我方做法與字面略有出入,先行提出而非接入當天才被退回。**

| | 我方行為 |
|---|---|
| **深層頁**(`/«PREFIX»/projects/*` 等) | ✅ **302 到 IdP 登入頁**,並帶 `next` 於登入後導回原頁 |
| **首頁**(`/«PREFIX»/`) | 保留一頁「請先登入」的落地說明頁,頁上有登入按鈕 |

**理由:** upload-program 是內部工具,首頁承擔「這是什麼系統、找誰開通」的說明功能。
契約 §4.3 要求待開通頁「不是冷冰冰的 Forbidden」,我方認為同一精神也適用於
未登入者的第一印象——直接彈到 IdP 會讓不知道自己該不該有權限的人無所適從。

**我方立場:** 此為**請求裁決**,不是既成事實。
若 portal 認為應嚴格照字面,改為「全部 302」對我方成本很低(一個分支 + 四條測試調整),
**請直接回覆要求,我方即刻改正。**

參考:貴方登記表中 `portal-landing` 的處理是「首頁不做授權,只是門牌」,
與我方首頁的定位相近,故推測此解讀可被接受——但仍請明示。

## 7. 回饋建議(供契約下一版參考,非申請事項)

依契約 §8「App 側要改需求走 §5 流程」,以下三點為我方接入過程中的發現,
**僅供參考,不影響本次申請**。

### 7.1 §4.1 的 redirect URI 寫法未反映 D2″ 的子路徑

§4.1 目前寫「redirect URI 固定為 `https://<你的 hostname>/oidc/callback/`」,
但 D2″ 之後所有 App 都掛在子路徑下,實際值應含前綴
(§9 登記表中 compliance 的值 `.../compliance/oidc/callback/` 即為明證)。

**建議:** §4.1 的範例改為 `https://catsapp.sporton.com.tw/<你的子路徑>/oidc/callback/`,
避免新接入的 App 照字面登記而漏掉前綴——這種錯只會在登入當下才發現。

### 7.2 🐛 access token 300 秒對「伺服器端算繪的 App」有一個不明顯的陷阱

§3.3 將 access token 定為 300 秒,理由(收權即時性)我方完全認同。

但我方接入時發現:**伺服器端算繪、沒有前端 JS 的 App,沒有任何角色會去呼叫
refresh**。瀏覽器導覽不會自己 refresh,而 SSO session 有 10 小時——
結果是**使用者登入 5 分鐘後,所有頁面靜默退回「未登入」**,伺服器沒有任何錯誤。

我方已修正(在伺服器端以 refresh_token grant 換發,**真的去問 IdP**,
IdP 停用帳號時 refresh 失敗即登出,收權即時性不受影響)。

**建議:** 契約可補一句提醒——「若你的 App 是伺服器端算繪、無前端 JS,
必須在伺服器端處理續期;不要假設瀏覽器會替你 refresh」。
compliance(`mozilla-django-oidc` session 模式)與 sporton_core 的網頁部分
**可能面臨相同問題**。

> 附帶提醒:此缺陷在我方 240 條測試中**一條都沒抓到**,
> 因為測試用的假 IdP token 永不過期。建議各 App 檢查自己的測試替身是否也抹平了過期行為。

### 7.3 §4.3 的「雞生蛋」問題建議在契約中明示

契約要求首登一律零角色 + deny-by-default,但**開通的人自己也要先登入**——
第一個使用者登入後,沒有任何人有權開通他,系統實質鎖死。

我方以設定檔中的 bootstrap admin `sub` 清單解決(該人首登即為管理員)。
這需要**在部署前先取得該人的 `sub`**,是一個容易到上線當天才發現的前置條件。

**我方的解法(已實作,供參考):** 待開通頁(未開通者登入後看到的畫面)直接顯示
使用者自己的 `sub`,讓指定人選**自助**取得,不需 portal 或該人另外查 Keycloak 後台。
連帶效果是「先部署、後拿 sub」變成可行順序——不必等 sub 到手才能上線。

**建議:** 契約 §4.3 或 §5 流程補一句提醒各 App 準備此機制(或直接建議「待開通頁
顯示使用者自己的 sub」這個做法),而不必依賴 portal 逐一提供指定人員的 `sub`。
