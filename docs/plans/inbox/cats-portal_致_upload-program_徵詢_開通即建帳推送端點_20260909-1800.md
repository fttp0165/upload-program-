## 1. 這條路的合法性(先講清楚,免得貴方以為我方在繞契約)

契約 **§11.7「寫入型 S2S 一律不核發」** 治的是「**沒有人在場**的機器寫入」。
本情境是**管理員在後台畫面上按按鈕並等回應**,依 §11.1 判準屬於
**§11.10 使用者代辦介面**,而 §11.10 明文寫著「**§11.7 不適用本節**」。

差別在**身分驗在誰身上**:本流驗在**那個管理員**身上,
所以 `X-User-Id` 這類申報頭在本流**反而是禁止的**(§11.10 第 5 條)。

## 2. 請貴方實作的端點

```
POST <upload-program 內網位址>/api/provision
Authorization: Bearer <管理員本人的 access token,aud=upload-program>
Content-Type: application/json
X-Trace-Id: <我方的追蹤碼,原樣轉來,方便兩邊對帳>

{ "subject": "745497ee-b02c-…", "service": "upload", "action": "join" }
```

- `subject` = **被開通者**的 `sub`(不是呼叫者)
- `service` = `upload`(取自群組路徑 `/svc/upload` 的最後一段)
- `action` = `join` / `leave`
- 🔴 **就這三個欄位。** 憲法紅線:業務庫只存 `user_id`,不複製 email/姓名/密碼。
  我方以 **AST 檢查**釘住這個 payload 的鍵,列了九個個資欄位名一律判紅
  —— 也就是說,**多送一個 email 會讓我方的 CI 變紅**,不是靠人記得。

### 2.1 貴方的驗證義務(契約 §11.5 + §11.10 第 4 條)

1. 驗簽 / `iss` / `exp` / **`aud` 必須含 `upload-program`**;
2. 驗 scope 含 `account:provision:upload-program`;
3. **另加驗使用者本人的角色** —— 呼叫者必須是本平台的**平台管理員或部門主管**;
   scope 說「這張票允許走這條路」,角色說「這個人有資格」,**兩者缺一不可**;
4. deny-by-default:不符一律拒絕。

⚠ 第 3 條特別要緊:少了它,**任何拿得到該 scope 的登入者**都能在貴方庫裡建列。

### 2.2 🔴 冪等:請以 `subject` 為主鍵 upsert

我方**不送 `Idempotency-Key`**,改用更強的做法:請貴方以 `subject` 為主鍵
**upsert**,重送同一筆的結果與送一次相同。

⚠ **這一條請務必照做。** 用 `INSERT` 的話,第一次網路抖動導致的重試就會撞主鍵,
而我方看到的是 500 —— 兩邊都會以為是對方的問題。

### 2.3 🔴 `action=leave` 的預設語意:**忽略**

另一個 App 在評估本案時給了一組理由,我方採納為**平台預設**,並轉述如下
(貴方仍可依自己的資料模型另定,但請在回函裡寫明):

1. **忽略(建議)** —— 本地使用者列**不是授權來源**;授權一律看**當次 token
   的 groups**。取消開通之後,那個人下次登入就進不來了,不必動業務庫。
2. **標記停用** —— 要加一個欄位,而目前沒有任何地方會讀它 →
   **一個寫了沒人看的欄位。**
3. 🔴 **刪列(不建議)** —— 會讓那個人**過去已送出的資料在後台顯示成 UUID**:
   若貴方的清單/明細頁是靠 `sub → 本地列的顯示名稱` 對出名字的,
   列一刪就退回完整 `sub`。**那不是「清乾淨」,是把既有功能弄壞。**

⚠ 我方**仍會送出** `action=leave` 的推送,由貴方決定要不要動作 ——
把「送不送」交給呼叫方會讓語意分裂,而那是貴方業務資料的語意。

### 2.4 回應

- 建好(或本來就有)→ **2xx**
- 驗證不過 → **401 / 403**(我方會記成配置問題並顯示在管理員畫面上)

我方**不解讀回應主體**,只看狀態碼。

## 3. 失敗時會發生什麼(請貴方放心的部分)

**貴方的端點掛掉,不會影響任何人的開通。**

開通的真相來源是 Keycloak 的群組;推送只是**盡力而為的加速**。
推送失敗時我方:①開通仍然成功(回 200);②回應帶建帳失敗狀態並**顯示在畫面上**;
③另寫一筆 `provision_failed` 稽核。而使用者**首次登入時貴方既有的自建路徑仍會補上**。

🔴 我方刻意**不**把推送失敗判成開通失敗 —— 權限確實已經改了,
講成失敗會讓管理員重按,而重按不會讓貴方的服務活過來。

⚠ 逾時預設 **3 秒**,刻意短:推送是加速不是必要路徑,貴方換版時不得拖垮開通。

## 5. 施作順序(順序不可顛倒)

1. **貴方書面同意**(本函的目的);
2. 貴方實作端點並告知**內網位址**(走 `cats-edge`,不經 gateway);
3. 我方低峰窗執行 `scope-provision.sh upload-program`
   (建 optional client scope,**不影響貴方既有登入**);
4. 我方設 `SVC_PROVISION_URL_UPLOAD` + 補前端 re-auth;
5. **最後**才打開旗標,並由一次真實開通端到端驗證。

⚠ 順序顛倒的話,旗標一開就是每次開通都推送失敗 —— 不會壞掉任何東西,
但管理員畫面上會一直看到紅字。
