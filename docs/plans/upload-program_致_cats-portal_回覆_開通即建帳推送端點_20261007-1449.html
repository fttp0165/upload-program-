1. 我方的驗證(來函 §2.1,四層全做)

# 檢查 不過
① 驗簽 / RS256 / iss / exp(既有 JWKS 驗證) 401
② aud 明確含 upload-program 401
③ scope 含 account:provision:upload-program(整詞比對) 403
④ 呼叫者本人:realm 角色含 portal-admin,或任一群組以 /mgr/ 開頭 403

需要貴方確認的兩點:

  1. ④ 的兩個名字是照貴方現況寫的:平台管理員角色 portal-admin(貴方 ADMIN_REALM_ROLE 預設值)、 主管群組前綴 /mgr/(貴方 kc.MGR_PREFIX)。我方已設定化(PROVISION_ADMIN_ROLE、 PROVISION_MANAGER_GROUP_PREFIX),貴方若改名請通知。 🔴 前提是貴方的推送 token 必須帶 realm_access.roles 與 groups 兩個 claim —— 少了的話,所有推送都會在 ④ 得到 403,而那看起來像權限問題,實際是 token 內容問題。
  2. 🔴 我方驗不到「管轄範圍」:部門主管能不能開通這一個人,需要組織資料,只有貴方有。 這一層請由貴方 _guard_target 守住;我方擋的是「根本不是管理者的人拿到 scope」。

⚠ 關於 ②:本服務既有的 token 驗證對 Keycloak 登入 token 有一條「aud 不含本服務時看 azp」的退路。 推送端點刻意不吃這條退路 —— 推送 token 的 azp 是 portal-admin,它能進來的唯一理由 必須是 aud 裡明寫了 upload-program。

2. 行為

action 我方庫裡已有那個人 沒有
join 一個欄位都不動,200 建一列 待開通(pending),201,寫稽核 user.provision
leave 忽略,200 忽略,200
  • 冪等:以 sub 唯一鍵,重送結果相同;並發撞鍵也回 200(來函 §2.2)。
  • 🔴 建的是「待開通」,不是「已開通」。 本服務的「誰能用」看本地狀態,由本服務管理員決定 (契約 §4.4)。推送解的是「人不在庫裡就設不了」 —— 現在管理員可以在那個人登入之前, 就在本服務後台把他開通、設角色、設單檔上限。推送本身不授予任何權限。
  • 已被本服務停用的人,推送不會解除停用。
  • 只收三個欄位:payload 多一個欄位(例如 email)→ 422。這是我方這一側對 「業務庫只存 sub」的結構保證,與貴方的 AST 檢查各守一道。
  • subject 必須是小寫標準形 UUID;service 必須是 upload;不符 → 422。 🔴 422 代表貴方的設定或程式錯了(不是暫時性失敗),重試不會好。

3. leave=忽略 在本服務的實際效果(請寫進登記表)

來函 §2.3 的第 1 點理由是「本地使用者列不是授權來源,授權看當次 token 的 groups」。 🔴 這一點在本服務不成立:本服務的授權看本地狀態,不看 groups (T63:/svc/upload 只讀不判,等貴方另行通知才接)。

所以在本服務,leave 被忽略的意思是: 貴方取消開通 /svc/upload,那個人在本服務仍然是已開通的,直到本服務管理員手動停用。 這與推送上線前完全相同(沒有變差),但不要讓任何人以為取消開通會連帶收權。

我方仍然選「忽略」而不是「收到 leave 就停用」,理由: 停用是本服務管理員的刻意決定,而貴方的群組變動可能來自別的原因(調部門、整理群組); 讓群組變動自動停用一個正在用的人,會在使用者那一側表現成「突然進不去」,而原因在別的系統。 若貴方認為 leave 應連帶停用,請來函,我方另立任務評估。

4. 一個貴方要知道的限制:本服務管理員看到的是 UUID

推送只帶 sub,所以被推送建出來的那一列沒有名字,本服務後台會顯示 sub 前 8 碼, 直到本人第一次登入(依 §4.2a L1 填入名字)。 本服務管理員要開通「還沒登入過的人」時,需要另一個管道對上「這個 UUID 是誰」 —— 例如貴方後台顯示該人的 sub。這不是本次要解的,只是先講,免得試點時被當成錯誤。
