0. 三題答覆(來函 §6)

# 問題 答覆
1 同意擔任試點? ✅ 同意。 端點已實作並有測試(見 §2),合併後隨下一版發布
2 端點路徑與內網位址 POST http://upload-program:8080/v1/provision(cats-edge 別名 upload-program,不經 gateway)。⚠ 路徑是 /v1/provision,不是來函範例的 /api/provision —— 本服務所有 API 都在 /v1/ 底下
3 action=leave 🔴 不採來函 §2.3 的「忽略」,改為停用。 我方決定(Benny 2026-10-07 裁示):portal 的開關就是本服務的開關 —— join 直接開通、leave 直接停用。理由與後果見 §3

貴方 .env 設定值(供施作順序第 4 步直接抄):

PORTAL_ADMIN_SVC_PROVISION_URL_UPLOAD=http://upload-program:8080/v1/provision

所需 scope 名稱:account:provision:upload-program (= scope-provision.sh upload-program 會建出來的那一個;我方由自己的 client_id 推導,不另設定)。

1. 我方的驗證(來函 §2.1,四層全做)

# 檢查 不過
① 驗簽 / RS256 / iss / exp(既有 JWKS 驗證) 401
② aud 明確含 upload-program 401
③ scope 含 account:provision:upload-program(整詞比對) 403
④ 呼叫者本人:realm 角色含 portal-admin,或任一群組以 /mgr/ 開頭 403

需要貴方確認的兩點:

  1. ④ 的兩個名字是照貴方現況寫的:平台管理員角色 portal-admin(貴方 ADMIN_REALM_ROLE 預設值)、 主管群組前綴 /mgr/(貴方 kc.MGR_PREFIX)。我方已設定化(PROVISION_ADMIN_ROLE、 PROVISION_MANAGER_GROUP_PREFIX),貴方若改名請通知。 🔴 前提是貴方的推送 token 必須帶 realm_access.roles 與 groups 兩個 claim —— 少了的話,所有推送都會在 ④ 得到 403,而那看起來像權限問題,實際是 token 內容問題。
  2. 🔴 我方驗不到「管轄範圍」:部門主管能不能開通這一個人,需要組織資料,只有貴方有。 這一層請由貴方 _guard_target 守住;我方擋的是「根本不是管理者的人拿到 scope」。

⚠ 關於 ②:本服務既有的 token 驗證對 Keycloak 登入 token 有一條「aud 不含本服務時看 azp」的退路。 推送端點刻意不吃這條退路 —— 推送 token 的 azp 是 portal-admin,它能進來的唯一理由 必須是 aud 裡明寫了 upload-program。

2. 行為(T147:portal 開關 = 本服務開關)

action 我方庫裡狀態 結果 HTTP
join 沒有 建一列並直接開通 201
join 待開通 / 已停用 開通 200
join 已開通 不動 200
leave 已開通 / 待開通 停用 200
leave 已停用 / 沒有 不動(沒有就不建列) 200
leave 對象是本服務唯一一位平台管理員 🔴 不動 409
  • 只動「能不能用」:名字、信箱、本服務的平台管理員身分一律不碰。
  • 冪等:以 sub 唯一鍵,重送結果相同,第二次不再寫稽核(來函 §2.2)。
  • 稽核:開通/停用與本服務後台按鈕用同一組 action(user.activate / user.disable), 新建另記 user.provision;操作者若在本服務有帳號就記他,沒有就記「系統」, 完整的「誰按的」以 X-Trace-Id 對回貴方稽核。
  • 只收三個欄位:payload 多一個欄位(例如 email)→ 422。這是我方這一側對 「業務庫只存 sub」的結構保證,與貴方的 AST 檢查各守一道。
  • subject 必須是小寫標準形 UUID;service 必須是 upload;不符 → 422。 🔴 422 代表貴方的設定或程式錯了(不是暫時性失敗),重試不會好。
  • 🔴 409 的意思:不讓 portal 一個點擊就讓本服務沒有任何管理員進得了後台。 請在貴方畫面上把它顯示成「推送失敗」—— 管理員需要先在本服務指派另一位管理員。

3. 為什麼不採「leave = 忽略」,以及貴方因此要知道的三件事

來函 §2.3 的第 1 點理由是「本地使用者列不是授權來源,授權看當次 token 的 groups」。 🔴 這在本服務不成立:本服務的授權看本地狀態,不看 groups。 所以若 join 直接開通而 leave 忽略,結果是開得了、關不掉 —— 兩條必須一起改。

貴方因此要知道:

  1. 🔴 leave 推送失敗 = 那個人在本服務仍然可用。 在 T147 之前,推送失敗只是「少了加速」; 現在取消開通的推送失敗,收權就沒有發生。貴方的「失敗語意第三種」(畫面顯示 + provision_failed 稽核)在這裡從「提醒」變成「唯一的線索」,請確保管理員看得到。
  2. ⚠ 旗標打開之前就已開通 / 已取消的人不會被補送。 第一次打開旗標時, 貴方 /svc/upload 成員與我方已開通名單可能不一致;需要一次性對帳(我方可提供已開通者的 sub 清單)。
  3. ⚠ 本服務管理員手動停用的人,貴方再按開通就會恢復 —— 我方沒有欄位區分「誰停用的」, 以貴方為準。部門主管因此等同能開通本服務:管轄範圍請由貴方 _guard_target 守住(見 §1 第 2 點)。

本服務後台的開通 / 停用按鈕保留,作為推送失敗時的補救。

4. 推送建出的列沒有名字

推送只帶 sub,所以被推送建出來的那一列沒有名字,本服務後台顯示 sub 前 8 碼, 直到本人第一次登入(依 §4.2a L1 填入名字)。這不影響使用(開通已經生效),只影響本服務後台的辨識。
