# 申請:將顯示名稱快取的用途擴大至「專案頁擁有者辨識」

**專案:** upload-program
**發文專案:** upload-program
**受文專案:** cats-portal
**發文時間:** 2026-08-12 19:30
**建立日期:** 2026-08-12 19:30
**最後更新:** 2026-08-12 19:30
**版本:** v1.0
**申請標的:** 帳號系統接入契約 **§4.2a L1** 之**用途**一項的範圍調整
**裁示前狀態:** 本專案**未顯示任何名字**——專案頁目前以 `sub` 前 8 碼過渡。
本文件是申請,不是通知。

---

## 1. 為什麼再來一次

2026-07-29 我方申請顯示名稱快取,貴方核准並寫進契約 §4.2a L1。
那份申請書的「用途」欄是**我方自己**寫的:

> 僅管理後台顯示(使用者管理、稽核紀錄的操作者辨識);
> **不出現在一般使用者可見頁面**、不進 API 回應、不作任何授權判定依據

當時把範圍縮到最小,是為了讓申請容易評估——這一點我方不後悔。
但上線營運後出現一個當時沒想到的場景,本文件請求**只調整用途一項**。

## 2. 現場問題

本服務是公司內部的**程式分享平台**:使用者上傳並互相下載
原始碼、**執行檔**與說明文件。

專案頁是使用者按下「下載」之前看到的最後一個畫面。目前那一頁能告訴他的是:
檔名、大小、SHA-256、掃毒狀態、容量、時間——**唯獨沒有「這是誰放的」**。

這在一般系統只是不方便,在本服務是**安全問題**:

- 🔴 **掃毒尚未接上**,每個檔案誠實標示 `not_scanned`(契約無關,是我方自我加嚴)。
  在沒有自動掃描的情況下,「發布者是誰」是使用者判斷要不要執行這支程式的
  **唯一**依據。
- 認不出發布者,使用者只有兩種選擇:全部信任,或全部不信任。兩種都不是我們
  想要的結果。
- 這與稽核紀錄的情況同構——貴方當初核准「稽核要認得出操作者」的理由是
  「認不出人的稽核紀錄等於沒有稽核紀錄」;認不出發布者的程式分享平台,
  在信任這件事上是一樣的處境。

## 3. 申請內容:只動「用途」一欄

| 欄位 | 現行 | 申請後 | 變動 |
|---|---|---|---|
| 快取內容 | 僅 `name` claim,不含 email | **同左** | 無 |
| 來源 | 使用者本人登入時的 ID token;**不呼叫 Admin API** | **同左** | 無 |
| 更新 | 每次登入覆寫(含覆寫成 NULL) | **同左** | 無 |
| **用途** | **僅管理後台顯示** | 管理後台顯示 **+ 專案頁 / 版本頁的擁有者、上傳者辨識** | ✅ **本申請** |
| 不進 API 回應 | 是 | **同左(維持)** | 無 |
| 不作授權判定依據 | 是 | **同左(維持)** | 無 |
| 可整批清除 | 是 | **同左** | 無 |

**請注意本申請刻意不含的東西:**

- ❌ **不申請** Admin API 或任何新的 IdP 權限(契約 v2.0 §4.2a L1 已明文禁用,
  我方接受;先前的 T73 申請書據此需重寫,另案處理)。
- ❌ **不申請**把名字放進 JSON API——只有 HTML 頁面。
  API 帶名字等於開一條整批匯出姓名對照表的路,這條界線我方主動維持。
- ❌ **不申請**任何新欄位、不動資料庫結構。快取欄位早已存在且已獲准。
- ❌ **不申請**顯示 email 或 `preferred_username`。

換句話說:**揭露面沒有變大,只是同一個已獲准的欄位多一個顯示位置**,
而且觀看者一律是**已登入且已開通**的內部同仁(本服務無匿名瀏覽)。

## 4. 我方在等待期間的做法

不等裁示、也不自行放寬。專案頁已加上「擁有者」欄位,顯示 **`sub` 前 8 碼**:

```
擁有者    a1b2c3d4…    識別碼(顯示名稱待平台核准)
```

- `sub` 是不透明識別碼、不是個資,而且業務庫本來就只存它(§4.2 的要求)。
- 截斷 8 碼比照管理後台既有慣例:僅供人眼對照,不給完整值。
- 旁邊照實標註「待平台核准」——做不到的事就明說,與 `not_scanned` 同一個態度。

獲准後,把這一格換成名字是**一行的事**;不准的話這個過渡狀態可以無限期維持,
不會有殘留。三條自動化測試釘住現況(欄位存在、**名字不得出現**、
**完整 sub 不得外流**),所以在裁示之前不可能有人不小心把名字放上去。

## 5. 契約增修建議稿(供貴方裁量,文字可自由改寫)

> §4.2a L1 用途一項,建議調整為:
>
> 「僅供**本服務 HTML 頁面**之使用者辨識——包含管理後台(使用者管理、稽核
> 紀錄的操作者)與**專案/版本頁的擁有者、上傳者**;不進 API 回應、
> 不作任何授權判定依據、不得再散布至本服務以外。」

## 6. 若貴方不同意

完全可以接受,我方維持 `sub` 前 8 碼的現狀,不會再提。
若不同意,懇請順帶指點一個方向:在不落地任何姓名的前提下,
**有沒有平台認可的方式讓使用者辨識發布者?**(例如平台提供的暱稱服務、
或由使用者自行在本服務設定一個與 IdP 無關的顯示暱稱。)
後者我方可以自建,但那等於在本服務造出第二套身分資料,
在提出之前想先聽貴方意見——這正是本文件而不是逕行實作的原因。
