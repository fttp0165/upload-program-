0. 建議裁示(五題,附理由)

# 題目 建議 理由
1 貼圖要不要 inline 顯示 ✅ 要,但依 §4.2 六條收窄 回報的價值有一半在截圖;要使用者「下載附件再自己開」會讓人乾脆不附圖,那等於沒收到那半的資訊。風險可用型別白名單 + 權限 + nosniff 壓到可接受
2 富文本形式 ✅ Markdown + 伺服器端白名單轉譯 同源之下一次 XSS = 全平台帳號淪陷;WYSIWYG 要收 HTML、要自託管編輯器 JS,兩者都在放大攻擊面。Markdown 的表達力對「回報一個問題」綽綽有餘
3 可見範圍 ✅ 僅回報者本人 + 平台管理員 回報常夾帶畫面截圖與內部資料;全站可見會讓人不敢寫實情,反而降低回報品質
4 保存期 ✅ 已關閉滿 365 天清除(工具 + cron,不自動跑) 與稽核同一節奏、同一模式;內容是使用者自由書寫,不該無限期留存
5 施工範圍 ✅ 分三期,先交付 T77 沒有附件的回報系統已經能收到問題;附件是風險最高的部分,值得單獨一個 PR 專心審

若第 1 題你選「維持 attachment」,施工計畫只需把 §4.2 的 inline 端點改為 沿用既有下載標頭,其餘不變——T78 的工作量與風險都會下降。

2. 資料庫變更

2.1 第一期 migration 0007_issues

CREATE TABLE issues (
    id              UUID PRIMARY KEY,
    reporter_id     UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    title           VARCHAR(200) NOT NULL,
    body_markdown   TEXT NOT NULL,
    status          issue_status NOT NULL DEFAULT 'open',
    page_url        VARCHAR(512) NOT NULL DEFAULT '',
    app_version     VARCHAR(32)  NOT NULL DEFAULT '',
    created_at      TIMESTAMPTZ NOT NULL,
    updated_at      TIMESTAMPTZ NOT NULL,
    closed_at       TIMESTAMPTZ,
    closed_by_id    UUID REFERENCES users(id) ON DELETE RESTRICT
);
CREATE INDEX ix_issues_reporter ON issues (reporter_id);
CREATE INDEX ix_issues_status   ON issues (status, created_at DESC);

CREATE TABLE issue_comments (
    id             UUID PRIMARY KEY,
    issue_id       UUID NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
    author_id      UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    body_markdown  TEXT NOT NULL,
    is_staff_reply BOOLEAN NOT NULL DEFAULT FALSE,
    created_at     TIMESTAMPTZ NOT NULL
);
CREATE INDEX ix_issue_comments_issue ON issue_comments (issue_id, created_at);
  • ON DELETE RESTRICT(對 users):有回報紀錄的使用者刪不掉——與稽核同一個立場。
  • ON DELETE CASCADE(comments → issue):回報刪掉時討論串一起走,不留孤兒。
  • issue_status 用 enum type(與現有 _enum() 慣例一致)。
  • 🔴 revision id 用檔名全名 0007_issues(v0.1.3 事故的結論)。

2.2 第二期 migration 0008_issue_attachments

CREATE TABLE issue_attachments (
    id             UUID PRIMARY KEY,
    issue_id       UUID NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
    comment_id     UUID REFERENCES issue_comments(id) ON DELETE CASCADE,
    storage_key    VARCHAR(512) NOT NULL,
    content_type   VARCHAR(64)  NOT NULL,   -- 判定出來的,不是使用者宣稱的
    size_bytes     BIGINT NOT NULL,
    sha256         VARCHAR(64) NOT NULL,
    uploaded_by_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    created_at     TIMESTAMPTZ NOT NULL
);
CREATE INDEX ix_issue_attachments_issue ON issue_attachments (issue_id);

MinIO key 前綴 issues/{issue_id}/{uuid},與 artifacts 完全分開。

4. 安全設計(逐條要有測試)

4.1 Markdown 轉譯

  • 伺服器端轉譯,輸出標籤白名單:p br strong em code pre ul ol li a img blockquote h3
  • a:只准 http/https,強制 rel="noopener noreferrer";javascript: / data: 一律剝除
  • img:只准指向我方附件端點(相對路徑 /upload/v1/issues/...),外部圖片一律剝除 ——否則回報頁會變成對外發請求的載體(追蹤像素、內容外洩)
  • 原始 HTML 一律逸出,不論白名單(Markdown 的 md_in_html 不啟用)
  • 轉譯後的結果不存回資料庫(存的永遠是 Markdown 原文,轉譯是顯示時的事)

4.2 inline 圖片端點的六條收窄

  1. 只有這一條路徑是 inline;/v1/releases/.../download 完全不動
  2. 型別由 magic bytes 判定,只放行 image/png image/jpeg image/gif
  3. 🔴 SVG 一律拒收(可執行的 XML)
  4. 回應帶 X-Content-Type-Options: nosniff;Content-Type 用判定值
  5. 僅回報者本人與平台管理員可讀,其他人 404
  6. 單張 ≤ 5 MB、單則回報 ≤ 5 張

5. 測試計畫(先紅後綠)

第一期(T77)預估 20–24 條

  • 權限矩陣逐格(上表 24 格擇要 12 條)
  • 🔴 XSS:<script>、<img onerror>、javascript: 連結、data: 圖片、內嵌 HTML → 全部不得出現可執行內容
  • 🔴 外部圖片被剝除(![](https://evil/x.png) 不得產生對外請求的 <img>)
  • 狀態機:合法轉移成功、非法轉移被拒、每次變更有稽核
  • 建立時自動帶入 app_version 與 page_url
  • 清單:分頁、狀態篩選、空狀態、他人的回報不出現
  • migration up→down→up

第二期(T78)預估 12–15 條

  • HTML / SVG / PDF 偽裝成 .png → 一律拒收且不留物件
  • inline 端點:三種型別各一條、nosniff 存在、Content-Disposition 不是 attachment
  • 非本人非管理員 → 404
  • 單張超過 5 MB → 413;第 6 張 → 422
  • 🔴 回歸測試:/v1/releases/.../download 仍然是 attachment(確保沒被順手改壞)
  • 關閉 JS 的情境:表單仍可送出(以無 JS 的純 POST 驗)

第三期(T79)預估 6–8 條

  • 管理總覽待辦出現「未處理回報 n」且數字正確;無回報時不出現
  • 清除工具:只刪「已關閉滿 365 天」者,連同附件物件一起刪;未達期限不刪

7. 風險與回滾

風險 處置
🔴 轉譯器漏洞導致 XSS 白名單而非黑名單;不啟用任何「允許原始 HTML」的選項;XSS 測試涵蓋五種載體;轉譯結果不落庫(改規則即全站生效)
🔴 inline 端點被拿來當圖床 / 外洩管道 權限限本人與管理員、型別白名單、大小與張數上限、走稽核
回滾會刪掉使用者的回報 DROP TABLE 列入 runbook 的不可逆清單;回滾前必備份
沒有通知機制,回報石沉大海 管理總覽待辦顯示未處理數;頁面明說「不會寄信,請回來看」
附件佔滿磁碟 單張 5 MB × 5 張上限;清除工具;總覽的儲存 KPI 已能看見成長
