1. T101 管理員權限(規模:小)

現況:後端早就做完了

  • User.platform_role(member / admin)欄位存在;
  • PATCH /v1/admin/users/{id} 已經可以改 platform_role,而且有稽核;
  • 管理後台的使用者清單已經會顯示「管理員」徽章;
  • BOOTSTRAP_ADMIN_SUBS 讓第一個管理員能從 .env 帶進來(否則雞生蛋)。

唯一缺的是網頁上的按鈕——跟 T100 同一個形狀:功能在,入口沒有。 目前要指派管理員只能自己打 API。

提案

/admin/users 每一列加「設為管理員 / 取消管理員」按鈕(POST 表單)。

🔴 三條防呆(這是給權限,不是給顏色)

  1. 不能取消自己的管理員身分——不然一個人手滑就沒人管得動系統了 (平台無 root 後門,只能改 .env 重啟)。
  2. 不能把「未開通」的人設為管理員:待開通是 deny-by-default 的狀態, 跳過開通直接給管理權等於繞過自己的門禁。
  3. 稽核照記(user.role_change 已存在),誰把誰升成管理員必須查得到。

驗收

授權變更走既有 API 路徑(不另寫一套權限邏輯);三條防呆各一條測試。

2. T102 發布審核(規模:🔴 最大)

這一項改變的是系統的核心承諾

現在的模型是兩態:draft(作者的工作區)→ published(大家可下載)。 你要的是三態:作者發布後先進「待審」,管理員准了才真的能下載。

這牽動的東西比看起來多:

牽動 說明
ReleaseStatus 列舉 加 pending_review(或 approved 另立欄位)——migration 🟡
latest_published_release() 「最新版」的定義要改成「最新已核准版」
下載端 每個 artifact 下載都要多一道狀態檢查
固定連結 F26 /releases/latest/artifacts/{name}/download 的語意跟著變
管理後台 要有審核佇列(核准 / 退回 + 理由)
通知 平台沒有 email / 推播——作者怎麼知道被退回?只能靠站內顯示
既有資料 現在已發布的版本,migration 時要當成「已核准」還是「待審」?

兩項設計(提案時為建議,§6 已裁示採納)

建議 A:退回時必須寫理由。 沒有理由的退回,作者只能猜,然後重傳一次一模一樣的東西。 理由欄位不是裝飾,是這個流程能不能運轉的關鍵。

建議 B:待審版本對「非成員」直接隱藏,不是顯示但不能下載。 顯示一個下載不了的版本,對使用者是純粹的挫折;而且「這個專案有一版正在審」 本身也是資訊。專案成員仍看得到(他們要知道自己送審的東西卡在哪)。

🔴 一個必須先想清楚的風險

審核會卡住發布流程。平台目前沒有任何通知管道(T79 已載明「不會寄信」), 所以:作者送審 → 管理員不知道有東西要審 → 版本卡住 → 作者以為系統壞了。

緩解:管理總覽的「待辦」區已經有「未處理的回報」,審核佇列比照加一項; 但這仍然要求管理員主動去看。如果實際運作上沒人天天看後台, 這個功能會製造比它解決的更多問題——這是要你評估的營運現實,不是技術問題。

3. T103 專案回饋(規模:中)

現況

平台有問題回報系統(T76–T79),但那是「回報這個網站的問題」, 只有本人與平台管理員看得到(🔴 404 不洩漏存在)。 它不是專案層的公開回饋,兩者的可見性設計完全相反。

三種可能的解讀,工作量差很多

解讀 是什麼 規模
(a) 專案留言板 專案頁下方一串留言,成員與使用者都能留 中(加一張表)
(b) 版本層回饋 每個版本各自的意見(「v1.2 在 Win11 會閃退」) 中偏大
(c) 評分 / 有用嗎 👍/👎 或星等,只計數不留文字 小

我方建議 (a):文字回饋對「這支程式好不好用」的價值遠高於分數, 而且與既有的 IssueComment 結構相近,可以沿用同一套逸出與長度限制。

🔴 不論哪一種都要面對的三件事

  1. 誰看得到:專案是 internal 的話,回饋跟著 internal;private 專案的回饋 絕不能外洩(比照 visible_projects_condition)。
  2. 留言者的身分怎麼顯示——又撞到契約 §4.2a L1(見 §4)。 在獲准之前只能顯示 sub 前 8 碼,一串 UUID 的留言板體驗很差。
  3. 保留與清理:留言會長期累積。purge_issues.py 有 365 天清理的先例, 回饋要不要比照?

一個要澄清的語意問題

「作者屬名」是指建立這一版的人,還是按下發布鍵的人? 現在只記前者(created_by_id)。若兩者可能不同(例如 jack 建版、benny 發布), 要新增 published_by_id 欄位——那就從 🟢 變成 🟡 加欄位 + migration。 §6-3 已裁示:採「建立這一版的人」,維持 🟢 不動資料。

5. 建議的施工順序

T101 管理員權限(小、無依賴)
   ↓  ← 必須先有可指派的管理員,審核才有人可審
T102 發布審核(最大、要 migration)
   ↓
T104 版本屬名(小;與 T102 同樣動版本頁,一起改省一次回歸)
   ↓
T103 專案回饋(獨立,可最後做)

🔴 T101 必須排在 T102 之前:審核制度需要「管理員」這個角色實際可指派, 否則上線當天會發現只有 .env 裡那一個 bootstrap 管理員能審,全部卡在他身上。

6. Benny 的裁示(2026-08-12 22:35)

# 問題 裁示
1 審核範圍 ✅ 做,所有版本都要審(無專案層開關——開關本身會變成繞過審核的路)
2 既有已發布版本 ✅ 依建議:migration 時一律視為已核准(不讓正在用的東西當天全部不能下載)
3 屬名指誰 ✅ 建立這一版的人(created_by_id,🟢 不動資料);日後若實務上常是 A 建版 B 發布,再加 published_by_id
4 回饋形態 ✅ 專案留言板

隨裁示確定的三項設計(原為建議,現為定案):

  • 退回必須寫理由;
  • 待審版本對非成員隱藏,專案成員看得到(他們要知道自己送審的東西卡在哪);
  • 🔴 通知缺口照實面對:管理總覽的待辦區加「待審版本」一項。 這仍要求管理員主動看後台——這是已知的營運限制,不是被忽略的問題, 上線後若發現版本常卡住,要回頭檢討的是流程不是程式。
