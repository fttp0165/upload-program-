申請:以 Keycloak Admin REST API 即時查詢顯示名稱(取代落地快取)

建立日期: 2026-07-31 21:40 最後更新: 2026-07-31 21:40 版本: v1.0 發文方: upload-program(申請人:Benny) 收文方: cats-portal / Platform 申請標的: 授予唯讀 view-users 之 service account,供管理後台即時查詢使用者顯示名稱; 本服務隨後移除已獲准的落地快取欄位(§4.2a L1 / §6.1 具名特例) 裁示前狀態: 本專案不動任何程式與資料庫——本文件是申請,不是通知。

🔴 本文推翻我方 2026-07-29 申請_姓名快取特例 §3 的評估結論。 當時我方主張「Admin API 是更大的授權面,為了顯示名字拿管理權限不成比例」, 貴方據此核准了較小的落地快取。現在我方改變立場,理由見 §2—— 這一點必須明講,不能讓貴方以為前後是同一套說法。

1. 現況

依 §4.2a L1 具名特例,本服務 users 表有一個 display_name_cache 欄位 (僅 name claim、登入時覆寫、僅後台顯示、不進 log、可整批清除,migration 0006)。 功能運作正常(2026-07-30 上線實測,管理後台顯示「benny lin 745497ee…」)。

2. 為什麼要改(Benny 2026-07-31 裁示)

個資最小化的最佳解是「根本不落地」。 目前的快取雖然受控,但畢竟:

現況(落地快取) 改為即時查詢
姓名寫進我方業務庫,隨 DB 備份一起複製到備份檔 我方資料庫與備份完全沒有姓名
使用者改名後,要等他再次登入才會更新 永遠是 IdP 的當下值
離職者的姓名留在我方庫,直到有人跑清除工具 帳號一停用,查詢即反映;無殘留
需要契約具名特例才合法 只顯示不儲存,回到 §4.2 的原則之內

換句話說,這是把「受控的例外」換成「不需要例外」。代價是需要一個新的權限, 以及執行期對 IdP 的依賴——這兩點在 §4、§5 說明。

3. 請求的權限(請儘量收緊)

項目 內容
形式 專用 confidential client + service account(不重用登入用的 upload-program client)
角色 僅 realm-management:view-users(唯讀)。不需要 manage-users、不需要 view-clients、不需要 query-groups 以外任何權限
呼叫端點 GET /admin/realms/{realm}/users/{sub} 單筆查詢;不使用 GET /users(列舉全 realm)
呼叫來源 僅伺服器端,經內部端點(同 T60 對齊:http://keycloak:8080/auth/...),不經瀏覽器
觸發時機 僅管理後台頁面(使用者管理、稽核紀錄)渲染時,依畫面上的 sub 逐一查詢;一般使用者頁面永不觸發
憑證 client secret 走 .env(chmod 600、不進 git),與現行 SSO secret 同一套保管方式

若貴方認為 view-users 仍過大,我方接受任何更小的替代介面,例如 portal 提供 一支「sub → 顯示名稱」的唯讀端點(我方改呼叫它即可,設計上是同一件事)。

4. 我方的實作承諾

  1. 只顯示不落地:查得的姓名不寫入資料庫、不寫入檔案、不進 log; 僅存在於單次請求的記憶體中,回應送出即消失。
  2. 不列舉:只用 sub 單筆查;不呼叫任何列舉端點,不建立本地目錄副本。
  3. 失敗不擋人:IdP 逾時或錯誤 → 該列回退顯示 sub,頁面照常可用 (§5 的耦合風險由此控制);逾時上限 2 秒、不重試。
  4. 請求內去重:同一頁多列相同 sub 只查一次;不做跨請求快取 (跨請求快取就是另一種落地,只是換到記憶體)。
  5. 移除既有落地:本案上線後,提供 migration 移除 display_name_cache 欄位 (🔴 刪欄位=刪資料,依我方憲法先備份、於 staging 雙向演練;backward 為重新加回 nullable 欄位), 並請貴方撤銷 §6.1 對本服務的具名特例——例外不該留著不用。
  6. 依憲法流程執行(先計畫、TDD 先紅後綠、開發日誌);任務編號 T73,裁示前不動工。

5. 我方自評的風險(不隱瞞)

風險 說明與處置
授權面擴大 service account 能讀全 realm 使用者資料——比目前的「登入者自己的 name claim」大。處置:專用 client、僅 view-users、僅單筆查、只在後台頁觸發
執行期耦合 IdP 抖動會影響管理後台。處置:2 秒逾時 + 回退顯示 sub;/health 不受影響,/ready 維持現行語意
後台頁效能 每列一次 API 呼叫。處置:管理頁本來就有分頁上限(200 筆),請求內去重;若貴方提供批次端點更佳
稽核頁的操作者欄 同樣改為即時查詢;查不到時顯示 user_id,不影響稽核紀錄本身的完整性

6. 需要貴方回覆的事項

  1. 是否同意授予 view-users service account?或改以 portal 提供的唯讀端點替代?
  2. 若同意:client 名稱、secret 交付方式(比照 SSO client 的安全管道)、realm 名稱確認。
  3. 具名特例的撤銷時點:我方建議「即時查詢上線並通過冒煙後」, 由我方通知貴方,再由貴方更新契約 §6.1。
  4. 過渡期間(貴方裁示前)我方維持現行快取——它仍是合法且已獲准的做法。
