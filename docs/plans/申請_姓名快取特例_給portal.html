申請:顯示名稱快取之契約具名特例(upload-program)

建立日期: 2026-07-29 15:00 最後更新: 2026-07-29 15:00 版本: v1.0 發文方: upload-program(申請人:Benny) 收文方: cats-portal / Platform 申請標的: 帳號系統接入契約 §4.2「業務庫只存 sub」之具名特例(比照 PLM §6.1 模式) 裁示前狀態: 本專案不動任何資料庫欄位——本文件是申請,不是通知。

1. 問題(營運實測,2026-07-29 上線首日)

契約 §4.2 之下,本服務管理後台的使用者清單只有 sub(UUID):

be9a536c-db97-470a-802e-14de7a7dd279   active   [停用]
745497ee-b02c-4063-a71f-6a775c40c0bf   active   管理員(你自己)

開通流程沒有問題:申請人到「待開通」頁複製自己的 sub 傳給管理員,一對一開通, 這是契約設計內的做法,我們照做且運作正常。

問題出在開通之後的日常管理:

  • 清單累積後,管理員面對一排 UUID 無法辨識誰是誰; 要停用某人、查某人的稽核紀錄,都得先翻出當初的 sub 對照(訊息紀錄、便條)
  • 稽核頁的「操作者」同樣只有識別碼,追查操作要人工二次對照
  • 使用者數成長後,這個對照成本線性增加,而且對照表本身 (管理員私下記的「誰=哪串 UUID」)反而成了契約管不到的影子個資—— 比受控的快取更糟

2. 請求

比照 PLM 的契約 §6.1 具名特例,准許 upload-program 快取使用者顯示名稱:

項目 內容
快取內容 僅顯示名稱(OIDC token 的 name claim);不含 email、不含其他個資
來源 使用者本人登入時服務已合法取得的 ID token——不另呼叫 Keycloak Admin API,不新增對 IdP 的權限需求
更新 每次登入覆寫(改名、離職停用後重登入自動反映;無背景同步)
用途 僅管理後台顯示(使用者管理、稽核紀錄的操作者辨識);不出現在一般使用者可見頁面、不進 API 回應、不作任何授權判斷依據
儲存 業務庫 users 表加一個 nullable 欄位(如 display_name_cache);未再登入者維持空值(畫面照舊顯示 sub)
清除 提供整批清除工具(比照 tools/purge_audit.py 模式);個別使用者資料刪除請求可即時清除
日誌 顯示名稱不進 log(維持現行「log 不記個資」鐵則)
備份 隨 DB 備份(既有備份保存 14 天輪替,無另外複本)

建議契約增修文字(供 portal 起草參考)

§6.1 增列:upload-program 得於業務庫快取使用者顯示名稱,限自該使用者 本人登入時之 ID token name claim 取得,每次登入覆寫;僅供管理後台辨識, 不得含 email、不得用於授權判斷、不得進入日誌;應提供整批清除機制。

3. 已評估的替代方案(以及為何不採)

方案 評估
維持現狀(sub 人工對照) 開通可行;日常管理隨人數線性惡化,且催生管理員私記的影子對照表——個資落在契約管轄外,風險更高
即時呼叫 Keycloak Admin API 查名字 需要 Admin API 權限——對 Platform 是更大的授權面(可查全 realm 使用者),且引入執行期耦合(IdP 抖動→管理後台跟著掛);為了「顯示名字」拿管理權限,不成比例
名字放前端 session 不落庫 只能顯示「自己」,無法解決「管理員認別人」的核心問題
顯示名稱快取(本申請) 最小揭露(單欄位、無 email)、最小權限(不加 IdP 權限)、可清除、有契約條文可稽

4. 若獲准,我方的實作承諾

  • 依憲法流程執行(先計畫、TDD 先紅後綠、開發日誌);任務編號 T59,裁示前不動工
  • migration 提供 backward(drop column 即回滾),上線前依規範於 staging 雙向演練
  • 快取欄位上線後,管理後台顯示格式:名字(sub 前 8 碼…)——名字是輔助,sub 仍是主鍵事實
  • 契約對齊紀錄照 T51 模式留檔,標明對齊版本

5. 請 portal 裁示的點

  1. 准/駁本特例
  2. 若准:契約 §6.1 增修文字由貴方定稿(§2 附建議稿),我方以定稿為準對齊
  3. 若駁:請指示可接受的替代方向,我方調整營運流程
