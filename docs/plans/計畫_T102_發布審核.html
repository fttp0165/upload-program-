計畫:T102 發布審核(ReleaseStatus 兩態 → 三態)

建立日期: 2026-08-26 11:05 最後更新: 2026-08-26 12:40 版本: v1.1

憲法第二條 3:大任務先立計畫。本篇為 T102 的施工計畫,依 Benny 2026-08-26 裁示動工。 需求來源:功能需求大綱之發布流程 + Benny 裁示(見 §1)。

1. 裁示(需求定案,2026-08-26)

# 裁示 落點
1 所有版本都要審——不分專案、不分作者,發布一律經平台管理員核准 §3 狀態機
2 既有已發布版本,migration 時視為已核准——不回頭補審 §5 migration(不 UPDATE 任何列)
3 待審版本對非成員隱藏——待審不是公開狀態 §4 可見性
4 退回必須寫理由——空理由不受理 §3 狀態機 + §6 UI
5 送審要通知管理員,email 跟 Keycloak 要(2026-08-26 追加) §7 通知

2. 目標

  1. 版本發布由「作者自行發布」改為「作者送審 → 平台管理員核准後才發布」。
  2. 待審版本只有專案成員與管理員看得到;「最新版」(F26)只認 published,固定連結不受影響。
  3. 管理員有一個審核佇列(後台分頁 + 管理總覽待辦區),退回時必須填理由,理由回到作者眼前。
  4. 送審當下寄 email 通知已訂閱的管理員;email 依 SSO 契約 §4.2b 自本人登入 token 快取。

不做(本次範圍外): 專案層級的免審白名單、多級審核、審核意見討論串、站內信(等 cats-inbox)。

3. 狀態機(兩態 → 三態)

            送審(submit)                核准(approve)
  draft ─────────────────▶ in_review ─────────────────▶ published
    ▲                          │
    │   退回(reject,必填理由)│
    └──────────────────────────┘
    ▲                          │
    └── 撤回(withdraw,作者)──┘
動作 誰 前置 效果
submit 送審 專案 maintainer+ draft、三類齊備(T65 規則不變,提前到送審時把關——管理員審的必須是完整交付) → in_review,記 submitted_at,清掉上一輪退回理由
withdraw 撤回 專案 maintainer+ in_review → draft(送錯了不必等管理員)
approve 核准 平台管理員 in_review → published,published_at=核准當下,記 reviewed_by_id/reviewed_at
reject 退回 平台管理員 in_review、理由必填 → draft,理由存 review_note,記 reviewed_by_id/reviewed_at
  • 「最新版」定義不變:只認 published、依 published_at 排序。改變的是 published_at 的語意 ——它從「作者按發布的時刻」變成「管理員核准的時刻」,F26/歷史頁排序自動一致。
  • 審核中凍結:in_review 不可上傳/刪除檔案、不可改版本說明(審核對象不得中途變動); 要改就先撤回。published 的既有行為(不可動檔、說明可改)維持不變。
  • 冪等:重複 submit、對 published 的 submit 與 approve 都回 200 原樣 (v1.1 修正:submit on published 原計畫 409,實作時改為冪等——舊 /publish 對 published 本來就回 200,別名不該讓既有腳本重跑爆炸);對 draft approve/reject 回 409。
  • 🔴 誠實記載:管理員可以核准自己送審的版本。平台現實是管理員只有一兩位,禁止自審會把 管理員自己的專案鎖死。稽核(§8)會留下「誰送審、誰核准」,自審看得見、不禁止。
  • 稽核動作:release.submit / release.withdraw / release.approve / release.reject。 退回理由不進稽核(AuditEvent 的 target_label 不收自由文字),理由存在 release 列上。

4. 可見性(裁示 3)

規則收斂成一句:非 published = 只有成員與管理員看得到(in_review 與 draft 同一待遇)。

位置 現行判斷 改為
queries.query_releases 非成員只看 published 不變(條件本來就是 == published)
releases.get_release is draft → 404 is not published → 404
artifacts.download_artifact is draft → 404 is not published → 404
web 歷史頁/專案頁 同 query_releases 不變;成員看得到的列加狀態徽章
F26 /latest 只認 published 不變

5. 對現有資料的影響:🟡 加欄位,有 migration(0009)

表 新欄位 型別 說明
releases submitted_at timestamptz NULL 送審時刻
releases reviewed_by_id uuid NULL → users.id 核准/退回者
releases reviewed_at timestamptz NULL 核准/退回時刻
releases review_note text NOT NULL default '' 退回理由(給作者看)
users notify_email_cache varchar(255) NULL §4.2b 通知信箱快取;無 unique、無 index(§4.2b 第 9 條)
users review_email_opt_in boolean NOT NULL default false 管理員訂閱待審通知(§4.2b 第 4/8 條)
  • 不 UPDATE 任何既有列(裁示 2):status 欄是 VARCHAR(native_enum=False、無 CHECK), 加 in_review 值不需改 schema;既有 published 列原樣保留=視為已核准, 其 reviewed_* 留 NULL(誠實:當年沒人審過,不偽造審核紀錄)。
  • backward(可回滾):drop 上述六欄。🔴 downgrade 前必須先處理 in_review 列 (回滾腳本把 in_review 改回 draft,否則舊程式不認識這個值)——寫在 migration 的 downgrade 內,先 UPDATE releases SET status='draft' WHERE status='in_review' 再 drop。
  • 演練:本機 SQLite 檔案版 up→down→up(同 T77 慣例);正式上線依紅線先備份。

6. 介面

  • API(/v1):POST /releases/{id}/submit、/withdraw、/approve、/reject(body:note 必填)。 POST /releases/{id}/publish 保留為 submit 的別名(既有腳本不斷),摘要註明「送審」。 ReleaseOut 增列 submitted_at / reviewed_at / review_note。
  • 網頁:上傳頁按鈕「發布」→「送出審核」;in_review 顯示「審核中」+ 撤回鈕; draft 且有 review_note 顯示退回理由(作者最需要看到的一句話)。 專案頁/歷史頁成員視角加徽章(草稿/待審/已發布)。
  • 後台:新分頁「版本審核」(佇列:專案、版本、送審時間、檔案數;核准鈕 + 退回表單含理由必填)。 管理總覽待辦區加「待審版本 n 件」。

7. 送審通知(email,依 SSO 契約 §4.2b)

平台沒有站內推播;沒有通知的話,管理員只有主動看後台才知道有東西要審(此風險已 在 §10 誠實記載)。Benny 裁示:email,跟 Keycloak 要。契約 §4.2a 第 1 條禁止 App 呼叫 Admin API,所以「跟 Keycloak 要」唯一合規的路是 §4.2b: 管理員本人登入時的 ID token 帶 email claim,落地為快取。

§4.2b 十條逐條對應:

條 要求 本專案做法
1 僅本人登入 token,不碰 Admin API、不許手填 upsert_user 於登入時寫 notify_email_cache,無其他寫入路徑
2 只落地 email_verified=true claim 為 false / 不存在 → 寫 NULL
3 每次登入覆寫、無背景同步 同顯示名稱快取,登入覆寫(含覆寫成 NULL)
4 唯一用途=已明示訂閱的通知;不顯示、不進 log 只用於「待審版本」通知信;log 只記 sub 與略過原因
5 不作認證/授權/身分判定 授權一律 platform_role
6 缺 email 不阻斷 無快取的管理員略過(log 記 sub+原因),送審照常完成
7 整批清除 + 個別即時清除 + 涵蓋孤兒 tools/purge_notify_email.py(--all / --sub;整批清空必然涵蓋孤兒,同 purge_name_cache 的論證)
8 必須可退訂 review_email_opt_in 預設關,審核佇列頁一鍵開/關——開啟那一下就是「明示訂閱」
9 email 不作查詢鍵、無 unique/index 欄位無索引;所有查詢輸入仍是 sub
10 空窗期寫進文件 見下方揭露;同段落進開發計畫書

空窗期揭露(§4.2b 第 10 條義務): 管理員在 IdP 改信箱後,本服務的快取最遲要到他 下次登入才更新,期間通知寄往舊信箱且寄件端顯示成功;離職管理員的信箱若停用或轉交, 通知會寄給接手者。平台側緩解=離職一律停用不刪除;本服務側緩解=通知信只含專案 slug、版本號與後台連結,不含任何使用者資料,寄錯人洩漏的只有「有東西待審」。

寄送設計:

  • app/mailer.py:標準庫 smtplib(不加相依),於執行緒送出;寄失敗只記 log, 絕不阻斷送審(§4.2b 第 6/16 條精神)。
  • 收件人=active + platform_role=admin + review_email_opt_in=true + 快取非 NULL。
  • .env 新增:SMTP_HOST(空=停用寄信,功能照常)、SMTP_PORT(25)、SMTP_FROM。 🔴 SMTP_FROM 只填信箱位址,不帶顯示名稱——公司 Exchange 會把帶顯示名稱的 From 靜默丟棄(契約 §5.3 坑表,portal 實測)。
  • 啟用前到契約 §4.2b 登記表掛號(登記非核准,不需等回覆):本次隨 T102 在 cats-portal 分支補上 upload-program 一列(用途/欄位/清除工具/退訂位置/空窗期揭露位置)。

8. 驗收標準

  1. maintainer 送審:三類齊備才收;成功後狀態 in_review,非成員看不到(404),成員與管理員看得到。
  2. 管理員核准 → published、published_at=核准時刻;F26 /latest 取得的是核准後的版本,審核中不入列。
  3. 管理員退回:無理由 → 422;有理由 → 回 draft,作者在上傳頁看得到理由;作者可修改後重送。
  4. in_review 不可上傳/刪檔/改說明(409);作者可撤回。
  5. 非管理員呼叫 approve/reject → 403;稽核留下 submit/withdraw/approve/reject 四種紀錄。
  6. 管理總覽待辦區出現「待審版本」;審核佇列頁列出全部 in_review。
  7. 登入時 email_verified=true 才落地快取;false/缺 claim 落 NULL;每次登入覆寫。
  8. 已訂閱且有快取的管理員在送審當下收到通知(測試以假 mailer 斷言);無 SMTP 設定、無快取、 寄送炸掉,三種情況送審都照常成功。
  9. migration up→down→up 演練通過;down 會把 in_review 改回 draft 再刪欄。
  10. 全套測試實跑綠燈、ruff check 乾淨。

9. 回滾方式

  1. 程式:git revert 該 PR。
  2. 資料:alembic downgrade -1(downgrade 內建 in_review→draft 的資料回寫;🔴 會刪掉 審核紀錄與通知快取欄位,回滾前必備份)。
  3. 通知:單獨停用只需把 SMTP_HOST 留空,不必回滾程式。

10. 已知風險與遺留(誠實記載)

  • 流程風險不是程式問題:通知要生效,管理員得先登入一次(讓 email 進快取)並在後台 打開訂閱。若上線後版本常態卡在待審,要檢討的是審核流程與人力,不是加程式。
  • 管理員可核准自己的版本(§3 的取捨),稽核可查。
  • T98–T101 為同批裁示的其他項目,另案入任務表;本篇只涵蓋 T102。
