## 1. 要做什麼

把現在只有一段「請聯絡管理員」文字的回報管道(T66/T75),變成真正的**站內問題追蹤**:

| 使用者端 | 管理員端 |
|---|---|

| 看到管理員的回覆 | 改**狀態**(處理中 / 已修正 / 已關閉 / 不處理) |

## 2. 🔴 先講最重要的取捨:富文本與貼圖會撞到既有紅線

這是本設計唯一需要 Benny 明確拍板的地方,其餘都是實作細節。

### 2.1 「富文本」不會是 HTML

本服務散布可執行檔,CSP 是 `default-src 'self'`,而且依 SSO 契約 §4.10,
**IdP 與各 App 同源**——我們出現一次 XSS,等於全平台帳號淪陷。

因此:**不接受使用者送 HTML、不存 HTML、不輸出使用者的 HTML**。

| 方案 | 評估 |
|---|---|
| 所見即所得編輯器(送 HTML)+ 後端消毒 | ❌ 消毒器是永無止境的軍備競賽;一次失手代價是全平台。而且要引入前端編輯器套件——CSP 禁 CDN,得自託管一包 JS,攻擊面再擴大 |
| **Markdown 純文字 + 伺服器端轉譯(白名單)** | ✅ **建議**。存的是純文字(不可執行),轉譯在我方掌控中,標籤白名單只放 p/br/strong/em/code/pre/ul/ol/li/a/img;`a` 強制 `rel="noopener noreferrer"`,`img` 只准指向**我方自己的附件端點** |
| 純文字 + 換行 | 可行但太陽春:回報常需要貼路徑、錯誤訊息(要 code 區塊)與截圖 |

> 這與 F44「README 呈現」當初定下的原則一致:**伺服器端轉譯後輸出消毒過的內容**,
> 不得把上傳的 HTML 餵給瀏覽器。

### 2.2 貼圖要 inline 顯示 = 本專案第一次開「非 attachment」的下載路徑

現況紅線:**所有下載一律 `Content-Disposition: attachment` + `nosniff`**,
絕不讓上傳內容在本網域被瀏覽器直接呈現。截圖要能在頁面上看到,就必須有一條 inline 路徑。

我建議的收窄方式(每一條都要有測試):

1. **只有回報附件端點**是 inline,`/v1/releases/.../download` 那條**完全不動**;
2. 只准 `image/png`、`image/jpeg`、`image/gif`——以 **magic bytes 判定**,不看副檔名、不看使用者宣稱;
3. 🔴 **SVG 一律拒收**(它是可執行的 XML,現有白名單已擋,這裡再擋一次);
4. 回應仍帶 `X-Content-Type-Options: nosniff`,`Content-Type` 用**判定出來的**型別;
5. 附件只能由**回報者本人與平台管理員**讀取(不是公開連結);
6. 單張上限 5 MB、單則回報最多 5 張(避免被當圖床)。

**如果你不接受這條 inline 路徑**,替代方案是:截圖仍以 attachment 下載
(點擊後下載檔案再自行開啟)。功能可用,但體驗差一截。**請擇一裁示。**

## 3. 資料模型(🟡 新增兩張表)

```
issues                         issue_comments
  id                             id
  reporter_id  → users.id        issue_id   → issues.id
  title                          author_id  → users.id
  body_markdown                  body_markdown
  status  open/in_progress/      is_staff_reply (bool)
          resolved/closed/wontfix created_at
  page_url      使用者當時的網址
  app_version   回報當下的服務版本(哪一版出的問題)
  created_at / updated_at      issue_attachments
  closed_at / closed_by_id       id, issue_id, comment_id(nullable)
                                 storage_key, content_type, size_bytes, sha256
                                 uploaded_by_id, created_at
```

- `app_version` 自動帶入(T68 的常數)——使用者不會記得自己看到問題時是哪一版。
- `page_url` 由前端帶入(使用者從哪一頁按的回報)。
- 圖片存 MinIO,key 前綴 `issues/{issue_id}/{uuid}`,與 artifacts 分開。
- **不加 email 欄位**:通知靠站內清單(§6),不落地任何聯絡方式。

## 4. 狀態機

```
open ──→ in_progress ──→ resolved ──→ closed
  └──────────────────────→ wontfix ──→ closed
```

- **只有平台管理員能改狀態**;回報者只能補充回覆。
- `resolved`(我方認為修好了)與 `closed`(結案)分開:讓回報者有機會說「還是不行」。
- 每次狀態變更都寫**稽核**(`issue.status_change`),沿用 T38 的單一入口。

## 5. 權限

| 動作 | 誰 |
|---|---|
| 建立回報 | **任何已登入者**(含**待開通**——他們最可能遇到問題卻無處可說) |
| 看自己的回報與其附件 | 回報者本人 |
| 看全部回報、回覆、改狀態 | 平台管理員 |
| 看別人的回報 | ❌ 不開放(回報內容常含畫面資料,不該全站可見) |

## 6. 通知(誠實面對現況)

本平台**沒有 email、沒有推播、沒有排程器**。所以:

- 使用者:自己的回報清單顯示狀態;有新回覆時在清單標「有更新」。
- 管理員:**管理總覽(T70)的待辦區**加一項「未處理的問題回報 n 件」——這是既有機制,最省。
- **不假裝會主動通知**;頁面上明說「我們不會寄信,請回來看這一頁」。

## 7. 頁面

| 路徑 | 內容 |
|---|---|
| `/issues/new` | 回報表單:標題、內容(Markdown,附即時預覽)、拖曳/貼上圖片 |
| `/issues` | 我的回報清單(管理員看到全部,可依狀態篩選) |
| `/issues/{id}` | 內容 + 附件 + 討論串 + (管理員)回覆框與狀態切換 |
| `/help#report` | 改為指向 `/issues/new`,保留「附什麼」的指引 |

貼上圖片需要 JS(`paste` 事件 + XHR 上傳),沿用 T44 上傳頁的做法:
**外部 JS 檔、參數走 `data-*`、不碰 token(靠 HttpOnly cookie)**。
🔴 **JS 壞掉時表單仍必須可用**(純文字送出、附件用 `<input type="file">`)——漸進增強。

## 8. 對現有資料的影響

🟡 **新增三張表 + 一個 MinIO 前綴**,不動任何既有資料。
migration 提供 backward(drop table),先在 staging 雙向演練。

**保存期**:建議**已關閉滿 365 天**的回報連同附件自動清除,
沿用 `tools/purge_audit.py` 的模式(工具 + cron,不自動跑)。
回報內容是使用者自由書寫,可能夾帶個資與畫面資料,不該無限期保存。

## 10. 驗收標準(紅測試方向)

1. 🔴 **XSS**:送入 `<script>`、`<img onerror=...>`、`javascript:` 連結、Markdown 內嵌 HTML
   ——輸出一律被逸出或剝除,頁面不得出現可執行內容。
2. 🔴 **附件型別**:HTML/SVG/PDF 偽裝成 `.png` 一律拒收(magic bytes 判定)。
3. 🔴 **inline 端點**:只回三種 image 型別、帶 `nosniff`、非本人非管理員一律 404。
4. 權限矩陣:待開通者可建、看不到別人的、非管理員不能改狀態。
5. 狀態機:非法轉移被拒;每次變更有稽核。
6. 漸進增強:關閉 JS 的情況下,表單仍可送出。
7. 清單分頁、空狀態、附件數與大小上限。
