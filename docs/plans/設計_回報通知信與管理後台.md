## 3. 🔴 憲法紅線:業務庫不存 email —— 這件事怎麼合法

本專案紅線寫著「業務庫**只存 `sub`**,不存 email / 姓名 / 密碼」,
而「寄給每一位管理員」必須知道管理員的信箱。合法路徑只有一條:

**SSO 契約 §4.2a **L1b 通知用信箱**(2026-08-12 通則化,Benny 裁決 A 案)。**
它是**通則**,契約明文「不必另外申請」。條件必須**全部**滿足:

| 條件 | 本任務怎麼做 |
|---|---|
| 只從**本人** ID token 取得 | 管理員自己登入時寫入;不查 Admin API(T73 仍卡在 portal 未裁示) |
| 每次登入覆寫(含覆寫成 NULL) | 沿用 T59 `display_name_cache` 同一條路徑 |
| 🔴 **只信 `email_verified=true`** | 未驗證 → 欄位留空(未驗證的信箱是「聲稱」不是「事實」) |
| 🔴 **不得顯示在任何頁面**(含管理後台清單) | UI 一律不輸出;以掃描測試釘住 |
| 🔴 **不進 log** | log 只記「寄了幾封 / 失敗原因類型」,不記地址 |
| 🔴 不得作 join key、不得用於授權 | 唯一鍵永遠是 `sub`;授權只看 `platform_role` |
| 欄位 nullable + **須有清除工具** | `tools/purge_notify_email.py`(整批清空,比照 `purge_name_cache.py` 的理由) |
| **寄信失敗不得阻斷業務流程** | 與裁示一致:回報照樣寫入,寄信在回應之後跑 |

⚠ 本 repo 的 `CLAUDE.md` 紅線要同步補上「L1b 通知信箱依契約通則落地」,
否則紅線與實作互相打架(T59 那次的教訓:憲法與現況要一起走)。

## 4. 實作切分

### T99-A:L1b 通知信箱快取(🟡 加欄位)

- `models.User.notify_email`(nullable,`String(320)`)
- migration `0009_notify_email`(**必須可 down**,依 git 紅線)
- `upsert_user()` 多收一個參數,語意與 `display_name` 完全一致
- callback:`claims.get("email") if claims.get("email_verified") is True else None`
- `tools/purge_notify_email.py`

### T99-B:寄信(不新增相依)

- **`smtplib` 是標準庫** —— 不引入任何套件(比照自寫 `markdown_lite` 的前例)
- `app/mailer.py`:`send_mail(settings, to, subject, body)`,逾時 10 秒
- 設定:`MAIL_ENABLED`(預設 **false**)、`SMTP_HOST`、`SMTP_PORT`(25)、`MAIL_FROM`
  🔴 預設關閉:沒設好就完全不寄,而不是每次回報都在 log 裡噴錯
- 觸發點:建立回報成功之後,以 **FastAPI `BackgroundTasks`** 寄出
  → 使用者的回應不等 SMTP;失敗只寫 log(裁示第三題)
- 內容:標題、回報者的**顯示名稱或 sub**(不放 email)、狀態、**直達連結**
  🔴 不放回報全文 —— 信箱不是稽核紀錄,而內容可能含使用者貼的敏感資訊

### T99-C:後台入口(補缺的那一塊)

- 側欄「管理」段新增「**回報管理**」→ `/issues`(僅管理員可見)
- 清單頁對管理員顯示「未處理 n 件」— 沿用 dashboard 已有的聚合,不另寫查詢

## 5. 對現有資料的影響

🟡 **加欄位**(`users.notify_email`,nullable)。無 UPDATE、無刪除。
migration 需 up→down→up 演練(git 紅線)。

## 6. 驗收標準

1. 管理員登入後,`notify_email` 只在 `email_verified=true` 時有值。
2. 新回報送出 → 每位有信箱的管理員收到一封;**SMTP 掛掉時回報仍成功**。
3. `MAIL_ENABLED=false`(預設)時完全不寄。
4. 🔴 email **不出現在任何頁面、任何 log、任何 API 回應**(反向測試)。
5. 側欄「管理」段有「回報管理」,一般使用者看不到。
6. 清除工具能整批清空。
7. 全套測試綠 + migration 雙向演練。

## 7. 明確不做

- 不寄給回報者本人(裁示只要求通知 ADMIN;要做的話另立任務,且 L1b 允許)
- 不做 email 樣板系統、不做退信處理、不做寄件佇列(單一內部 relay,失敗只寫 log)
- 不查 Keycloak Admin API(T73 未裁示)

### 施工中改正的三件事(依 CI 紅線說明)

1. **「`/v1/me` 不得含 email」這個斷言是錯的。** `MeOut.email` 來自 IdP claims
   (schema 註解明寫「不存在業務庫」),而且是呼叫者自己的信箱;L1b 管的是**快取副本**。
   照錯的斷言改程式,會為了讓測試綠而拆掉一個合法且既有的功能。
   改為釘住「`notify_email` 這個欄位名不得出現在 API 表面與 OpenAPI」。
2. **log 測試的層級要用 INFO,不是 DEBUG。** DEBUG 會打開 aiosqlite 驅動層的 SQL
   參數輸出,那裡當然有地址。🔴 由此得到一條必須寫進文件的結論:
   **正式環境不得把 `LOG_LEVEL` 開成 DEBUG** —— 開了,信箱就會隨 SQL 參數進 log。
   已寫進 `.env.example`。
3. 🐛 **側欄同時反白兩個項目**(截圖抓到):「回報問題」與「回報管理」都指向
   `/issues*`,active 條件都是 `startswith('/issues')`。已收窄並加測試釘住。

### 遺留

1. `MAIL_ENABLED` 仍是 false —— **上線前要在 VM 的 `.env` 設 `SMTP_HOST` 並開啟**,
   而且要先在 VM 實測 relay 連得到(裁示是「公司內部 relay 不需帳密」,但**沒有人驗過**)。
2. 不寄給回報者本人(裁示只要求通知 ADMIN)。要做的話 L1b 允許,另立任務。
