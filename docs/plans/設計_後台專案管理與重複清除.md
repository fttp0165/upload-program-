## 3. 重複怎麼判定(本任務唯一真正的新邏輯)

截圖裡的例子是 `Key_word_serach_V88` / slug `key-word-serach-v88-2` ——
**T96 撞名自動加後綴**的產物:使用者按了兩次建立,第二次的短名自動變成 `-2`。

### 判定規則:同一個「正規化後的名稱」算一組

```
group_key(project) = slugify(project.name)  或  name.strip().casefold()(前者為空時)
一組內 ≥ 2 個 → 疑似重複,依 created_at 排序,最早的標「最早建立」
```

🔴 **刻意不用「把 slug 的 `-N` 後綴去掉」當判準**,雖然它更直覺:

> 那會把 `Tool` 與 `Tool 2` 判成同一組 —— 而 `Tool 2` 是**使用者自己取的名字**,
> 不是系統加的後綴。系統加的後綴只出現在 slug 上,名稱一字未改;
> 所以**用名稱判定同時抓得到真重複、又不會誤判刻意的第二代**。

🔴 **`slugify()` 為空時退回名稱本身**(不是退回空字串當 key):
純中文名稱的 `slugify()` 一律回 `""`(T96 已載明),若拿 `""` 當 key,
**全站所有中文名稱的專案會被歸成一大組** —— 那不是提示,是災難。

⚠ 誠實記載本規則抓不到的:使用者兩次打的名字不完全一樣(多一個空格以外的差異)、
或刻意改名之後的重複。那些要靠人眼,而本頁會列出全部專案供瀏覽。

## 4. 介面

`/admin/projects`(管理後台第五個分頁,放在「使用者」之後)

**每一列顯示:** 名稱 · 短名 · 擁有者 · 建立時間 · **版本數 / 檔案數 / 容量**

🔴 那三個數字是本頁的核心,不是裝飾:**沒有它們,管理員無法判斷該刪哪一個**。
兩個同名專案,一個有 3 版 12 個檔、一個是空的 —— 該刪哪個顯而易見;
而只列名稱與時間的話,那個判斷就變成猜。

**疑似重複的分組置頂**,每組標明「最早建立」那一個。

### 刪除(A 案)

```
POST /admin/projects/{slug}/delete
表單欄位:confirm_slug —— 必須逐字等於該專案短名
```

- 不符 → **不刪**,回原頁顯示錯誤(帶「你輸入的是 X,應為 Y」)
- 相符 → 走與 API **同一段刪除邏輯**(物件先刪、metadata 後刪、稽核留痕)

🔴 **有已發布版本的專案,那一列要多一行紅字警告**(不是禁止):
別人可能已經把固定連結貼進文件或信件裡,刪掉之後那些連結會 404 而沒有人知道為什麼。
**警告而不禁止**是因為「重複建立的那一個」有時候正好是有版本的那一個(傳錯地方),
禁止會讓管理員無路可走。

## 5. 對現有資料的影響

🟢 **程式面不動資料結構、無 migration。**
🔴 **但這一頁的按鈕會刪資料,而且不可逆**:連同該專案在 MinIO 的所有物件。
沒有垃圾桶、沒有還原路徑 —— 這正是採 A 案(輸入短名確認)的理由。

## 6. 驗收標準(先寫會失敗的測試)

1. 🔴 `/admin/projects` 列出全部專案,並把疑似重複分組置頂
2. 🔴 `confirm_slug` 不符 → **不刪**,顯示錯誤
3. 🔴 `confirm_slug` 相符 → 刪掉 + 稽核 + MinIO 物件一起消失
4. 🔴 **`Tool` 與 `Tool 2` 不得被判成重複**(反向:防過度分組)
5. 🔴 **兩個不同的純中文名稱不得被判成重複**(反向:`slugify()` 皆為 `""`)
6. 非管理員進不去(守門)
7. 刪一個不得動到別的(守門)

## 7. 回滾方式

程式面:還原檔案即可(🟢 無 migration)。
🔴 **已經刪掉的專案回不來** —— 這是本功能的性質,不是缺陷。
⚠ 因此上線後第一次使用前,建議先跑一次 `./backup.sh`(runbook §C.1)。
