# 設計:後台可設定「每個帳號」的單檔上限

**專案:** upload-program
**建立日期:** 2026-09-08 12:20
**最後更新:** 2026-09-08 12:20
**版本:** v1.0
**對應任務:** T141(尚未動工;第二條 3 要求大任務先立計畫)

---

## 1. 需求

Benny:「新增後台可設定每個帳號單個檔案上限」。

目前單檔上限是**全站一個值**(`MAX_ARTIFACT_BYTES`,現為 500 MB),
只能改 `.env` + 重啟,沒有任何後台。本任務要讓平台管理員**逐個帳號**設定。

---

## 2. 🔴 這個功能有一個天花板,而它會撒謊

上限不是我們一家說了算。實際上有**三道牆**,由外而內:

```
gateway client_max_body_size 640m   ← nginx,不在本 repo(cats-portal)
        ↓ 通過才到得了 App
MAX_ARTIFACT_BYTES 500 MB           ← 全站上限(.env)
        ↓
帳號個別上限(本任務)               ← 新增
```

🔴 **如果後台允許填一個大於 gateway 的值,那個欄位就是在撒謊:**
存得下、畫面說可以,而上傳會撞 **nginx 的 413** —— 那一頁不說上限、不說用量,
使用者只看到「上傳失敗(413)」。**2026-09-08 這件事剛剛真的發生過一次**
(App 已是 500 MB 而 gateway 還是 128m),所以這不是假設。

**故本設計的第一條紅線:帳號上限一律夾在 `MAX_ARTIFACT_BYTES` 之下。**
超過就拒絕儲存,並在錯誤訊息裡寫出目前的全站上限是多少。

⚠ **App 看不到 gateway 的設定**(它在另一個 repo、另一個容器),
所以「不得超過 gateway」這件事只能靠 `MAX_ARTIFACT_BYTES` 這個代理值 ——
而它本來就被要求 ≤ gateway(`.env.example` 檔頭那條紅線)。
**這是刻意用既有的那條紀律當防線,不是新發明一個。**

---

## 3. 設計

### 3.1 資料

`users` 新增一欄:

| 欄位 | 型別 | 意義 |
|---|---|---|
| `max_artifact_bytes` | `BIGINT NULL` | `NULL` = **沿用全站上限**(預設);有值 = 這個帳號的個別上限 |

🔴 **用 nullable 而不是「建帳號時填入全站值」**:後者會讓全站上限被調整時,
既有帳號**全部卡在舊值**,而且看不出哪些是「刻意設定」哪些是「當時的預設快照」。
`NULL` 讓「沒有特別規定」與「規定成某個數字」在資料上分得開。

**🟡 需要 migration**(加欄位,`0012_user_upload_limit`),提供 backward。

### 3.2 有效上限的計算

集中在一個純函式(比照 `quota.limit_for`),**不散在路由裡**:

```python
def effective_artifact_limit(settings, user) -> int:
    """回傳這個帳號實際適用的單檔上限。
    NULL → 全站上限;有值 → 取兩者的**較小者**。
    """
    if user.max_artifact_bytes is None:
        return settings.max_artifact_bytes
    return min(user.max_artifact_bytes, settings.max_artifact_bytes)
```

🔴 **為什麼是 `min` 而不是直接用帳號的值**:全站上限**事後**被調小時
(例如磁碟吃緊),個別帳號的舊設定不該繞過它。
**沒有這個 `min`,調小全站上限這個動作會靜默地對某些帳號無效。**

### 3.3 生效的三個地方(少一個就會出現「說可以卻失敗」)

| # | 位置 | 不改的後果 |
|---|---|---|
| 1 | `PUT /v1/releases/{id}/artifacts/{name}` 的 Content-Length 預檢 | 上限根本沒生效 |
| 2 | 串流上限(`upload_stream(..., limit)`) | 沒有 Content-Length 的請求可繞過 #1 |
| 3 | 上傳頁的 `data-max-bytes` | 🔴 **前端預檢會用錯的值** —— 對被調小的帳號,它會放行一個必定失敗的上傳;對被調大的帳號,它會擋掉一個其實可以的上傳 |

### 3.4 後台介面

`/admin/users` 每一列加一個欄位與「儲存」。⚠ **不做成獨立頁面**:
那一頁已經有開通 / 停用 / 設為管理員,上限屬於同一類「對這個人的設定」。

- 空白 = 沿用全站(顯示「沿用全站 500 MB」)
- 輸入以 **MB** 為單位(不要求人算位元組;`524288000` 這種數字是給程式看的)
- 🔴 只有**平台管理員**可設(比照 F17 的級距:owner 若能自調就等於沒有上限)
- 稽核動作 `user.set_upload_limit`,`target_label` 記 `sub:新值`
  ——`action` 欄是 `String(64)` 且刻意不下 CHECK,**新動作不需要 migration**

### 3.5 錯誤訊息

超限時沿用既有的 RFC 7807(`problems.payload_too_large`),但 detail 要說清楚
**是帳號限制還是全站限制** —— 否則使用者去問「為什麼我只能傳 50 MB」時,
沒有人分得出是他被單獨設定過、還是全站就這麼小。

---

## 4. 對現有資料的影響:🟡 加欄位

- 既有帳號一律 `NULL` → **行為逐字不變**(仍走全站上限)
- 不動任何既有檔案、專案、版本
- migration 提供 backward,並依 git 紅線在 staging 雙向演練

---

## 5. 驗收標準(先寫會失敗的測試)

1. 🔴 `NULL` 的帳號 → 有效上限 = 全站上限(**行為不變**的守門)
2. 🔴 設 100 MB 的帳號 → 傳 150 MB 被擋,detail 說明是帳號限制
3. 🔴 設 **1 GB** 的帳號(> 全站 500 MB)→ **儲存被拒**,訊息寫出全站上限
4. 🔴 全站上限事後調成 200 MB → 帳號設 400 MB 的人**實際只能傳 200 MB**(`min` 的守門)
5. 🔴 上傳頁的 `data-max-bytes` = **該使用者的**有效上限(不是全站值)
6. 🔴 非平台管理員呼叫設定端點 → 403
7. 稽核有記 `user.set_upload_limit`

⚠ 第 4、5 兩條是**最容易被漏掉、而症狀最不指向根因**的兩條,
它們不是補充驗收,是本任務的重點。

## 7. 刻意不做

- **不做「每個專案」的單檔上限** —— 專案已經有級距(F17),再加一層會出現
  「同一個檔案在 A 專案可以、在 B 專案不行」而兩邊都對的局面。
- **不做自助申請** —— 那是 F18(P2)。
- **不把全站上限也搬進後台** —— 它必須 ≤ gateway,而 App 看不到 gateway;
  放進後台就是製造一個能設定成無效值的欄位(見 §2)。
