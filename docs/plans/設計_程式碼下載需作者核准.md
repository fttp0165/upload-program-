# 設計:程式碼(source)下載需作者核准

**專案:** upload-program
**建立日期:** 2026-09-08 17:30
**最後更新:** 2026-09-08 17:30
**版本:** v1.0
**對應任務:** T142(**尚未動工**;第二條 3 要求大任務先立計畫)

---

## 1. 需求與裁示

Benny:「程式碼要鎖住不能下載,除了管理員需要專案作者同意才可以下載或加入成員」。

同時裁示三題(2026-09-08):

| 題 | 裁示 |
|---|---|
| 鎖的範圍 | **只鎖程式碼(`source`)** —— 說明與執行檔維持現狀 |
| 核准粒度 | **核准一次 = 該專案的程式碼都可下載**(長期授權,可撤銷) |
| 專案成員 | **成員自動可下載** —— 「加入成員」本身就是作者的同意 |

---

## 2. 判準(一句話)

> `kind == source` 的下載,只有下列四種人可以:
> **① 平台管理員 ② 專案成員(含 owner / maintainer / viewer)
> ③ 已被作者核准的申請人 ④ 沒有第四種。**

其餘一律**擋下並提供「申請下載」的入口** —— 🔴 **擋的同時要給路**:
一個只說「不行」而不說「怎麼才可以」的畫面,使用者的下一步是來問人,
而那正是這個功能想省下來的事。

⚠ **`viewer` 也能下載程式碼**:那是既有語意(能讀專案就能取得其內容),
本任務不改它 —— 要限制得更嚴屬另一個決定,不夾帶。

---

## 3. 資料

新表 `source_access_requests`:

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | UUID PK | |
| `project_id` | FK projects CASCADE | 🔴 授權綁**專案**不綁版本(裁示的核准粒度) |
| `user_id` | FK users RESTRICT | 申請人。RESTRICT:有申請紀錄的人刪不掉(同稽核立場) |
| `status` | enum | `pending` / `approved` / `rejected` / `revoked` |
| `reason` | String(500) | 申請人寫「我要做什麼用」 |
| `decided_reason` | String(500) null | 🔴 **拒絕必須寫理由**(比照 T123 退回:沒有理由,申請人只能猜,然後重送一模一樣的東西) |
| `requested_at` / `decided_at` | timestamptz | |
| `decided_by_id` | FK users null | 誰決定的(稽核要對得回人) |

**唯一約束:`(project_id, user_id)`** —— 一個人對一個專案只有一筆,
重複申請是更新那一筆而不是長出第二筆。
🔴 理由:沒有這個約束,被拒絕的人可以連按十次,作者的待辦就變成垃圾場。

**🟡 加表 migration `0013_source_access`**,提供 backward。

## 4. 三個生效點(漏一個就等於沒鎖)

| # | 位置 | 漏掉的後果 |
|---|---|---|
| 1 | `GET /v1/releases/{id}/artifacts/{aid}/download` | 主要路徑沒鎖 |
| 2 | `GET /v1/projects/{slug}/releases/latest/artifacts/{name}/download`(F26 捷徑) | 🔴 **鎖了主路徑卻留一條捷徑,等於沒鎖** —— 而那條網址是設計成「能寫進文件」的,最容易被傳出去 |
| 3 | 網頁的版本頁 / 檔案清單的下載連結 | 連結還在,點了才被擋 —— 體驗差,但**不是漏洞**(伺服器端仍擋) |

🔴 **判準寫成一個共用函式並放進 `_download_response`**,
而不是在兩個端點各寫一次 —— 那段程式碼的檔頭已經寫著同一個道理
(「安全標頭絕不能因為換了一條路徑就鬆掉」),本任務沿用它。
⚠ `_download_response` 目前拿不到 `project`,需一併帶入(小重構)。

## 5. 介面

| 頁面 | 加什麼 |
|---|---|
| 版本頁的程式碼檔案 | 不可下載時,把下載鈕換成「**申請下載**」(帶用途說明的表單) |
| 專案頁(作者視角) | 「待處理的下載申請(N)」入口 |
| 新頁 `/projects/{slug}/access` | 申請清單:核准 / 拒絕(需理由) / 撤銷;並提示「也可以直接**加為成員**」並連到成員頁 |
| 管理總覽待辦 | ⚠ **不加。** 這是**作者**的待辦不是管理員的 —— 混進去會讓管理員以為該他處理 |

🔴 **平台沒有通知管道**(§7 既有限制):作者不會收到 email 也不會收到推播。
所以「待處理的下載申請」**必須出現在他一定會看到的地方** —— 專案頁,
而不是只在一個要主動點進去的頁面。
⚠ 這一點誠實記下:**這個功能的成敗取決於作者會不會回來看**,
與 T123 審核制度是同一個營運風險,不是技術問題。

## 6. 稽核

新增四個動作(`action` 是 `String(64)` 且刻意不下 CHECK → **不需要 migration**):
`source_access.request` / `.approve` / `.reject` / `.revoke`。

🔴 **`artifact.download` 一字未改** —— 誰下載了什麼仍然照記,
本任務只是多一道門,不是換一套紀錄。

## 7. 對現有資料的影響:🟡 加表

- **既有專案與檔案一列都不用改**
- 🔴 **但行為會變**:今天能下載 source 的**非成員**,明天起要申請。
  這是需求本身,不是副作用 —— 但**上線前要講**,否則使用者只會覺得壞了。
- 既有的下載連結不會 404,而是 403 + 申請入口

---

## 8. 驗收標準(先寫會失敗的測試)

1. 🔴 非成員下載 `source` → **403**,回應含申請入口
2. 🔴 非成員下載 `doc` / `binary` → **仍然 200**(守門:只鎖程式碼)
3. 🔴 平台管理員 → 200
4. 🔴 專案成員(viewer) → 200(守門:成員自動可下載)
5. 🔴 **F26 最新版捷徑同樣被擋**(守門:不留後門)
6. 🔴 核准後 → 200;**撤銷後 → 403**
7. 🔴 拒絕**不寫理由** → 422
8. 🔴 同一人重複申請 → 仍只有一筆(唯一約束)
9. 非作者/非管理員去核准別人的申請 → 403
10. 稽核四個動作都有記

⚠ 第 2、5 兩條是本任務最容易漏而症狀最不明顯的:
**第 2 條漏了會鎖到不該鎖的東西**(使用者以為平台壞了),
**第 5 條漏了等於整個功能沒有生效**(而測試會全綠)。

## 9. 回滾方式

`alembic downgrade` 一版(表刪除 → **所有核准紀錄消失**;
🔴 退版前先匯出 `source_access_requests`,否則作者要重新核准一輪);
程式碼還原。

---

## 10. 刻意不做

- **不做「申請時附帶到期日」** —— 長期授權可撤銷已經足夠;到期要有人去掃,
  而掃描沒跑就等於沒有(與 T135 的稽核保留期同一個教訓)。
- **不寄信** —— `MAIL_ENABLED` 仍是 false 且 relay 從沒驗過(§5.1 欠項)。
  硬接上去只會讓「申請了沒人理」變成「申請了沒人理而且 log 有一行錯誤」。
- **不鎖瀏覽** —— 只鎖下載。看得到有這個檔案、看不到內容,才有辦法申請。
