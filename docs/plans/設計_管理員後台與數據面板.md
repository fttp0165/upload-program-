## 2. 設計原則(紅線先行,不是事後檢查)

1. 🔴 **個資邊界不因「後台」而放寬。** 面板只顯示 `sub` 與 `display_name_cache`
   (§4.2a L1 明文特例,僅後台顯示)。
   **面板的下載統計一律是聚合數字,不按人拆解**——T37 刻意不做下載事件表、
   業務統計只到「次數」,那是個資決定。
   (精確地說:稽核表**確實**記錄了 `artifact.download` 事件與 `actor_id`,
   那是 F54 明文賦予稽核的職責,有其專屬頁面與用途說明;
   但「資料剛好存在」不等於「面板可以展示」——見 §4.6(b)。)
2. 🔴 **CSP 逐字不放寬。** 外部圖表庫(Chart.js 等 CDN)一律被 `default-src 'self'` 擋下,
   inline `<style>` / `<script>` 同樣被擋。所以**圖表在伺服器端算好,輸出內嵌 SVG**
   ——這與憲法第四條 5「圖示以內嵌 SVG 呈現」本來就同一個方向。
   互動只用連結與表單,不引入前端框架。
3. 🔴 **Light 主題**(第四條 1–2),圖表配色沿用 T56 設計 token(藏青/綠),
   不使用深色配色、不用 `prefers-color-scheme`。
4. **面板唯讀。** 所有操作(開通、停用、調級距)留在既有頁面。
   看數據與改狀態混在同一頁,誤點成本高而收益低。
5. **只跑聚合查詢,數量固定。** 每頁的查詢數不隨資料量成長;排行榜一律 top-N;
   不做輪詢、不做自動刷新(要新數字就重整,誠實且省事)。
6. **算不出來的就說算不出來。** 例如「每日登入數」——`users.last_login_at` 只存
   最後一次,無法回推每日曲線。面板寧可標示「本平台不記錄登入歷史」,
   也不用近似值假裝有(這與 `scan_status` 誠實標示 `not_scanned` 同一個態度)。

## 3. 資訊架構

```
/admin            總覽(數據面板)   ← 新增,管理後台的新首頁
/admin/users      使用者            ← 既有
/admin/projects   專案治理          ← 新增
/admin/audit      稽核紀錄          ← 既有
```

現有的 `admin-tabs` 由兩項擴充為四項;側欄「管理」段落加「總覽」與「專案」兩條。
`/admin` 是管理員登入後最該先看的一頁,因此側欄的管理段落把它排在最上。

## 4. 面板內容(全部由現有 schema 算得出,**無需 migration**)

### 4.1 KPI 卡片(第一排,六張)

| 卡片 | 數字 | 資料來源 |
|---|---|---|
| 帳號 | 總數,其中**待開通 n**(可點進使用者頁) | `users` count / group by status |
| 專案 | 總數(internal / private 分計) | `projects` group by visibility |
| 版本 | 已發布數 / draft 數 | `releases` group by status |
| 檔案 | 總數 / 其中 `not_scanned` **n** | `artifacts` group by scan_status |
| 儲存 | 總佔用(人類可讀)/ 全站配額總和 | `sum(projects.total_bytes)` 與 `quota.limit_for` |
| 下載 | 累計下載次數 | `sum(artifacts.download_count)` |

「待開通」與「未掃描」兩個數字**刻意做成顯眼的待辦**,不是裝飾——
前者擋著人用不了平台,後者是我們對使用者誠實揭露的風險。

### 4.2 趨勢(近 30 天,內嵌 SVG 長條圖)

| 圖 | 定義 | 來源 |
|---|---|---|
| 每日發布版本數 | `releases.published_at` 落在該日者 | releases |
| 每日上傳檔案數 | `artifacts.completed_at`(ready 者)落在該日者 | artifacts |
| 每日操作事件數 | 稽核事件筆數(平台熱度) | audit_events |
| 每日下載次數 | `artifact.download` 稽核事件筆數(見 §4.6) | audit_events |

**限制要寫在圖旁邊**(而不是留給讀者誤會):
- 已刪除的專案/版本不會出現在前兩張圖(那些列已經不存在);
- 稽核保留 365 天,超過期間的資料已被清除;
- **沒有登入趨勢**(理由見原則 6)。

### 4.3 排行(各 top 5)

- 下載最多的**專案**(sum(download_count) join release/artifact)
- 下載最多的**檔案**(artifact 名 + 所屬專案)
- 佔用容量最多的**專案**(含級距與使用率條)
- 最近發布的 5 個版本(專案 + 版本號 + 發布時間)

### 4.4 需要管理員動作的清單(面板的真正價值)

| 項目 | 判準 | 連結去哪 |
|---|---|---|
| 待開通帳號 | `status=pending` | `/admin/users` |
| 逼近配額的專案 | `total_bytes ≥ 80%` 該級距上限 | `/admin/projects` |
| 停滯的 draft | 建立超過 **14 天**仍未發布 | 該專案頁 |
| 未掃描檔案 | `scan_status=not_scanned` 的總數 | 說明頁(掃毒未接,T46)|
| 擁有者已停用的專案 | owner 的 `status=disabled` | `/admin/projects`(提示走 F16 轉移)|

最後一項是實務會踩到的坑:人離職後帳號停用,專案就沒有能改設定的人了。
F16(轉移擁有權)已經做好,但**沒有任何地方會告訴管理員「該轉移了」**。

### 4.5 系統資訊

服務版本(`APP_VERSION`,T68)、環境、DB / 物件儲存 / IdP 就緒狀態(`/ready` 同一組檢查)、
稽核保留天數與「清理需由 cron 執行」的既有提醒。

### 4.6 下載統計(Benny 追加:「還有統計下載次數」)

平台裡的下載資料**有兩個來源,性質完全不同**,設計時必須分清楚,
否則會做出「兩個數字對不起來」的面板——那比沒有面板更糟:

| 來源 | 是什麼 | 有時間維度? | 會不會被清掉 |
|---|---|---|---|
| `artifacts.download_count` | **累計計數器**(T37,原子 UPDATE) | ❌ 只有總數 | 不會(除非檔案被刪) |
| `audit_events` 的 `artifact.download` | **逐次事件**(T38,含 `occurred_at`) | ✅ 可分日 | ✅ 保留 365 天後由 `purge_audit.py` 清除 |

因此下載統計分兩層,並且**在頁面上標明各自的口徑**:

**(a) 累計(來自計數器,永久且精確)**

| 指標 | 說明 |
|---|---|
| 平台累計下載次數 | `sum(artifacts.download_count)`(KPI 卡) |
| 依類型分布 | binary / source / doc 各佔多少——看得出大家主要抓執行檔還是原始碼 |
| 下載排行 top 5 | 專案別、檔案別、版本別各一組 |
| **零下載的已發布版本數** | 發了但沒人下載——治理訊號(要嘛沒人需要,要嘛沒人找得到) |
| 最新版佔比 | 最新已發布版本的下載數 ÷ 該專案總下載數,看使用者是否卡在舊版 |

**(b) 趨勢(來自稽核事件,近 30 / 90 天)**

每日下載次數長條圖 + 期間總計。🔴 **只做「每日總數」的聚合,不做任何按人拆解**——
稽核表雖然存了 `actor_id`(F54 明文「下載了什麼」是稽核的職責),
但**數據面板不是稽核頁**:面板要回答「平台被用得多不多」,不是「誰下載了什麼」。
要追個別行為請走 `/admin/audit`,那一頁有它自己的用途說明與存取限制。
這條界線與 T37 當初「統計只到次數」的決定一致,**不因為資料「剛好存在」就展示**。

**(c) 兩個數字為什麼會對不上(頁面要明講)**

累計數 ≥ 近 30 天事件數,這是正常的,原因有三:計數器從開站起算、
稽核只留 365 天、以及檔案被刪除後計數消失但稽核事件還在。
面板把兩塊分開標題與口徑說明,不硬湊成一個數字。

**(d) 刻意不做**

- ❌ 每日下載**快照表**(把每天的計數器差額存起來):要新增表 + 排程器,
  而稽核事件已經能算出同一條曲線;為了圖表引入寫入路徑不划算(與 §7 同一個判斷)。
- ❌ 下載者名單、部門/人員排行:見上;那是稽核的職責,不是面板的。
- ❌ IP、User-Agent 等「加值」維度:本平台從不記錄這些,面板不該成為引入它們的理由。

## 5. 專案治理頁 `/admin/projects`

管理員視角的專案清單(**含 private**——F53 明文管理員可見全部),欄位:
專案 / 擁有者(sub 或顯示名)/ 可見性 / 級距 / 已用容量與使用率 / 版本數 / 最後發布時間。
排序預設「使用率高的在前」;可篩「逼近配額」「擁有者已停用」。
調整級距的入口指向既有 API 動作(`project.set_quota` 已在稽核字彙內)。

## 6. 圖表的技術規格(CSP 之下怎麼畫)

- 伺服器端把 30 天分桶算好,模板迴圈輸出 `<rect>`;幾何用 SVG **屬性**表示
  (`x`/`y`/`width`/`height`),**不寫 `style=`**——inline style 會被 CSP 擋。
- 顏色用 class,實際色值寫在 `static/app.css`(設計語言只有一份)。
- 無資料時輸出「尚無資料」文字,不輸出空圖。
- 無障礙:`<svg role="img">` + `<title>`,並在圖下方附**同一份數字的表格**
  ——圖表不得是資訊的唯一載體。

## 7. 對現有資料的影響

🟢 **不動資料。** 全部是唯讀聚合查詢:無 migration、無新欄位、無新表、無 `.env` 變更。

刻意**不做**「每日快照表」:資料量小、即時算得出來;為了圖表引入一條寫入路徑
(還要配排程器)是這個階段划不來的複雜度。等資料量或效能真的出現問題再說,
屆時屬獨立任務。

## 9. 驗收標準(每個任務的紅測試方向)

1. **權限**:匿名 → 302 去登入;已登入非管理員 → 403;管理員 → 200
   (沿用 `_require_web_admin`,不另立規則)。
2. **數字正確**:fixture 造出已知資料(3 專案 / 5 版本 / 2 待開通…),
   斷言頁面上的數字**等於**那些值——不是「頁面有出現數字」。
3. **個資紅線**:面板 HTML 不得出現 email 樣式字串;不得有任何「誰下載了什麼」的欄位;
   顯示名稱僅來自 `display_name_cache`。
4. **CSP 相容**:頁面無 `style=`、無 inline `<script>`、無外部資源(沿用既有掃描測試模式)。
5. **空狀態**:全新平台(零專案零檔案)不得炸,且顯示合理的空狀態文字。
6. **連結帶前綴**:沿用既有「所有連結必須經 `url()`」的掃描斷言。

## 10. 風險與取捨

| 風險 | 處置 |
|---|---|
| 趨勢圖看不到已刪除的資料 | 圖旁明文標示,不假裝完整 |
| 稽核保留 365 天,更早的熱度查不到 | 同上,標示保留期 |
| 資料量成長後聚合變慢 | 目前規模(單機、內部平台)無虞;若出現,再評估索引或 60 秒快取,列後續任務 |
| 面板成為「另一個放個資的地方」 | 驗收標準 3 以測試釘住;程式碼審查時對照本節 |
| 下載的兩個口徑(累計 vs 近 30 天)被誤讀成資料有錯 | §4.6(c):兩塊分開標題並在頁面上寫明原因,不硬湊成一個數字 |
| 稽核被清除後下載趨勢出現斷層 | 圖旁標示保留期;累計數不受影響,兩者互補 |
