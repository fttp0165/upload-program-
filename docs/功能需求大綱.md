## 0. 一句話定義

**公司內部的開發者程式分享平台**:登入後建立專案,在專案內上傳**原始碼、執行檔、程式文件**,
以**版本**為單位發布,同事可以瀏覽、搜尋、下載。

做的是「**有版本管理的程式發布倉庫**」,不是分散式版本控制系統。

---

## 1. 使用者角色

| 角色 | 定義 | 能做什麼 |
|---|---|---|
| **訪客** | 未登入 | 只能被導向登入頁,看不到任何內容 |
| **待開通使用者** | 首登建立,零角色(`pending`) | 只能看到自己的身分與「請找管理員開通」的指引 |
| **一般使用者** | 已開通(`active`) | 建立自己的專案;瀏覽/搜尋/下載所有 internal 專案 |
| **專案 viewer** | 被加入專案的成員 | 讀取與下載該專案(含 private) |
| **專案 maintainer** | 被加入專案的成員 | viewer 權限 + 建版本、上傳檔案、發布 |
| **專案 owner** | 專案建立者 | maintainer 權限 + 改專案設定、管成員、刪除專案 |
| **平台管理員** | `platform_role=admin` | 開通/停用帳號、指派平台角色;可見全部專案 |

> **權限原則:deny-by-default。** 身分由 Keycloak 認證,但「能做什麼」完全由本平台自己決定,
> 不碰 Keycloak 的角色設定。

## 2. 主要使用情境

| # | 情境 | 流程 |
|---|---|---|
| U1 | **第一次使用** | 開站 → 導向 SSO 登入 → 回站後看到「待開通」指引 → 管理員開通 → 可用 |
| U2 | **發布一個工具** | 建立專案 → 建立版本 v1.0.0 → 上傳執行檔 + 原始碼 + 使用說明 → 發布 |
| U3 | **找別人的工具來用** | 搜尋關鍵字 → 開專案 → 看版本列表 → 下載執行檔 → 用 SHA-256 校驗 |
| U4 | **發新版** | 開既有專案 → 建立版本 v1.1.0 → 上傳新檔 → 發布(舊版仍在,可回頭下載) |
| U5 | **內部限定的工具** | 建專案時設 private → 加入指定同事為成員 → 只有成員找得到、下得到 |

**F17 的級距設計(2026-07-26 定案):**

| 級距 | 上限 | 適用 | 誰能改 |
|---|---|---|---|
| `standard`(預設) | **2 GB** | 一般員工開發的小工具——約可容納 25 個一般版本 | — |
| `extended`(需申請) | **10 GB** | 帶 runtime 或多平台安裝包的大型專案 | 平台管理員 |

- **為什麼預設取 2 GB 而非 5 GB:** 上限**調高比調低容易**。調低要面對已經超標的既有專案,
  調高只是改一個數字。先收緊、按需放寬,是風險較低的方向。
- **MVP 的「申請」怎麼走:** 管理員直接調整專案級距,申請本身走線下(口頭/郵件)。
  站內申請單(提交 → 審核 → 通知)是獨立功能,列 P2(F18)。
- **超過上限時**:回 413,錯誤訊息要指出目前級距、已用量與「可申請擴充」的指引,
  不能只丟一句 Payload Too Large。

**可見性規則**

- `internal`(預設):所有已開通使用者可讀、可下載
- `private`:僅成員可讀;**對非成員一律回 404**,不洩漏該專案是否存在

**F26 的網址設計(供後續實作定樁):**

- `GET /v1/projects/{slug}/releases/latest` — 最新**已發布**版本(draft 不算)
- `GET /v1/projects/{slug}/releases/latest/artifacts/{filename}/download` — 直接抓最新版的某個檔案

「最新」的定義:`published_at` 最大者。版本號採自由字串(非強制 SemVer),
**不以字串排序決定新舊**——那會讓 `v10` 排在 `v9` 前面。

| F35 | **安全下載** | 一律 `Content-Disposition: attachment` + `nosniff`;絕不讓上傳內容在本網域被瀏覽器執行 | P0 | M5 | ✅ |

| F38 | 病毒掃描 | 實際接上掃毒引擎(ClamAV) | P2 | **M8** | ⬜ 不納入 MVP,**保留接點**(T46)|

**F38「先預留」預留了什麼(2026-07-26 定案):**

| 已預留 | 現況 |
|---|---|
| `artifacts.scan_status` 欄位與 `not_scanned` / `clean` / `infected` 三態 | ✅ 已存在,不必再改 schema |
| 下載回應的 `X-Artifact-Scan-Status` 標頭 | ✅ 已存在 |
| 上傳完成後的掛載點(`upload_status` 轉 `ready` 之處) | ✅ 位置明確,屆時在該處送出掃描工作 |
| 尚缺 | 背景工作機制(佇列/worker)、掃描結果回寫 API、`infected` 時是否封鎖下載的政策 |

> **未接掃毒期間的誠實義務:** `scan_status` 一律維持 `not_scanned` 並隨下載回傳,
> 不得因為「是內部平台」就把未掃描說成安全。

> **為什麼 F32/F35 是 P0 而不是「加分項」:** 這是一個**散布可執行檔**的平台。
> 若讓上傳內容以 HTML/JS 在本服務網域被瀏覽器執行,等於自己開一個 XSS 給全公司。

## 4. 非功能需求

| 面向 | 需求 |
|---|---|
| **安全** | 不自建帳號/不存密碼/不自簽 JWT;業務庫只存 `sub`;上傳驗 magic bytes;下載強制 attachment |
| **容量** | **單檔上限 100 MB**;專案總容量**標準 2 GB / 擴充 10 GB**(2026-07-26 定案)。gateway `client_max_body_size` 需設 ≥128 MB 留餘裕 |
| **效能** | 大檔上傳記憶體固定;DB 連線池 ≤20 |
| **可用性** | `/health` 啟動 60 秒內回 200;SIGTERM 後 30 秒內優雅關閉,換版不斷既有請求 |
| **相容性** | 服務掛在 gateway 子路徑 `/«PREFIX»/` 下且前綴會被剝掉,所有對外連結都要正確 |
| **可維運** | log 可依 `trace_id` 跨服務追查;migration 可雙向回滾 |
| **合規** | 通過 Cats 接入指南 §11 的 Definition of Done 全部檢查項 |

## 5. 範圍外(MVP 不做)

與開發計畫書 §1.2 一致:

| 不做 | 理由 |
|---|---|
| git 協定(`clone`/`push`)、commit 圖、diff | GitHub 的核心難點;本平台以「版本化的檔案集」取代 |
| Pull Request / code review | 第二期再議 |
| Issue 追蹤 | 第二期再議 |
| 線上編輯程式碼 | 上傳既有產物即可 |
| CI 建置 | 本平台不負責編譯 |
| 外網公開 | 內部平台,登入才可見 |
| 留言 / 評分 / 訂閱通知 | 非核心,先確認平台有人用再說 |

**Q10 我補的兩個判斷,不同意請推翻:**

1. **擴充級距訂 10 GB**——裁示只說「開大容量」沒給數字。取 2 GB 的 5 倍,
   足以容納帶 runtime 的多平台安裝包;若只給 5 GB,擴充後很快又要再申請。
2. **MVP 的「申請」走線下**——管理員直接調級距即可(F17);
   站內申請單(提交→審核→通知)是獨立功能,列 P2(F18)。先做「能調」再做「能申請」。

**Q7 我做的兩個補充判斷,若不同意請糾正:**

1. 「50~100M」我取**上限 100 MB**——執行檔動輒數十 MB,取 50 MB 容易卡住合理用途。
2. 你只指定了單檔上限,**專案總容量**我暫定 **5 GB**;若 VM 磁碟吃緊要調小,請給數字。
