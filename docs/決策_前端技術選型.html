決策紀錄:前端技術選型

建立日期: 2026-07-26 00:41 最後更新: 2026-07-26 00:41 版本: v1.0 狀態: ✅ 已定案(2026-07-26,Benny 裁示) 對應: 功能需求大綱 Q9、模組 H(F70–F76)、任務 T39

1. 決定

採用 Jinja2 伺服器端模板 + 少量原生 JS,放在現有的 svc 容器內,不另起 SPA、不另加容器與路由。 上傳頁維持既有的 PUT raw body API,由 XHR 發送。

2. 背景:這個決定被什麼綁住

前端不是自由命題。Cats 平台的拓撲先限制了選項:

限制 出處 後果
服務掛在 /«PREFIX»/ 下,gateway 剝掉前綴 接入指南 §6 所有連結與靜態檔路徑都要帶前綴,否則掉到落地頁 404
靜態檔的「剝前綴 vs 保留前綴」要選對 接入指南 §6 PLM v1.1.0 上線時 CSS 全部 404 就是栽在這
全 VM 只有 portal-gateway 持 80/443 接入指南 §1 多一個前端容器 = 多一條路由 = 多一次 cats-portal 的 PR
「靜態檔由誰供應?」是接入前必答題 接入指南 §10 第 6 題 不決定就申請不到路由
Python image 目標 ≤300 MB platform-charter SPA 的 node build stage 會讓 CI 與 image 變複雜

3. 選項比較

A. Jinja2 + 原生 JS(採用) B. Jinja2 + HTMX C. SPA(React / Vue)
容器數 1(現有) 1(現有) 1~2
gateway 路由 1 條(已規劃) 1 條 1~2 條,多一次 portal PR
靜態檔風險 低——URL 由我們自己組,前綴可控 低 中——build 產物要設 base path,錯了就是 PLM 那個坑
CI / build 無前端 build 無前端 build 多 node stage、多 Trivy 掃描面
SSO 整合 直接吃現有 session cookie 同左 同源可用 cookie,但 token 落進 JS 就變資安問題
大檔下載 <a href> 走瀏覽器原生下載 同左 fetch + blob 對 100 MB 檔案很難看,通常仍退回 <a>
開發速度 快 快,互動更順 慢,要先搭骨架
多一份維運 否 否 是

判準: M7 指定的五個畫面(主頁、導航列、專案頁、專案歷史、最新版置頂)全是讀取與呈現, 沒有一個需要 SPA 的用戶端狀態管理。選 SPA 是拿工具的複雜度換不需要的彈性。

4. 這個決定的代價(誠實列出)

代價 說明 可接受的理由
互動性上限較低 複雜的即時篩選、拖放、樹狀瀏覽會比較費工 這些功能全在 MVP 範圍外(F41、F44 是 P2)
前端與後端耦合在同一個容器 改版面也要重建整個 image 換版 runbook 本來就是換 image tag,成本相同
前端人才不見得熟 Python 模板 若之後有前端主力加入,會覺得綁手 API-first 已就定位,屆時可獨立加 SPA 而不動後端

止損設計: 系統是 API-first——所有業務邏輯都在 /v1/* 的 JSON API,模板只是消費者。 日後要換 SPA,後端一行不用改。這是敢從簡的主因。

5. 評估時發現的兩個既有缺口

5.1 坑一:現有上傳 API 用純 HTML 表單做不到

上傳設計為 PUT /v1/releases/{id}/artifacts/{filename},body 是檔案原始位元組 ——因為 multipart 解析會把大檔落到暫存檔,違反平台鐵則「容器內不寫檔當狀態」。

但 HTML <form> 只能發 GET / POST,且只能送 urlencoded 或 multipart,發不出 raw body 的 PUT。

決定:維持 PUT,上傳頁用 XHR。 不新增 multipart 端點——那等於把「不落暫存檔」的設計退回去。 附帶好處:XHR 提供上傳進度事件,100 MB 的檔案沒有進度條會很難用。

→ 寫進 T44 的驗收標準:上傳頁必須有進度顯示與失敗重試提示。

5.2 坑二:錯誤回應目前只會吐 JSON

app/problems.py 依平台規約一律回 application/problem+json。但 F75 要求 「未開通者看到指引頁,而非裸 403 JSON」——瀏覽器導覽拿到一坨 JSON 是不可接受的體驗。

決定:依 Accept 標頭做內容協商。 瀏覽器導覽(Accept: text/html)回 HTML 錯誤頁, API 呼叫維持 problem+json。RFC 7807 的義務只及於 API 回應,不禁止對瀏覽器回 HTML。

→ 開新任務 T47,列為 T40 的前置。

6. 實作綱要

6.1 相依與檔案配置

  • 新增相依:jinja2(其餘沿用現有)
  • app/templates/(模板)、app/static/(CSS / JS),由 FastAPI 的 StaticFiles 掛在 /static
  • 新增 app/routers/web.py 回傳 HTMLResponse,與 /v1/* 的 API 路由分離

6.2 子路徑處理(這裡錯了就是 PLM 的坑)

  • 頁面與靜態檔 URL 一律用 settings.api_prefix 組,不從 request 推導 (TLS 在 gateway 終結,推導會得到 http://)
  • 靜態檔採「剝前綴」,與主 location 一致:

nginx location /«PREFIX»/static/ { proxy_pass http://upload-program:8080/static/; # 結尾帶 /static/ = 剝前綴 }

  • 我們不使用 WhiteNoise,所以不會發生「框架自動剝前綴、gateway 卻保留前綴」的錯配 ——PLM 的 404 事故正是這個錯配造成的

6.3 上傳

XHR PUT,監聽 upload.onprogress 顯示進度;成功後導回版本頁。 X-Content-SHA256 為選填,前端不強制在瀏覽器算雜湊(大檔太慢)。

6.4 下載

一律 <a href="…/download">,由瀏覽器原生處理。後端已強制 Content-Disposition: attachment + nosniff,前端不需也不得改變此行為。

6.5 CSRF

session cookie 已是 HttpOnly + Secure + SameSite=Lax, 跨站送出的 PUT / PATCH / DELETE 不會帶上 cookie,CSRF 風險已大幅降低。 若日後新增以 POST 表單送出的狀態變更,需另評估是否加 CSRF token。

7. 什麼情況下這個決定該被推翻

任一條成立就應重新評估,改採 SPA:

  1. 要做線上瀏覽原始碼、diff、目錄樹這類重互動功能(目前皆在 MVP 範圍外)
  2. 公司有既有前端設計系統或元件庫要沿用
  3. 團隊主力是前端工程師,Python 模板反成阻力
  4. 要做手機 App 或第三方整合 —— 此條已被滿足(API-first),不構成推翻理由
