3. v0.3.0:做完了什麼

app/version.py 的 APP_VERSION 已是 0.3.0(第八條 4:必須在打 tag 之前改好)。

3.1 🔴 這一版改變了既有行為

POST /v1/releases/{id}/publish 的語意變了。 原本是「發布,馬上可下載」,現在是「送審,等管理員核准」。 同一條端點、同樣回 200,但結果完全不同。

作者按下「發布」之後,版本停在待審核;要管理員到 /admin/reviews 核准, 其他人才下載得到。🔴 核准前沒有任何人會收到通知——平台沒有 email 也沒有推播, 管理總覽的待辦區是唯一的提醒。這是已知的營運限制,不是被忽略的問題。

這也是版本號從 0.2.x 跳到 0.3.0 的理由:用 patch 版發這種東西, 等於對看 Release 頁的人說「只是小修正」,而他下一步就會發現自己發布的東西沒人下載得到。

三筆是同一個來源套件(openssl)的三個二進位套件,同一個 CVE。

4.2 為什麼我方修不掉

  • 我方 image 的 runtime stage 從頭到尾沒有任何 apt-get, OS 套件原封不動來自官方 python:3.12-slim。main 現在建也會紅。
  • Debian 已發布修好的 3.5.7-1~deb13u2,但官方 image 尚未重建併入。 建置已帶 --pull(T96),但上游沒動,我們就沒得取。
  • 試過在 runtime stage 自己升 openssl → 失敗: deb.debian.org 從 CI runner 的容器網路 connection timed out (三個 suite 全部),與 2026-07-30 run #85 同一堵牆。

4.3 📌 那次嘗試順便挖出一個更重要的東西

W: Some index files failed to download. They have been ignored, or old ones used instead.
libssl3t64 is already the newest version (3.5.6-1~deb13u2).
0 upgraded, 0 newly installed, 0 to remove and 0 not upgraded.
#9 DONE 37.7s                    ← 建置「成功」

🔴 apt-get update 抓不到索引時只印 W:,exit code 仍是 0。 後續的 --only-upgrade 因此拿 base image 裡的舊索引比對,回報「已經是最新版」, 整條 && 鏈成功——建置產出一個看起來已修補、實際一個位元組都沒動的 image。

當時特地寫了「刻意不加 || true」來防這件事,護欄守錯了地方: 防的是「指令回傳非 0 而我吞掉」,而 apt 根本不回傳非 0。 真正抓到它的是 Trivy,不是任何一道自寫的保險。

一課:&& 鏈只證明「每個指令都自稱成功」,不證明「事情做到了」。 對「取得外部資源」這類步驟必須自己驗結果,不能把 exit code 當成事實。 (與 T84 / T103 的假綠同病,只是載體從測試換成了 shell。)

已回退,Dockerfile 不留任何無效的 apt——留著會讓下一個讀的人以為 openssl 有在升。
