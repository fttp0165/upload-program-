6. 發版步驟(v0.3.1 已照此走完;v0.3.2 同一套)

  1. 合併 T133–T136 的 PR 到 main
  2. 🔴 打 tag 之前先在 main 上確認 APP_VERSION == "0.3.1" (v0.2.4 事故:tag 指到了 APP_VERSION 還是舊值的 commit,而 CI 照樣綠、 錯的 image 照樣推上 GHCR)
  3. 打 v0.3.1 tag(🔴 我方 tag push 得 403,這是政策,不繞過 —— 由 Benny 推)
  4. Release 頁貼四段內容(第八條 3:本版內容 / 資料影響 / 部署注意 / 測試)
  5. VM 換版: - .env 無新增變數、不需跑 migration - 🔴 換版重建容器後必須 docker exec portal-gateway nginx -s reload,否則 502 - ⚠ 先 docker login ghcr.io(見 §5.1)
  6. 換版後驗證: - tools/smoke.sh --vm --expect v0.3.2(v0.3.1 時用的是 v0.3.1) - 🖐 專案頁看到明顯的「建立新版本」按鈕;用 viewer 帳號看不到它 - 🖐 /admin/projects 列得出專案與版本/檔案/容量;先 ./backup.sh 再試刪除 - 🖐 管理總覽:稽核保留期的待辦不該出現(cron 已掛、未到期)

🔴 回滾的代價

v0.3.1 → v0.3.0:退回舊 image 即可,無資料代價(本版無 migration)。 ⚠ 但再往下退到 0.2.x 仍有 v0.3.0 的代價:退 0010 會把待審版本一律當回草稿、 退回理由整欄消失;退 0011 會失去全部專案留言(runbook §B)。

7. 已知的營運限制(不是缺陷,是取捨)

  1. 🔴 平台沒有任何通知管道。 作者送審後、專案被留言後,對方都不會收到提醒。 審核靠管理員主動看管理總覽的待辦區。若實際運作上沒人天天看後台, 審核制度會製造比它解決的更多問題 —— 這是要評估的營運現實,不是技術問題。 ⚠ MAIL_ENABLED 即使打開也只寄「有人回報問題」給管理員(T99), 不包含送審與留言。
  2. 掃毒尚未接上,每個檔案誠實標示 not_scanned(T46)。
  3. 留言沒有分頁,少的時候沒問題,多起來要加。不預先做,但記在這裡。
  4. requirements 仍是相容區間不是 lock 檔 —— 建置不可重現(T82 遺留)。
  5. /admin/projects 的刪除沒有還原路徑,也沒有「軟刪除」。 確認方式是輸入短名(T134 A 案),那是唯一的煞車。
