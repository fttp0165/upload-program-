## 3. v0.3.0:做完了什麼

`app/version.py` 的 `APP_VERSION` 已是 **0.3.0**(第八條 4:必須在打 tag 之前改好)。

### 3.1 🔴 這一版改變了既有行為

**`POST /v1/releases/{id}/publish` 的語意變了。**
原本是「發布,馬上可下載」,現在是「**送審**,等管理員核准」。
同一條端點、同樣回 200,但結果完全不同。

作者按下「發布」之後,版本停在**待審核**;要管理員到 `/admin/reviews` 核准,
其他人才下載得到。🔴 **核准前沒有任何人會收到通知**——平台沒有 email 也沒有推播,
管理總覽的待辦區是唯一的提醒。這是已知的營運限制,不是被忽略的問題。

這也是版本號從 0.2.x 跳到 0.3.0 的理由:用 patch 版發這種東西,
等於對看 Release 頁的人說「只是小修正」,而他下一步就會發現自己發布的東西沒人下載得到。

### 3.2 四項新功能(2026-08-12 需求)

| 任務 | 內容 | 資料影響 |
|---|---|---|
| **T101** | 管理員指派入口(`/admin/users` 可直接設為/取消管理員) | 🟢 不動 |
| **T102** | 發布審核:`草稿 →(送審)→ 待審核 →(核准)→ 已發布` | 🟡 加欄位 |
| **T103** | 專案留言板(專案頁的「使用回饋」) | 🟡 加表 |
| **T104** | 版本作者屬名(版本歷史每一版顯示建立者) | 🟢 不動 |

三條刻意寫下的界線:
- 🔴 **不能取消自己的管理員身分**(平台無 root 後門,手滑就沒人管得動系統)。
- 🔴 **退回必須寫理由**——沒有理由的退回,作者只能猜,然後重傳一模一樣的東西。
- 🔴 **專案擁有者不能刪別人的留言**,只有留言者本人與平台管理員可以。
  擁有者若能刪掉評語,留言板就只會剩好話,而**一個只留得住讚美的回饋區比沒有回饋區更糟**。

## 4. 🔴 卡住的事:CI Trivy 紅燈(T106)

### 4.1 現況

| CI job | 結果 |
|---|---|
| 測試 / lint / 文件同步 | ✅ 綠(559 passed) |
| **Build image + Trivy 掃描** | ❌ **紅** |
| Push GHCR(僅版本 tag) | ⏭ 因 `needs: build` 而跳過 |

```
upload-program:ci (debian 13.6)          Total: 3 (HIGH: 3, CRITICAL: 0)

libssl3t64 / openssl / openssl-provider-legacy
CVE-2026-14456  HIGH  fixed  3.5.6-1~deb13u2 → 3.5.7-1~deb13u2
```

三筆是**同一個來源套件(openssl)的三個二進位套件**,同一個 CVE。

### 4.2 為什麼我方修不掉

- 我方 image 的 runtime stage **從頭到尾沒有任何 `apt-get`**,
  OS 套件原封不動來自官方 `python:3.12-slim`。**`main` 現在建也會紅。**
- Debian 已發布修好的 `3.5.7-1~deb13u2`,但**官方 image 尚未重建併入**。
  建置已帶 `--pull`(T96),但**上游沒動,我們就沒得取**。
- 試過在 runtime stage 自己升 openssl → **失敗**:
  `deb.debian.org` 從 CI runner 的容器網路 **connection timed out**
  (三個 suite 全部),與 2026-07-30 run #85 同一堵牆。

### 4.3 📌 那次嘗試順便挖出一個更重要的東西

```
W: Some index files failed to download. They have been ignored, or old ones used instead.
libssl3t64 is already the newest version (3.5.6-1~deb13u2).
0 upgraded, 0 newly installed, 0 to remove and 0 not upgraded.
#9 DONE 37.7s                    ← 建置「成功」
```

🔴 **`apt-get update` 抓不到索引時只印 `W:`,exit code 仍是 0。**
後續的 `--only-upgrade` 因此拿 base image 裡的**舊索引**比對,回報「已經是最新版」,
整條 `&&` 鏈**成功**——建置產出一個**看起來已修補、實際一個位元組都沒動**的 image。

當時特地寫了「刻意不加 `|| true`」來防這件事,**護欄守錯了地方**:
防的是「指令回傳非 0 而我吞掉」,而 apt 根本不回傳非 0。
**真正抓到它的是 Trivy,不是任何一道自寫的保險。**

一課:**`&&` 鏈只證明「每個指令都自稱成功」,不證明「事情做到了」。**
對「取得外部資源」這類步驟必須自己驗結果,不能把 exit code 當成事實。
(與 T84 / T103 的假綠同病,只是載體從測試換成了 shell。)

已回退,Dockerfile 不留任何無效的 apt——留著會讓下一個讀的人以為 openssl 有在升。

### 4.4 裁示與已採取的行動

Benny 2026-08-26 裁示:**開通 apt**(不等上游、不放寬掃描)。

已備妥跨專案申請書並登記進索引(第 11 份),申請內容擇一:

| | 內容 |
|---|---|
| A | 開通 `docker build` 網路對 `deb.debian.org` / `security.debian.org` 的 egress |
| **B** | 提供**公司內部 Debian 鏡像**位址,我方改寫 `sources` 指過去(**我方偏好**) |

範圍刻意寫小:**只在建置期**、**只要 Debian 官方兩個網域**、**只升不裝**。

> 誠實揭露:CVE-2026-14456 是 OpenSSL **QUIC 伺服器**的記憶體無限成長,
> 本服務沒有任何 QUIC 伺服器路徑(TLS 在 gateway 終結;OpenSSL 只被 Python
> 用在對外 client:JWKS、MinIO),**幾乎確定不適用**。
> **仍然申請開通而不主張豁免**,理由有二:判斷可能錯且會隨相依演進失效;
> 更重要的是**這次成不成立不影響下一次**——真正的問題是
> 「runtime stage 沒有 apt 就代表我方對 OS 層 CVE 完全無能為力」。

📌 **這是第三次**被 base image 的 OS 套件擋(run #85 繞掉了、T96 上游剛好已重建、
本次沒有運氣)。所以申請的是制度,不是這一個 CVE。

## 7. 已知的營運限制(不是缺陷,是取捨)

1. 🔴 **平台沒有任何通知管道。** 作者送審後、專案被留言後,對方都不會收到提醒。
   審核靠管理員**主動看**管理總覽的待辦區。若實際運作上沒人天天看後台,
   審核制度會製造比它解決的更多問題——**這是要評估的營運現實,不是技術問題**。
2. 🔴 **三處顯示的是識別碼不是名字**(專案擁有者、版本建立者、留言者)。
   全部卡在同一份申請書(#10)。一串 UUID 的體驗確實不好,
   這是**誠實的過渡狀態,不是設計目標**。
3. **掃毒尚未接上**,每個檔案誠實標示 `not_scanned`(T46)。
4. **留言沒有分頁**,少的時候沒問題,多起來要加。**不預先做**,但記在這裡。
5. **requirements 仍是相容區間不是 lock 檔**——建置不可重現(T82 遺留)。
